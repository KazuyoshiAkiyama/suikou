# 決定の記録

後から読む人が同じ検討を繰り返さずに済むようにする。
判断が分かれた箇所を追記していく。

## D-01 文書スコープの指標を textlint の中に収めない

textlint はノードの位置に紐づけて指摘する仕組みである。
文書全体でしか計算できない指標には、紐づけるべき位置がない。
さらに、指標の多くは欠落の指摘である。
形式名詞が少ない、指示詞が少ない、直喩の標識が少ない。
欠落には定義上どこにも位置がない。

当初は Document ノードに対して報告する textlint の規則として実装する案を採った。
これは誤りだった。textlint の中に収めると解析基盤が JavaScript に縛られ、
語種を返す形態素解析が得られず、漢語率が実装できなくなる。
実装の都合で検証済みの指標を捨てることになり、順序が逆である。

フロントツールが textlint を呼び出し、自前の文書解析と統合する構成を採る。
MCP はフロントツール自身が提供すればよく、
むしろ合成済みのレポートを一度に返せる分、エージェントには有利である。

## D-02 実装言語は Rust を中心とし、Python は較正と探索に限定する

検証を通った指標はすべて純 Rust で実装できる。
lindera-unidic が UniDic の全素性を返し、語種と活用形が取得できるためである。

Python が必要だったのは現在分詞節、名詞化、modifier stack、依存距離であり、
これらはすべて実測で棄却された指標である。
深い構文解析を要する指標ほど実験設計に敏感で、先行研究の効果量が転移しなかった。

そこで層を分ける。
確定した指標は Rust で実装し、探索と較正は Python で行う。
Python で有効性が確認された指標だけを Rust に移す。

Claude Code の hooks から Write と Edit のたびに実行される用途では
起動コストが支配的になる。spaCy の読み込みに2秒から5秒かかるため、
Python を本番の実行経路に置くことはできない。

## D-03 Markdown パーサを使わず行ベースで実装する

`research/` の参照実装が行ベースであり、
ゴールデンテストの値を一致させるために同じ方式を採る。
依存が減る分、バージョン差による事故も減る。

## D-04 形態素解析をトレイトの裏に隔離する

lindera の API と UniDic の素性の並びはバージョンで変わる。
バージョンに依存するコードを一つの構造体に閉じ込めれば、
壊れうる面積が数十行に縮む。

加えて、既定の feature に lindera を含めないことで、
辞書を落とさずに規則と指標のロジックをテストできる。
変更の検証が速くなる。

## D-05 起動時に素性の並びを自己診断する

バージョンの固定だけでは、更新したときに静かに壊れる問題が残る。
素性の並びがずれると、語種と活用形が別の位置から読まれる。
値は返るが中身が違う。

漢語率と連用中止がこの二つに依存しているため、
壊れた値のまま動くと、指摘の内容そのものが誤りになる。
既知の語を流して確かめ、ずれていれば落ちる方がよい。

## D-06 文体で閾値を分けない

常体と敬体で指標が変わるかを、二つのモデルの出力で対比した。
モデル間で方向が一致せず、体系的な影響は見られなかった。
差はモデル差に吸収される。

文体の判定は残すが、用途は体言止めのような文体依存の規則の
適用可否に限る。閾値の表を二重に持つ必要はない。

## D-07 形式名詞と漢語率の severity を info に置く

ジャンルによる変動が大きい。手順書では形式名詞が閾値に接し、
概念解説では漢語率が人間ネイティブの値に近づく。
漢語率はトピックへの感度も高い。

日本語の人間コーパスは解説書に偏っており、手順書型が足りない。
ジャンル別のベースラインが揃うまでは info に置き、
揃った時点で warning に上げる。

## D-08 先行研究の効果量を転移させない

英語の現在分詞節について、人間の5.3倍という報告に基づいて
閾値を9から10と見積もった。実測では人間帯と重なり、使えなかった。
名詞化についても同様である。

原因は実験設計の違いと見ている。
報告元は人間が書いた文章を与えて同じ文体で続けさせる設計だが、
こちらは文書の作成を指示している。

先行研究は仮説の源にはなるが、効果量をタスクをまたいで流用してはならない。

## D-09 メンテナンス性の層は人間の平均に合わせない

箇条書きの導入文を正しく書いているのは AWS S3 ユーザーガイドだけだった。
Linux kernel は不完全な導入が優勢である。
人間の平均に合わせると、この層は意味を失う。

この層は AI 臭さを消す層ではなく、
人間が書いた文書の大半より良くする層である。

## D-10 予防で消せる層と lint でしか消せない層を分ける

書式を抑制する指示を与えた条件と与えない条件を比べた。
書式は完全に消えたが、語彙と文構造は変わらなかった。

メンテナンス性の指示についても同じ実験を行った。
構造の規則は簡潔な指示で完全に守られ、
時点依存語は詳細な指示で初めてゼロになった。
項目数の明示、見出しの連番、手動番号は指示がなくても発生しない。

したがって `brief` には、指示で守れることだけを入れる。
効かない制約を入れることは、トークンの無駄であり、過剰修正の危険もある。

副次効果として、メンテナンス性の指示だけで文書指標も改善した。
導入文を書かせた結果として地の文が生じ、
地の文比率と箇条書き割合が人間帯に近づいた。

## D-11 用語の辞書を同梱せず文書から作る

生きた比喩と死んだ比喩の弁別が、比喩の層の最大の難点である。
cache や handshake は分野の確立した用語であって比喩ではない。

指摘されて有名になった語は頻度が下がる。
2024年初頭に指摘された語群は、指摘の直後から減少した。
同梱の辞書は古びる。

自分の文書から生成する辞書は古びない。
プロジェクトごとに用語が違うという理由に加えて、
これが辞書の陳腐化への構造的な回答になる。

## D-12 漢語率のテストは期待値の側を直した

`kango_ratio_counts_only_content_words` が落ちていた。
入力「設定を変更すること」に対して実装は 0.5 を返し、テストは 0.5 超を期待していた。

`TASKS.md` はテストが落ちたら実装を直すと定めている。この件は例外にあたる。
テストのコメントは自立語を「設定」「変更」「こと」の3語と数えていたが、
`FakeMorphology` の仕様には「する」が動詞として登録されており、自立語は4語になる。
`docs/METRICS.md` は分母を自立語のうち語種が 和 漢 外 混 のものと定めており、
動詞の「する」も分母に入る。実装が返す 2/4 が規定どおりの値である。
実装をテストに合わせると、METRICS.md の定義から外れる。

テストの意図は、助詞を分母から外すことの確認にある。
期待値を 0.5 の厳密一致に変えてもこの意図は保たれる。
助詞「を」を分母に入れた場合の値は 0.4 であり、両者は区別できる。

実装を直してよいのは、実装が仕様から外れている場合に限る。
期待値が仕様から外れている場合は、期待値を直す。

## D-13 M2 と M6 は出現ごとに数える

参照実装は `findall` で1行あたりの出現回数を数えるが、Rust 実装はブロック単位で
高々1件しか指摘していなかった。`tests/golden/input/en_maintainability.md` の
「The validator currently reports ... The latest release」が1行に2語を含み、
参照実装の 2 に対して Rust が 1 を返していた。

出現ごとに数える側を採った。根拠は本プロジェクト自身の制約にある。
1行に2件あって1件しか報告しないと、指摘された側だけを直した文書が
`check --quiet` で再び落ちる。層ごとに lint と修正を往復させないという設計が、そこで崩れる。

`Position` に使われていない `column` があったのは、
本来は出現ごとに位置を持たせる想定だったことを示している。
出現ごとに列を持たせたことで、同じ行の複数の違反を区別できる。

M7 は行末に錨を打つため1行に高々1件であり、この変更の影響を受けない。

## D-14 語数と文数は相対誤差で突き合わせる

`tests/golden/README.md` は、比率に絶対誤差 0.02、密度に 0.5、M 系に整数の一致を
定めていた。語数はこのいずれにも当てはまらない。

`en_prose.md` の語数は参照実装が 445、Rust が 444 だった。
原因は `trade-off` の扱いにある。spaCy は三つのトークンに割って記号を除くため2語と数え、
空白分割は1語と数える。この文書に含まれるハイフン語はちょうど一つであり、差と一致する。

トークナイザの定義差であって実装の誤りではない。
絶対値の一致を求めると、定義が違うものを同じ数にしろと要求することになる。
相対誤差 1% で突き合わせ、系統的なずれだけを捕らえる。

## D-15 形式名詞の対象範囲が参照実装と仕様で食い違っている

`docs/METRICS.md` は語彙系を地の文＋箇条書き本文で計算すると定め、
形式名詞をその一つに挙げている。Rust 実装はこれに従っている。

参照実装 `research/jametrics.py` は、指示詞について
`指示詞_千字`（地の文）と `指示詞_全千字`（地の文＋箇条書き本文）の両方を出すが、
形式名詞は地の文だけの `形式名詞_千字` しか出さない。

`tests/golden/input/ja_maintainability.md` で測ると、
地の文だけなら 14.98、箇条書き本文を含めると 15.77 になる。
差は 0.79 であり、密度の許容範囲 0.5 を超える。

ここで実装を変えてはならない。METRICS.md の定義には理由が書かれている。
出力の大半が箇条書きであるモデルがあり、地の文だけで測ると本文の8割以上を捨てることになる。

食い違うのは閾値の側である。`corpus/baselines.toml` の人間帯 11.095〜11.163 と
D5 の閾値 8.5 は、地の文だけの定義で測った値である。
箇条書きを含めると値が上がるため、D5 は較正時より発火しにくくなる。
D5 の severity を info に置いてある判断（D-07）は、この点でも妥当である。

較正をやり直すまで、この食い違いは開いたままになる。
やり直しには `research/jametrics.py` に `形式名詞_全千字` を足し、
コーパスに対して測り直すことが要る。

## D-16 辞書を埋め込んだ単一バイナリで配る

配布の形を決めるにあたって、埋め込み辞書の大きさを測った。

| 構成 | 大きさ |
|---|---|
| 辞書を同梱したバイナリ | 191 MB |
| 同 xz 圧縮 | 26 MB |
| 辞書を含まないバイナリ | 1.1 MB |

`strip` は効かない。実体がシンボルではなく辞書のデータだからである。

辞書を外に出して初回に取得する構成も取れる。
lindera 6.0.0 には `load_dictionary_from_path` があり、mmap で読める。
それでも埋め込みを採った。理由は用途にある。
hooks から Write と Edit のたびに起動する道具では、失敗経路の数がそのまま信頼性になる。
外部辞書は、欠落、破損、版の食い違いという経路を増やす。
版の食い違いは `verify_schema` が捕らえるが、捕らえたところで利用者は動けない。
取得後にネットワークを必要としない形の方が、この用途には合う。

配布の単位は OS ごとのアーカイブとする。
全 OS を一つに束ねると圧縮後 78 MB になり、利用者は使わない OS の分を必ず落とすことになる。

対象は x86_64 の Linux (musl)、Apple Silicon の macOS、x86_64 の Windows に絞った。
Linux を musl にするのは、glibc の版に依存させないためである。
古いディストロやコンテナで動かない道具は、hooks から呼ぶ用途では痛い。
Intel Mac と ARM Linux は外した。要る場合は利用者がソースからビルドする。

## D-17 辞書の feature を既定で有効にしない

`suikou-cli` に `lindera-unidic` を足したが、既定では無効のままにした。
既定に入れると `cargo test --all` が辞書を引き込み、
辞書なしで本体のロジックを検証できるという前提（D-04）が壊れる。

代わりに二つの手当てをした。
リリース用のビルドは feature を明示して作り、起動して辞書の有無を確かめてから梱包する。
辞書なしの版で日本語を要求された場合は、`morphology::load` が明示的に落ちる。

黙って空の解析結果を返してはならない。
形態素解析が空を返すと、漢語率も連用中止も形式名詞も 0 になる。
0 は閾値の下にあるため、指摘が出るものと出ないものが入り混じり、
「指摘なし」という誤った結論に至る経路がある。

どちらの版かは `suikou --version` で判別できるようにした。
利用者が握っているバイナリを特定できないと、日本語が解析されない理由を追えない。

## D-18 配布物の確認は辞書の実体に対して行う

リリースのワークフローを `act` で走らせて発覚した。
梱包されたバイナリは 1.2 MB しかないのに、`--version` は「UniDic 同梱」と表示していた。
辞書は 191 MB あるため、両立しない。

原因はリンカのデッドコード除去にある。
サブコマンドがすべて `todo!()` であったため、`morphology::load` に到達経路がなく、
埋め込み辞書のデータごと落とされていた。
到達経路を作ってビルドし直すと 191.5 MB になり、実際に解析結果を返した。

問題はスモークテストの側にもあった。
`--version` の表示は `#[cfg]` によるコンパイル時の分岐であり、
feature が有効かどうかしか語らない。辞書が実在するかは語らない。
辞書を持たないバイナリに対して、この検査は通ってしまう。

`selftest` サブコマンドを足し、実際に辞書を読んで解析させる形に変えた。
配布物の確認は、ビルドの設定ではなく成果物の挙動に対して行う。
`verify_schema` が素性の並びを実際の辞書で確かめているのと同じ考え方である。

副次的に、`morphology::load` に到達経路ができたため、
`crates/suikou-cli/src/morphology.rs` に置いていた `#![allow(dead_code)]` を外せた。
利用者にとっても、掴んでいるバイナリが期待どおりかを確かめる手段になる。
