この文書は、Rust の実装が満たさなければならない指標と規則の定義をまとめた参照資料である。
参照実装は `research/` の Python であり、その出力は `tests/golden/` が固定している。

lindera と fugashi は形態素解析器が異なるので、値の完全な一致は求めない。
照合には許容範囲を設ける。許容範囲を超える指標が出たときは、
どちらの実装が正しいかを個別に判断する。

## 前処理

前処理は、実行する順序によって結果が変わる。次の順序で実行する。

1. YAML のフロントマターを除去する
2. 囲みのコードブロックを除去する
3. 中身がコードになっている Hugo のショートコードを除去する
4. **バックスラッシュのエスケープを戻す**（`\.` を `.` に戻す）
5. HTML のタグを除去する
6. 各行をブロックの種類に分類する
7. 行の中の記法（リンク、コード、強調）を除去する

除去した範囲は、同じ数の改行で置き換える。
置き換えないと、指摘に出る行番号が、利用者の開いているファイルの行番号とずれる。

囲みのコードブロックは、一行ずつ走査して判定する。
閉じる行とみなすのは、開いた行と同じ記号を、開いた行と同じ数以上並べ、その後に何も書かれていない行だけである。
この判定は CommonMark の規定に従っている。
長いコードブロックの中に短いコードブロックを入れる書き方があり、
内側の短いブロックで閉じたと判定すると、その後のコードが本文として読まれてしまう。

三つめの手順で除去するのは、`highlight` と `mermaid`、および `codelang` を宣言した `tab` に限る。
これらはどれも、文書の側で中身がコードであると宣言している。
`note` や `caution` は地の文を囲むショートコードなので、除去すると本文そのものが消える。
閉じる側が見つからない開始側は、除去の対象にしない。
対応が崩れた文書でこれを除去すると、その後の本文がすべて消えてしまうからである。

四つめの手順を省くと、文分割が正しく動かない。
AWS の doc_source はこのエスケープを含む形式であり、戻さずに測ると平均文長が3倍以上に増える。
この動作は `tests/golden/input/en_escaped.md` で固定している。
このファイルの文の数は、エスケープを戻す前が6、戻した後が11である。

### 各行をブロックに分類する方法

| 種類 | 判別の方法 |
|---|---|
| 見出し | 行頭の3桁までの空白の後に `#` が1個から6個並び、その後に空白が続く |
| リスト項目 | 行頭の空白の後に `-` `*` `+` のどれか、または数字と `.` か `)` があり、その後に空白が続く |
| 表 | 行頭が `\|` |
| 引用 | 行頭が `>` |
| 地の文 | 上のどれにも当てはまらない、空でない行 |

見出しの字下げを3桁までとするのは、CommonMark の規定に従ったものである。
4桁以上字下げした行はコードであり、その中の `#` を見出しとして解釈してはならない。

### 指標ごとの対象範囲

| 指標の種類 | 対象範囲 |
|---|---|
| 語彙（MATTR、漢字率、漢語率、指示詞、形式名詞） | 地の文と、リスト項目の本文 |
| 文の構成（文長、読点、文末、連用中止、テ形接続） | 地の文だけ |
| 書式（地の文比率、箇条書き比率、太字） | すべての行 |

語彙の指標は、地の文に限定して測定してはならない。
モデルによっては、出力の大半が箇条書きになるからである。
その場合に地の文だけで測ると、本文の8割以上を捨てることになる。

## 文分割

日本語は、`。` `！` `？` の直後で文を区切る。
区切った結果が5文字未満の断片や、日本語の文字を含まない断片は捨てる。

英語は、spaCy の文分割の結果に従う。
記号を除いたトークンが4個未満の文は捨てる。

## 日本語の指標

形態素解析には UniDic を使う。IPADIC では語種も活用形も取得できないからである。

### ja.mattr100

幅100トークンの移動窓を使う。
窓ごとに異なり語の数を窓の幅で割り、すべての窓について平均を取る。
トークンの数が窓の幅に満たない場合は、文書全体の異なり語の数をトークンの数で割る。
トークンには表層形を使う。

人間の文書は 0.559 から 0.581、AI の文書は 0.629 から 0.665 だった。閾値は 0.60 とする。

### ja.renyo_per_1k（連用中止）

品詞が動詞で、活用形が「連用形」で始まり、
直後のトークンが読点である箇所を数える。
その数を地の文の文字数（空白を除く）で割り、1000倍する。

### ja.te_per_1k（テ形接続）

表層形が `て` または `で` で、品詞の細分類が接続助詞であり、
直後のトークンが読点である箇所を数える。前の指標と同じく、1000文字あたりの値に換算する。

### ja.renyo_te_ratio

`renyo_per_1k` を `te_per_1k` で割った値である。
割る数が 0.05 未満の文書では、この比を出力しない。

人間のネイティブの文書は 2.00、人間による翻訳は 1.79、AI の文書は 3.62 から 15.94 だった。閾値は 3.0 とする。

この指標は、人間と AI を最もはっきり分ける。テ形は話し言葉で多く使われ、複数の節を一つにまとめる。
連用中止は書き言葉で多く使われ、節を横に並べる。AI の文書は連用中止に偏る。
この偏りは、英語で分詞節が多すぎる現象と同じものである。

### ja.keishiki_meishi_per_1k（形式名詞）

品詞が名詞で、表層形が `こと` `もの` `ため` `よう` `点` `場合` のどれかである
トークンを数える。1000文字あたりの値に換算する。

人間の文書は 11.1、AI の文書は 4.99 から 6.95 だった。値が閾値の 8.5 を下回ったときに指摘する。
**この指摘は何かが不足していることを示す**ので、指摘は位置を持たない。

この指標は、書かせる文書の種類によって値が大きく変わる。手順書では AI の値が 8.11 まで上がり、閾値に近づく。
文書の種類ごとに人間の値を確かめて一致するまでは、severity を info にしておく。

### ja.demonstrative_per_1k（指示詞）

表層形が `これ` `それ` `この` `その` `これら` `それら` `こちら` `そちら` `ここ` `そこ`
のどれかであるトークンを数える。1000文字あたりの値に換算する。

人間の文書は 5.69 から 6.47、AI の文書は 1.38 から 3.39 だった。値が閾値の 4.5 を下回ったときに指摘する。
この指摘も、何かが不足していることを示す。この指標は日本語のゼロ照応と関係がある。

### ja.kango_ratio（漢語率）

自立語（名詞、動詞、形容詞、副詞、形状詞）のうち、
語種が `漢` であるものの割合を求める。
割る数は、語種が `和` `漢` `外` `混` のどれかである自立語の数とする。

人間の文書は 0.326 から 0.397、AI の文書は 0.455 から 0.519 だった。閾値は 0.42 とする。
この指標は、書かせる文書の種類と話題によって値が大きく変わるので、severity を info にしている。

### ja.kanji_ratio（漢字率）

対象とする文に含まれる漢字（U+4E00 から U+9FFF）の数を、
日本語の文字（ひらがな、カタカナ、漢字）の数で割る。

### ja.prose_ratio と ja.list_ratio

地の文比率は、地の文の文字数を、「地の文とリスト項目の本文」の文字数で割った値である。
箇条書き比率は、リスト項目の行数を、空でない行の数で割った値である。

どちらの比率も、空白を除いて数える。

## 英語の指標

英語で検証を通過した指標は、三つしかない。
分詞節と名詞化は、人間の文書の範囲と重なった。
先行研究が報告した5.3倍という差は、文書を書かせる課題では再現しなかった。

### en.mattr100

定義は日本語の場合と同じである。
トークンには小文字に変換した表層形を使い、記号と空白は除く。

人間の文書は 0.58 から 0.69、AI の文書は 0.72 から 0.82 だった。閾値は 0.71 とする。
AI のどの条件の値も、人間のどのコーパスの値より高い。英語の指標の中で最も安定している。

### en.prose_ratio

定義は日本語の場合と同じである。人間の文書は 0.66 から 0.97、AI の文書は 0.31 から 0.56 だった。閾値は 0.65 とする。

### en.simile_marker_per_1k

次の語句が出現する回数を数え、1000語あたりの値に換算する。大文字と小文字は区別しない。

`like a` / `like the` / `as if` / `as though` / `akin to` / `similar to` /
`think of it as` / `imagine` / `analogous to` / `for example` / `for instance`

人間の文書は 0.84 から 2.54、AI の文書は 0.00 から 0.60 だった。値が閾値の 0.8 を下回ったときに指摘する。

**1,250語に満たない文書では、閾値との比較をしない。**
閾値 0.8 に標識1件で達する語数は、1000 ÷ 0.8 = 1,250 である。
これより短い文書では、標識が0件か、1件で閾値を超えるかのどちらかにしかならず、指標として差を表せない。

この下限を設ける前は、参照コーパスの 45%、ADR の 75% で指標が発火していた。
下限を設けた後は、それぞれ 1% と 4% になった。経緯は D-43 に書いてある。

下限の判定は、指標の計算ではなく、閾値と比べる段階で行う。
密度の値そのものは、語数に関係なく計算できるからである。

AI は比喩的な語彙を多く使う一方で、それが比喩であることを示す語を使わない。
この指標は、暗喩を避け、直喩と例え話を使うという方針に対応している。

## M 系の規則

### M1 箇条書きの導入文

リストの直前にある空でない行を、導入文とみなす。
直前の行が見出しかリストである場合は、判定しない。

日本語の判定の基準は次の表のとおりである。

| 結果 | 条件 |
|---|---|
| ok | 行末が `。` `！` `？` |
| ok | 行末が `:` か `：` で、その直前のトークンの品詞が名詞、接尾辞、代名詞のどれか |
| ng | 行末が `:` か `：` で、その直前のトークンが用言 |
| ng | 行末のトークンが助詞 |
| ng | 行末のトークンが動詞か助動詞で、活用形が連用形 |
| other | 上のどれにも当てはまらない |

英語では、行末が `:` のとき、行に
`the following` `as follows` `these` `below` `steps` `following`
のどれかが含まれていれば ok、含まれていなければ ng とする。
行末が `.` `!` `?` であれば ok とする。

厳密には、定形動詞があるかどうかで判定するべきである。
それでも、この判定方法だけで
AWS S3 ユーザーガイド（不完全30対完全145）と
Linux kernel（105対16）を区別できている。

違反の比率は `ng / (ok + ng)` で求める。

### M2 項目数を地の文に書くこと

地の文（見出しを除く）で、次に挙げる形を数える。

日本語では、数詞の後に `つ` `個` `点` `種` `類` のどれかが続き、さらに
`理由` `方法` `ポイント` `点` `要素` `ステップ` `手順` `方針` `特徴` `観点` `側面`
`利点` `欠点` `課題` `原則` `要因` `種類` のどれかが続く形を数える。
`以下の3つ` `次の2点` のような形と、`3つある` `3つあります` のような形も数える。

英語では、`two` から `seven` まで、または `2` から `7` までの数の後に、
`reasons` `ways` `steps` `things` `types` `categories` `benefits` `points`
`factors` `approaches` `options` `principles` `rules` `components` `parts`
のどれかが続く形を数える。

地の文に項目の数を書くと、項目を増やしたり減らしたりしたときに、本文が実態と合わなくなる。

**この規則は、数が後に続く内容を予告している場合にだけ適用する。** 予告の手掛かりは次の表のとおりである。

| 手掛かり | 理由 |
|---|---|
| 文に `以下`、`次の`、`下記` がある | 後に続く内容を予告している |
| 箇条書き、見出し、表が続く | その文とは別に編集できる構造である |
| 列挙の語（`第一に`、`1つ目`、`まず`）を含む地の文が続く | これも別に編集できる |

列挙を同じ文の中で済ませている文には、この規則を適用しない。
`無効化の方法は大きく分けて二つある。時間で切る方法と、変更を検知して切る方法である。`
がその例である。方法を増やす場合はこの文自体を書き直すことになるので、数と内容が食い違う余地がない。

この条件は、参照コーパス798件で発火した168件を分類して決めた。
手掛かりの語を持たず地の文が続く81件のうち、列挙の語を含むものは3件だけだった。
この条件を加えたことで、発火した文書は112件から67件に減った。経緯は D-45 に書いてある。

英語では、`following`、`below`、`these` を予告の語とし、
`first`、`second`、`one is` を列挙の語とする。
英語の参照コーパスでは分類をしていないので、これらの語は日本語側の語に対応させて選んだものである。

### M3 見出しの連番

見出しの行のうち、`#` の後に数字があり、その後に `.` `、` `)` `章` `節` のどれかが続くものを数える。

標題は対象から除く。ADR は `# 3. 題` という書式を使い、その番号は識別子であって、節の連番ではない。
節を増減すると番号を振り直す必要があるという問題は、標題には生じない。
公開されている ADR 190件のうち155件が標題で発火していたので、先頭の第1階層の見出しを対象から除いた。

### M4 手で付与した番号

箇条書きの記号が `-` `*` `+` のどれかで、その本文が数字と `.` か `)` で始まるものを数える。

### M5 項目のそろい

同じリストに含まれる項目について、末尾の形を分類する。

日本語では、句点で終わる形、体言で終わる形、用言で終わる形の三つに分類する。
英語では、ピリオドで終わる形と、ピリオドで終わらない形の二つに分類する。

同じリストの中に二つ以上の形が現れた場合、そのリストは形が混ざっているとみなす。
混ざっている比率は `混ざったリストの数 / 項目が2個以上あるリストの数` で求める。

### M6 時点に依存する語

次に挙げる語の出現回数を数える。同じ行に二つあれば、二回と数える。

日本語では `現在` `現時点` `最新の` `新しい` `今後` `将来的に` `まもなく` `既存の` `目下` `現行の`、
および `最近` `近年` `直近` `先日` `従来` `当面` `順次` を数える。

英語では `currently` `presently` `eventually` `soon` `latest` `newest` `newer`
`as of this writing` `at present` `in the future` `in the near future` `for now`、
および `recently` `lately` `these days` `nowadays` `so far` `for the time being` `up to now` を数える。

後半に挙げた語も、書いた時点を基準にするという点で、前半の語と同じ働きをする。
Google の timeless documentation は `recently` と `soon` と `new` を挙げており、後半の日本語の語はそれに対応する。

### 係留のない相対の期間

語の一覧では検出できない形として、数を伴う相対的な期間も検出する。
`直近3ヶ月` `過去2年` `ここ数日` `先週` `来月` がその例である。
これらは数を伴うので、語を列挙するだけでは網羅できない。

### 絶対の係留がある文は見送る

時点に触れること自体は誤りではない。誤りなのは、読む時点によって意味が変わることである。
同じ文の中に絶対的な基準点があれば、この規則は発火しない。

| 係留 | 例 |
|---|---|
| 西暦 | `2026年3月の計測では` |
| バージョン番号 | `lindera 6.0.0 で確認した` |
| 番号の付いた文書 | `RFC 7322 は` |

`lindera 6.0.0 で現在の素性の順序を確認した` は過去の事実を述べた文であり、内容が古くならない。
`現在の素性の順序はこうである` は、読む時点によって正しいかどうかが変わる。
両者を分けているのは時制ではなく、基準点があるかどうかである。

基準点は文ごとに判定する。同じ段落の別の文に年号があっても、この文が時点に依存することは変わらない。
小数をバージョン番号と取り違えないように、`v` の付いた形か、3つの数を並べた形だけを基準点とみなす。
`2.5倍` は基準点ではない。

この見送りは、「意図して時点に触れる場合は除く」という決まりを、実際に運用するための形である。
意図の判断に任せると機械では判定できないので、基準点の有無という形に置き換えている。

### 英語の語彙を絞る理由

英語の語彙は、確実に時点に依存する語だけに限定している。
`new` `now` `future` `existing` を加えると、誤検出が多くなる。
これらを加えた場合、Google eng-practices の違反の比率が 6.13 となり、すべてのコーパスの中で最も高くなった。
限定した語彙では 0.58 となり、すべてのコーパスの中で最も低くなる。

この規則だけは、短い指示を与えても守られない。
生成の前に適用するレイヤーにこの規則を入れる場合は、禁止する語を列挙する必要がある。

### M7 列挙の末尾

日本語では、行末が `など` か `等` であるものを数える。
英語では、行末が `etc.` `and so on` `and more` であるものを数える。

地の文とリスト項目の両方を対象にする。

## 文体の規則

### register/rare-wago 文体から外れた和語

プロによる日本語訳での頻度と比べて、偏って多く使われている和語の内容語を検出する。
対象は語種が和の内容語とし、数詞と1文字のカタカナは除く。
分野の用語には漢語やカタカナ語が多いので、和語に限定することで誤検出を避けられる。

同じ語が3回以上出現していることを条件にする。
一回しか出ない語では、文体から外れているのか、たまたま使った表現なのかを区別できない。

判定には二つの統計量を使う。
Dunning (1993) の対数尤度比が 15.13 以上（自由度1で p < 0.0001）であり、かつ
Hardie (2014) の Log Ratio が 7.0 以上（参照の128倍）である場合に指摘する。
有意性だけでは条件として足りない。普通の語を少し多く使っただけでも、有意になるからである。

参照は `crates/suikou-core/data/register_ja.toml` に置いている。
この頻度表は、Kubernetes、MDN、Vue の日本語訳652ページ、内容語でおよそ29万語から作成した。
入門書は文体が異なるので含めていない。表には、2分野以上に出現する語だけを載せている。
頻度表を作り直す手順は `research/lexshift/build_reference.py` にある。

`.suikou/terms.toml` と `.suikou/register-allow.toml` に載っている語は、対象から除く。
参照コーパスは Web の文書から作ったので、計算や統計の分野の語が少ないからである。

### register/prefer-katakana カタカナ語が優勢な漢語

同じ意味を漢語でもカタカナ語でも表せる組のうち、
プロによる日本語訳でカタカナ語が優勢な組を対応表に持ち、漢語の側が使われていれば指摘する。
統計量ではなく対応表で判定するので、出現するたびに指摘する。

対応表は `crates/suikou-core/data/kata_pairs_ja.toml` にある。
候補は人が挙げ、採用するかどうかは複数の分野にわたる実測で決めた。
採用の条件は、出現数の合計でカタカナ語が漢語の2倍以上あること、
合計が20回以上あること、漢語の出現が60回以下であることとする。

最後の条件は、多義語を避けるために設けた。
「対象」「対応」「状態」はプロもよく使う語だが、カタカナ語と同じ意味で使われているとは限らない。
プロがその漢語をほとんど使っていない組に限定すれば、置き換えの対応として信頼できる。

直前が名詞である場合は、複合語の一部とみなして指摘しない。
`英語版` や `第3版` の `版` を `バージョン` に置き換えると、誤りになるからである。

分野によって別の意味で使う語は、`.suikou/register-allow.toml` に登録して対象から除く。

## 構造の規則

構造の規則は、文体の規則と違って、言語に依存しない。
節の構成、節の順序、段落の単位は文書の論理に関わる性質であり、語彙の体系とは別のものだからである。
この考えは測定でも裏付けられた。7文以上の段落の割合は、プロの英語で 0.27%、
プロの日本語で 0.59% であり、言語が違っても同じ桁に収まる。
言語ごとに持つのは、節の名前と文の区切り方だけとする。

この規則の出典は次のとおりである。
必須の節と推奨する順序という枠組みは、RFC 7322 に基づく。
節が下位の節だけを含んでもよいことも、同じ RFC に明記されている。
型ごとの節は、Rust RFC テンプレート、Kubernetes Enhancement Proposal、
Michael Nygard の Architecture Decision Record、Diátaxis に基づく。
段落を一つの考えの単位にすることは、Google developer documentation style guide と
Strunk の The Elements of Style に基づく。
標題で主題を示すことと、見出しをたどれば全体を把握できることは、「公用文作成の考え方」に基づく。

### 文書の型

型は `crates/suikou-core/data/structure.toml` に定義している。
各型は、必須の節、推奨する順序、見出しの同義語、
各節が答える問いと書くべき内容を持つ。

節は `scale`（どのくらいの分量を書くか）も持てる。この値は `plot` と `brief` が出力する。
`check` では、この値で発火させない。人間の文書では四分位の範囲が中央値の 2.5 倍から 3 倍に広がり、
人間と AI が分かれないからである。この値を持つ型は `readme` だけである。経緯は D-46 に書いてある。

| 型 | 用途 |
|---|---|
| `design` | 提案と設計。何を作るか、なぜ必要か、どこまでを範囲にするかを示す |
| `enhancement` | 段階的に導入する提案。試験の計画、昇格の条件、切り戻しを含む |
| `decision` | 決定の記録。文脈、決定、その帰結を残す |
| `howto` | 手順。前提から始めて、確認で終わる |
| `reference` | 定義。必須の節は設けない |
| `log` | 記録をまとめた文書。決定の記録、作業の一覧、変更の履歴 |
| `readme` | README。先頭の一段落で、それが何であるかを述べる |
| `overview` | 入り口となる文書。それが何であるかから書き始める |

型を選ぶときは、`suikou doctype` が問いを示す。
最大2問の問いで型が決まる。ツールは利用者に質問せず、問いのツリーを出力するだけである。
対話的な入力を設けないのは、CI やエージェントから呼び出されるからである。
ツリーは `structure.toml` の `[[select]]` に定義しており、
どの型にもたどり着けることをテストで確認している。

型の宣言は、文書に近い場所から順に探す。

| 場所 | 書き方 |
|---|---|
| フロントマター | `doctype: "design"` |
| 他のツールが付けた項目の読み替え | `[front_matter]` と `[front_matter.map]` |
| `.suikou/structure.toml` の `[paths]` | `"README.md" = "readme"` |
| プロットの先頭 | `<!-- suikou:doctype design -->` |

パスの接頭辞が重なる場合は、長いほうを優先する。

文書によっては、型を別の名前ですでに宣言している。
Hugo の `content_type` がその例である。
この場合は、項目の名前と値の対応を書けば、文書を書き換えずに型が決まる。

```toml
[front_matter]
field = "content_type"

[front_matter.map]
task = "howto"
reference = "reference"
```

対応表に無い値からは、型を決めない。知らない値を、suikou 側の推測で型に割り当てないためである。

プロットは `--doctype` を指定して作るので、作った時点で型を持っている。
そのため、プロットを書いた文書には、型の宣言を書き足す必要がない。
型の印を HTML のコメントにしているのは、Markdown として表示したときに見えないようにするためである。

どの場所でも型が宣言されていない文書には、型に依存する規則を適用しない。
型を宣言していない文書が、後から規則が追加されたことで不合格になるのを防ぐためである。

宣言された型の名前が定義に無い場合は、その時点で異常終了する。
黙って読み飛ばすと、型の名前を書き誤ったときに、その判定が行われなくなるからである。

### structure/missing-section 要る節が無い

宣言した型で必須とされる節に当たる見出しが無い場合に指摘する。severity は error とする。

節と見出しの対応は、同義語を使って照合する。
先頭の第1階層の見出しは標題であり節ではないので、照合の対象から除く。
節があるかどうかは、見出しの階層に関係なく判定する。
見出しの階層は書式の選択であり、意味の違いを表すものではないからである。
たとえば KEP では、`Goals` を `## Motivation` の下に `###` で置いている。

節の順序は、最上位の見出しだけで判定する。
入れ子になった見出しを最上位の見出しと並べて順序を比べても、意味がないからである。経緯は D-47 に書いてある。

主題を述べる節に限っては、標題のすぐ後に置いた地の文で代用できる。
`lead_ok` を持つ節が、これに当たる。
RFC 7322 の abstract は、見出しを付けずに標題と目次の間に置かれており、これが前例になる。README も同じ形を取る。
この位置にまで見出しを強制すると、かえって読みにくくなる。

代用できるのは `lead_ok` を持つ節に限る。代用の可否は、節の位置ではなく節の性質で決める。
位置で決めると、最初の必須の節が何であっても、導入の地の文で条件を満たしてしまう。
実際に、Kubernetes の concept ページ120件のすべてが `howto` の必須の節を満たしていた。
前提や文脈は、導入の地の文では代用できない。経緯は D-31 に書いてある。

照合には、両方の言語の同義語を使う。
日本語の文書に英語の見出しが使われていることがあるからである。

指摘では、節が欠けていることを伝えるだけでなく、その節が答える問いと、そこに書くべき内容も示す。

必須の節は、型ごとに異なる。
`howto` で必須なのは前提だけであり、手順と確認は必須から除いている。
Kubernetes の task ページ120件に適用したところ、手順で120件、確認で113件が発火したからである。
手順そのものは本文であり、節として立てるものではない。経緯は D-31 に書いてある。

必須から除いた節も、問いと書くべき内容は型の定義に残している。
`plot` と `brief` は、「どうやるのか」と「うまくいったことをどう確かめるのか」を引き続き問う。
検出できる項目と、書く前に問うべき項目は一致しない。

### structure/section-order 節の順序

見つかった節の並びが、型の定める順序と食い違う場合に指摘する。severity は warning とする。
順序は読者が理解する道筋であり、破ってはならない決まりではないからである。

推奨する順序が実際の文書の書き方と一致することは、公開されている ADR 190件で確かめた。
そのうち189件が判定の条件を満たし、発火はゼロだった。

### structure/long-paragraph 段落が長い

一つの段落に含まれる文の数が `MAX_SENTENCES_PER_PARAGRAPH` を超えた場合に指摘する。
severity は warning とする。
Google developer documentation style guide は5〜6文を上限の目安としており、
それに合わせて上限を6文とする。

段落は空行で区切る。日本語の文の区切りには `split_sentences_ja` を使う。
英語は、終止符の直後に空白が続く箇所だけを文の切れ目とする。
こうしないと、`11.095` のような小数点で文が切れて、文の数が実際より多くなる。

### structure/empty-section 節に本文が無い

末端の節に本文が無い場合に指摘する。severity は warning とする。

下位の節を持つ節は、本文が無くてもよい。RFC 7322 にそのことが明記されている。
コードだけを含む節も、本文を持つ節として扱う。

### structure/plot-mismatch プロットと構成が違う

`.suikou/plans/` にプロットがある場合、プロットの見出しと本文の見出しを照合する。
severity は warning とする。

プロットはバージョン管理しない作業用の文書なので、CI からは見えない。
この規則が働くのは、手元での作業とエージェントの作業ループの中だけである。

### structure/work-note 作業について述べた文

読者に向けた文書の中に、著者が自分のために残した文脈が入っていないかを検出する。
重大度は warning である。

検出するのは、試した案、作業で分かったこと、作業の段階、以前の状態を述べた形である。

検出するかどうかは、型によって切り替える。
`work_notes_ok` を持つ型では検出しない。該当するのは `design`、`decision`、`log` の3つである。
これらの型では、何を試して何がうまくいかなかったかが、伝えるべき内容そのものだからである。

| 形 | README | 参照(英) | 参照(日) | Rust RFC | ADR |
|---|---|---|---|---|---|
| 試した案 | 0.4% | 0.2% | 0.1% | 4.5% | 3.2% |
| 判明したこと | 0% | 0.3% | 0.1% | 7.5% | 1.6% |
| 作業の段階 | 0% | 0% | 0.1% | 0% | 0.5% |
| 以前はこうだった | 0% | 0.3% | 0.3% | 5.0% | 0.5% |

`変更の経緯` は、検出する形の候補から除いた。
英語では11件のうち8件が読者に参照先を示す文であり、日本語では通常の動詞と区別できなかったからである。

この形を例として引用する場合は、コードとして書く。地の文に書くと、検出の対象になる。

型を宣言していない文書では検出しない。読者に向けた文書かどうかを判定できないからである。
経緯は D-40 と D-42 に書いてある。

### structure/lead-opener 冒頭の形

先頭の段落の書き出しを検出する。重大度は warning である。

先頭の段落とは、標題の後で、最初の節の見出しより前にある最初の地の文を指す。
先頭の段落が無い文書では、何も検出しない。

検出する形は、言語ごとに定義している。

| 形 | 日本語 | 英語 |
|---|---|---|
| 一般論から始める | `近年`、`従来`、`昨今` | `In recent years`、`Traditionally` |
| 著者の経緯から始める | `筆者は`、`当初は` | `I built`、`We decided`、`Originally` |
| 文書の目的を宣言する | `本文書の目的は` | `The goal of this`、`This aims to` |

検出する形は実測で決めた。先頭の段落 831件（著名 OSS の README 199、Rust RFC 20、
ADR 10、参照コーパスの英語 602）では、3つの形のどれも0件だった。
日本語でも、参照コーパスの先頭の段落 653件で0件だった。

文書が自身に言及する形（`本文書は`、`This document describes`）は検出しない。
この形は参照コーパスの英語で 37/602 件（6%）出現し、API の説明では自然な書き方だからである。

実際の文書 2,080件に適用したところ、発火は0件だった。経緯は D-39 に書いてある。

この規則は、著者の備忘を見つけるための規則ではない。
文書の途中に書かれた備忘は検出できない。
先頭の段落を主題から書き始めると決めることで、備忘が文書の後ろのほうへ移る。

### 書き方の指針

構造の規則には、検出以外の出力もある。
`suikou plot` と `suikou brief --doctype` は、書き始める前にテンプレートと書き方の指針を出力する。

違反を列挙するだけでは、避けるべき形は分かっても、書くべき形は決まらない。
そのため、節ごとに、その節が答える問いと書くべき内容を示す。
あわせて、段落の作り方と、結論を先に書くことも示す。
指針の文面は、`structure::writing_rules` の一か所だけに置いている。

## 閾値の調整

### すべての文書に共通する調整

`.suikou/profile.toml` に書いた項目だけが、組み込みの値を置き換える。
プロファイル全体を差し替える方式にすると、1つの値を変えるためだけに全体を写すことになる。

```toml
[thresholds."ja.kango_ratio"]
value = 0.55

# 出さない指標はここに並べる
disable = ["en.simile_marker_per_1k"]
```

組み込みの閾値を持たない指標を追加する場合は、`value` と `direction` の両方を指定する。
片方だけでは判定できないので、その指定を無視せず、エラーにする。

### 型ごとの調整

同じ指標でも、文書の用途によって適用の仕方が変わる。
入り口となる README と参照の文書では、求める文体の硬さが異なる。

```toml
[doctype.readme]
reason = "利用者と調整した結果。入り口は箇条書きが主になる"
rules = ["structure/long-paragraph"]

[doctype.readme.thresholds."ja.kango_ratio"]
value = 0.65
```

`reason` は、調整した経緯を記録するための項目である。
条件を緩めた判断を、後から読む人が同じ検討を繰り返さなくて済む形で残す。
組み込みの調整は、必ず `reason` を持つ。そのことをテストで確認している。

`rules` は、局所の規則を出力しないようにする項目である。
指標は閾値で強さを加減できるが、局所の規則は出力するかしないかのどちらかしかない。

設定は、組み込みの全体設定、組み込みの型の設定、利用者の全体設定、利用者の型の設定の順に重ねる。
利用者が書いた設定は、常に組み込みの設定より後に適用される。
組み込みの調整を利用者が上書きできない形にすると、実測と合わない現場で対処の手段が無くなる。

型ごとの調整では、指標を追加できない。指標の追加は全体設定の上書きで行う。
型ごとに別の指標が現れると、どの文書が何によって判定されたかを追跡できなくなる。

### 組み込みの型の調整

組み込みの設定では、`readme`、`design`、`decision` に調整を入れている。
これらの調整は、著名な OSS の README（英語 240件、日本語 150件）、Rust RFC 200件、
公開されている ADR 190件を実測して導いた。

既定の閾値を適用した場合の発火率を次の表に示す。

| 指標 | README | 参照 | 比 |
|---|---|---|---|
| `en.mattr100` | 70% | 15% | 4.7 |
| `en.prose_ratio` | 32% | 11% | 2.9 |
| `en.simile_marker_per_1k` | 74% | 45% | 1.6 |

発火率が 70% に達する指標は、文書の性質ではなく、閾値が文書に合っていないことを示している。

調整した後の発火率を次の表に示す。

| 指標 | README | 参照（不変） |
|---|---|---|
| `en.mattr100` | 6% | 15% |
| `en.prose_ratio` | 7% | 11% |
| `en.simile_marker_per_1k` | 0% | 45% |

日本語の README 150件では、調整後の発火率が 0% から 2% の範囲に収まる。

文体の硬さの差は、どの指標でも同じ方向に出るわけではない。
日本語の README は、参照の文書より漢語率が高い（0.62 対 0.52）。
README では名前と機能を列挙するので、漢語が増えるからである。経緯は D-41 に書いてある。

## 指摘に付す抜粋

指摘の位置には、一致した文字列と、その前後の短い範囲を付ける。

```
- L9:31 現時点｜…の選択肢を比較検討しました。現時点で候補となっていたのは、El…
```

一致した文字列を先頭に置くのは、どの語を直せばよいかを示すためである。
行の先頭から決まった文字数を切り出す方式では、行の後ろのほうにある一致が抜粋に入らない。
また、同じ行に一致が複数あると、まったく同じ抜粋が並び、区別できなくなる。

前後の範囲の幅は、言語によって変える。日本語は14字、英語は20字とする。
日本語は1文字あたりの情報量が多く、14字でほぼ一つの節になる。
英語で同じ文字数を取ると、2語ほどにしかならない。

## ゴールデンテスト

`tests/golden/input/` の各ファイルに対する期待値を、
`tests/golden/expected/` に置いている。

| ファイル | 目的 |
|---|---|
| `ja_maintainability.md` | 日本語の文書で M1 から M7 を検出させる |
| `en_maintainability.md` | 英語の文書で同じ規則を検出させる |
| `ja_prose.md` | 地の文が主体の文書で、日本語の文書指標を確認する |
| `en_prose.md` | 地の文が主体の文書で、英語の文書指標を確認する。英語の指標には445語以上が必要である |
| `en_escaped.md` | バックスラッシュのエスケープを戻すか否かで、文分割の結果が変わることを確認する |

期待値は、用意した入力ファイルから生成している。
実際のコーパスに対する回帰の確認には、`corpus/fetch.sh` で取得したコーパスを使う。
コーパス本体は、ライセンス上の理由でリポジトリに含めない。

## 用語集の規則

### glossary/variant 用語集の表記と違う

用語集が定めた形と異なる書き方を見つけた場合に指摘する。severity は warning とする。

検出の対象は2つである。

- 表記。`サーバ` を `サーバー` に統一する。
- 複数の文字からなる直訳語。`根因` を `根本原因` に統一する。

語の選択そのものは、`register/prefer-katakana` が担当する。
同じ箇所を2つの規則が指摘すると、修正する人は同じ内容の指摘を二度読むことになる。

単独の漢字一字からなる直訳語（`版`、`枝`、`題`）は、この規則では扱わない。
部分一致で探すと「問題」の中の「題」まで検出してしまうので、形態素解析が必要になる。
`prefer-katakana` が形態素の単位で判定しているので、この規則では重ねて扱わない。

対象は地の文と箇条書きの本文とする。見出しとコードは対象にしない。
形態素解析を使わないので、辞書を含まないバージョンでも適用できる。

### 表記の決め方

JTCA「外来語（カタカナ）表記ガイドライン」第3版は、英語の語尾
-er、-or、-ar、-y を長音符号「ー」で表すと定めている。

参照コーパス438万字で確かめたところ、-er、-or、-ar は規約と一致した。

| 語 | 長音あり | 長音なし |
|---|---|---|
| サーバー | 591 | 130 |
| ユーザー | 1830 | 328 |
| パラメーター | 158 | 6 |
| クラスター | 1279 | 5 |

一方、-y は規約と逆の結果になった。そのため、表記は規約から一律に導かず、語ごとに実測で決める。

| 語 | 長音あり | 長音なし |
|---|---|---|
| プロパティ | 3 | 870 |
| メモリ | 75 | 402 |
| ディレクトリ | 9 | 227 |
| コンテナ | 95 | 1783 |

`コンテナ` は語尾が -er に当たるが、この分野では長音符号を付けない表記が定着している。
