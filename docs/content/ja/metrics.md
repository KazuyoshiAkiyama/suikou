Rust の実装が満たすべき定義をここに置く。
`research/` の Python が参照の実装であり、`tests/golden/` がその出力を固定している。

形態素解析器が lindera と fugashi で違うため、値が完全にと合うことは求めない。
照合には許容範囲を置く。その幅を超えた指標が出た場合は、
どちらの実装が正しいかをそのつど決める。

## 前処理

順序が結果を変更する。次の順で行う。

1. YAML のフロントマターを取り除く
2. 囲みのコードブロックを取り除く
3. 中身がコードである Hugo のショートコードを取り除く
4. **バックスラッシュのエスケープを戻す**（`\.` を `.` に戻す）
5. HTML のタグを取り除く
6. 行をブロックに分類する
7. 行の中の記法（リンク、コード、強調）を取り除く

取り除いた範囲は、同じ数の改行に置き換える。
そうしないと、指摘の行番号が利用者の開いているファイルとずれる。

三つめの対象は `highlight` と `mermaid`、そして `codelang` を宣言した `tab` に限る。
どれも文書の側が中身をコードだと宣言している。
`note` や `caution` は地の文を包むため、取り除くと本文そのものが消える。
閉じが見つからない開きは対象にしない。
対応が崩れている文書で、そこから先の本文をすべて落とすことになるためである。

四つめを飛ばすと文分割が成り立たない。
AWS の doc_source がこの形式であり、戻さない場合の平均文長は3倍以上にふくらむ。
`tests/golden/input/en_escaped.md` がこの振る舞いを固定している。
戻す前の文の数は6、戻したあとは11である。

### ブロックの分け方

| 種類 | 判別方 |
|---|---|
| 見出し | 行頭が `#` 1個から6個と、それに続く空白 |
| リスト項目 | 行頭の空白に続いて `-` `*` `+` のいずれか、または数字と `.` か `)`、その後に空白 |
| 表 | 行頭が `\|` |
| 引用 | 行頭が `>` |
| 地の文 | 上のいずれでもない、空でない行 |

### 何を対象にするか

| 指標の種類 | 対象 |
|---|---|
| 語彙（MATTR、漢字率、漢語率、指示詞、形式名詞） | 地の文とリスト項目の本文 |
| 文の構成（文長、読点、文末、連用中止、テ形接続） | 地の文だけ |
| 書式（地の文比率、箇条書き比率、太字） | すべての行 |

語彙の指標を地の文だけで測定してはならない。
出力の大半が箇条書きになるモデルがあるためである。
その場合、本文の8割以上を破棄することになる。

## 文分割

日本語は `。` `！` `？` の直後で切る。
5文字未満のもの、または日本語の文字を含まない切れ端は破棄する。

英語は spaCy の分割に従う。
記号を除いたトークンが4個未満の文は破棄する。

## 日本語の指標

形態素解析には UniDic を使う。IPADIC では語種も活用形も取れないためである。

### ja.mattr100

窓の幅を100トークンとする移動窓を取る。
窓ごとの異なり語の数を窓の幅で割って、すべての窓で平均する。
トークンの数が窓の幅未満の場合は、全体の異なり語の数をトークンの数で割る。
トークンは表層形とする。

人間は 0.559 から 0.581、AI は 0.629 から 0.665。閾値は 0.60 とする。

### ja.renyo_per_1k（連用中止）

動詞であって、活用形が「連用形」で始まり、
直後のトークンが読点である箇所を数える。
地の文の文字数（空白を除く）で割って1000倍する。

### ja.te_per_1k（テ形接続）

表層形が `て` か `で` であって、品詞の細分類が接続助詞であり、
直後のトークンが読点である箇所を数える。同様に1000文字あたりに修正する。

### ja.renyo_te_ratio

`renyo_per_1k` を `te_per_1k` で割る。
割る側が 0.05 未満の文書では、この比を出さない。

人間のネイティブは 2.00、人間の翻訳は 1.79、AI は 3.62 から 15.94。閾値は 3.0 とする。

この指標がいちばん強く分割する。テ形は話し言葉に寄っていて、節をひとつにまとめる。
連用中止は書き言葉に寄っていて、節を並べる。AI は後者に偏る。
これは英語の分詞節が多すぎることと同じ現象にあたる。

### ja.keishiki_meishi_per_1k（形式名詞）

品詞が名詞であって、表層形が `こと` `もの` `ため` `よう` `点` `場合` のいずれかである
トークンを数える。1000文字あたりに修正する。

人間は 11.1、AI は 4.99 から 6.95。閾値の 8.5 を下回ったら指摘する。
**これは不足していることの指摘である**ため、指摘の位置を持たない。

書かせる文書の種類に敏感である。手順書では AI 側が 8.11 まで上がって閾値に近づく。
種類ごとの人間の値が一致するまで、severity は info に置く。

### ja.demonstrative_per_1k（指示詞）

表層形が `これ` `それ` `この` `その` `これら` `それら` `こちら` `そちら` `ここ` `そこ`
のいずれかであるトークンを数える。1000文字あたりに修正する。

人間は 5.69 から 6.47、AI は 1.38 から 3.39。閾値の 4.5 を下回ったら指摘する。
これも不足していることの指摘である。日本語のゼロ照応と関わる。

### ja.kango_ratio（漢語率）

自立語（名詞、動詞、形容詞、副詞、形状詞）のうち、
語種が `漢` であるものの比率を出す。
割る側は、語種が `和` `漢` `外` `混` のいずれかであるものの数とする。

人間は 0.326 から 0.397、AI は 0.455 から 0.519。閾値は 0.42 とする。
書かせる文書の種類と話題に敏感であるため、severity は info に置く。

### ja.kanji_ratio（漢字率）

対象の文の中にある漢字（U+4E00 から U+9FFF）の数を、
日本語の文字（ひらがな、カタカナ、漢字）の数で割る。

### ja.prose_ratio と ja.list_ratio

地の文比率は、地の文の文字数を「地の文とリスト項目の本文」の文字数で割る。
箇条書き比率は、リスト項目の行数を、空でない行の数で割る。

どちらも空白を除いて数える。

## 英語の指標

確認を成功したものは三つだけである。
分詞節と名詞化は人間の範囲と重なった。
先行研究が挙げた5.3倍という効果は、文書を書かせるという仕事には移らなかった。

### en.mattr100

日本語と同じ定めとする。
トークンは小文字にした表層形とし、記号と空白は除く。

人間は 0.58 から 0.69、AI は 0.72 から 0.82。閾値は 0.71 とする。
AI のすべての条件が、人間のすべてのコーパスを上回る。いちばん安定した指標である。

### en.prose_ratio

日本語と同じ定めとする。人間は 0.66 から 0.97、AI は 0.31 から 0.56。閾値は 0.65 とする。

### en.simile_marker_per_1k

次の語句の出る数を数えて、1000語あたりに修正する。大文字と小文字は区別しない。

`like a` / `like the` / `as if` / `as though` / `akin to` / `similar to` /
`think of it as` / `imagine` / `analogous to` / `for example` / `for instance`

人間は 0.84 から 2.54、AI は 0.00 から 0.60。閾値の 0.8 を下回ったら指摘する。

AI は比喩を表す語彙をよく使う一方で、比喩であることを示さない。
この指標は、暗喩を避けて、直喩と例え話を使うという方針に対応する。

## M 系の規則

### M1 箇条書きの導入文

リストの直前にある、空でない行を導入文とする。
直前が見出しかリストである場合は判じない。

日本語の分け方を示す。

| 結果 | 条件 |
|---|---|
| ok | 行末が `。` `！` `？` |
| ok | 行末が `:` か `：` で、その直前のトークンの品詞が名詞、接尾辞、代名詞 |
| ng | 行末が `:` か `：` で、その直前のトークンが用言 |
| ng | 行末のトークンが助詞 |
| ng | 行末のトークンが動詞か助動詞で、活用形が連用形 |
| other | 上のいずれでもない |

英語は、行末が `:` の場合に
`the following` `as follows` `these` `below` `steps` `following`
のいずれかを含めば ok、含まなければ ng とする。
行末が `.` `!` `?` であれば ok とする。

厳密に見れば定形動詞があるかどうかを見るべきである。
それでも、この判別方だけで
AWS S3 ユーザーガイド（不完全30対完全145）と
Linux kernel（105対16）を分けられている。

違反の比率は `ng / (ok + ng)` とする。

### M2 項目数を地の文に書くこと

地の文（見出しを除く）で、次の形式を数える。

日本語は、数詞に続く `つ` `個` `点` `種` `類` のいずれかと、
`理由` `方法` `ポイント` `点` `要素` `ステップ` `手順` `方針` `特徴` `観点` `側面`
`利点` `欠点` `課題` `原則` `要因` `種類` のいずれかが続く形式。
`以下の3つ` `次の2点` のような形式。`3つある` `3つあります` のような形式。

英語は、`two` から `seven` または `2` から `7` に、
`reasons` `ways` `steps` `things` `types` `categories` `benefits` `points`
`factors` `approaches` `options` `principles` `rules` `components` `parts`
のいずれかが続く形式。

項目の数を地の文に書くと、項目を増やしたり減らしたりしたときに本文が壊れる。

この規則をどこまで当てるかには、まだ決めきれない点がある。
リストが続かない、ただの説明文で数を述べる場合も検出してしまう。
`tests/golden/input/ja_prose.md` がその例にあたる。

### M3 見出しの連番

見出しの行のうち、`#` の後に数字と `.` `、` `)` `章` `節` のいずれかが続くものを数える。

### M4 手で付与した番号

箇条書きの記号が `-` `*` `+` であって、その本文が数字と `.` か `)` で始まるものを数える。

### M5 項目のそろい

同じリストの中の項目について、末尾の形式を分割する。

日本語は、句点で終わる形式、体言で終わる形式、用言で終わる形式の三つに分類する。
英語は、ピリオドで終わる形と終わらない形の二つに分類する。

同じリストの中に二つ以上の形式が現れたら、そのリストを混ざっているとみなす。
混ざっている比率は `混ざったリストの数 / 項目が2個以上あるリストの数` とする。

### M6 時点に依存する語

次の語が出る数を数える。同じ行に二つあれば二つと数える。

日本語は `現在` `現時点` `最新の` `新しい` `今後` `将来的に` `まもなく` `既存の` `目下` `現行の`。

英語は `currently` `presently` `eventually` `soon` `latest` `newest` `newer`
`as of this writing` `at present` `in the future` `in the near future` `for now`。

英語の語彙は厳密な側に限定してある。
`new` `now` `future` `existing` を入れると、誤検出する数が多くなる。
これらを入れた場合、Google eng-practices の違反の比率が 6.13 で最も多くなった。
厳密な側では 0.58 で、すべてのコーパスの中で最も少なくなる。

この規則だけは、短い指示では遵守されない。
生成の前に置くレイヤーに入れる場合は、禁じる語を並べる必要がある。

### M7 列挙の末尾

日本語は行末が `など` か `等` であるもの。
英語は行末が `etc.` `and so on` `and more` であるもの。

地の文とリスト項目の両方を対象とする。

## 文体の規則

### register/rare-wago 文体から外れた和語

プロの日本語訳での頻度と比べて、偏って多く使われている和語の内容語を検出する。
対象は語種が和の内容語とし、数詞と1文字のカタカナは除く。
分野の用語は漢語やカタカナ語が多いため、和語に絞ることで誤検出を避けられる。

同じ語が3回以上出ていることを条件とする。
一度きりの語は、文体から外れているのか偶然の表現なのかを判別できない。

判定には二つの統計を使う。
Dunning (1993) の対数尤度比が 15.13 以上（自由度1で p < 0.0001）であることと、
Hardie (2014) の Log Ratio が 7.0 以上（参照の128倍）であることの両方を満たす場合に出す。
有意性だけでは足りない。普通の語を少し多く使っただけでも有意になるためである。

参照は `crates/suikou-core/data/register_ja.toml` に置いてある。
Kubernetes、MDN、Vue の日本語訳652頁、内容語およそ29万語から作った頻度表である。
入門書は文体が違うため入れない。2分野以上に現れる語だけを載せる。
作り直す手順は `research/lexshift/build_reference.py` にある。

`.suikou/terms.toml` と `.suikou/register-allow.toml` に載る語は対象から外す。
参照コーパスは Web の文書で作ってあり、計算や統計の語が手薄であるためである。

### register/prefer-katakana カタカナ語が優勢な漢語

同じ意味に漢語とカタカナ語の両方が使われる組のうち、
プロの日本語訳でカタカナ語が優勢な組を対応表に持ち、漢語の側を見つけたら示す。
統計ではなく対応表で判定するため、出現ごとに指摘する。

対応表は `crates/suikou-core/data/kata_pairs_ja.toml` にある。
候補は人が挙げ、採否は分野をまたいだ実測が決めた。
条件は、合計の出現がカタカナ側で漢語側の2倍以上あること、
合計が20回以上あること、そして漢語側が60回以下であることとする。

最後の条件は多義語を避けるためである。
「対象」「対応」「状態」はプロもよく使うが、カタカナ語と同じ意味とは限らない。
プロがその漢語をほとんど使っていない組に限れば、置き換えの対応として信頼できる。

直前が名詞である場合は、複合語の一部とみなして見送る。
`英語版` や `第3版` の `版` を `バージョン` に置き換えると誤りになるためである。

分野で別の意味に使う語は `.suikou/register-allow.toml` で外す。

## 構造の規則

文体の規則と違い、構造の規則は言語を問わない。
節の構成、順序、段落の単位は文書の論理の性質であって、語彙の体系の外にあるためである。
測定でもそれが裏づけられた。7文以上の段落はプロの英語で 0.27%、
プロの日本語で 0.59% と、言語をまたいで同じ桁に収まる。
言語ごとに持つのは節の名前と文の分割の仕方だけとする。

この規則の出どころは次のとおりである。
必須の節と推奨する順序という枠組みは RFC 7322 による。
節が下位の節だけを含んでよいことも、そこに明記がある。
型ごとの節は Rust RFC テンプレート、Kubernetes Enhancement Proposal、
Michael Nygard の Architecture Decision Record、Diátaxis による。
段落を一つの考えの単位とすることは Google developer documentation style guide と
Strunk の The Elements of Style による。
標題が主題を示すことと、見出しを追えば全体がつかめることは「公用文作成の考え方」による。

### 文書の型

型は `crates/suikou-core/data/structure.toml` に規定してある。
型ごとに、必須の節、推奨する順序、見出しの同義語、
そしてその節が答える問いと何を書くかを持つ。

| 型 | 何のためか |
|---|---|
| `design` | 提案と設計。何を作るか、なぜ要るか、どこまでやるかを示す |
| `decision` | 決定の記録。文脈、決定、帰結を残す |
| `howto` | 手順。前提から始めて、確認で終わる |
| `reference` | 定義。必須の節は置かない |
| `overview` | 入口の文書。何であるかから始める |

型の宣言は近いところから順に見る。

| 場所 | 書き方 |
|---|---|
| フロントマター | `doctype: "design"` |
| ほかの道具が付けた欄の読み替え | `[front_matter]` と `[front_matter.map]` |
| `.suikou/structure.toml` の `[paths]` | `"README.md" = "overview"` |
| プロットの先頭 | `<!-- suikou:doctype design -->` |

接頭辞が重なった場合は長いほうが勝つ。

型を既に別の名前で宣言している文書がある。
Hugo の `content_type` がその例である。
その場合は欄の名前と値の対応を書けば、文書の側を書き換えずに型が決まる。

```toml
[front_matter]
field = "content_type"

[front_matter.map]
task = "howto"
reference = "reference"
```

表に無い値は型を決めない。知らない値をこちらの見立てで割り当てないためである。

プロットは `--doctype` を与えて作るため、型を既に持っている。
そのため、プロットを書いた文書には型の宣言を書き足さなくてよい。
印を HTML のコメントにしてあるのは、Markdown として表示したときに見えないためである。

どこにも無い文書には、型に依る規則を当てない。
型を宣言していない文書に、後から規則が増えて落ちることがないようにするためである。

宣言した型の名前を知らない場合は、その場で異常終了する。
黙って読み飛ばすと、綴りを誤ったときにその判定が消えるためである。

### structure/missing-section 要る節が無い

宣言した型の必須の節に当たる見出しが無い場合に出す。severity は error とする。

節と見出しの照合には同義語を使い、最上位の階層の見出しだけを見る。
先頭の第1階層の見出しは標題であって節ではないため外す。
型が規定するのは最上位の並びであり、節の中の小見出しは節ではない。

主題を述べる節だけは、標題の直下に置いた地の文で代えられる。
`lead_ok` を持つ節がそれにあたる。
RFC 7322 の abstract が標題と目次の間に見出し無しで入る前例であり、README も同じ形を取る。
見出しを強いると、かえって読みにくくなる。

代えられるのを最初の節と決めていた時期がある。
その場合、最初の必須の節が何であっても導入で満たされてしまう。
Kubernetes の concept 頁120件すべてが `howto` の必須を満たしたことで分かった。
前提や文脈は、導入では代えられない。

照合は両方の言語の同義語に対して行う。
日本語の文書が英語の見出しを持つことがあるためである。

指摘は欠落を告げるだけにせず、その節が答える問いと、そこに何を書くかまで示す。

必須の節は型ごとに違う。
`howto` の必須は前提だけである。手順と確認は必須から外してある。
Kubernetes の task 頁120件に当てたところ、手順が120件、確認が113件で発火したためである。
手順そのものは本文であって節ではない。経緯は D-31 にある。

必須から外しても、問いと書くことは型に残る。
`plot` と `brief` は「どうやるのか」と「うまくいったとどう分かるのか」を尋ね続ける。
検出できるものと、書く前に尋ねるべきものは一致しない。

### structure/section-order 節の順序

見つかった節が、型の規定する順序と食い違う場合に出す。severity は warning とする。
順序は読み手の理解の筋であって、破ってはならない決まりではない。

### structure/long-paragraph 段落が長い

一つの段落の文の数が `MAX_SENTENCES_PER_PARAGRAPH` を超えた場合に出す。
severity は warning とする。
Google developer documentation style guide が5〜6文を上限の目安としており、
それに合わせて6文とする。

段落は空行で区切る。日本語の文の分割は `split_sentences_ja` を使う。
英語は終止符の直後に空白が続く場合だけを切れ目とする。
そうしないと `11.095` のような小数点で切れて、文の数が水増しされる。

### structure/empty-section 節に本文が無い

末端の節に本文が無い場合に出す。severity は warning とする。

下位の節を持つ節は本文が無くてもよい。RFC 7322 がそう明記している。
コードだけを含む節も本文を持つものとして数える。

### structure/plot-mismatch プロットと構成が違う

`.suikou/plans/` にプロットがある場合に、その見出しと本文の見出しを突き合わせる。
severity は warning とする。

プロットはバージョン管理しない作業用の文書である。そのため CI では見えない。
手元とエージェントのループの中でだけ働く。

### 書き方の指針

構造の規則には、検出しない側の出力もある。
`suikou plot` と `suikou brief --doctype` が、書く前にテンプレートと書き方の指針を出す。

違反を挙げるだけでは、避ける形は分かっても書くべき形が決まらない。
そのため、節ごとにその節が答える問いと何を書くかを示し、
段落の作り方と結論を先に置くことを併せて出す。
指針の文面は `structure::writing_rules` に一か所だけ置いてある。

## ゴールデンテスト

`tests/golden/input/` の各ファイルに対する期待の値を
`tests/golden/expected/` に置いてある。

| ファイル | 何のためか |
|---|---|
| `ja_maintainability.md` | M1 から M7 を日本語で出させる |
| `en_maintainability.md` | 同様に英語で出させる |
| `ja_prose.md` | 地の文が中心の文書で、日本語の文書指標を確認する |
| `en_prose.md` | 同様に英語で確認する。英語の指標には445語以上が必要である |
| `en_escaped.md` | バックスラッシュを戻すかどうかで文分割が変わることを確認する |

期待の値は、構成した入力から作ってある。
実際のコーパスに対する回帰は `corpus/fetch.sh` で取ってきたものを使う。
ライセンスの都合で、コーパスそのものはリポジトリに入れない。
