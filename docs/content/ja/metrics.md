本文書は、Rust実装が準拠すべき各指標および検出規則の定義をまとめたリファレンスである。参照実装は `research/` にあるPythonコードであり、その期待出力は `tests/golden/` に固定されている。

形態素解析器としてRust側ではlindera、Python側ではfugashiを使用するため、算出値の完全一致は要求しない。照合時には許容誤差を設け、許容範囲を超える差が生じた指標については、都度どちらの実装が正しいかを判断する。

## 前処理

前処理は実行順序によって解析結果が変わるため、次に示す順序で処理を行う。

1. YAMLフロントマターを除去する
2. フェンスコードブロックを除去する
3. 中身がコードであるHugoショートコードを除去する
4. **バックスラッシュによるエスケープを解除する**（`\.` を `.` に変換する）
5. HTMLタグを除去する
6. 各行をブロック種別に分類する
7. インライン記法（リンク、インラインコード、強調）を除去する

除去した範囲は、元の行数と同じ数の改行に置換する。この処理を行わないと、検出結果の行番号が利用者の開いているファイルと一致しなくなる。

フェンスコードブロックは行単位で走査する。終端とみなすのは、開始行と同じ記号を用い、開始行以上の長さがあり、その後に余分な文字が続かない行だけである。これはCommonMarkの仕様に基づく規定である。長いフェンスの中に短いフェンスを入れ子にする記述方法が存在するため、内側のフェンスで終端と判定してしまうと、それ以降のコードが本文として解析される。

三番目の手順の除去対象は `highlight`、`mermaid`、および `codelang` を指定した `tab` に限定する。これらはいずれも文書側で中身がコードであることを明示しているショートコードである。一方、`note` や `caution` は地の文を囲む用途で使われるため、除去すると本文そのものが失われる。また、対応する終端が見つからない開始タグは除去対象としない。タグの対応が崩れた文書で終端なしのまま除去すると、それ以降の本文がすべて消去されてしまうためである。

四番目の手順を省略すると、後続の文分割が正常に機能しない。AWSのdoc_sourceはこのエスケープ形式を採用しており、解除せずに解析すると平均文長が3倍以上に増加する。この挙動は `tests/golden/input/en_escaped.md` によって固定されており、エスケープ解除前の文数は6、解除後の文数は11となる。

### ブロック分類

| 種別 | 判定条件 |
|---|---|
| 見出し | 行頭の空白3文字以内に続く1個から6個の `#` と、それに続く空白 |
| リスト項目 | 行頭の空白に続く `-`、`*`、`+` のいずれか、または数字と `.` もしくは `)`、その後に続く空白 |
| 表 | 行頭が `\|` |
| 引用 | 行頭が `>` |
| 地の文 | 上記のいずれにも該当しない空でない行 |

見出しの字下げを3文字以内としているのはCommonMarkの仕様による。4文字以上の字下げはインデントコードブロックとみなされるため、その中に含まれる `#` を見出しとして扱ってはならない。

### 指標ごとの対象範囲

| 指標の分類 | 計測対象 |
|---|---|
| 語彙（MATTR、漢字率、漢語率、指示詞、形式名詞） | 地の文およびリスト項目の本文 |
| 文構造（文長、読点、文末、連用中止、テ形接続） | 地の文のみ |
| フォーマット（地の文比率、リスト比率、太字） | すべての行 |

見出しは語彙と文構造の指標の対象外である。文体の規則（`register/`）と用語集の表記の規則（`glossary/variant`）も見出しを対象としない。見出しの文字列を対象とする規則は「見出しの規則」に一覧がある。構造の規則は見出しを文字列ではなく文書の骨格として読むため、この一覧には含まれない。

リスト比率の分母である非空行には見出しの行も含まれる。見出しの多い文書ではリスト比率が下がる。

語彙に関する指標は地の文のみを対象にしてはならない。出力の大部分を箇条書きで構成するモデルが存在するため、地の文だけに限定すると本文の8割以上を計測対象から除外することになる。

## 文分割

日本語では、`。`、`！`、`？` の直後で文を分割する。分割後の文字列が5文字未満の場合、または日本語の文字を含まない場合は破棄する。

英語では、spaCyの文分割アルゴリズムに従う。記号を除いたトークン数が4個未満の文は破棄する。

## 日本語の指標

日本語の形態素解析にはUniDicを使用する。IPADICでは語種および活用形の情報を取得できないためである。

### ja.mattr100

幅100トークンの移動窓を設定し、各窓における異なり語数を窓幅で割った値を全窓で平均して算出する。総トークン数が窓幅に満たない場合は、全体の異なり語数を総トークン数で割った値を採用する。トークンの単位は表層形とする。

人間の実測値は 0.559 から 0.581、AIの実測値は 0.629 から 0.665 の範囲にある。閾値は 0.60 とする。

### ja.renyo_per_1k（連用中止）

動詞のうち活用形が「連用形」で始まり、かつ直後のトークンが読点である箇所を計数する。得られた件数を地の文の文字数（空白を除く）で割り、1000倍する。

### ja.te_per_1k（テ形接続）

表層形が `て` または `で` であり、品詞細分類が接続助詞に該当し、直後のトークンが読点である箇所を計数する。連用中止と同様に、1000文字あたりの出現数に換算する。

### ja.renyo_te_ratio

`renyo_per_1k` を `te_per_1k` で割った値を算出する。分母となる値が 0.05 未満の文書では、この比率を算出しない。

実測値は人間のネイティブ執筆で 2.00、人間による翻訳で 1.79、AI生成文書で 3.62 から 15.94 である。閾値は 3.0 とする。

この指標は、人間とAIの文書を最も明確に分離する。テ形接続は話し言葉に近く節をひとまとめにする働きを持つのに対し、連用中止は書き言葉に近く節を並列に連ねる働きを持つ。AIは後者に偏る傾向があり、これは英語において分詞節が過剰に使われる現象と共通している。

### ja.keishiki_meishi_per_1k（形式名詞）

品詞が名詞で、表層形が `こと`、`もの`、`ため`、`よう`、`点`、`場合` のいずれかに一致するトークンを計数し、1000文字あたりに換算する。

人間の実測値は 11.1、AIは 4.99 から 6.95 である。閾値の 8.5 を下回った場合に指摘対象とする。**不足を検出する指標であるため**、特定の箇所を示す位置情報は持たない。

この指標は生成する文書の種類による変動が大きい。手順書ではAI側の値が 8.11 まで上昇して閾値に接近する。文書の種類ごとの人間の値が一致するまで、severityはinfoに設定する。

### ja.demonstrative_per_1k（指示詞）

表層形が `これ`、`それ`、`この`、`その`、`これら`、`それら`、`こちら`、`そちら`、`ここ`、`そこ` のいずれかに一致するトークンを計数し、1000文字あたりに換算する。

人間の実測値は 5.69 から 6.47、AIは 1.38 から 3.39 である。閾値の 4.5 を下回った場合に指摘対象とする。形式名詞と同様に不足を検出する指標であり、日本語のゼロ照応と関係している。

### ja.kango_ratio（漢語率）

自立語（名詞、動詞、形容詞、副詞、形状詞）の中で、語種が `漢` に分類される語の比率を算出する。分母には、語種が `和`、`漢`、`外`、`混` のいずれかに分類される自立語の総数を用いる。

人間の実測値は 0.326 から 0.397、AIは 0.455 から 0.519 である。閾値は 0.42 とする。文書の種類や主題による変動が大きいため、severityはinfoに設定する。

### ja.kanji_ratio（漢字率）

対象テキストに含まれる漢字（U+4E00からU+9FFF）の文字数を、日本語の文字（ひらがな、カタカナ、漢字）の総文字数で割って算出する。

### ja.prose_ratio と ja.list_ratio

地の文比率は、地の文の文字数を「地の文とリスト項目の本文」の合計文字数で割った値である。リスト比率は、リスト項目の行数を空でない全行数で割った値である。

いずれの算出においても空白は除外して数える。

## 英語の指標

検証で有効性が確認された英語の指標は三指標のみである。分詞節と名詞化についてはAIの値が人間の分布範囲と重なり、判別できなかった。先行研究で報告された5.3倍という効果は、文書を生成するタスクでは再現されなかった。

### en.mattr100

算出方法は日本語と同一である。トークンには小文字化した表層形を用い、記号および空白は除外する。

人間の実測値は 0.58 から 0.69、AIは 0.72 から 0.82 である。閾値は 0.71 とする。検証したAIのすべての条件が人間のすべてのコーパスを上回っており、最も安定した指標である。

### en.prose_ratio

算出方法は日本語と同一である。人間の実測値は 0.66 から 0.97、AIは 0.31 から 0.56 であり、閾値は 0.65 とする。

### en.simile_marker_per_1k

次に挙げる語句の出現回数を大文字・小文字を区別せずに計数し、1000語あたりに換算する。

`like a` / `like the` / `as if` / `as though` / `akin to` / `similar to` /
`think of it as` / `imagine` / `analogous to` / `for example` / `for instance`

人間の実測値は 0.84 から 2.54、AIは 0.00 から 0.60 である。閾値の 0.8 を下回った場合に指摘対象とする。

**1,250語未満の文書では閾値との比較を行わない。** 直喩標識が1件出現しただけで閾値 0.8 に達する語数は 1000 ÷ 0.8 = 1,250 語である。これより短い文書では、標識が0件で下回るか、1件で閾値を超えるかの二択になり、十分な分解能が得られない。

語数下限を設ける前は、参照コーパスの 45%、ADR の 75% で検出されていた。下限の導入後はそれぞれ 1% と 4% に低下した。詳細な経緯は D-43 に記録されている。

この語数下限は指標値の算出段階ではなく、閾値との比較段階に適用する。密度の値自体は文書長にかかわらず算出できるためである。

AIは比喩的な語彙を多用する一方で、それが比喩であることを明示しない傾向がある。この指標は、暗喩を避けて直喩や例え話を用いるという方針に対応する。

## M 系の規則

### M1 箇条書きの導入文

リストの直前に位置する空でない行を導入文とみなす。直前の行が見出しまたは別のリストである場合は判定対象としない。

日本語における判定条件は次のとおりである。

| 判定結果 | 条件 |
|---|---|
| ok | 行末が `。`、`！`、`？` のいずれかである |
| ok | 行末が `:` または `：` であり、その直前のトークンの品詞が名詞、接尾辞、代名詞のいずれかである |
| ng | 行末が `:` または `：` であり、その直前のトークンが用言である |
| ng | 行末のトークンが助詞である |
| ng | 行末のトークンが動詞または助動詞であり、活用形が連用形である |
| other | 上記のいずれにも該当しない |

英語では、行末が `:` の場合に `the following`、`as follows`、`these`、`below`、`steps`、`following` のいずれかを含めばok、含まなければngと判定する。行末が `.`、`!`、`?` のいずれかであればokとする。

厳密には定形動詞の有無を確認すべきである。ただし、この簡易な判定基準だけでも、AWS S3 ユーザーガイド（不完全30件対完全145件）と Linux kernel（105件対16件）を明確に区別できている。

違反率は `ng / (ok + ng)` によって算出する。

### M2 地の文への項目数の記載

見出しを除く地の文を対象に、後続の項目数を示す表現を検出する。

日本語では、数詞に助数詞 `つ`、`個`、`点`、`種`、`類` のいずれかが付き、さらに `理由`、`方法`、`ポイント`、`点`、`要素`、`ステップ`、`手順`、`方針`、`特徴`、`観点`、`側面`、`利点`、`欠点`、`課題`、`原則`、`要因`、`種類` のいずれかが続く形式を対象とする。これに加え、`以下の3つ` や `次の2点` のような表現、および `3つある` や `3つあります` のような表現も計数する。

英語では、`two` から `seven` まで、または `2` から `7` までの数詞に、`reasons`、`ways`、`steps`、`things`、`types`、`categories`、`benefits`、`points`、`factors`、`approaches`、`options`、`principles`、`rules`、`components`、`parts` のいずれかが続く形式を対象とする。

地の文に項目数を記載すると、項目を増減した際に本文の記述との不整合が生じる。

**検出対象とするのは、その数値が前方参照として機能している場合だけである。** 前方参照と判定する条件は次のとおりである。

| 条件 | 理由 |
|---|---|
| 文中に `以下`、`次の`、`下記` が含まれる | 後続の展開を明示的に予告しているため |
| 後続に箇条書き、見出し、または表が配置されている | 当該の文とは独立して編集可能な構造であるため |
| 列挙を示す語（`第一に`、`1つ目`、`まず`）を含む地の文が続く | 同様に独立して編集可能であるため |

同一の記述内で列挙を完結させている表現は対象外とする。たとえば `無効化の方法は大きく分けて二つある。時間で切る方法と、変更を検知して切る方法である。` はこれに該当する。方法を追加する場合はこの箇所自体を書き換えることになるため、数と実態が食い違う余地がない。

この条件は、参照コーパス798件で検出された168件を分類した結果から定めた。前方参照の語を含まず地の文が続く81件のうち、列挙の語を伴うものは3件だけであった。この絞り込みにより、検出される文書数は112文書から67文書へ減少した。詳細な経緯は D-45 に記録されている。

英語では `following`、`below`、`these` を前方参照の語とし、`first`、`second`、`one is` を列挙の語とする。英語の参照コーパスを用いた個別分類は実施していないため、この語彙一覧は日本語側の定義に対応させて作成したものである。

### M3 見出しの連番

見出し行のうち、`#` の後に数字と `.`、`、`、`)`、`章`、`節` のいずれかが続く行を計数する。対象は標題を除くすべての見出しであり、本文は対象としない。判定は `headings.rs` に置いている。

文書の標題は対象外とする。ADRでは `# 3. 題` のようなフォーマットが採用されており、この番号は文書識別子であって節の連番ではない。節の増減に伴う番号の振り直しが発生するという問題も標題には当てはまらない。公開されているADR 190件のうち155件がこの規則で誤検出されていたため、先頭にある第1階層の見出しを除外した。

### M4 箇条書きの手動採番

箇条書きの記号が `-`、`*`、`+` のいずれかであり、本文が数字と `.` または `)` で始まっている行を計数する。

### M5 リスト項目の末尾統一

同一リスト内の各項目について、末尾の形式を分類する。

日本語では、句点で終わる形式、体言で終わる形式、用言で終わる形式の三区分に分類する。英語では、ピリオドで終わる形式と終わらない形式の二区分に分類する。

同一リスト内に二区分以上の形式が含まれる場合、そのリストは末尾形式が混在しているとみなす。混在率は `混ざったリストの数 / 項目が2個以上あるリストの数` によって算出する。

### M6 時点に依存する語

次に挙げる語の出現回数を計数する。同一行に二回出現した場合は二件として計上する。対象は標題を含む見出しと、地の文、リスト項目、表、引用である。見出し以外のすべてのブロックを見る実装であるため、引用の中の記述も検出される。見出しの判定は `headings.rs` に置き、本文の検出位置と合わせて1件の指摘にまとめる。

日本語の対象語は、`現在`、`現時点`、`最新の`、`新しい`、`今後`、`将来的に`、`まもなく`、`既存の`、`目下`、`現行の`、および `最近`、`近年`、`直近`、`先日`、`従来`、`当面`、`順次` である。

英語の対象語は、`currently`、`presently`、`eventually`、`soon`、`latest`、`newest`、`newer`、`as of this writing`、`at present`、`in the future`、`in the near future`、`for now`、および `recently`、`lately`、`these days`、`nowadays`、`so far`、`for the time being`、`up to now` である。

後半に挙げた語群も、執筆時点を起点とする点で前半の語群と同じ性質を持つ。Googleのtimeless documentationが指摘する `recently`、`soon`、`new` の日本語側に相当する。

### 基準点のない相対期間

固定の語彙一覧では検出できない表現として、数値を伴う相対期間の記述も対象とする。`直近3ヶ月`、`過去2年`、`ここ数日`、`先週`、`来月` がこれに該当する。数値の組み合わせが多様であるため、語を列挙する方式では網羅できない。

### 絶対的な基準点がある文の除外

時点に言及すること自体は誤りではなく、閲覧時点によって意味が変化することが問題である。同一の文の中に絶対的な基準点が含まれている場合、この規則は検出を行わない。

| 基準点 | 例 |
|---|---|
| 西暦 | `2026年3月の計測では` |
| バージョン番号 | `lindera 6.0.0 で確認した` |
| 番号の付いた文書 | `RFC 7322 は` |

`lindera 6.0.0 で現在の素性の順序を確認した` は過去の事実を述べており、時間が経過しても内容が陳腐化しない。一方、`現在の素性の順序はこうである` は閲覧時点によって真偽が変動する。両者を区別する基準は時制ではなく、基準点の有無である。

基準点の有無は文単位で判定する。同じ段落内の別の文に年号が含まれていても、当該文の時点依存性は解消されない。また、通常の小数をバージョン番号と誤認しないよう、先頭に `v` が付く形式か、3つの数値で構成される形式だけを基準点とみなす。そのため `2.5倍` は基準点に該当しない。

この除外条件は、「意図して時点に触れる場合は除く」という方針を具体化したものである。人間の解釈に委ねる基準は機械で判定できないため、基準点の有無という客観的な条件に変換している。

### 英語の対象語を絞る理由

英語の対象語は厳密な範囲に限定している。`new`、`now`、`future`、`existing` を対象に含めると誤検出が大幅に増えるためである。これらを含めた場合、Google eng-practicesの違反率は 6.13 となり検証対象の中で最も高くなった。一方、厳密な範囲に限定した場合は 0.58 に低下し、全コーパスの中で最も低い値となる。

この規則は簡潔な指示だけでは遵守されにくい。生成前のレイヤーに組み込む場合は、禁止する語彙を具体的に列挙する必要がある。

### M7 列挙の末尾

日本語では行末が `など` または `等` で終わる表現、英語では行末が `etc.`、`and so on`、`and more` のいずれかで終わる表現を検出する。

地の文とリスト項目の両方を対象とする。

## 見出しの規則

見出しの文字列を対象とする規則は `crates/suikou-core/src/headings.rs` に集約してある。規則ごとに対象ブロックを個別に絞る構成では、どの規則が見出しに当たるかを実装を読むまで判断できないためである。

`structure/missing-section`、`structure/section-order`、`structure/empty-section` はこの一覧に含まれない。これらは見出しを文字列として検査するのではなく、セクションの有無と配列順序を判定するために読む。

| 規則 | 対象とする見出し |
|---|---|
| `structure/heading-form` | 章タイトルのみ |
| `maint/numbered-heading` | 標題を除くすべての見出し |
| `maint/time-dependent` | 標題を含むすべての見出し |
| `glossary/defined-name` | すべての見出し。本文と合わせて判定する |

規則の識別子ごとに報告は1件に束ねる。本文と見出しの双方を対象とする規則では、見出しの側が検出位置のみを返し、本文側が1件の指摘にまとめる。2件に分かれると、Markdown 出力で同じ規則の説明文が二重に表示され、`MAX_POSITIONS_PER_RULE` の上限が検出経路ごとに適用される。

### structure/heading-form 章タイトルの形式

章タイトルの末尾の形態素が用言である場合に検出する。重大度は warning である。

章タイトルとは `structure::sections` が返す見出しを指す。先頭の第1階層の見出しは標題であってセクションではなく、残りのうち最も浅い階層のみが章にあたる。階層を2に固定しないのは、`##` から始まる文書と `###` から始まる文書を同一の定義で扱うためである。

判定の前に末尾を整える。句読点と、末尾が閉じ括弧である場合は対応する開き括弧までを除去する。`設定を変更する（任意）` の用言止めを検出するためである。開き括弧を伴わない閉じ括弧では何も除去しない。日本語の文字を含まない見出しは対象外とする。`ja.renyo_per_1k` のような識別子の見出しに形態素解析の結果を適用しても意味を持たないためである。

この規則は日本語の文書にのみ適用する。英語には体言止めと述語止めの区別が存在せず、英語の実行経路では形態素解析器が参照されない設計になっている。

参照コーパスでの章タイトルの用言率は、人間のネイティブ執筆 798件で 3.34%、公開 ADR 123件で 1.78%、手順書 200件で 11.16%、AI の出力 150件で 6.37% である。人間と AI の分布は分離しない。この値は文体の判定には使用できず、規則の根拠は参照コーパスで優勢な慣行からの逸脱である。

章タイトルより下の見出しでは用言率が上がる。人間のネイティブ執筆で 13.04%、手順書で 13.12%、公開 ADR で 6.29%、AI の出力で 22.80% である。

人間のネイティブ執筆では章タイトルの 3.34% に対して 3.9 倍であり、下位の見出しでは用言止めが正当な形式として一定の割合を占める。そのため対象を章タイトルのみとしている。計測はいずれも `examples/structure_rate.rs` による。

`howto` 型と `log` 型では適用しない。手順書では章が一つの操作であり、作業記録では章が決定や作業の項目を言い切るため、いずれも用言止めが正しい形式となる。手順書コーパスにおける発火率は 24.5% であり、適合の基準である 10% を大きく超える。

`log` 型の根拠はこのリポジトリの `docs/content/ja/decisions.md` であり、章タイトル50件のうち49件（98.00%）が用言止めである。同じ `log` 型の `TASKS.md` は 2件（6.06%）に留まる。章タイトルが `（済み）` で終わり、末尾の整形後に名詞句となるためである。型の中でも様式によって分布が分かれる。

`decision` 型は適用対象から除外していない。公開 ADR は決定文を第1階層の標題に配置し、`structure::sections` がこれを除外するため、判定対象となるのは体言止めのセクション名である。発火率は 4.9% で基準の範囲内に収まる。

文書型を宣言していない文書にも適用する。型ごとの除外は型が解決できた場合にのみ機能するため、宣言のない手順書では 24.5% の割合で指摘を受ける。該当する文書は型を宣言するか、`.suikou/profile.toml` で規則を無効化する。

判断の経緯は [決めたことの記録]({{< relref "decisions.md" >}}) の D-52 に記録されている。

## 文体の規則

### register/rare-wago 文体にそぐわない和語

プロの日本語訳における出現頻度と比較して、不自然に多用されている和語の内容語を検出する。対象は語種が和に分類される内容語とし、数詞および1文字のカタカナは除外する。専門用語の大半は漢語やカタカナ語であるため、和語に限定することで誤検出を防げる。

検出には、同一の語が文書内で3回以上出現していることを条件とする。一度きりの出現では、文体からの逸脱なのか偶然の語選択なのかを判別できないためである。

統計的な判定には、Dunning (1993) の対数尤度比とHardie (2014) のLog Ratioの二つの統計量を併用する。対数尤度比が 15.13 以上（自由度1で p < 0.0001）であり、かつLog Ratioが 7.0 以上（参照頻度の128倍）である場合に検出する。統計的有意性だけでは一般的な語をわずかに多く使っただけでも条件を満たしてしまうため、効果量の基準も組み合わせている。

参照用の頻度表は `crates/suikou-core/data/register_ja.toml` に格納されている。この頻度表はKubernetes、MDN、Vueの日本語訳652ページ、内容語およそ29万語から構築したものである。入門書は文体が異なるため除外し、2分野以上に出現する語だけを収録している。再構築の手順は `research/lexshift/build_reference.py` に定義されている。

`.suikou/terms.toml` および `.suikou/register-allow.toml` に登録された語は検出対象から除外する。参照コーパスがWeb関連の文書で構成されており、計算や統計に関する語彙の収録が少ないためである。

### register/prefer-katakana カタカナ語が優勢な漢語

同じ意味を表す漢語とカタカナ語のペアのうち、プロの日本語訳でカタカナ語が優勢な組み合わせを対応表として保持し、対応する漢語が出現した箇所を指摘する。統計的な閾値ではなく対応表で照合するため、出現するたびに検出する。

対応表は `crates/suikou-core/data/kata_pairs_ja.toml` に格納されている。候補の選定は人手で行い、採否は複数分野を横断した出現頻度の実測値に基づいて決定した。採用条件は、カタカナ側の合計出現数が漢語側の2倍以上であること、両者の合計出現数が20回以上であること、および漢語側の出現数が60回以下であることのすべてを満たす場合とする。

最後の条件は多義語による誤検出を避けるための制約である。「対象」「対応」「状態」といった語はプロの翻訳でも頻繁に用いられるが、カタカナ語と常に同じ意味で使われるとは限らない。プロの訳文で漢語側がほとんど使われていないペアに絞ることで、置換候補としての信頼性を担保している。

直前のトークンが名詞である場合は、複合語の一部とみなして検出対象から除外する。`英語版` や `第3版` に含まれる `版` を `バージョン` に置換すると誤りになるためである。

特定の分野で別の意味に用いられる語については、`.suikou/register-allow.toml` で個別に除外する。
## 構造の規則

文体に関する規則とは異なり、構造の規則は言語に依存しない。セクションの構成や配置順序、段落のまとまりは語彙体系ではなく文書の論理構造に関わる性質だからである。実測でも、7文以上の段落が占める割合はプロの英語文書で 0.27%、プロの日本語文書で 0.59% となり、言語をまたいで同じ桁に収まった。そのため、言語ごとに定義するのはセクション名と文の分割方法のみとしている。

これらの規則は複数の文献を根拠としている。必須セクションと推奨順序の枠組みは RFC 7322 に基づいており、あるセクションが下位セクションのみで構成されてよい点も同仕様に明記されている。文書型ごとのセクション構成は Rust RFC テンプレート、Kubernetes Enhancement Proposal、Michael Nygard の Architecture Decision Record、および Diátaxis を参考にした。段落を一つの考えの単位とする原則は Google developer documentation style guide と Strunk の The Elements of Style に由来し、標題で主題を示して見出しから全体像を把握できるようにする方針は「公用文作成の考え方」に基づいている。

### 文書の型

文書の型は `crates/suikou-core/data/structure.toml` に定義されている。各型は必須セクション、推奨順序、見出しの同義語に加えて、各セクションが答えるべき問いと記述すべき内容を保持する。

セクションには分量の目安を表す `scale` も設定でき、`plot` と `brief` がその情報を出力する。一方、`check` では検査対象としない。人間の文書では四分位が中央値の 2.5 倍から 3 倍に広がり、判定基準として分離できないためである。D-46 の判断に基づき、この項目を設定している型は `readme` のみである。

| 型 | 用途 |
|---|---|
| `design` | 提案と設計。何を作るか、なぜ必要か、どこまで扱うかを示す |
| `enhancement` | 段階的に導入する提案。テスト計画、昇格条件、切り戻し手順を含む |
| `decision` | 意思決定の記録。文脈、決定内容、その結果を残す |
| `howto` | 作業手順。前提条件から始め、結果の確認で終える |
| `reference` | 定義や仕様の参照文書。必須セクションは設けない |
| `log` | 記録を集約した文書。決定記録、作業一覧、変更履歴など |
| `readme` | README。冒頭の一段落で対象が何であるかを説明する |
| `overview` | 最初に参照される導入文書。対象が何であるかから書き始める |

文書型を選ぶ際は `suikou doctype` を実行すると判定用の質問が表示される。最大2問で型が定まる設計であり、特定のツールに依存せず質問ツリーをそのまま出力する。CI やエージェントから呼び出される前提のため、対話的な入力は設けていない。質問ツリーは `structure.toml` の `[[select]]` に定義されており、すべての型へ到達できることをテストで検証している。

型の宣言は、対象文書に近い設定から順に参照される。

| 設定場所 | 記述例 |
|---|---|
| フロントマター | `doctype: "design"` |
| 他ツールが付与したフィールドのマッピング | `[front_matter]` と `[front_matter.map]` |
| `.suikou/structure.toml` の `[paths]` | `"README.md" = "readme"` |
| プロットの先頭 | `<!-- suikou:doctype design -->` |

複数のパス接頭辞が一致した場合は、より長い接頭辞が優先される。

文書によっては、Hugo の `content_type` のように別のフィールド名で型が宣言されている場合がある。その際はフィールド名と値の対応表を設定すれば、文書側を修正せずに型を判定できる。

```toml
[front_matter]
field = "content_type"

[front_matter.map]
task = "howto"
reference = "reference"
```

対応表に含まれない値に対しては型を確定させない。未知の値を推測で割り当てるのを防ぐためである。

プロットは `--doctype` を指定して生成するため、作成時点で型情報を持っている。したがって、プロットをもとに執筆した文書へ型の宣言を追記する必要はない。型情報の印に HTML コメントを用いているのは、Markdown として表示した際に読者の目に触れないようにするためである。

いずれの場所にも型が宣言されていない文書には、型に依存する規則を適用しない。型を明示していない文書が、後の規則追加によって突然エラーになる事態を避けるためである。

宣言された型名が未定義の場合は、その場で異常終了する。黙って無視すると、型名のスペルミスによって検査自体が行われなくなるためである。

### structure/missing-section 必須セクションの欠落

宣言された型で必須とされるセクションに対応する見出しがない場合に検出される。重大度は error である。

セクションと見出しの照合には同義語を用いる。先頭の第1階層見出しは文書全体の標題でありセクションではないため、照合対象から除外する。セクションの有無は、見出しの階層を問わずに判定する。見出しレベルはフォーマット上の選択であって意味の違いではないためであり、たとえば KEP では `Goals` が `## Motivation` の下に `###` で配置される。

一方、セクションの順序判定は最上位の見出しのみを対象とする。入れ子になった下位見出しを最上位の見出しと並べて順序を比較しても意味がないためである。この判断の経緯は D-47 に記録されている。

主題を説明するセクションに限り、標題の直後に配置した地の文で代用できる。これに該当するのが `lead_ok` を持つセクションである。RFC 7322 の abstract は標題と目次の間に見出しなしで置かれ、README も同様の構成を取る。こうした箇所に見出しを強制すると、かえって可読性が損なわれる。

代用を認めるのは `lead_ok` を持つセクションのみであり、出現位置ではなくセクションの性質によって判定する。位置だけで判定すると、最初の必須セクションの種類にかかわらず導入文で条件が満たされてしまい、Kubernetes の concept ページ120件すべてが `howto` の必須条件を通過する結果になる。前提条件や文脈は導入文では代替できない。経緯は D-31 に記録されている。

見出しの照合は日本語・英語の双方の同義語に対して実行する。日本語で書かれた文書に英語の見出しが使われる場合があるためである。

また、診断メッセージでは欠落の事実だけを通知するのではなく、そのセクションが答えるべき問いと記載すべき内容まで併せて提示する。

必須セクションの構成は文書型によって異なる。`howto` で必須としているのは前提条件のみであり、手順と確認は必須対象から除外している。Kubernetes の task ページ120件に適用したところ、手順が120件、確認が113件で検出されたためである。手順そのものは文書の本文全体であり、独立したセクションではない。経緯は D-31 に記録されている。

必須対象から除外しても、問いと記載内容の定義は型の中に保持される。`plot` と `brief` は引き続き「どうやるのか」と「うまくいったとどう分かるのか」を提示する。機械的に検出できる要素と、執筆前に検討すべき要素は必ずしも一致しない。

### structure/section-order セクションの順序

検出されたセクションの並びが、文書型で推奨される順序と一致しない場合に警告する。重大度は warning である。順序は読者が内容を理解しやすくするための構成方針であり、厳格に禁止すべき規約ではないためである。

推奨順序が実務の慣習と合致していることは、公開されている ADR 190件を用いて確認している。そのうち189件が判定条件を満たし、違反の検出はゼロであった。

### structure/long-paragraph 長すぎる段落

一つの段落に含まれる文数が `MAX_SENTENCES_PER_PARAGRAPH` を超えた場合に検出される。重大度は warning である。Google developer documentation style guide が5〜6文を上限の目安としていることから、上限値は6文に設定している。

段落の境界は空行で判定し、日本語の文分割には `split_sentences_ja` を使用する。英語では終止符の直後に空白が続く場合のみを文の区切りとみなす。これにより、`11.095` のような小数点で誤って分割され、文数が実際より多く計上されるのを防いでいる。

### structure/empty-section 本文のないセクション

末端のセクションに本文が存在しない場合に検出される。重大度は warning である。

下位セクションを持つ親セクションは、直下に本文がなくても許容される。この扱いは RFC 7322 に明記されている。また、コードブロックのみを含むセクションも本文ありとして扱う。

### structure/plot-mismatch プロットとの構成不一致

`.suikou/plans/` にプロットが存在する場合、その見出し構成と本文の見出し構成を照合し、差異があれば警告する。重大度は warning である。

プロットはバージョン管理の対象外とする作業用ファイルであるため、CI 環境からは参照されない。ローカル環境およびエージェントの作業ループ内でのみ機能する。

### structure/work-note 作業メモ的な記述

読者向けの文書に、著者が自分用に残した作業文脈が混入していないかを検出する。重大度は warning である。検出対象は、試した案、判明したこと、作業の段階、以前の状態に関する表現である。

検出の有無は文書型に応じて切り替える。`work_notes_ok` を持つ型では検査を行わない。`design`、`decision`、`log` の3種類がこれに該当する。これらの文書型では、検討した案と棄却した案そのものが伝えるべき情報だからである。

| パターン | README | 参照(英) | 参照(日) | Rust RFC | ADR |
|---|---|---|---|---|---|
| 試した案 | 0.4% | 0.2% | 0.1% | 4.5% | 3.2% |
| 判明したこと | 0% | 0.3% | 0.1% | 7.5% | 1.6% |
| 作業の段階 | 0% | 0% | 0.1% | 0% | 0.5% |
| 以前はこうだった | 0% | 0.3% | 0.3% | 5.0% | 0.5% |

`変更の経緯` は検出候補から除外した。英語では11件のうち8件が読者に行き先を示す表現であり、日本語では通常の動詞と区別できないためである。

例示としてこれらの表現を引用する場合はコードとして記述する必要がある。地の文にそのまま書くと検出対象になる。

型を宣言していない文書では検査を実行しない。読者向けの文書かどうかを判断できないためである。経緯は D-40 と D-42 に記録されている。

### structure/lead-opener 導入段落の書き出し

先頭段落の書き出し表現を検査する。重大度は warning である。先頭段落とは、標題の後にあり、最初のセクション見出しより前に置かれた最初の地の文を指す。先頭段落を持たない文書では何も検出されない。

検出する表現パターンは言語ごとに定義している。

| パターン | 日本語 | 英語 |
|---|---|---|
| 一般論から始める | `近年`、`従来`、`昨今` | `In recent years`、`Traditionally` |
| 著者の経緯から始める | `筆者は`、`当初は` | `I built`、`We decided`、`Originally` |
| 文書の目的を宣言する | `本文書の目的は` | `The goal of this`、`This aims to` |

パターンの採否は実測に基づいて決定した。先頭段落 831件（著名 OSS の README 199、Rust RFC 20、ADR 10、参照コーパスの英語 602）を調査したところ、上記3パターンはいずれも0件であった。日本語でも、参照コーパスの先頭段落 653件に対して0件であった。

自己言及（`本文書は`、`This document describes`）は検出対象から除外している。英語の参照コーパスでは 37/602 件（6%）で出現しており、API 仕様の説明などでは自然な書き出しとして成立するためである。

実際の文書 2,080件に対する検証でも検出は0件であった。経緯は D-39 に記録されている。

なお、この規則は著者の備忘録を直接検出する仕組みではなく、文書の途中に書かれた備忘的な記述は対象外である。先頭段落を主題から書き始めるよう促すことで、備忘的な記述を文書の後方へ移動させる役割を担う。

### 執筆指針の提示

構造の規則には、違反を検出するだけでなく執筆前に指針を提示する機能もある。`suikou plot` と `suikou brief --doctype` は、執筆開始前にテンプレートと書き方のガイドラインを出力する。

違反を指摘するだけでは避けるべき表現は分かっても、どのように書くべきかは定まらない。そのため、セクションごとに答えるべき問いと記述内容を示し、段落の構成方法や結論を先に述べる方針を併せて提示する。指針の文面は `structure::writing_rules` に一元管理されている。

## 閾値のカスタマイズ

### 全体設定の上書き

`.suikou/profile.toml` に記述した項目だけが組み込み設定を上書きする仕組みとしている。プロファイル全体を差し替える方式では、1つの値を変更したいだけでもすべての設定を複製する必要が生じるためである。

```toml
[thresholds."ja.kango_ratio"]
value = 0.55

# 出さない指標はここに並べる
disable = ["en.simile_marker_per_1k"]
```

組み込みで閾値が設定されていない指標を追加する際は、`value` と `direction` の双方を指定する必要がある。片方だけでは判定できないため、黙って無視せずエラーとして扱う。

### 文書型ごとの調整

文書の用途によって、同じ指標に対する適切な基準は異なる。最初に読む README と参照文書では文体の硬さが違うためである。

```toml
[doctype.readme]
reason = "利用者と調整した結果。入り口は箇条書きが主になる"
rules = ["structure/long-paragraph"]

[doctype.readme.thresholds."ja.kango_ratio"]
value = 0.65
```

`reason` は調整の背景を記録するためのフィールドである。基準を緩和した理由を明記しておけば、後から確認する人が同じ検討をやり直さずに済む。組み込みの型調整には `reason` の記述を必須としており、テストでその存在を確認している。

`rules` は局所規則の抑止に用いる。数値指標は閾値で強弱を調整できるが、局所規則は出力するか抑止するかの二択になるためである。

設定の適用順序は、組み込みの全体設定、組み込みの型設定、利用者の全体設定、利用者の型設定の順とする。利用者が定義した設定を常に最優先にしているのは、組み込みの調整を元に戻せない仕様にすると、実測傾向が異なる現場で対処できなくなるためである。

型ごとの設定では指標の新規追加を認めておらず、追加は全体設定の上書きで行う役割分担としている。文書型ごとに異なる指標が増減すると、どの文書がどの基準で評価されたのか追跡しにくくなるためである。

### 組み込みの文書型に対する調整

組み込みでは `readme`、`design`、`decision` の各型に閾値調整を施している。著名な OSS の README（英語 240件、日本語 150件）、Rust RFC 200件、公開されている ADR 190件の実測データから導いた値である。

既定の閾値をそのまま適用した場合の検出率を次に示す。

| 指標 | README | 参照 | 比 |
|---|---|---|---|
| `en.mattr100` | 70% | 15% | 4.7 |
| `en.prose_ratio` | 32% | 11% | 2.9 |
| `en.simile_marker_per_1k` | 74% | 45% | 1.6 |

検出率が 70% に達する指標は、文書の品質ではなく閾値の不一致を表している。

型ごとの調整を適用した後の検出率は次のようになる。

| 指標 | README | 参照（不変） |
|---|---|---|
| `en.mattr100` | 6% | 15% |
| `en.prose_ratio` | 7% | 11% |
| `en.simile_marker_per_1k` | 0% | 45% |

日本語の README 150件でも、調整後の検出率は 0% から 2% の範囲に収まる。

文体の硬さの差は一方向に偏るわけではない。日本語の README では参照文書よりも漢語率が高い（0.62 対 0.52）。名称や機能を列挙する記述が漢語を増やすためである。経緯は D-41 に記録されている。

## 指摘時の抜粋表示

違反位置を示す際は、一致した文字列本体と、その前後の短い文脈を併せて出力する。

```
- L9:31 現時点｜…の選択肢を比較検討しました。現時点で候補となっていたのは、El…
```

一致した文字列を先頭に示すのは、修正対象の語を一目で特定できるようにするためである。行頭から一定文字数を切り出す方式では、行の後半にある一致箇所が抜粋に含まれない。また、同一行に複数の一致箇所がある場合、同じ抜粋が並んで区別できなくなる。

前後に表示する文脈の幅は言語ごとに変えており、日本語は14字、英語は20字としている。日本語は1文字あたりの情報量が多く、14字でおおよそ一節に相当するが、英語で同じ幅を取ると2語程度しか含まれないためである。

## ゴールデンテスト

`tests/golden/input/` に配置した各入力ファイルに対応する期待出力を、`tests/golden/expected/` に格納している。

| ファイル | 検証内容 |
|---|---|
| `ja_maintainability.md` | 日本語で M1 から M7 の規則を検出させる |
| `en_maintainability.md` | 同様に英語で検出させる |
| `ja_prose.md` | 地の文が中心の文書で日本語の文書指標を確認する |
| `en_prose.md` | 英語で同様に文書指標を確認する。英語の指標には445語以上が必要である |

期待出力はテスト用に作成した入力から生成している。実コーパスを用いた回帰検証には `corpus/fetch.sh` で取得したデータを使用する。ライセンス上の制約により、コーパス本体はリポジトリに含めていない。

## 用語集の規則

### glossary/defined-name 定義した名前以外の呼び方

`.suikou/defined.toml` に登録した名前を、別の語で呼んでいる箇所を検出する。重大度は error である。

設定ファイルには、定義した名前 `name`、その名前で呼ぶべき対象を指す別の言い方 `instead_of`、および命名の根拠 `note` を記述する。`note` を記述すると指摘に添えて出力される。

対象は地の文、リスト項目、および見出しである。定義した名前の統一は文体の問題ではなく識別子の問題であり、見出しで別の呼び方を用いると読者は同一の対象であると判断できない。本文と見出しの検出位置は1件の指摘にまとめる。

設定ファイルが存在しない場合は何も検出しない。

### glossary/variant 用語集との表記不一致

用語集で定義された表記と異なる記述が見つかった場合に検出される。重大度は warning である。

この規則が検査対象とする項目は次のとおりである。

- 表記の違い。`サーバ` を `サーバー` に統一する。
- 多字の直訳語。`根因` を `根本原因` に統一する。

語彙の選択そのものは `register/prefer-katakana` が担当する。同一箇所に対して2つの規則が重複して指摘すると、修正する側が同じ指摘を2度確認することになるため、役割を分けている。

単字の直訳語（`版`、`枝`、`題`）はこの規則の検査対象外としている。部分一致で検索すると「問題」の中の「題」まで誤検出してしまうため、形態素解析が必要になる。これらは `prefer-katakana` が形態素単位で検査しているため、重複させない。

検査対象は地の文および箇条書きの本文であり、見出しとコードは除外する。形態素解析を用いない実装のため、辞書を含まないバージョンでも適用できる。

### 表記基準の決定方法

JTCA「外来語（カタカナ）表記ガイドライン」第3版では、英語の語尾 -er、-or、-ar、-y に対して長音符号「ー」を付ける方針が示されている。

参照コーパス438万字で実態を確認したところ、-er、-or、-ar はガイドラインどおりの傾向であった。

| 語 | 長音あり | 長音なし |
|---|---|---|
| サーバー | 591 | 130 |
| ユーザー | 1830 | 328 |
| パラメーター | 158 | 6 |
| クラスター | 1279 | 5 |

一方で -y は逆の傾向を示した。そのため、ガイドラインから一律に決めるのではなく、語ごとの実測値に基づいて表記を決定している。

| 語 | 長音あり | 長音なし |
|---|---|---|
| プロパティ | 3 | 870 |
| メモリ | 75 | 402 |
| ディレクトリ | 9 | 227 |
| コンテナ | 95 | 1783 |

`コンテナ` は語尾が -er であるものの、この分野では長音を省く表記が定着している。
