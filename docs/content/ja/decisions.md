後から読む人が、同じ検討を繰り返さずに済むようにするための記録である。
判断が分かれた箇所を、そのつど追記していく。

## D-01 文書の全体で測定する指標を textlint に収めない

textlint はノードの位置に紐づけて指摘する仕組みである。
文書の全体でしか測定できない指標には、紐づけるべき位置がない。
さらに、その指標の多くは不足していることの指摘である。
形式名詞が少ない、指示詞が少ない、直喩の標識が少ない。
不足しているものには、どこにも位置がない。

はじめは Document ノードに対して報告する textlint の規則として書く案を採った。
これは判断を誤っていた。
textlint の中に収めると解析の土台が JavaScript に縛られる。
そうなると語種を返す形態素解析が得られず、漢語率を書けなくなる。
書く都合で、確認を成功した指標を破棄することになって、順序が逆である。

前面のツールが textlint を呼び出して、自前の文書の解析とまとめる形を採る。
MCP は前面のツールそのものが出せばよい。
むしろ、まとめたレポートを一度に返せる分、エージェントには都合がよい。

## D-02 書く言語は Rust を中心として、Python は較正と探索に限定する

確認を成功した指標は、すべて純 Rust で書ける。
lindera-unidic が UniDic のすべての素性を返して、語種と活用形が取れるためである。

Python が必要だったのは分詞節、名詞化、修飾の積み重ね、係り受けの距離である。
これらはすべて、測定した値で除外した指標である。
深い構文の解析が必要である指標ほど実験の構成に敏感で、先行研究の効果が移らなかった。

そこでレイヤーを分割する。
決まった指標は Rust で書いて、探索と較正は Python で行う。
Python で使えると分かった指標だけを Rust に移す。

Claude Code の hooks から Write と Edit のたびに動かす使われ方では、
起動の費用が効いてくる。
spaCy の読み込みに2秒から5秒かかるため、Python を本番の経路に置くことはできない。

## D-03 Markdown のパーサを使わず行で処理する

`research/` の参照の実装が行で処理していて、
ゴールデンテストの値を統一するために同じやり方を採る。
依存が減る分、バージョンの違いによる事故も減る。

## D-04 形態素解析をトレイトの裏に隔離する

lindera の API と UniDic の素性の順序は、バージョンで変わる。
バージョンに依存するコードをひとつの構造体に閉じ込めれば、壊れうる面が数十行に短縮される。

加えて、既定の feature に lindera を入れないことで、
辞書を落とさずに規則と指標を確認できる。そのため変更の確認が速くなる。

## D-05 起動のときに素性の順序を自分で確認する

バージョンを固定するだけでは、更新したときに気付かれずに壊れる問題が残る。
素性の順序が一致しなくなると、語種と活用形が別の位置から読まれる。
値は返るが、その内容が違う。

漢語率と連用中止がこの二つに依存しているため、
壊れた値のまま動くと、指摘の内容そのものが間違いになる。
知っている語を流して確認して、一致せずいれば異常終了する方がよい。

## D-06 文体で閾値を分割しない

常体と敬体で指標が変わるかを、二つのモデルの出力で比べた。
モデルの間で方向が一致しず、決まった効果は見られなかった。
その差はモデルの差に吸い取られる。

文体の判定は残すが、その用途は体言止めのような文体に依存する規則を当てるかどうかに限定する。
閾値の表を二重に持つ必要はない。

## D-07 形式名詞と漢語率の severity を info に置く

文書の種類による振れが大きい。
手順書では形式名詞が閾値に触れて、概念の解説では漢語率が人間ネイティブの値に近づく。
漢語率は話題への感度も高い。

日本語の人間のコーパスは解説書に偏っていて、手順書の型が不足している。
種類ごとの値が一致するまでは info に置いて、一致した時点で warning に上げる。

## D-08 先行研究の効果を導入さない

英語の分詞節について、人間の5.3倍という報告をもとに閾値を9から10と見積もった。
測定してみると人間の範囲と重なって、使えなかった。名詞化についても同じである。

理由は実験の構成方の違いと見ている。
報告の元は人間が書いた文章を与えて同じ文体で続けさせる形だが、こちらは文書を作らせている。

先行研究は仮説のもとにはなるが、その効果を仕事をまたいで導入してはならない。

## D-09 保ちやすさのレイヤーは人間の平均に合わせない

箇条書きの導入文を正しく書いているのは AWS S3 ユーザーガイドだけだった。
Linux kernel は不完全な導入の方が多い。
人間の平均に合わせると、このレイヤーは意味を失う。

このレイヤーは AI らしさを除去するものではない。
人間が書いた文書の大半より良くするためのレイヤーである。

## D-10 予防で除去できるレイヤーと lint でしか消せないレイヤーを分割する

フォーマットを抑える指示を与えた条件と与えない条件を比べた。
フォーマットは完全に消失したが、語彙と文の構成は変わらなかった。

保ちやすさの指示についても同じ実験を行った。
構成の規則は短い指示で完全に守られ、
時点に依存する語は詳しい指示で初めてゼロになった。
項目の数、見出しの連番、手で付与した番号は、指示がなくても起きない。

したがって `brief` には、指示で守れることだけを入れる。
効果のない制約を入れることは、トークンの無駄であって、直しすぎる危うさもある。

副次の効果として、保ちやすさの指示だけで文書指標も良くなった。
導入文を書かせたことで地の文が生まれて、地の文比率と箇条書き比率が人間の範囲に近づいた。

## D-11 語の辞書を同梱せず文書から作る

生きた比喩と死んだ比喩の判別が、比喩のレイヤーでいちばん難しい。
cache や handshake は分野で定まった語であって、比喩ではない。

指摘されて有名になった語は、出る数が減る。
2024年の初めに指摘された語の群は、その直後から減った。同梱の辞書は陳腐化する。

自分の文書から作る辞書は古びない。
プロジェクトごとに語が違うという理由に加えて、
これが辞書の古びへの構えになる。

## D-12 漢語率のテストは期待値の側を修正した

`kango_ratio_counts_only_content_words` が落ちていた。
入力「設定を変更すること」に対して実装は 0.5 を返して、テストは 0.5 超を見込んでいた。

`TASKS.md` はテストが失敗したら実装を修正すると規定している。この件は例外にあたる。
テストの注記は自立語を「設定」「変更」「こと」の3語と数えていたが、
`FakeMorphology` の仕様には「する」が動詞として入っていて、自立語は4語になる。
指標の定義は、分母を自立語のうち語種が 和 漢 外 混 のものとしている。
そのため動詞の「する」も分母に入って、実装が返す 2/4 が定義どおりの値である。
実装をテストに合わせると、定義に反する。

テストのねらいは、助詞を分母から外すことの確認にある。
期待値を 0.5 の完全一致に変更しても、そのねらいは保たれる。
助詞「を」を分母に入れた場合の値は 0.4 であって、両者は判別できる。

実装を修正してよいのは、実装が定義から外れている場合に限る。
期待値が定義から外れている場合は、期待値を修正する。

## D-13 M2 と M6 は出る数ごとに数える

参照の実装は1行あたりの出る数を数えるが、
Rust の実装はブロックの単位で高々1件しか指摘していなかった。
`tests/golden/input/en_maintainability.md` の
「The validator currently reports ... The latest release」が1行に2語を含んでいて、
参照の実装の 2 に対して Rust が 1 を返していた。

出る数ごとに数える側を採った。根拠はこのプロジェクト自身の制約にある。
1行に2件あって1件しか報告しないと、
指摘された側だけを修正した文書が `check --quiet` でまた異常終了する。
レイヤーごとに lint と修正を往復させないという設計が、そこで崩れる。

`Position` に使われていない `column` があったのは、
もともと出る数ごとに位置を持たせる見込みだったことを示している。
出る数ごとに列を持たせたことで、同じ行の複数の違反を判別できる。

M7 は行末だけを見るため1行に高々1件であって、この変更の影響を受けない。

## D-14 語数と文数は相対の誤差で照合する

照合の方針は、比率に絶対の誤差 0.02、密度に 0.5、M 系に完全一致を定めていた。
語数はこのいずれにも当てはまらない。

`en_prose.md` の語数は参照の実装が 445、Rust が 444 だった。
理由は `trade-off` の扱いにある。
spaCy は三つのトークンに割って記号を除くため2語と数えて、空白での分割は1語と数える。
この文書に含まれるハイフンの語はちょうど一つであって、差と一致する。

トークナイザの定義の違いであって、実装の間違いではない。
完全一致を求めると、定義が違うものを同じ数にしろと求めることになる。
相対の誤差 1% で照合て、決まったずれだけを捕らえる。

## D-15 形式名詞の対象範囲が参照の実装と定めで相違している

指標の定義は、語彙の指標を地の文とリスト項目の本文で測定するとしていて、
形式名詞をその一つに挙げている。Rust の実装はこれに従っている。

参照の実装 `research/jametrics.py` は、指示詞について
地の文だけの値と、地の文とリスト項目の本文の値の両方を出す。
その一方で形式名詞は、地の文だけの値しか出さない。

`tests/golden/input/ja_maintainability.md` で測定すると、
地の文だけなら 14.98、リスト項目の本文を含めると 15.77 になる。
その差は 0.79 であって、密度の許容範囲 0.5 を超える。

ここで実装を変更してはならない。定義には理由が書いてある。
出力の大半が箇条書きになるモデルがあって、
地の文だけで測定すると本文の8割以上を破棄することになる。

相違するのは閾値の側である。
人間の範囲 11.095 から 11.163 と D5 の閾値 8.5 は、地の文だけの定義で測定した値である。
リスト項目を含めると値が上がるため、D5 は較正のときより出にくくなる。
D5 の severity を info に置く判断（D-07）は、この点でも正しかった。

較正をやり修正するまで、この相違は開いたままになる。
やり修正には `research/jametrics.py` に地の文とリスト項目の値を追加して、
コーパスに対して測定し修正することが必要である。

## D-16 辞書を埋め込んだひとつのバイナリで配布する

配布する形を決めるにあたって、埋め込んだ辞書の大きさを測定した。

| 内容 | 大きさ |
|---|---|
| 辞書を同梱したバイナリ | 191 MB |
| 同じものを xz で圧縮 | 26 MB |
| 辞書を含まないバイナリ | 1.1 MB |

`strip` は効果がない。内容がシンボルではなく辞書のデータであるためである。

辞書を外に出して初回に取ってくる形も採れる。
lindera 6.0.0 には `load_dictionary_from_path` があって、
複製せずに読める。それでも埋め込みを採った。

その理由は使われ方にある。
hooks から Write と Edit のたびに動かすツールでは、
失敗の経路の数がそのまま信頼になる。外に出した辞書は、欠け、壊れ、
バージョンの相違という経路を増やす。バージョンの相違は自己診断が捕らえるが、
捕らえたところで使う人は動けない。取ってきたあとにネットワークが必要ない形の方が、
この使われ方には合う。

配布する単位は OS ごとの書庫とする。
すべての OS をひとつに束ねると圧縮後 78 MB になって、
使う人は使わない OS の分を必ず除外することになる。

対象は x86_64 の Linux (musl)、
Apple Silicon の macOS、x86_64 の Windows に限定した。
Linux を musl にするのは、glibc のバージョンに依存させないためである。
古いディストロやコンテナで動かないツールは、hooks から呼ぶ使われ方では痛い。
Intel Mac と ARM Linux は外した。必要な場合は、使う人がソースから作る。

## D-17 辞書の feature を既定で有効にしない

`suikou-cli` に `lindera-unidic` を追加したが、既定では切ったままにした。
既定に入れると `cargo test --all` が辞書を引き込んで、
辞書なしで本体を確認できるという前提（D-04）が壊れる。

代わりに二つの手段当てをした。
配布用のビルドは feature を書いて作って、起動して辞書のあるなしを確認してから梱包する。
辞書なしのバージョンで日本語を求められた場合は、`morphology::load` がその場で異常終了する。

気付かれずに空の解析結果を返してはならない。
形態素解析が空を返すと、漢語率も連用中止も形式名詞も 0 になる。
0 は閾値の下にあるため、指摘が出るものと出ないものが入り混じる。
そして「指摘なし」という誤った結びに至る経路がある。

どちらのバージョンかは `suikou --version` で判別できるようにした。
使う人が握っているバイナリを特定できないと、日本語が解析されない理由をたどれない。

## D-18 配布する物の確認は辞書の実体に対して行う

配布用のワークフローを `act` で実行させて見つかった。
梱包されたバイナリは 1.2 MB しかないのに、`--version` は「UniDic 同梱」と出していた。
辞書は 191 MB あるため、両立しない。

理由はリンカが使われないコードを除外することにある。
サブコマンドがすべて `todo!()` であったため、`morphology::load` に到達する経路がなく、
埋め込んだ辞書のデータごと削除されていた。
到達する経路を作ってビルドし直すと 191.5 MB になって、実際に解析の結果を返した。

問題はスモークテストの側にもあった。
`--version` の表示は `#[cfg]` による構成のときの分岐であって、
feature が有効かどうかを示すだけであって、辞書が実在するかを示さない。
辞書を持たないバイナリに対して、この確認は通ってしまう。

`selftest` サブコマンドを追加して、実際に辞書を読んで解析させる形に変更した。
配布する物の確認は、構成の設定ではなく、できあがった物の振る舞いに対して行う。
自己診断が素性の順序を実際の辞書で確認しているのと同じ考え方である。

副次の効果として、`morphology::load` に到達する経路ができたため、
`crates/suikou-cli/src/morphology.rs` に置いていた抑制を外せた。
使う人にとっても、握っているバイナリが思ったとおりのものかを確認する手だてになる。

## D-19 指摘の行番号は前処理の前の行に合わせる

自分の文書に `suikou check` を適用して見つかった。
指摘された行番号が、実際の行より4つ前を指していた。
その差は、取り除いたフロントマターの行数と完全一致する。

前処理はフロントマターとコードブロックを内容ごと消していた。
そのため後続の行が前へ詰まって、行番号が実際のファイルと一致しなくなる。

取り除いた範囲を、同じ数の改行に置き換える形に変更した。
空の行は数えないため、空でない行の数と箇条書き比率は変わらない。

lint の指摘は、使う人が開いているファイルの行を指さなければ使えない。
値が正しくても、位置が一致せずいればその指摘は役に立たない。

## D-20 文書を Hugo のサイトにして、既定の言語を英語にする

文書を `docs/` の直下に置く形から、`docs/content/{en,ja}/` に移した。
既定の言語は英語とする。

テーマを外から取らず、自前の最小のレイアウトを置く。
依存を増やさないためであって、バージョンを固定するという本体の方針を文書の側でも保つためでもある。

文書の正本をひとつに規定したことで、サイトとリポジトリで同じ内容を二重に持たずに済む。

## D-21 brief の詳しさはプロファイルではなくフラグに持たせる

設計の文書には、brief の詳しさをプロファイルの設定として持たせる案がある。
今回の実装では、この案を採らずに `--detail concise|balanced|detailed` という
フラグだけで制御する形にした。

理由を挙げる。Profile は指標の閾値を保つための構造体である。
そこへ brief 専用の設定を追加すると、この構造体が二つの役目を抱えることになる。
較正で書き戻す値と、出力の形だけを選ぶ値を同じ構造体に混ぜると、
`suikou baseline` が書き戻すべき範囲があいまいになる。閾値だけを保つという
Profile の役目を保つほうを選んだ。

フラグの水準も、当初の書き付けから変更した。`TASKS.md` の最初の案は
concise と detailed の二つだけを挙げていたが、実装の途中で balanced を
間に置くほうが自然だと分かった。構成の規則を1文で書きつつ時点依存語だけを
すべて列挙するという brief の制約は、balanced という真ん中の水準にそのまま収まる。
concise はそこからさらに切り詰めた形にし、detailed は規則ごとに理由まで添えた。

プロファイルへ持たせる案は、決めていないことの一覧に残す。
用途ごとに既定の detail を変更したいという求めが実際に出たときに、
プロファイルへ移すかどうかを決めることにする。

## D-22 baseline の閾値は Tukey の外れ値境界で決める

`suikou baseline` を実装するにあたって、閾値の決め方を選ぶ必要があった。
`docs/content/ja/design.md` は、
閾値を人間の範囲の上と AI の範囲の下との間に置くと規定している。
ただし baseline が見るのは人間コーパスだけであり、AI 側の分布は分からない。
そこで、人間の分布そのものから見て外れ値と言える境界を出す方針にした。

採ったのは Tukey の外れ値境界である。第1四分位と第3四分位の差を四分位範囲と呼び、
その1.5倍を四分位の外側へ追加した点を境界とする。1.5という係数は Tukey (1977) の
「外れ値」の定義に使われている値であり、統計で広く使われている。
恣意的な余裕を独自に決めるより、名前の付いた定義に乗る方が根拠を示しやすいと判じた。
3.0倍の「極端な外れ値」という、より緩い定義もあるが、サンプル数の少ない使われ方では
境界が外側へ寄りすぎて較正の意味が薄れるため、採らなかった。

四分位を割る方法は hinge 法にした。サンプルを中央値で二つに割り、それぞれの中央値を
第1四分位と第3四分位とする。サンプル数が奇数の場合、中央値そのものはどちらの半分にも
含めない。線形補間を使うパーセンタイル法もあるが、hinge 法は仕組みが単純で、
テストの期待値を手計算で確かめやすい。

サンプルが4件未満の指標は較正しないことにした。3件以下だと、上半分か下半分の
どちらかが1件になり、四分位範囲が分布の広がりではなく個々の値でほぼ決まってしまう。
較正できない指標を0や仮の値で埋めて出すと、使う人が根拠のない閾値に気づけない。
そのため出力からその指標を外し、理由を標準エラーに出す形にした。

この一次実装には欠陥があった。below 方向の指標は、比率や千字あたりの出現数のように
値域が0以上に限られる。サンプルが一かたまりに寄っていると、Q1 - 1.5*IQR が0を下回る。
このツール自身の日本語文書（`docs/content/ja/*.md`、
`README.ja.md`、`CLAUDE.md`、
`TASKS.md`）をサンプルにして較正したところ、
`ja.demonstrative_per_1k` の境界が -4.96、
`ja.keishiki_meishi_per_1k` の境界が -4.98 になって出た。
密度と比率は負にならないため、
この境界を下回る実測値は原理的に存在せず、`check::evaluate` の below の判定
（value < threshold）を満たす文書は現れない。有効な TOML として読み戻せてしまうため、
この閾値を含むプロファイルへ `suikou check` を適用しても指摘ゼロが返り、指摘ゼロだけを
見る検証はこの欠陥を較正の成功と取り違えた。

0でクランプする案は採らなかった。境界を0にしても、密度と比率はもともと0以上であり、
value < 0 を満たす実測値はやはり存在しないため、閾値が発火しないことに変わりがない。
代わりに、below の境界が0以下まで下がった場合を較正の失敗として扱うことにした。
サンプル不足の場合と同様に、その指標は出力から外し、理由を標準エラーに出す。

above 方向には同じ手当てをしていない。below の下限（0）はどの指標にも共通するが、
above の上限は指標によって違う。比率は1が上限になる一方、千字あたりの出現数には
決まった上限がない。指標ごとの上限を較正のロジックに導入すると、その指標固有の
知識を混ぜ込むことになるため、below だけに限定した。

`guidance` と `direction` と `severity` は、同梱の oss プロファイルからそのまま
引き継ぐことにした。baseline を実行させるたびにこの文面を書き写すと、oss.toml を
修正したときに baseline の出力だけ古いまま取り残される経路ができる。
較正の対象は value だけに限定した。

`corpus/fetch.sh` で取れるコーパスはこの環境になく、ライセンスの都合でリポジトリに
含めていない。そのため、この決め方で実際に `corpus/baselines.toml` や
同梱のプロファイルと同じ桁の値が出るかどうかは確認していない。
`tests/golden/input/` の文書は数が少なく、指標ごとのサンプルが4件に対応できないため、
その代わりの確かめもできない。コーパスをこの環境に置ける環境で実際に実行させて
照合するまで、TASKS.md に未検証として残す。

較正できた below 方向の閾値が実際に働くことは確認してある。上の文書をサンプルにして
生き残った `ja.prose_ratio`（境界 0.69）を含むプロファイルを作り、箇条書きばかりの
文書へ `suikou check --profile` を適用すると発火し、地の文だけの文書では発火しないことを
実行結果で確認した。

## D-23 textlint プリセットの実装で分かれた判断

`packages/textlint-rule-preset-tech-maintainability`（T7）を書く過程で、
一つにまとめきれない判断が複数出た。以下に並べる。

**textlint が実際に表示するルールIDは、標準の設定では `maint/` にならない。**
指示は Rust側に合わせて `maint/list-lead-in` のような ID にすることを求めていた。
`@textlint/config-loader` の `loader.js` と `@textlint/utils` の
`normalizeTextlintRulePresetKey` を読んで確認すると、プリセットの接頭辞は
`.textlintrc` に書いた設定キーから、先頭の `preset-` を取り除いた文字列になる。
このパッケージを標準の書き方どおり `"preset-tech-maintainability": true` で
読み込むと、表示される ID は `tech-maintainability/list-lead-in` になる。
設定キーは `preset-` で始まらないとプリセットとして認識されず
（`isPresetRuleKey` がそう規定している）、認識された場合はその `preset-` が
必ず剥がされるため、標準の読み込み経路では `maint/` という接頭辞に
どうやっても到達しない。

個々のルールの名前（`list-lead-in` のような接頭辞なしの部分）は指示どおり
Rust側の名前に合わせてある。接頭辞だけは textlint 自身の命名規則に従うほかなく、
それを曲げるとしたら npm パッケージ名を `textlint-rule-preset-maint` のように
変更する必要があるが、パッケージの置き場所である
`packages/textlint-rule-preset-tech-maintainability` という名前と相違して
かえって分かりにくくなる。パッケージ名は置き場所に合わせたままとし、
実際に表示される ID が `tech-maintainability/` 接頭辞になることを README に
明記した。ゴールデンテストの照合では、`@textlint/kernel` を直に使い
`maint/` 接頭辞で手動登録しているため、この制約の影響を受けない
（`test/support/lint.js`）。

**AST を経由せず行ベースで判定する。** textlint は Markdown を段落や見出しなどのノードに分けて渡す。ソフトラップで複数行に
またがる段落は、textlint の中でひとつの Paragraph ノードに統合される。
一方 `markdown.rs`
の `Document::parse` は行ごとにブロックを作り、ソフトラップの続きも独立した行として扱う。
この相違は、`en_maintainability.md` の14〜15行目のような、ひとつの文が2行にまたがる
段落で表面化する。ノード単位で判定すると2行分の文字列がひとつにまとまり、Rust側が
決して結び付けない語同士が正規表現の一致範囲に入ってしまう。

選択肢は二つあった。
textlint の Paragraph ノードのテキストをそのまま判定にかける道と、
`Document::parse` と同じ行ベースの手順を JS に移植して、
textlint の側では文字列としての原文しか使わない方法である。
前者は「textlint らしい」実装ではあるが、
ノードの粒度が変わるたびに件数が一致しなくなる。

後者を採った。
`src/lib/blocks.js` が `markdown.rs` の`preprocess`・`strip_inline`・`Document::parse`・`list_blocks`・`block_before` を、
正規表現も含めてそのまま移植している。
各ルールは `context.getSource(node)` で原文を取り、
自前のブロック抽出にかけてから判定する。textlint が担うのは、
ファイルの読み込みと設定、報告の一本化であって、構造の解析ではない。

この選び方の代償は、報告する行・列が前処理後の文字列に基づく点である。原文の生の
文字列上での位置は、エスケープの解除やインライン記法の除去によって前処理後の位置と
相違することがある。`src/lib/position.js` は、一致した文字列を対象の行の中で順に
探して原文の文字インデックスへ近似的に結びつける。この近似は指摘を見失わせない
ためのものであり、正確さそのものを保証しない。`tests/golden/` との照合は
件数だけを見ており、位置の正確さは条件に含めていない。

**IPADIC は UniDic の体言4分類をひとつの品詞にまとめる。**
M1・M5の日本語判定は、行末や項目末尾のトークンが体言止めかどうかを見る。
suikou-core は UniDic を使い、品詞大分類が名詞・接尾辞・代名詞・形状詞のいずれかを
体言とみなす。textlint 界隈の標準である kuromojin は IPADIC を使い、この4分類を
持たない。

kuromojin 3.0.1 に実測させると、UniDic で接尾辞・代名詞・形状詞に立つ語は、IPADIC
では名詞の下位分類（品詞細分類1が代名詞・接尾・形容動詞語幹）として現れる。
「これ」は名詞/代名詞、「委員長」の「長」は名詞/接尾、「静か」は名詞/形容動詞語幹
だった。したがって IPADIC では、pos が名詞であることのひとつの条件に判別をまとめて
よい。`src/lib/morphology-ja.js` の `isTaigen` はこの実測に基づく。

連用形の判定も同様に実測で確認した。UniDic は「連用形-一般」のように活用形を細分
するが、IPADIC は単に「連用形」という値を返す（「使い」「し」で確認した）。
`cform.startsWith("連用形")` という Rust 側の判定はそのまま移植して問題ない。

**説明文の言語は文書の言語に合わせる。** Rust側は日本語で固定している。
suikou-core の `finding()` は、文書が英語であっても日本語の説明文を返す。
`en_maintainability.md` に対する `suikou check` の出力で確認した。

textlint プリセットの利用者には英語文書だけを書く人もいる。日本語しか読めない
説明文を出すと、その人たちにとって指摘が使えない。判定ロジックと正規表現は
Rust側と一致させる一方、説明文だけは検出した言語に合わせて日本語・英語を
出し分割することにした。`src/lib/messages.js` に両方を持たせてある。件数の
照合に説明文の内容は関わらないため、この差はゴールデンテストの完了条件に
影響しない。

**テストは textlint-tester ではなく node:test を直接使う。**
textlint-tester は Mocha の `describe`/`it` を前提に作られている。それらが
グローバルに無い環境では、`method.apply(this)` を呼ぶだけの代用に異常終了する。
この代用は `testValid`・`testInvalid` が返す Promise を待たないため、
`node --test` の実行環境にそのまま載せると、lint が終わる前にテストが
成功したことになってしまう箇所があった。

Mocha を依存に加えて textlint-tester を使う方法と、`@textlint/kernel` を
直に使う薄いレイヤーを書く案の二つを検討した。依存を増やさない方を選び、
`test/support/lint.js` に `TextlintKernel` を包む数行を置いた。プリセットの
全ルールを `maint/` 接頭辞付きで登録し、`async/await` で素直に結果を待つ。
`node --test` の非同期テストとそのまま噛み合う。

**`@textlint-ja/textlint-rule-preset-ai-writing` の `no-ai-colon-continuation`
と重なる指摘を、あえて抑えない。** そのルールは、コロンの手前が述語で終わる
文を kuromojin で検出しており、判別の作りが M1 の日本語版とよく似ている。

目的は違う。あちらは AI が書いた文体の特徴を検出し、こちらは項目の増減に
弱い箇条書きの構造を検出する。それでも同じ行が両方から指摘されることがある。
どちらか一方を優先させる仕組みは設けなかった。二つのプリセットを同時に
有効にする利用者は、両方を読んだうえで自分の文書に合う方を選べる立場に
あり、片方を黙らせると選ぶ材料を減らすことになる。README にこの重なりを
明記した。

## D-24 terms の抽出は品詞だけでなく構造で語を切る

日本語は、名詞が連続する範囲を複合語ひとつとしてまとめる。
UniDic は「素」や「性」のような接尾辞を pos1 が接尾辞になる形で切り出すため、
名詞だけを対象にすると「形態素解析」が「形態」と「解析」に割れ、
「メンテナンス性」が「メンテナンス」だけになった。この劣化は、自分の文書にこのツールを適用して見つけた。

接尾辞を名詞と同じ扱いに加えると、今度は「つ」のような助数詞まで
複合語の先頭に立ってしまう。UniDic の素性は、助数詞だけを判別できる細かさの情報を持たない。
そのため、助数詞の一覧を新たに作ることはしない。
代わりに、接尾辞は直前に名詞の連続が既にある場合に限って連続を伸ばす形にした。
数詞で連続が断たれたあとの接尾辞は、単独では語にならないためである。

UniDic は空白を語の区切りとしてだけ使い、トークンとしては残さない。
半角の語が隣接するトークンをそのままつなぐと、本文にない語ができる。
自分の文書にある「Linux kernel」（`design.md` の複数箇所にある）で、
「Linuxkernel」という本文にない語ができることを確認した。
半角英数字の語どうしが隣接するときは間に空白を1個入れる。
半角の語と日本語の語が隣接するとき（「API仕様」のような語）は空白を入れない。
日本語の文中でこの組み合わせが直に続く場合、元の文でも空白を置かない書き方が普通であるため。

一般語を除く一覧は `metrics/ja.rs` の `KEISHIKI_MEISHI` をそのまま使い、
別の一覧を新たに作ることはしない。
一般語が語彙集に混じっても、比喩の判定から除外されるだけで害は小さい。
分野の語を取りこぼす害の方が大きいと見て、こぼさない側へ倒した。

自分の文書に適用すると、1字の候補が上位を占めた。
395語のうち54語が1字で、上位20語は文(50)、形(49)、語(48)、指示(43)、値(36)と続き、
地(28)、数(27)を経て、`版`(22)、行(22)、`層`(20)まで並んだ。
「地」は「地の文」が「の」で分割された残骸で、残りは日本語の一般語として
どんな文章にも高頻度で出る、分野に紐付かない語である。

個別の語を挙げて除く一覧は作らない。挙げる基準そのものが直感になるためである。代わりに、
結果の文字数という構造だけで限定し、1字の候補を対象から外した。

日本語の術語抽出では1字の候補を除く扱いが広く採られている。
意味の運び手になるのはほとんどが複数字の複合語であり、
1字の語は最小の形態素で多義になりやすく、単独では分野を特定できないためである。
「文書」のような2字の1トークン語は、この限定し込みの対象にならない。
限定し込んだあとの自分の文書での上位語は、指示、規則、指標、人間、文書、日本語、指摘、閾値、
辞書、実装のように変わり、1字の語は残らなかった。

英語には形態素解析器も文分割もない。
頭文字だけの語、文の先頭ではない大文字始まりの語、識別子ひとつの形をした
インラインコードを手掛かりにする。表の行はこの対象から外した。
表の列の値は文の形をしておらず文頭の手掛かりが働かないうえ、
同じ値が行をまたいで繰り返され出る数の下限もすり抜けることを、
自分の文書にかけて確認した。

見出しの先頭に ID が立つ形にも同じ問題があった。
`decisions.md` 自身の見出し「D-04 The tokenizer hides behind a trait」で、
先頭の語だけを文頭とみなすと、次に来る The を文中の語と見誤った。
先頭から ID の形をした語が続く間は、まだ文頭の続きとみなす形に修正した。

見出しの先頭に ID の形をした語が並ぶ場合には、別の欠陥が残っている。
英語版の `decisions.md` の見出し「D-13 M2 and M6 count every occurrence」で、
`D-13` と `M2` の間に区切りの記号がないため、隣接する語がひとつの複合語
「D-13 M2」として統合される。`M2` という語だけの出る数がここで失われ、
出る数の下限を割ることがある。取りこぼしであって、本文にない語を
作る間違いではないため、害は小さいと見て今回は修正しない。
修正するには、隣接する ID の形をした語をどこまで一語として扱ってよいかの判断が必要である。
「AWS S3」のように隣接する頭字語を一語として扱って初めて意味をなす固有名詞もあり、
それを壊さずに直す規則をまだ見つけていない。

出る数の下限は既定で2とする。
1回しか出ない語は、分野の語と偶然の表現を判別する材料がない。
terms のもう一つの目的である語の一貫性の確認も、同じ語が繰り返し出て
初めて成り立つ。この値は実測ではなく、この二つの目的から導いた下限である。

この抽出の結果は、比喩のレイヤーが使うためのものである。
その比喩のレイヤーはまだ書いていないため、抽出のよしあしを最後に決めるのは、
そのレイヤーを書いたときのことになる。

## D-25 MCP は依存を足さず自分で JSON-RPC を書き、daemon は置かない

T9 では、二つの判断が必要だった。MCP サーバの実装のしかたと、常駐の形を作るかどうかである。

**MCP は `serde_json` だけで書いた。** 
候補は `rmcp` のような専用の crate を追加する案と、
`initialize`・`tools/list`・`tools/call` の3種類だけを手で書く案の二つだった。

実装する要求はこの3種類にとどまり、MCP の仕様のうち resources や prompts、
サーバ発の通知は使わない。専用の crate を追加すると、使わない機能ごとバージョンを固定する
ことになり、依存を `=` で固定して更新のたびに `verify_schema` を通すという
このリポジトリの重さに見合わない。`serde_json` は両クレートに既に入っているため、
増える依存は0である。stdio のトランスポートも「1行に1つの JSON-RPC メッセージ」
という単純な形で十分である。実装は `crates/suikou-cli/src/mcp.rs` に置いた。判定ロジック
自体は `check::analyze` と `brief::run` を呼ぶだけであり、CLI と MCP のあいだで
二重に書いていない。

**daemon は実装しない。** 常駐の形のもとの根拠は「辞書の読み込みを一度に抑える」
ことだったが、T2 で測定した値（release で 0.68〜0.70 ミリ秒）はこの根拠を支持しない。
TASKS.md は「プロセスの起動そのものの費用を別に測定してから決める」と定めていた
ため、
release ビルド（`--features lindera-unidic`）で `suikou check` を短い文書に
対して50回起動し、壁時計の時間を測定した。比較として `suikou --version` も50回測定した。
WSL2 上での値を挙げる。

| コマンド | 平均 | 最大 |
|---|---|---|
| `suikou --version` | 約1.5〜1.6ミリ秒 | 約1.9〜2.4ミリ秒 |
| `suikou check`（辞書あり、短い文書） | 約3.7〜3.9ミリ秒 | 約4.3〜4.7ミリ秒 |

`--version` は辞書を読まないため、
この値はバイナリの起動そのもの（約200MBの実行ファイルを読み込み、動的リンクし、
引数を解釈する費用）を表す。`check` との差は2ミリ秒台であり、
辞書の読み込み（0.7ミリ秒）と短い文書1件の形態素解析・指標計算をあわせた費用にあたる。
どちらの値も、hooks から Write や Edit のたびに起動する使い方において、
LLM の1ターンにかかる秒単位の時間と比べて無視できる大きさである。

常駐にすると、ソケットや名前つきパイプの管理、ファイルの変更をどう検知するか、
複数の呼び出し元が同時に動く場合の直列化といった複雑さが増える。
それに見合う速さの向上がないため、daemon を置かないことにした。
`suikou daemon`サブコマンドは残し、
実行すると測定した値とこの判断を説明して終える形にした。CLI から丸ごと除去するより、
なぜ無いかを使う人に直接示せる利点を優先した。

## D-26 文体から外れた和語を、参照コーパスとの頻度の比較で検出する

生成モデルは、英語から日本語にするとき漢語を和語へ置き換えることがある。
「確認する」が「確かめる」に、「必要である」が「要る」になる類である。
技術文書の文体としては軟らかすぎて、速く読めない。

何が文体に合うかは、語の対応表を作らずに決めた。
対応表にすると、分野ごとの表現の違いをすべて数え上げることになるためである。
代わりに、プロの日本語訳のコーパスでの頻度と比較する形にした。

対応表を作らなかった判断は、実測が裏づけている。
Kubernetes の文書だけで見ると「使う」は Sonnet の訳に320回、プロ訳に33回で、
「使う→使用」を規則にしたくなる。
ところが分野を Kubernetes、MDN、Vue に広げると、プロ訳にも「使う」が461回現れる。
同じく「次→以下」「仕組み→メカニズム」「既定→デフォルト」も棄却された。
MDN は「既定」を使うなど、分野ごとに方針が違う。

判定には二つの統計を使う。
Dunning (1993) の対数尤度比で有意かどうかを見て、
Hardie (2014) の Log Ratio で偏りの大きさを見る。
有意性だけでは足りない。普通の語を少し多く使っただけでも有意になるためである。

Log Ratio の下限は測定で決めた。
参照に使っていないプロの日本語訳12頁と、このリポジトリの日本語の文書とで分布を比べた。
4 ではプロの文書に9語、6 では1語の誤検出が出て、7 でゼロになる。
設計の方針では、人間の書いた文書に警告が出ることを偽陽性として扱う。
取りこぼしは許すが、プロの文書に出る誤検出は許さない側に寄せた。

参照コーパスの作り方にも二つの条件を置いた。
入門書を混ぜてはならない。Rust Book の訳には「確かめる」が36回あり、参照に入ってしまう。
文書の種類による差は文体による差より大きいという測定と整合する。
もう一つは、2分野以上に現れる語だけを参照に載せることである。
一つの分野だけに出る語は、その分野の表現であって参照にならない。

分野で定まった語のために `.suikou/register-allow.toml` を用意した。
参照コーパスは Web の文書で作ってあり、計算や統計の語が手薄である。
その偏りをプロジェクトの側で補う。辞書を同梱せず文書から作るという D-11 と同じ形である。

## D-27 漢語率の指示文は誤りだった

D7 の指示文は「漢語を和語動詞に開く」だった。この指示は実測に反している。

プロの日本語訳とこのリポジトリの文書とで、自立語の語種の構成を比べた。

| | 和 | 漢 | 外 | 混 |
|---|---|---|---|---|
| プロの日本語訳 | 0.384 | 0.329 | 0.280 | 0.007 |
| このリポジトリ | 0.470 | 0.463 | 0.050 | 0.017 |

プロが漢語率を下げているのは、和語に開いているからではない。
定着したカタカナ語を使っているからである。和語の比率はむしろプロの方が低い。
指示文を「定着したカタカナ語を使い、漢語の名詞を重ねない」に直した。

この間違いの影響は大きかった。
この指示に従って文書を書き直した結果、「検証」が「確かめ」に、「制約」が「縛り」に、
「抽出」が「取り出し」に置き換わり、文体が劣化した。
D-26 の規則は、この劣化を検出するために作ったものである。

指標を最小化することを目標にしてはならない。
D7 の severity は info であり、参考値である。
それをゼロにしようとしたことが、そもそもの間違いだった。
文書が満たすべき条件は error と warning が出ないことまでとし、
info は参考として読むにとどめる。

## D-28 文体の規則は英語には移らなかった

D-26 の方法を英語にも当てようとして、二つの実験を行った。どちらも成立しなかった。
英語の規則は実装しない。

一つめは、文書と参照コーパスの頻度を比べる形である。
Kubernetes、MDN、Vue の英語の原文652頁、51万語から頻度表を作り、日本語と同じ統計で測定した。
参照に使っていないプロの英語14頁に対する誤検出は、閾値を9まで上げても20語残る。
上位に並ぶのは両側とも分野の用語である。プロ側は portworx、cinder、ebs、
こちらの文書側は prose、corpus、metric だった。
3分野すべてに現れる語だけに絞っても、プロ側に operations のような話題の語が残る。

原因は語彙の構造にある。
日本語では「語種が和である」という条件が、分野の用語をほぼ機械的に除いていた。
分野の用語は漢語かカタカナ語であるためである。
英語の語彙にはその印が無い。ある話題の文書はその話題の語を一般のコーパスより遥かに多く使うため、
頻度だけでは話題の語と文体の語を分けられない。

二つめは、話題を完全に一致させる形である。プロの日本語訳を LLM に英語へ訳し戻させて、
元の英語の原文と比べた。36頁、各3万語である。

有意な差は1語も出なかった。臨界値 15.13 に対して、最大が your の 13.2、
次が will の 11.1 であり、どちらも原文の側が多い。
語の選び方が逆向きに偏っているわけでもない。
日本語で同じ設計を使ったときは「使う」が 320 対 33 で、
対数尤度比が 320 に達していた。

この結果は D-08 と同じ性質を持つ。
先行研究の効果量を仕事をまたいで持ち込んではならないのと同じく、
一つの言語で成立した方法を、言語をまたいでそのまま持ち込んではならない。

確かめたのは語の選び方だけである。
英語の指標として採用した MATTR、地の文比率、直喩の標識は別の性質を測定しており、そちらは残る。

再現の手順は `research/lexshift/` に置いてある。
`build_reference_en.py` が英語の頻度表を、
`translate_back.sh` が訳し戻しを作る。
同じ実験を繰り返さずに済むよう、失敗した側も残してある。

## D-29 カタカナ語が優勢な漢語は対応表で置き換える

D-26 では対応表を作らないと決めた。分野ごとに逆転する語があるためである。
その判断を、漢語とカタカナ語の組については改めた。
反例があっても、分野をまたいだ合計で優勢なら、その側に従う。

同義であることを機械的に決める方法は、いくつか試して落とした。
英語の原文を軸にして段落の共起で結び付ける形は、同義ではなく連語を拾う。
「永続ボリューム」や「ポート番号」のような組が出てくる。
持ち上がり度でも Dice 係数でも同じで、共起からは同義性が分からない。
置き換えの関係は共起ではなく入れ替わりであり、段落の単位では測れなかった。

そこで候補の列挙と採否の判断を分けた。候補は人が挙げ、採否は実測が決める。
D-26 と同じ構造である。97組の候補のうち53組を採った。

採否の条件は三つとする。カタカナ側が漢語側の2倍以上であること、
合計が20回以上あること、そして漢語側が60回以下であることである。

三つめの条件は多義語を避けるために置いた。
測ってみると「対象」「対応」「状態」「場合」はプロもよく使う。
だがそれは、カタカナ語と同じ意味で使っているとは限らない。
このリポジトリでも「対象」は扱う範囲の意味であって、オブジェクトではない。
プロがその漢語をほとんど使っていない組に限れば、置き換えとして信頼できる。

直前が名詞である場合は、複合語の一部とみなして見送る。
`英語版` や `第3版` の `版` を置き換えると間違いになる。

分野で別の意味に使う語は `.suikou/register-allow.toml` で外す。
このリポジトリでは「記録」「一覧」「比率」「経路」「分岐」「実体」を外した。
たとえば「比率」は漢語率や地の文比率の意味であって、レートではない。


## D-30 文書の構造をガードレールにして、書く前に型枠を出す

文章の単位の規則だけでは、構造の壊れた文書を救えない。
節の欠落、筋の通らない順序、一段落に主張を詰め込む書き方は、
一文ずつ読んでいる限り見つからない。

構造の規則は言語を問わずに当てることにする。
節の構成、順序、段落の単位は文書の論理の性質であって、語彙の体系の外にあるためである。
測定でもそれが裏づけられた。7文以上の段落はプロの英語で 0.27%、
プロの日本語で 0.59% と、言語をまたいで同じ桁に収まる。
文体の規則が英語に移らなかった D-28 とは、この点で結果が分かれた。

型と必須の節は自分で考えずに、既にある標準から取った。
RFC 7322 が必須の節と推奨する順序を規定している。
型ごとの節は Rust RFC テンプレート、Kubernetes Enhancement Proposal、
Michael Nygard の Architecture Decision Record、Diátaxis から取った。
段落の上限は Google developer documentation style guide の5〜6文に合わせて6文とする。
直感で立てた規則を導入しないという制約は、構造の規則でも同じである。

severity は欠落だけを error として、順序と段落と空の節は warning とする。
必須の節が無い文書は読み手の問いに答えられない。
一方で、順序と段落の長さは理解の筋であって、破ってはならない決まりではない。

節の照合は最上位の階層の見出しだけを見る。
先頭の第1階層の見出しは標題であって節ではないため外す。
下位の見出しまで見ると、節の中の小見出しが別の節に当たって順序の判定が狂う。
実際にこのリポジトリの英語の設計文書で、その誤検出が出た。

最初の節だけは、標題の直下に置いた地の文で代えられることにする。
RFC 7322 の abstract が標題と目次の間に見出し無しで入る前例であり、README も同じ形を取る。
`## これは何か` を強いると、かえって読みにくくなる。

### 書く前に構成を承認する

`suikou plot` がテンプレートを `.suikou/plans/` に出す。
節の見出しと、その節が答える問いと、そこで述べる主張の欄だけを持つ文書である。
主張を一行で書けない節は、まだ考えが足りていない。
それを本文を書く前に見つけられる。

プロットはバージョン管理しない。思考の側の文書であり、成果物ではないためである。
そのため CI からは見えず、突き合わせは手元とエージェントのループの中だけで働く。
このことは弱点ではない。構成の誤りは書く前に直すものであり、
配る前の関門で止める種類のものではない。

### 検出だけでなく誘導も出す

ここまでの規則は、違反を見つけて直させる負の方向だけを持っていた。
違反の一覧は避けるべき形を決めるが、書くべき形を決めない。

そのためテンプレートに、節ごとの問いと何を書くかを持たせた。
`suikou plot` と `suikou brief --doctype` がそれを書く前に出す。
指針の文面は `structure::writing_rules` に一か所だけ置いて、
指摘の文面と食い違わないようにした。

トークンの出る量は増やさない。テンプレートは `--doctype` を与えた場合だけ出す。

## D-31 手順の型の必須の節は、実測で二つ落ちた

型ごとの必須の節は、既にある枠から取って書いた。
Diátaxis の how-to guide を根拠に、前提と手順と確認の三つを必須とした。
そのうち二つが、プロの文書に当てた時点で落ちた。

Kubernetes の task 頁120件に `howto` を当てたところ、
`Steps` が120件すべてで、`Verify` が113件で「無い」と出た。
発火しない文書はひとつも無かった。

見出しを数えると理由が分かる。
task 頁の見出しは `{{%/* heading "prerequisites" */%}}` が111件、
`{{%/* heading "whatsnext" */%}}` が84件で、あとは頁ごとに固有の見出しである。
`Create a namespace` や `Edit a Secret` のように、その頁で行う操作の名前が並ぶ。

手順そのものは本文であって、節ではない。
Diátaxis が言うのは「how-to guide は手順の並びである」ということであって、
`Steps` という見出しを置けということではない。
見出しを `Steps` にそろえさせると、何の手順かが見出しから消える。
これは「見出しだけを追って全体の論理が分かるようにする」という指針に反する。

そのため `steps` と `verify` を必須から外した。
`prerequisites` だけを必須として残す。

### 測り直して、さらに二つの欠陥が出た

最初の計測では `prerequisites` が120件すべてで満たされていた。
これは正しく満たされていたのではなく、こちらの規則が緩すぎたためである。

導入で代えられる節を、位置で決めていた。
標題の直下に地の文があれば、最初の必須の節は何であっても満たされる。
そのことは、concept 頁120件に `howto` を当てても1件も発火しないことで分かった。
型が型として働いていない。

代えられるかどうかは節の性質である。位置ではない。
主題を述べる節にだけ `lead_ok` を与える形に直した。
前提や文脈は、導入では代えられない。
直したあと、concept 頁は120件中117件で発火する。型が区別できるようになった。

節の同義語を、文書の言語の側だけで照合していた。
Kubernetes の日本語訳は `{{%/* heading "prerequisites" */%}}` をそのまま使っており、
日本語の同義語だけで照合すると111件中110件で節が無いと出た。
両方の言語の同義語に対して照合する形に直した。
文書の言語と見出しの言語は一致するとは限らない。

### 直したあとの発火率

| コーパス | 頁 | 必須の節が欠けるもの |
|---|---|---|
| 英語の task 頁 | 120 | 9件（7.5%） |
| 日本語の task 頁 | 111 | 6件（5.4%） |
| 英語の concept 頁に `howto` を当てたもの | 120 | 117件（97.5%） |
| 日本語の concept 頁に `howto` を当てたもの | 120 | 116件（96.7%） |

言語をまたいで同じ幅に収まった。
型が違う文書に当てた場合はほぼ全件で発火し、正しい型に当てた場合はほとんど発火しない。
この差が、型が型として働いていることを示す。
発火した頁を読むと、`Before you begin` を本当に置いていない。
`Dependency on Docker explained` のように、`task` と宣言しながら解説の頁がある。
これはこちらの誤検出ではなく、Kubernetes が自分の雛形から外れた箇所である。

### 検出から外しても、誘導からは外さない

問いと書くことは型に残したままにする。
`suikou plot` と `suikou brief --doctype howto` は、
「どうやるのか」と「うまくいったとどう分かるのか」を尋ね続ける。

検出できるものと、書く前に尋ねるべきものは一致しない。
確認の手立てを書くことは良い手順の条件であるが、
`確認` という見出しがあるかどうかで判定できるものではない。
この二つを分けたことが、この決定でいちばん効いた点である。

### 外から測れたのは手順の型だけである

`design`、`decision`、`overview` の必須の節は、このリポジトリの文書でしか確かめていない。
その文書の見出しは、こちらが型に合わせて書いたものである。
自分で書いたものに自分の型を当てても、確かめたことにはならない。

外のコーパスで計測するには、型の宣言を持つ文書が要る。
Kubernetes は `content_type` を持つが、その値は `task` と `concept` と
`reference` と `tutorial` であり、こちらの型と重なるのは `task` だけである。
`concept` と `tutorial` に当たる型を置いていない。
置くとすれば Diátaxis の explanation と tutorial になるが、
当てる相手を用意せずに型だけを増やすことはしない。

## D-32 設計の型は、その型の出どころである Rust RFC で落ちた

`design` の必須の節は Rust RFC テンプレートから取ったと書いた。
その主張を検証するため、`rust-lang/rfcs` の `text/` 直下の200件に当てた。
番号の大きいものから採った。テンプレートが定着したあとの書き方を見るためである。
型の出どころそのものに当てるため、これが最も厳しい確認になる。

最初の結果は、`Design` が200件すべて、`Non-goals` が199件、`Scope` が198件であった。
原因は節ごとに違っていた。

### 名前の食い違い

`Design` の200件は、必須の置き方が誤っていたのではなく、名前を取り違えていた。

Rust RFC テンプレートはこの節を `Guide-level explanation` と
`Reference-level explanation` と呼ぶ。実測でも前者が157件、後者が148件ある。
同義語に `Explanation` を追加した。両方の名前がこれを含む。
`Implementation` と `Proposal` も追加した。設計の文書で広く使われる名前である。

### 型に無い節を必須にしていた

`Scope` と `Non-goals` は Rust RFC テンプレートに無い。
この二つは Kubernetes Enhancement Proposal の様式である。
様式の違うものを合わせて必須にしていたことになる。

必須から外した。問いと書くことは残す。
`plot` と `brief` は「どこまでやるのか」と「何をやらないのか」を問い続ける。
D-31 と同じ分け方である。

### 解析の欠陥が二つ出た

見出しの字下げに上限を置いていなかった。
4桁以上の字下げはコードであり、CommonMark は見出しとして認めない。
字下げしたコードの中の `#` が第1階層の見出しとして読まれ、
その文書の節が第1階層だけになって、本来の節がひとつも見つからなくなった。
字下げを3桁までとする形に修正した。

コードブロックの範囲を正規表現で取り除いていた。
長いコードブロックの中に短いものを入れる書き方があり、内側で閉じたことになっていた。
そこから先のコードが本文として読まれ、`# [dependencies]` が見出しになった。
開きと同じ記号で開き以上の長さの行だけを閉じとする行走査に修正した。
CommonMark がそう規定している。

この二つは textlint のプリセットにも移した。
実際の RFC 2件で、M 系の件数が両実装で一致することを確認した。

### 直したあとの発火率

200件中21件（10.5%）で必須の節が欠ける。
そのうち18件は、機能の提案ではない。
ロードマップ、プロジェクトグループの憲章、チーム編成、方針の RFC であり、
`text/` に置かれてはいるが機能の様式には従っていない。
残る3件は `Proposed additions` や `Solution` のような一度きりの節の名前である。

同義語の追加はここで打ち切る。
節の名前を増やし続ければ発火はゼロに近づくが、それはコーパスに合わせているだけである。
追加の根拠は、様式の文書に載っている名前に限る。

## D-33 決定の型は外の ADR でも成立した。節の順序もここで初めて測れた

`decision` の必須の節は Michael Nygard の Architecture Decision Record から取った。
28のリポジトリから190件の ADR を集めて当てた。
`research/structure/fetch_adrs.py` が `adr-tools` の作る最初の記録を起点として収集する。
インデックスと雛形は決定の記録ではないため対象から外す。

| 規則 | 190件中 |
|---|---|
| 必須の節が無い | 20件（10.5%） |
| 節の順序が違う | 0件 |
| 段落が長い | 6件（3.2%） |
| 末端の節に本文が無い | 2件（1.1%） |

`howto` と `design` が成立しなかったのに対して、この型は成立した。
違いは、ひとつの様式をそのまま取ったか、複数の様式を合わせたかにある。
`design` は Rust RFC と KEP を合わせていた。`howto` は Diátaxis の記述を節の名前と読み違えた。
`decision` は ADR という様式をそのまま取っている。

### 節の順序を初めて測れた

節の順序を判定するには、型が規定する節が2つ以上見つかる必要がある。
Kubernetes の task 頁では、その条件を満たすのが120件中7件しかなく、測定にならなかった。
ADR では190件中189件が条件を満たす。そのうえで発火がゼロである。

文脈、決定、帰結という順序は、実務と一致している。
この順序を推奨として置いてよい根拠が、ここで得られた。

### 残る20件の内訳

11件は MADR の様式である。
`Context and Problem Statement` と `Decision Outcome` を使い、
帰結を `Decision Outcome` の下の階層に置く。
節の照合を最上位の階層に限っているため、下の階層にある帰結は見つからない。

この制限を外すことはしない。
下の階層まで見ると、節の中の小見出しが別の節に当たって順序の判定が狂う。
その誤りは D-31 で実際に起きている。
MADR を扱うなら、階層を下げて探すのではなく、様式ごとに型を分けることになる。

残る9件のうち、`Status` と `Context` しか持たないものがある。
決定と帰結のどちらも書いていない決定の記録であり、これは本物の欠落である。
`Decision` の代わりに `Proposal` と書くものもある。

ここで同義語を足すのはやめる。D-32 と同じ線を引く。

## D-34 natural-japanese の規則を測り、どれも採らなかった

`coji/natural-japanese`（MIT）は、仕事の日本語を読みやすく書くためのスキルである。
28 種類の検出器と、禁止語のカタログと、翻訳調のパターン集を持つ。
そこから規則を取り込めるかどうかを、このリポジトリの基準で確かめた。

規則を追加する条件は、実測した値で人間と AI の幅が重ならないか、
明文のスタイルガイドの規約を出典とともに示すかのいずれかである。
候補は人が挙げてよいが、採否は計測した値が決める。D-26 と同じ手順である。

### 測り方

`corpus/cache/k8s/` は、同じ文書の人間訳と AI 訳を対で持つ。
同じ原文に対する訳を比べるため、分野や題材の違いが差に紛れ込まない。
参照コーパス 798 文書も合わせて見た。手順は `research/translationese/` にある。

### 結果

| 候補 | 人間訳 | AI訳 | 参照 | 判定 |
|---|---|---|---|---|
| 「することができる」 | 2.43 | 0.85 | — | 向きが逆 |
| 翻訳調パターン10個 | ほぼ0 | ほぼ0 | — | 技術文書に出現しない |
| 段落頭の接続詞 | 1.6% | 1.2% | 1.6% | 分かれない |
| 文末の同形3連 | 11.8% | 10.5% | 6.0% | 分かれない |
| 二重否定 | 0.16 | 0.11 | 0.16 | 分かれない |
| 「の」の3連続 | 3.67 | 3.03 | 2.84 | 人間の方が多い |
| 禁止語カタログ48語 | 最大1回 | 最大5回 | — | G² の水準に届かない |

数値は1万文字あたりの出現数である。段落の割合だけ百分率で示す。

どれも採らない。`corpus/baselines.toml` の `[rejected]` に理由とともに記録した。

### 分かれなかった理由

禁止語のカタログは随筆とビジネス文書に向けて作られている。
「いかがでしたか」や「見ていきましょう」は技術文書には現れない。
48 語のうち、このコーパスに出るのは19語だけであった。
文書の種類が違えば、AI の手癖も違う。これは D-28 と同じ方向の結果である。

翻訳調のパターンについては、比較の相手の選び方に注意が必要である。
このコーパスの人間側は英語文書のプロの翻訳である。
翻訳調が出るのは当然であり、「翻訳調かどうか」をここで判定することはできない。
計測できたのは「AI 訳が人間訳より翻訳調か」であって、その答えは否である。

### 取り込んだもの

規則は取り込まなかったが、向こうの証拠表は取り込む価値がある。
`corpus/reports/research/prose-rhythm-evidence-matrix.md` は、
文長の分散、バースト性、自己相関、TTR、perplexity について、
先行研究と自前の実測を突き合わせて「反証的」と判定している。

このリポジトリが `[rejected]` に置いた指標と、独立に同じ結論へ達している。
文長の変動係数について、向こうは現行閾値で人間の誤検出率 32.4% と計測している。
自己相関については、仮説と逆向きの結果を得て削除の候補としている。

別の作り手が別のコーパスで同じ結論に達したことは、この判断を強める。
`[rejected]` の根拠として、この出典を残す。

### 両方を同じ文書に当てて比べた

規則の一覧だけでは、実際に何を拾うかが分からない。
AI が書きそうな日本語の設計文書を用意して、両方を当てた。

| | suikou | natural-japanese |
|---|---|---|
| 指摘 | 13件（5規則）と文書指標4件 | 6件（5カテゴリ） |
| 規則の重なり | ゼロ | ゼロ |

拾うものが完全に分かれた。
suikou が出したのは、項目数の明記、見出しの連番、項目のそろい、時点に依存する語、
カタカナ語の優先である。いずれも後から直すときに壊れる箇所と、古びる箇所である。
natural-japanese が出したのは、常套句、無生物主語、翻訳調、リズムである。
文章の自然さに関わる箇所である。

同じ行を両方が指した箇所もあるが、理由は違った。
冒頭の一文に対して、suikou は時点に依存する語を指し、
natural-japanese は常套句を指した。同じ行でも、見ているものが違う。

プロの文書（Kubernetes の日本語訳の手順頁）では、suikou が2件、
natural-japanese が1件であった。どちらも静かである。

### 対になったコーパスでの量

同じ原文の人間訳12本と AI 訳12本に当てた。

| | 人間訳 | AI訳 | 比 |
|---|---|---|---|
| suikou | 43件 | 62件 | 1.44 |
| natural-japanese | 87件 | 82件 | 0.94 |

natural-japanese の内訳を見ると、量の出どころが分かる。
`translationese` が人間13件に対し AI 2件、`translationese_morph` が19件に対し2件で、
どちらも人間訳の側に強く出ている。この向きは D-34 の計測と一致する。
人間側が英語文書のプロの翻訳であるため、翻訳調が出るのは当然である。

### 唯一、向きの合った規則

`repeated_sentence_lead`（文頭2形態素が同一文書で6回以上）だけが、
期待どおり AI 訳の側に多く出た。suikou には無い規則である。
そこで、ほかの候補と同じ手順で計測した。

| 群 | 文書 | 発火した文書 | 100文あたり |
|---|---|---|---|
| 人間訳 | 39 | 35% | 14.2 |
| AI訳 | 78 | 50% | 16.4 |
| 参照コーパス | 60 | 26% | 10.6 |

向きは合っているが、幅が重なる。AI と人間の比は 1.15 にとどまる。
参照コーパスでも26%の文書が発火する。
規則を追加する条件は「幅が重ならないこと」であり、これは満たさない。

出力の形も合わない。この規則は該当する文をすべて指すため、
71文の文書ひとつで17件を出した。ひとつの規則につき示す位置を絞るという方針に反する。

採らない。ただし、候補のうち唯一向きが合ったものとして数値を残す。

## D-35 時点への依存は、時制ではなく係留の有無で判定する

生成する側には、自分の置かれた文脈に過剰に適応するという性質がある。
セッションの中で文書を書くと、その瞬間を文書にとって永続する時点だと混同する。
`現在レイテンシが悪化しており` と書いた瞬間、その文は書いた日にしか正しくない。

M6 の理由づけを「文書が風化する」から、この機構の側へ移す。
そのほうが、なぜこの規則だけが簡潔な指示では守られず、
禁じる語をすべて列挙する必要があるのか（`brief` の実測）を説明できる。

### 時制は予測子にならない

対処として「時制的な表現を取り除いて無時間的に保つ」という案があった。採らない。

| 文 | 時制 | 古びるか |
|---|---|---|
| `2026年3月に2.5倍になった` | 過去 | 風化しない |
| `現在は640ミリ秒である` | 非過去 | 翌日に風化する |

分けているのは時制ではなく、絶対の係留があるかどうかである。

時制を対象にすると、成立している型を壊す。
決定の記録の文脈の節は過去形で書くものであり、
その型が公開されている ADR 190件で成立することは D-33 で計測した。
手順の順序（「〜したあとに」）も時制の形を取るが、これは読む時点に依存しない。

### 「意図した場合は除く」を運用可能にする

例外を判断に委ねると機械では判定できない。係留の有無という形に変換する。

同じ文に西暦、バージョン番号、番号の付いた文書があれば、この規則は発火しない。
`lindera 6.0.0 で現在の素性の順序を確認した` は過去の事実であり、風化しない。

係留は文ごとに見る。段落の別の文の年号を借りてはならない。
小数をバージョン番号と混同しないよう、`v` の付いた形か3つ組だけを係留とする。
`2.5倍` を係留と読むと、その文の指摘がすべて消える。実装の途中で実際に起きた。

### 語の一覧では拾えない形

数を伴う相対の期間は、語を並べても網羅できない。
`直近3ヶ月` `過去2年` `先週` を型として見る。

この穴は実際の文書で確認した。
AI が書いた設計文書に当てたところ、M6 は `現在` `現時点` `今後` `既存の` を検出したが、
`直近3ヶ月でリクエスト数が約2.5倍に増加した` を見逃していた。

語の追加は、Google の timeless documentation が挙げる `recently` と `soon` と `new` の
日本語側にあたる。同じ条項の範囲であり、思いつきで立てた仮説ではない。

### 計測

| コーパス | 前 | 後 |
|---|---|---|
| task 頁（日本語）60本 | 119件 / 36文書 | 123件 / 36文書 |
| 参照コーパス60本 | 179件 / 39文書 | 185件 / 39文書 |
| AI 訳39本 | 85件 / 26文書 | 92件 / 27文書 |

増えた分は小さい。参照コーパスは既に無時間的に書かれているためである。
係留の見送りが働いた例は200文書で1件あった。
`既存のHyper-V分離サポートは、v1.10の試験的な機能であり` がそれにあたる。
この文は `v1.10` の時点の事実を述べており、風化しない。

このリポジトリの文書はすべて、変更の前後どちらでも通る。

### 採らなかった範囲

過去形そのもの、継続の描写（「〜している」）、順序の表現は対象にしない。
手順は順序を必要とし、決定の記録は履歴を必要とする。
これらを消すと、読み手が得る情報が減るだけである。
