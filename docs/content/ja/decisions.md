この文書は、判断が分かれた箇所とその理由を、決めるたびに追記していく記録である。
後から読む人が、同じ検討を繰り返さなくて済むようにするために残している。

## D-01 文書全体で測る指標は textlint に組み込まない

textlint は、指摘をノードの位置に結び付けて出力する仕組みである。
文書全体でしか測れない指標には、結び付けるべき位置がない。
しかも、そうした指標の多くは、何かが不足していることを示す指摘である。
形式名詞が少ない、指示詞が少ない、直喩の標識が少ない、といった指摘がそれに当たる。
不足しているものは、文書のどこにも位置を持たない。

最初は、Document ノードに対して報告する textlint の規則として実装する案を採った。
この判断は誤りだった。
textlint の中に組み込むと、解析の基盤が JavaScript に限られる。
その場合、語種を返す形態素解析器が使えないので、漢語率を実装できなくなる。
実装の都合で、検証を通過した指標を捨てることになり、順序が逆になる。

そこで、フロントエンドのツールが textlint を呼び出し、その結果を自前の文書解析の結果とまとめる方式を採る。
MCP は、フロントエンドのツールそのものが提供すればよい。
この方式なら、まとめたレポートを一度に返せるので、エージェントにとってはむしろ都合がよい。

## D-02 実装は Rust を中心にし、Python は較正と探索に限る

検証を通過した指標は、すべて純粋な Rust で実装できる。
lindera-unidic が UniDic の素性をすべて返すので、語種と活用形を取得できるからである。

Python が必要だったのは、分詞節、名詞化、修飾の積み重ね、係り受けの距離である。
これらはどれも、測定の結果として除外した指標である。
深い構文解析を必要とする指標ほど実験の設計に左右されやすく、先行研究で報告された差が再現しなかった。

そこで、実装をレイヤーに分ける。
採用が決まった指標は Rust で実装し、探索と較正は Python で行う。
Python で有効だと分かった指標だけを、Rust に移す。

Claude Code の hooks から Write と Edit のたびに実行する使い方では、
起動にかかる時間が無視できなくなる。
spaCy は読み込みに2秒から5秒かかるので、Python を本番の処理経路に入れることはできない。

## D-03 Markdown のパーサを使わず、行単位で処理する

`research/` の参照実装は行単位で処理している。
ゴールデンテストの値を一致させるため、Rust の実装も同じ方式を採る。
依存が減るので、バージョンの違いによる不具合も減る。

## D-04 形態素解析器をトレイトの背後に隔離する

lindera の API と UniDic の素性の並び順は、バージョンによって変わる。
バージョンに依存するコードを一つの構造体に閉じ込めれば、影響を受けうる範囲を数十行に抑えられる。

さらに、既定の feature に lindera を含めないことで、
辞書をダウンロードしなくても規則と指標を確認できる。そのため、変更の確認が速くなる。

## D-05 起動時に、素性の並び順を自分で検証する

バージョンを固定するだけでは、更新したときに誰も気付かないまま動作がおかしくなるという問題が残る。
素性の並び順が合わなくなると、語種と活用形が、本来とは別の位置から読み取られる。
値は返ってくるが、その中身は誤っている。

漢語率と連用中止はこの二つの判定に依存しているので、
誤った値のまま動き続けると、指摘の内容そのものが誤りになる。
内容の分かっている語を解析させて確かめ、結果が合わなければ異常終了するほうが望ましい。

## D-06 文体によって閾値を分けない

常体と敬体で指標が変わるかどうかを、二つのモデルの出力で比べた。
差の方向はモデルの間で一致せず、文体による一定の効果は見られなかった。
文体による差は、モデルの違いによる差の中に埋もれる。

文体の判定は残すが、用途は、体言止めのような文体に依存する規則を適用するかどうかの判断に限る。
閾値の表を文体ごとに二重に持つ必要はない。

## D-07 形式名詞と漢語率の severity を info にする

この二つの指標は、文書の種類による値の変動が大きい。
手順書では形式名詞が閾値に近づき、概念の解説では漢語率が人間ネイティブの値に近づく。
漢語率は、話題による変動も大きい。

日本語の人間のコーパスは解説書に偏っており、手順書の型の文書が足りない。
文書の種類ごとの値が一致するまでは info とし、一致した時点で warning に上げる。

## D-08 先行研究で報告された差を、そのまま持ち込まない

英語の分詞節については、人間の5.3倍という報告に基づいて、閾値を9から10と見積もった。
実際に測定すると人間の範囲と重なり、使えなかった。名詞化についても同じ結果だった。

原因は、実験の設計の違いにあると考えている。
報告の元になった研究では、人間が書いた文章を与えて同じ文体で続きを書かせたが、この実験では文書を作成させている。

先行研究は仮説の出発点にはなる。しかし、そこで得られた差を、課題の異なる場面に持ち込んではならない。

## D-09 保ちやすさのレイヤーは、人間の平均に合わせない

箇条書きの導入文を正しく書いていたのは、AWS S3 ユーザーガイドだけだった。
Linux kernel では、不完全な導入文のほうが多い。
人間の平均に合わせると、このレイヤーは存在する意味を失う。

このレイヤーの目的は、AI らしさを取り除くことではない。
人間が書いた文書の大半よりも良い文書にすることが、このレイヤーの目的である。

## D-10 指示で予防できるレイヤーと、lint でしか取り除けないレイヤーを分ける

書式を抑える指示を与えた条件と、与えない条件を比べた。
書式は完全に消えたが、語彙と文の構成は変わらなかった。

保ちやすさについての指示でも、同じ実験を行った。
構成の規則は短い指示で完全に守られ、
時点に依存する語は詳しい指示を与えて初めてゼロになった。
項目の数、見出しの連番、手で付けた番号は、指示がなくても違反が起きない。

したがって、`brief` には、指示によって守らせられる制約だけを含める。
効果のない制約を含めるとトークンが無駄になり、モデルが必要以上に修正するおそれもある。

副次的な効果として、保ちやすさについての指示を与えただけで、文書指標も改善した。
導入文を書かせたことで地の文が増え、地の文比率と箇条書き比率が人間の範囲に近づいた。

## D-11 語の辞書を同梱せず、文書から作る

比喩のレイヤーで最も難しいのは、生きた比喩と死んだ比喩の区別である。
cache や handshake は分野で定着した語であり、比喩ではない。

指摘されて広く知られた語は、出現数が減る。
2024年の初めに指摘された一群の語は、指摘の直後から減った。同梱した辞書は、時間とともに役に立たなくなる。

利用者自身の文書から作る辞書は、時間がたっても役に立たなくなることがない。
プロジェクトごとに使う語が異なるという理由に加えて、
この点が、辞書が古くなる問題への対策になる。

## D-12 漢語率のテストでは、期待値の側を直した

`kango_ratio_counts_only_content_words` が失敗していた。
入力「設定を変更すること」に対して、実装は 0.5 を返し、テストは 0.5 を超える値を期待していた。

`TASKS.md` は、テストが失敗したら実装を直すと定めている。この件は、その例外に当たる。
テストの注記では、自立語を「設定」「変更」「こと」の3語と数えていた。
しかし `FakeMorphology` の仕様では「する」が動詞として扱われるので、自立語は4語になる。
指標の定義では、割る数を、自立語のうち語種が 和 漢 外 混 のどれかであるものとしている。
したがって、動詞の「する」も割る数に入り、実装が返す 2/4 が定義どおりの値になる。
実装をテストに合わせると、定義に反することになる。

このテストの目的は、助詞を割る数から除いていることの確認にある。
期待値を 0.5 との完全一致に変えても、この目的は保たれる。
助詞「を」を割る数に入れた場合の値は 0.4 なので、二つの場合は区別できる。

実装を直してよいのは、実装が定義から外れている場合に限る。
期待値が定義から外れている場合は、期待値のほうを直す。

## D-13 M2 と M6 は、出現するたびに数える

参照実装は1行の中の出現回数を数えるが、
Rust の実装はブロックごとに最大1件しか指摘していなかった。
`tests/golden/input/en_maintainability.md` の
「The validator currently reports ... The latest release」は1行に2つの語を含んでおり、
参照実装が 2 を返すのに対して、Rust は 1 を返していた。

出現するたびに数える方式を採った。根拠は、このプロジェクト自身の制約にある。
1行に2件あるのに1件しか報告しないと、
指摘された箇所だけを直した文書を `check --quiet` で検査したときに、また異常終了する。
レイヤーごとに lint と修正を往復させないという設計が、そこで成り立たなくなる。

`Position` に使われていない `column` があったことは、
もともと出現ごとに位置を持たせる予定だったことを示している。
出現ごとに列番号を持たせたので、同じ行にある複数の違反を区別できる。

M7 は行末だけを判定するので1行につき最大1件であり、この変更の影響を受けない。

## D-14 語数と文数は、相対誤差で照合する

照合の方針では、比率に絶対誤差 0.02、密度に 0.5、M 系に完全な一致を定めていた。
語数は、このどれにも当てはまらない。

`en_prose.md` の語数は、参照実装が 445、Rust が 444 だった。
原因は `trade-off` の扱いにある。
spaCy はこの語を三つのトークンに分けて記号を除くので2語と数えるが、空白で区切る方式では1語と数える。
この文書に含まれるハイフンでつないだ語はちょうど一つであり、差の大きさと一致する。

この差は、トークナイザの定義の違いによるもので、実装の誤りではない。
完全な一致を求めると、定義の異なるものに同じ数を返すよう求めることになる。
相対誤差 1% で照合し、決まったずれだけを検出する。

## D-15 形式名詞の対象範囲が、参照実装と定義とで食い違っている

指標の定義では、語彙の指標を地の文とリスト項目の本文で測るとしており、
形式名詞をその一つに挙げている。Rust の実装は、この定義に従っている。

参照実装の `research/jametrics.py` は、指示詞については、
地の文だけの値と、地の文とリスト項目の本文を合わせた値の両方を出力する。
一方、形式名詞については、地の文だけの値しか出力しない。

`tests/golden/input/ja_maintainability.md` で測ると、
地の文だけでは 14.98、リスト項目の本文を含めると 15.77 になる。
差は 0.79 で、密度の許容範囲である 0.5 を超える。

この食い違いを理由に、実装を変えてはならない。定義には理由が書いてある。
出力の大半が箇条書きになるモデルがあり、
地の文だけで測ると本文の8割以上を捨てることになる。

食い違っているのは、閾値の側である。
人間の範囲 11.095 から 11.163 と、D5 の閾値 8.5 は、地の文だけの定義で測った値である。
リスト項目を含めると値が上がるので、D5 の指摘は較正したときより出にくくなる。
D5 の severity を info にした判断（D-07）は、この点から見ても正しかった。

較正をやり直すまで、この食い違いは未解決のまま残る。
やり直すには、`research/jametrics.py` に地の文とリスト項目を合わせた値の出力を追加し、
コーパスに対して測定し直す必要がある。

## D-16 辞書を埋め込んだ単一のバイナリで配布する

配布の形式を決めるために、辞書を埋め込んだ場合の大きさを測った。

| 内容 | 大きさ |
|---|---|
| 辞書を同梱したバイナリ | 191 MB |
| 同じものを xz で圧縮 | 26 MB |
| 辞書を含まないバイナリ | 1.1 MB |

`strip` を使っても小さくならない。中身がシンボルではなく、辞書のデータだからである。

辞書をバイナリの外に置き、初回の実行時にダウンロードする方式も採れる。
lindera 6.0.0 には `load_dictionary_from_path` があり、
辞書を複製せずに読み込める。それでも、埋め込む方式を採った。

理由は、このツールの使われ方にある。
hooks から Write と Edit のたびに実行するツールでは、
失敗する経路が少ないほど信頼できる。辞書を外に置くと、辞書の欠落、破損、
バージョンの食い違いという失敗の経路が増える。バージョンの食い違いは自己診断で検出できるが、
検出しても、利用者はツールを使えない。ダウンロードした後にネットワークを必要としない方式のほうが、
この使われ方に合っている。

配布の単位は、OS ごとの書庫とする。
すべての OS 向けのバイナリを一つにまとめると、圧縮後で 78 MB になり、
利用者は使わない OS の分を必ず削除することになる。

対象は、x86_64 の Linux (musl)、
Apple Silicon の macOS、x86_64 の Windows に限った。
Linux 向けに musl を使うのは、glibc のバージョンに依存させないためである。
古いディストリビューションやコンテナで動かないツールは、hooks から呼び出す使い方では大きな支障になる。
Intel の Mac と ARM の Linux は、対象から除いた。これらが必要な利用者は、ソースからビルドする。

## D-17 辞書の feature は、既定では有効にしない

`suikou-cli` に `lindera-unidic` を追加したが、既定では無効のままにした。
既定で有効にすると `cargo test --all` が辞書を取り込むので、
辞書なしで本体を確認できるという前提（D-04）が成り立たなくなる。

その代わりに、二つの対策を取った。
配布用のビルドは feature を明示して作り、起動して辞書があることを確かめてからパッケージ化する。
辞書を含まないバージョンで日本語の解析を求められた場合は、`morphology::load` がその時点で異常終了する。

誰にも気付かれないまま空の解析結果を返してはならない。
形態素解析が空の結果を返すと、漢語率も連用中止も形式名詞も 0 になる。
0 は閾値より下にあるので、指摘が出る指標と出ない指標が混在する。
その結果、「指摘なし」という誤った結論に至る経路が生じる。

どちらのバージョンなのかは、`suikou --version` で見分けられるようにした。
利用者が手元のバイナリを特定できないと、日本語が解析されない原因をたどれないからである。

## D-18 配布物の確認は、辞書の実体に対して行う

配布用のワークフローを `act` で実行したときに、この問題が見つかった。
パッケージ化したバイナリは 1.2 MB しかないのに、`--version` は「UniDic 同梱」と表示していた。
辞書は 191 MB あるので、この二つは両立しない。

原因は、リンカが使われないコードを取り除くことにあった。
サブコマンドがすべて `todo!()` だったので、`morphology::load` に到達する経路がなく、
埋め込んだ辞書のデータもまとめて削除されていた。
到達する経路を作ってビルドし直すと、バイナリは 191.5 MB になり、実際に解析結果を返した。

スモークテストの側にも問題があった。
`--version` の表示は `#[cfg]` によるビルド時の分岐であり、
feature が有効かどうかを示すだけで、辞書が実際に含まれているかどうかは示さない。
そのため、辞書を持たないバイナリでも、この確認を通過してしまう。

そこで、`selftest` サブコマンドを追加し、実際に辞書を読み込んで解析させる方式に変えた。
配布物の確認は、ビルドの設定ではなく、できあがった配布物の動作に対して行う。
自己診断で、素性の並び順を実際の辞書を使って確かめているのと同じ考え方である。

副次的な効果として、`morphology::load` に到達する経路ができたので、
`crates/suikou-cli/src/morphology.rs` に入れていた警告の抑制を取り除けた。
利用者にとっても、手元のバイナリが想定どおりのものかを確かめる手段になる。

## D-19 指摘の行番号は、前処理の前の行に合わせる

自分たちの文書に `suikou check` を適用したときに、この問題が見つかった。
指摘された行番号が、実際の行より4行前を指していた。
この差は、除去したフロントマターの行数と完全に一致する。

前処理は、フロントマターとコードブロックを、中身ごと削除していた。
そのため後に続く行が前に詰まり、行番号が実際のファイルと合わなくなっていた。

除去した範囲を、同じ数の改行で置き換える方式に変えた。
空の行は数えないので、空でない行の数と箇条書き比率は変わらない。

lint の指摘は、利用者が開いているファイルの行を指していなければ使えない。
値が正しくても、位置がずれていれば、その指摘は役に立たない。

## D-20 文書を Hugo のサイトにし、既定の言語を英語にする

文書を `docs/` の直下に置く構成から、`docs/content/{en,ja}/` に置く構成に移した。
既定の言語は英語とする。

テーマは外部から取り込まず、自前で用意した最小限のレイアウトを使う。
依存を増やさないためであり、バージョンを固定するという本体の方針を、文書の側でも守るためでもある。

文書の正本を一か所に定めたので、サイトとリポジトリで同じ内容を二重に持たずに済む。

## D-21 brief の詳しさは、プロファイルではなくフラグで指定する

設計の文書には、brief の詳しさをプロファイルの設定として持たせる案がある。
今回の実装ではこの案を採らず、`--detail concise|balanced|detailed` という
フラグだけで制御する方式にした。

理由は次のとおりである。Profile は、指標の閾値を保持するための構造体である。
そこに brief 専用の設定を追加すると、この構造体が二つの役割を持つことになる。
較正の結果として書き戻す値と、出力の形式を選ぶだけの値を同じ構造体に混ぜると、
`suikou baseline` が書き戻すべき範囲がはっきりしなくなる。閾値だけを保持するという
Profile の役割を守るほうを選んだ。

フラグの水準も、最初のメモから変えた。`TASKS.md` の最初の案では、
concise と detailed の二つだけを挙げていた。しかし実装を進める中で、その間に balanced を
設けるほうが自然だと分かった。構成の規則を1文で書き、時点に依存する語だけは
すべて列挙するという brief の制約は、balanced という中間の水準にそのまま当てはまる。
concise はそれよりさらに短くし、detailed は規則ごとに理由まで添えた。

プロファイルに持たせる案は、未決定の事項の一覧に残しておく。
用途ごとに既定の detail を変えたいという要望が実際に出たときに、
プロファイルに移すかどうかを決める。

## D-22 baseline の閾値は、Tukey の外れ値の境界で決める

`suikou baseline` を実装するにあたって、閾値の決め方を選ぶ必要があった。
`docs/content/ja/design.md` では、
閾値を、人間の範囲の上端と AI の範囲の下端の間に置くと定めている。
しかし、baseline が扱うのは人間のコーパスだけであり、AI 側の分布は分からない。
そこで、人間の分布そのものから見て外れ値と言える境界を、閾値として出す方針にした。

採用したのは、Tukey の外れ値の境界である。第1四分位と第3四分位の差を四分位範囲と呼び、
その1.5倍を四分位の外側に加えた点を境界とする。1.5という係数は、Tukey (1977) が
「外れ値」の定義に使った値であり、統計の分野で広く使われている。
独自に余裕の幅を決めるより、名前の付いた定義に従うほうが、根拠を示しやすいと判断した。
3.0倍を使う「極端な外れ値」という、より緩い定義もある。しかし、サンプル数が少ない使い方では
境界が外側に寄りすぎて較正の意味が薄れるので、採用しなかった。

四分位の求め方には、hinge 法を使った。サンプルを中央値で二つに分け、それぞれの中央値を
第1四分位と第3四分位とする。サンプル数が奇数の場合、中央値そのものはどちらの半分にも
含めない。線形補間を使うパーセンタイル法もあるが、hinge 法は仕組みが単純で、
テストの期待値を手計算で確かめやすい。

サンプルが4件に満たない指標は、較正しないことにした。3件以下だと、上半分か下半分の
どちらかが1件になり、四分位範囲が分布の広がりではなく、個々の値によってほぼ決まってしまう。
較正できない指標を0や仮の値で埋めて出力すると、利用者は根拠のない閾値に気付けない。
そのため、その指標を出力から除き、理由を標準エラー出力に書く方式にした。

この最初の実装には欠陥があった。below 方向の指標は、比率や千字あたりの出現数のように、
値が0以上に限られる。サンプルが一か所に集中していると、Q1 - 1.5*IQR が0を下回る。
このツール自身の日本語の文書（`docs/content/ja/*.md`、
`README.ja.md`、`CLAUDE.md`、
`TASKS.md`）をサンプルにして較正したところ、
`ja.demonstrative_per_1k` の境界が -4.96、
`ja.keishiki_meishi_per_1k` の境界が -4.98 で出力された。
密度と比率は負の値にならないので、
この境界を下回る実測値は原理的に存在せず、`check::evaluate` の below 方向の判定
（value < threshold）を満たす文書は現れない。しかも出力は有効な TOML として読み込めてしまう。
そのため、この閾値を含むプロファイルで `suikou check` を実行しても指摘はゼロになり、指摘がゼロかどうかだけを
見る検証では、この欠陥を較正の成功と取り違えた。

境界を0で切り詰める案は採らなかった。境界を0にしても、密度と比率はもともと0以上なので、
value < 0 を満たす実測値はやはり存在せず、閾値が発火しないことに変わりはないからである。
その代わりに、below 方向の境界が0以下になった場合を、較正の失敗として扱うことにした。
サンプルが足りない場合と同じく、その指標を出力から除き、理由を標準エラー出力に書く。

above 方向については、同じ対処をしていない。below 方向の下限の0はどの指標にも共通するが、
above 方向の上限は指標ごとに異なるからである。比率の上限は1だが、千字あたりの出現数には
決まった上限がない。指標ごとの上限を較正の処理に持ち込むと、指標ごとに固有の
知識を混ぜることになるので、対処を below 方向に限った。

`guidance`、`direction`、`severity` は、同梱の oss プロファイルの値を
そのまま使うことにした。baseline を実行するたびにこれらの文面を書き写すと、oss.toml を
直したときに、baseline の出力だけが古いまま残る経路ができてしまう。
較正の対象は value だけに限った。

`corpus/fetch.sh` で取得できるコーパスはこの環境になく、ライセンス上の理由でリポジトリにも
含めていない。そのため、この決め方で実際に `corpus/baselines.toml` や
同梱のプロファイルと同じ桁の値が出るかどうかは、確かめていない。
`tests/golden/input/` の文書は数が少なく、指標ごとのサンプルが4件に届かないので、
これで代わりに確かめることもできない。コーパスを置ける環境で実際に実行して
照合するまで、TASKS.md に未検証の項目として残しておく。

較正できた below 方向の閾値が実際に機能することは、確かめてある。前述の文書をサンプルにして
出力から除かれずに残った `ja.prose_ratio`（境界 0.69）を含むプロファイルを作った。このプロファイルで、箇条書きばかりの
文書に `suikou check --profile` を適用すると発火し、地の文だけの文書では発火しないことを、
実行結果で確かめた。

## D-23 textlint のプリセットを実装する中で分かれた判断

`packages/textlint-rule-preset-tech-maintainability`（T7）を実装する中で、
一つの結論にまとめられない判断がいくつか出た。それぞれの判断を、次に順に記す。

**textlint が実際に表示するルールIDは、標準の設定では `maint/` で始まらない。**
指示では、Rust側に合わせて `maint/list-lead-in` のような ID にすることを求めていた。
`@textlint/config-loader` の `loader.js` と `@textlint/utils` の
`normalizeTextlintRulePresetKey` を読んで確かめると、プリセットの接頭辞は、
`.textlintrc` に書いた設定キーから先頭の `preset-` を除いた文字列になる。
このパッケージを標準の書き方どおりに `"preset-tech-maintainability": true` で
読み込むと、表示される ID は `tech-maintainability/list-lead-in` になる。
設定キーは `preset-` で始まらないとプリセットとして認識されない
（`isPresetRuleKey` がそう定めている）。認識された場合は、その `preset-` が
必ず取り除かれる。そのため、標準の読み込み方法では、どうしても `maint/` という接頭辞には
ならない。

個々のルールの名前（`list-lead-in` のような、接頭辞を除いた部分）は、指示どおり
Rust側の名前に合わせている。接頭辞だけは、textlint 自体の命名規則に従うしかない。
命名規則に逆らうには、npm のパッケージ名を `textlint-rule-preset-maint` のように
変える必要がある。しかし、そうするとパッケージの置き場所である
`packages/textlint-rule-preset-tech-maintainability` という名前と食い違い、
かえって分かりにくくなる。そこで、パッケージ名は置き場所に合わせたままにし、
実際に表示される ID が `tech-maintainability/` で始まることを README に
明記した。ゴールデンテストの照合では、`@textlint/kernel` を直接使い、
各ルールを `maint/` の接頭辞で手作業で登録しているので、この制約の影響を受けない
（`test/support/lint.js`）。

**AST を使わず、行単位で判定する。** textlint は、Markdown を段落や見出しなどのノードに分けてルールに渡す。ソフトラップで複数行に
わたる段落は、textlint の中で一つの Paragraph ノードにまとめられる。
一方、`markdown.rs`
の `Document::parse` は行ごとにブロックを作り、ソフトラップで続く行も独立した行として扱う。
この違いは、`en_maintainability.md` の14〜15行目のように、一つの文が2行にわたる
段落で問題になる。ノード単位で判定すると2行分の文字列が一つにまとまり、Rust側では
結び付けることのない語どうしが、正規表現の一致範囲に入ってしまう。

選択肢は二つあった。
一つは、textlint の Paragraph ノードのテキストをそのまま判定に使う方法である。
もう一つは、`Document::parse` と同じ行単位の手順を JS に移植し、
textlint からは原文の文字列だけを受け取る方法である。
前者は textlint の一般的な使い方に沿った実装だが、
ノードの分け方が変わるたびに件数が一致しなくなる。

後者を採用した。
`src/lib/blocks.js` は、`markdown.rs` の`preprocess`・`strip_inline`・`Document::parse`・`list_blocks`・`block_before` を、
正規表現も含めてそのまま移植したものである。
各ルールは `context.getSource(node)` で原文を取得し、
自前のブロック抽出にかけてから判定する。textlint が受け持つのは、
ファイルの読み込み、設定、報告の集約であり、構造の解析ではない。

この方法の代償は、報告する行と列が、前処理した後の文字列に基づくことである。原文そのものの
文字列での位置は、エスケープの解除やインライン記法の除去によって、前処理後の位置と
ずれることがある。`src/lib/position.js` は、一致した文字列を対象の行の中で順に
探し、原文での文字の位置に近似的に対応付ける。この近似は指摘を見失わないための
ものであり、位置が正確であることを保証するものではない。`tests/golden/` との照合では
件数だけを比べており、位置の正確さは条件に含めていない。

**IPADIC は、UniDic で体言に当たる4つの分類を、一つの品詞にまとめる。**
M1・M5の日本語の判定では、行末や項目の末尾のトークンが体言止めかどうかを調べる。
suikou-core は UniDic を使い、品詞大分類が名詞・接尾辞・代名詞・形状詞のどれかであれば、
体言とみなす。textlint の周辺で標準的に使われる kuromojin は IPADIC を使っており、この4つの分類を
持たない。

kuromojin 3.0.1 で実際に解析させると、UniDic で接尾辞・代名詞・形状詞に分類される語は、IPADIC
では名詞の下位分類（品詞細分類1が代名詞・接尾・形容動詞語幹）として現れた。
「これ」は名詞/代名詞、「委員長」の「長」は名詞/接尾、「静か」は名詞/形容動詞語幹
になった。したがって IPADIC では、pos が名詞であるという一つの条件で判定してよい。
`src/lib/morphology-ja.js` の `isTaigen` は、この実測に基づいている。

連用形の判定も、同じように実測で確かめた。UniDic は「連用形-一般」のように活用形を細かく分けるが、
IPADIC は単に「連用形」という値を返す（「使い」「し」で確かめた）。
したがって、`cform.startsWith("連用形")` という Rust 側の判定を、そのまま移植して問題ない。

**説明文の言語は、文書の言語に合わせる。** Rust側では、説明文の言語を日本語に固定している。
suikou-core の `finding()` は、文書が英語であっても日本語の説明文を返す。
このことは、`en_maintainability.md` に対する `suikou check` の出力で確かめた。

textlint のプリセットの利用者には、英語の文書だけを書く人もいる。日本語でしか読めない
説明文を出すと、そうした人にとっては指摘が役に立たない。そこで、判定の処理と正規表現は
Rust側と一致させつつ、説明文だけは、検出した言語に合わせて日本語と英語を
使い分けることにした。`src/lib/messages.js` に両方の言語の説明文を持たせている。件数の
照合には説明文の内容は関係しないので、この違いはゴールデンテストの完了条件に
影響しない。

**テストには textlint-tester を使わず、node:test を直接使う。**
textlint-tester は、Mocha の `describe`/`it` があることを前提に作られている。それらが
グローバルに存在しない環境では、`method.apply(this)` を呼び出すだけの代用の実装に切り替わる。
この代用の実装は、`testValid`・`testInvalid` が返す Promise の完了を待たない。そのため、
`node --test` の実行環境でそのまま使うと、lint が終わる前にテストが
成功扱いになる箇所があった。

Mocha を依存に加えて textlint-tester を使う案と、`@textlint/kernel` を
直接使う薄いレイヤーを書く案の二つを検討した。依存を増やさないほうを選び、
`test/support/lint.js` に、`TextlintKernel` を包む数行の処理を置いた。この処理では、プリセットの
すべてのルールを `maint/` の接頭辞付きで登録し、`async/await` でそのまま結果を待つ。
この方式は、`node --test` の非同期テストとそのまま組み合わせられる。

**`@textlint-ja/textlint-rule-preset-ai-writing` の `no-ai-colon-continuation`
と重なる指摘を、意図して抑えない。** このルールは、コロンの前が述語で終わる
文を kuromojin で検出しており、判定の仕組みが M1 の日本語版とよく似ている。

ただし、目的は異なる。ai-writing 側のルールは AI が書いた文体の特徴を検出し、suikou 側の規則は項目の増減に
弱い箇条書きの構造を検出する。それでも、同じ行が両方から指摘されることはある。
どちらか一方を優先する仕組みは設けなかった。二つのプリセットを同時に
有効にしている利用者は、両方の指摘を読んで、自分の文書に合うほうを選べる。
一方の指摘を出さないようにすると、利用者が判断するための材料を減らすことになる。README には、この重なりを
明記した。

## D-24 terms の抽出では、品詞だけでなく構造も使って語を区切る

日本語では、名詞が続く範囲を、一つの複合語としてまとめる。
UniDic は「素」や「性」のような接尾辞を、pos1 が接尾辞である形で切り出す。そのため、
名詞だけを対象にすると、「形態素解析」が「形態」と「解析」に分かれ、
「メンテナンス性」が「メンテナンス」だけになった。この不具合は、自分たちの文書にこのツールを適用して見つけた。

接尾辞を名詞と同じように扱うと、今度は「つ」のような助数詞まで
複合語の先頭に来てしまう。UniDic の素性には、助数詞だけを見分けられるほど細かい情報がない。
そうかといって、助数詞の一覧を新たに作ることはしない。
その代わりに、接尾辞は、直前にすでに名詞が続いている場合に限って、複合語を延ばす形にした。
数詞で名詞の連続が途切れた後の接尾辞は、単独では語にならないからである。

UniDic は、空白を語の区切りとして使うだけで、トークンとしては残さない。
そのため、隣り合う半角の語のトークンをそのままつなぐと、本文にない語ができてしまう。
自分たちの文書にある「Linux kernel」（`design.md` の複数の箇所にある）から、
「Linuxkernel」という本文にない語ができることを確かめた。
そこで、半角英数字の語どうしが隣り合う場合は、間に空白を1個入れる。
半角の語と日本語の語が隣り合う場合（「API仕様」のような語）は、空白を入れない。
日本語の文の中でこの組み合わせが続く場合、元の文でも空白を入れない書き方が普通だからである。

一般的な語を除くための一覧には、`metrics/ja.rs` の `KEISHIKI_MEISHI` をそのまま使い、
別の一覧を新たに作ることはしない。
一般的な語が語彙集に紛れ込んでも、比喩の判定から除かれるだけなので、害は小さい。
分野の語を取りこぼす害のほうが大きいと判断し、取りこぼさないほうを選んだ。

自分たちの文書に適用すると、1文字の候補が上位を占めた。
395語のうち54語が1文字で、上位20語には文(50)、形(49)、語(48)、指示(43)、値(36)が続き、
地(28)、数(27)を経て、`版`(22)、行(22)、`層`(20)までが並んだ。
「地」は「地の文」が「の」で分かれた後に残った断片であり、残りは日本語の一般的な語として
どんな文章にも頻繁に出る、分野に関係しない語である。

除外する語を個別に挙げた一覧は作らない。どの語を挙げるかの基準そのものが、感覚に頼ったものになるからである。その代わりに、
結果の文字数という構造上の条件だけで絞り込み、1文字の候補を対象から除いた。

日本語の術語抽出では、1文字の候補を除く扱いが広く採られている。
意味を担うのはほとんどが複数の文字からなる複合語であり、
1文字の語は最小単位の形態素で多義になりやすく、単独では分野を特定できないからである。
「文書」のような2文字で1トークンの語は、この絞り込みの対象にならない。
絞り込んだ後に自分たちの文書で上位になった語は、指示、規則、指標、人間、文書、日本語、指摘、閾値、
辞書、実装などに変わり、1文字の語は残らなかった。

英語には、形態素解析器も文分割もない。
そこで、頭文字だけからなる語、文頭以外の位置にある大文字で始まる語、識別子一つだけからなる
インラインコードを手掛かりにする。表の行は、この対象から除いた。
表の列の値は文の形をしていないので文頭の手掛かりが働かない。さらに、
同じ値が行をまたいで繰り返し出るので、出現回数の下限による絞り込みも通り抜けてしまう。このことは、
自分たちの文書に適用して確かめた。

見出しの先頭に ID がある形にも、同じ問題があった。
`decisions.md` 自身の見出し「D-04 The tokenizer hides behind a trait」では、
先頭の語だけを文頭とみなすと、次に来る The を文の途中の語と取り違えた。
先頭から ID の形をした語が続く間は、まだ文頭が続いているとみなすように直した。

見出しの先頭に ID の形をした語が並ぶ場合には、別の欠陥が残っている。
英語版の `decisions.md` の見出し「D-13 M2 and M6 count every occurrence」では、
`D-13` と `M2` の間に区切りの記号がないので、隣り合う語が一つの複合語
「D-13 M2」としてまとめられる。その結果、`M2` という語単独の出現回数が減り、
出現回数の下限を下回ることがある。これは語を抽出しきれないだけで、本文にない語を
作り出す誤りではないので、害は小さいと判断して今回は直さない。
直すには、隣り合う ID の形をした語をどこまで一語として扱ってよいかを判断する必要がある。
「AWS S3」のように、隣り合う頭字語を一語として扱って初めて意味が通る固有名詞もある。
そうした固有名詞を崩さずに直す規則は、見つかっていない。

出現回数の下限は、既定で2とする。
1回しか出ない語については、分野の語か偶然使った表現かを区別する材料がない。
terms のもう一つの目的である、語の使い方が一貫しているかの確認も、同じ語が繰り返し出て
初めて成り立つ。この値は実測から得たものではなく、この二つの目的から導いた下限である。

この抽出の結果は、比喩のレイヤーで使うためのものである。
比喩のレイヤーはまだ実装していないので、抽出の良し悪しを最終的に判断できるのは、
そのレイヤーを実装したときになる。

## D-25 MCP は依存を追加せず JSON-RPC を自前で実装し、daemon は設けない

T9 では、二つの判断が必要だった。MCP サーバーをどう実装するかと、常駐の方式を設けるかどうかである。

**MCP は `serde_json` だけで実装した。** 
候補は二つあった。一つは `rmcp` のような専用のクレートを追加する案で、
もう一つは `initialize`・`tools/list`・`tools/call` の3種類の要求だけを手作業で実装する案である。

実装する必要がある要求はこの3種類だけで、MCP の仕様のうち resources、prompts、
サーバーから送る通知は使わない。専用のクレートを追加すると、使わない機能まで含めてバージョンを固定する
ことになる。依存を `=` で固定し、更新のたびに `verify_schema` を通すという
このリポジトリの運用の手間に、得られるものが見合わない。`serde_json` は両方のクレートがすでに依存しているので、
増える依存は0である。標準入出力でのやり取りも、「1行に1つの JSON-RPC メッセージ」
という単純な形式で足りる。実装は `crates/suikou-cli/src/mcp.rs` にある。判定の処理
そのものは `check::analyze` と `brief::run` を呼び出すだけであり、CLI と MCP で
同じ処理を二重に書いてはいない。

**daemon は実装しない。** 常駐の方式を検討した元々の理由は、「辞書の読み込みを一回で済ませる」
ことだった。しかし、T2 で測定した値（release で 0.68〜0.70 ミリ秒）からは、この理由は成り立たない。
TASKS.md には「プロセスの起動そのものの費用を別に測定してから決める」と定めていた。
そこで、release ビルド（`--features lindera-unidic`）の `suikou check` を短い文書に
対して50回起動し、実時間を測定した。比較のために、`suikou --version` も50回測定した。
WSL2 上での結果は次の表のとおりである。

| コマンド | 平均 | 最大 |
|---|---|---|
| `suikou --version` | 約1.5〜1.6ミリ秒 | 約1.9〜2.4ミリ秒 |
| `suikou check`（辞書あり、短い文書） | 約3.7〜3.9ミリ秒 | 約4.3〜4.7ミリ秒 |

`--version` は辞書を読み込まないので、
この値はバイナリの起動そのものにかかる時間（約200MBの実行ファイルを読み込み、動的リンクを行い、
引数を解釈する時間）を表す。`check` との差は2ミリ秒台であり、
これは辞書の読み込み（0.7ミリ秒）と、短い文書1件の形態素解析と指標の計算を合わせた時間に当たる。
どちらの値も、hooks から Write や Edit のたびに起動する使い方では、
LLM の1ターンにかかる秒単位の時間と比べて無視できる。

常駐の方式にすると、ソケットや名前付きパイプの管理、ファイルの変更の検知方法、
複数の呼び出し元が同時に動く場合の直列化といった、複雑な処理が増える。
それに見合うほど速くはならないので、daemon は設けないことにした。
`suikou daemon`サブコマンドは残しておき、
実行すると測定値とこの判断を説明して終了するようにした。CLI からコマンドそのものを削除するより、
daemon がない理由を利用者に直接伝えられる利点を優先した。

## D-26 文体に合わない和語を、参照コーパスとの頻度の比較で検出する

生成モデルは、英語から日本語に訳すときに、漢語を和語に置き換えることがある。
「確認する」が「確かめる」に、「必要である」が「要る」になる、といった置き換えである。
技術文書の文体としては柔らかすぎるので、読む速さが落ちる。

どの語が文体に合うかは、語の対応表を作らずに判断した。
対応表を作ると、分野ごとの表現の違いをすべて列挙することになるからである。
その代わりに、プロによる日本語訳のコーパスでの頻度と比べる方式にした。

対応表を作らなかった判断は、実測の結果が裏付けている。
Kubernetes の文書だけで見ると、「使う」は Sonnet の訳に320回、プロの訳に33回出現するので、
「使う→使用」という規則を作りたくなる。
ところが、分野を Kubernetes、MDN、Vue に広げると、プロの訳にも「使う」が461回出現する。
同じように、「次→以下」「仕組み→メカニズム」「既定→デフォルト」も採用されなかった。
MDN は「既定」を使うなど、分野ごとに表記の方針が異なる。

判定には、二つの統計量を使う。
Dunning (1993) の対数尤度比で有意かどうかを判定し、
Hardie (2014) の Log Ratio で偏りの大きさを判定する。
有意性だけでは条件として足りない。普通の語を少し多く使っただけでも、有意になるからである。

Log Ratio の下限は、測定によって決めた。
参照に使っていないプロの日本語訳12ページと、このリポジトリの日本語の文書とで、分布を比べた。
下限が 4 ではプロの文書に9語、6 では1語の誤検出が出て、7 でゼロになった。
設計の方針では、人間が書いた文書に警告が出ることを偽陽性として扱う。
そこで、検出漏れは許容するが、プロの文書での誤検出は許容しない側を選んだ。

参照コーパスの作り方にも、二つの条件を設けた。
一つは、入門書を混ぜないことである。Rust Book の訳には「確かめる」が36回出現し、参照に入ってしまう。
この結果は、文書の種類による差が文体による差より大きいという測定の結果と一致する。
もう一つは、2つ以上の分野に出現する語だけを参照に載せることである。
一つの分野にしか出ない語はその分野に特有の表現であり、参照にならない。

分野で定着した語のために、`.suikou/register-allow.toml` を用意した。
参照コーパスは Web の文書から作ったので、計算や統計の分野の語が少ない。
その偏りは、プロジェクトの側で補う。辞書を同梱せずに文書から作るという、D-11 と同じ考え方である。

## D-27 漢語率の指示文は誤っていた

D7 の指示文は「漢語を和語動詞に開く」だった。この指示は、実測の結果に反している。

プロによる日本語訳とこのリポジトリの文書とで、自立語の語種の構成を比べた。

| | 和 | 漢 | 外 | 混 |
|---|---|---|---|---|
| プロの日本語訳 | 0.384 | 0.329 | 0.280 | 0.007 |
| このリポジトリ | 0.470 | 0.463 | 0.050 | 0.017 |

プロの訳の漢語率が低いのは、漢語を和語に置き換えているからではない。
定着したカタカナ語を使っているからである。和語の比率は、むしろプロの訳のほうが低い。
指示文は「定着したカタカナ語を使い、漢語の名詞を連ねない」に直した。

この誤りの影響は大きかった。
誤った指示に従って文書を書き直した結果、「検証」が「確かめ」に、「制約」が「縛り」に、
「抽出」が「取り出し」に置き換わり、文体が悪くなった。
D-26 の規則は、このように悪くなった文体を検出するために作ったものである。

指標を最小にすることを目標にしてはならない。
D7 の severity は info であり、参考値にすぎない。
その値をゼロにしようとしたことが、そもそもの誤りだった。
文書が満たすべき条件は、error と warning が出ないことまでとし、
info は参考として読むだけにする。

## D-28 文体の規則は、英語には適用できなかった

D-26 の方法を英語にも適用しようとして、二つの実験を行った。どちらの実験でも、規則は成り立たなかった。
そのため、英語の規則は実装しない。

一つ目の実験は、文書と参照コーパスの頻度を比べる方式である。
Kubernetes、MDN、Vue の英語の原文652ページ、51万語から頻度表を作り、日本語と同じ統計量で測定した。
参照に使っていないプロの英語の文書14ページに対しては、閾値を9まで上げても、誤検出が20語残った。
上位に並んだのは、どちらの側でも分野の用語だった。プロ側は portworx、cinder、ebs、
このリポジトリの文書の側は prose、corpus、metric である。
3つの分野のすべてに出現する語だけに絞っても、プロ側に operations のような話題の語が残った。

原因は、語彙の構造にある。
日本語では、「語種が和である」という条件によって、分野の用語をほぼ自動的に除けていた。
分野の用語は、漢語かカタカナ語だからである。
英語の語彙には、そのような目印がない。ある話題の文書は、その話題の語を一般のコーパスよりはるかに多く使う。
そのため、頻度だけでは、話題の語と文体の語を区別できない。

二つ目の実験は、話題を完全にそろえる方式である。プロによる日本語訳を LLM に英語へ訳し戻させ、
元の英語の原文と比べた。36ページで、それぞれ3万語ずつである。

有意な差のある語は、1語も出なかった。臨界値 15.13 に対して、最大は your の 13.2、
次が will の 11.1 であり、どちらも原文の側に多かった。
語の選び方が、逆向きに偏っているわけでもない。
日本語で同じ設計の実験をしたときは、「使う」が 320 対 33 で、
対数尤度比は 320 に達していた。

この結果は、D-08 と同じ性質のものである。
先行研究で報告された効果量を、課題の異なる場面に持ち込んではならないのと同じく、
一つの言語で成り立った方法を、別の言語にそのまま持ち込んではならない。

確かめたのは、語の選び方だけである。
英語の指標として採用した MATTR、地の文比率、直喩の標識は別の性質を測っており、これらは残す。

再現の手順は、`research/lexshift/` に置いてある。
`build_reference_en.py` が英語の頻度表を作り、
`translate_back.sh` が訳し戻しを作る。
同じ実験を繰り返さなくて済むように、うまくいかなかった実験の手順も残している。

## D-29 カタカナ語が優勢な漢語は、対応表を使って置き換える

D-26 では、対応表を作らないと決めた。分野によって優勢な語が逆になる場合があるからである。
しかし、漢語とカタカナ語の組については、この判断を改めた。
反例があっても、分野をまたいだ合計でどちらかが優勢なら、優勢な側に従う。

同義かどうかを機械的に決める方法は、いくつか試したが採用しなかった。
英語の原文を手掛かりにして、段落の中での共起から語を結び付ける方式では、同義語ではなく連語が検出された。
たとえば、「永続ボリューム」や「ポート番号」のような組が出てくる。
持ち上がり度で測っても Dice 係数で測っても同じであり、共起からは同義かどうかが分からない。
置き換えの関係は、共起ではなく入れ替わりであり、段落の単位では測れなかった。

そこで、候補の列挙と、採用するかどうかの判断を分けた。候補は人が挙げ、採用するかどうかは実測で決める。
D-26 と同じ考え方である。97組の候補のうち、53組を採用した。

採用の条件は、カタカナ語の側が漢語の側の2倍以上出現すること、
合計の出現が20回以上であること、漢語の側の出現が60回以下であることとする。

最後の条件は、多義語を避けるために設けた。
測定すると、「対象」「対応」「状態」「場合」はプロもよく使っていた。
しかし、プロがそれらをカタカナ語と同じ意味で使っているとは限らない。
このリポジトリでも、「対象」は扱う範囲という意味で使っており、オブジェクトの意味ではない。
プロがその漢語をほとんど使っていない組に限れば、置き換えの対応として信頼できる。

直前が名詞である場合は、複合語の一部とみなして判定を見送る。
`英語版` や `第3版` の `版` を置き換えると、誤りになるからである。

分野によって別の意味で使う語は、`.suikou/register-allow.toml` で除外する。
このリポジトリでは、「記録」「一覧」「比率」「経路」「分岐」「実体」を除外した。
たとえば「比率」は漢語率や地の文比率という意味で使っており、レートの意味ではない。

## D-30 文書の構造をガードレールにし、書く前に型枠を示す

文の単位の規則だけでは、構造が崩れた文書を直せない。
節の欠落、筋の通らない順序、一つの段落に複数の主張を詰め込む書き方は、
一文ずつ読んでいる限り見つからない。

構造の規則は、言語に関係なく適用することにする。
節の構成、順序、段落の単位は文書の論理に関わる性質であり、語彙の体系とは関係がないからである。
この考えは測定でも裏付けられた。7文以上の段落の割合は、プロの英語で 0.27%、
プロの日本語で 0.59% であり、言語が違っても同じ桁に収まる。
文体の規則が英語に適用できなかった D-28 とは、この点で異なる結果になった。

型と必須の節は、自分たちで考えずに、既存の標準から取った。
RFC 7322 は、必須の節と推奨する順序を定めている。
型ごとの節は、Rust RFC テンプレート、Kubernetes Enhancement Proposal、
Michael Nygard の Architecture Decision Record、Diátaxis から取った。
段落の上限は、Google developer documentation style guide の5〜6文に合わせて6文とする。
感覚に頼って規則を追加しないという制約は、構造の規則にも同じく当てはまる。

severity は、節の欠落だけを error とし、順序、段落、空の節は warning とする。
必須の節がない文書は、読者の問いに答えられない。
一方、順序と段落の長さは読者が理解する道筋であり、破ってはならない決まりではない。

節の照合では、最上位の階層の見出しだけを対象にする。
先頭の第1階層の見出しは標題であり節ではないので、照合から除く。
下位の見出しまで対象にすると、節の中の小見出しが別の節と一致してしまい、順序の判定が誤る。
実際に、このリポジトリの英語の設計文書で、この誤検出が起きた。

最初の節だけは、標題のすぐ後に置いた地の文で代用できることにする。
RFC 7322 の abstract は、見出しを付けずに標題と目次の間に置かれており、これが前例になる。README も同じ形を取る。
`## これは何か` という見出しを強制すると、かえって読みにくくなる。

### 書く前に構成の承認を受ける

`suikou plot` は、`.suikou/plans/` にテンプレートを出力する。
このテンプレートは、節の見出し、その節が答える問い、その節で述べる主張の欄だけからなる文書である。
主張を一行で書けない節は、検討が足りていない。
このテンプレートを使えば、そうした節を、本文を書く前に見つけられる。

プロットはバージョン管理の対象にしない。考えた過程を書いた文書であり、成果物ではないからである。
そのため CI からは見えず、本文との照合は、手元の環境とエージェントの作業ループの中でしか働かない。
これは弱点ではない。構成の誤りは書く前に直すものであり、
配布の直前の検査で止めるような種類の誤りではないからである。

### 検出に加えて、書き方の指針も示す

ここまでの規則は、違反を見つけて直させるという、否定の方向の働きしか持っていなかった。
違反の一覧からは避けるべき形が分かるが、書くべき形は分からない。

そこで、テンプレートに、節ごとの問いと書くべき内容を持たせた。
`suikou plot` と `suikou brief --doctype` は、書く前にこれらを示す。
指針の文面は `structure::writing_rules` の一か所だけに置き、
指摘の文面と食い違わないようにした。

出力するトークンの量は増やさない。テンプレートは、`--doctype` を指定した場合にだけ出力する。

## D-31 手順の型の必須の節は、実測の結果、二つを必須から外した

型ごとの必須の節は、既存の枠組みから取って定めた。
Diátaxis の how-to guide を根拠に、前提、手順、確認の三つを必須にした。
そのうち二つは、プロの文書に適用した時点で成り立たなかった。

Kubernetes の task ページ120件に `howto` を適用したところ、
`Steps` は120件すべてで、`Verify` は113件で「無い」と判定された。
発火しなかった文書は一つもなかった。

見出しを数えると、理由が分かる。
task ページの見出しは、`{{%/* heading "prerequisites" */%}}` が111件、
`{{%/* heading "whatsnext" */%}}` が84件で、それ以外はページごとに固有の見出しである。
`Create a namespace` や `Edit a Secret` のように、そのページで行う操作の名前が並んでいる。

手順そのものは本文であり、節として立てるものではない。
Diátaxis が述べているのは「how-to guide は手順を並べたものである」ということであり、
`Steps` という見出しを置けということではない。
見出しを `Steps` にそろえさせると、何の手順なのかが見出しから分からなくなる。
これは、「見出しだけをたどれば全体の論理が分かるようにする」という指針に反する。

そこで、`steps` と `verify` を必須から外した。
必須として残すのは `prerequisites` だけである。

### 測り直したところ、さらに二つの欠陥が見つかった

最初の計測では、`prerequisites` は120件すべてで条件を満たしていた。
しかしそれは、文書が正しく書かれていたからではなく、suikou の規則が緩すぎたからだった。

導入の地の文で代用できる節を、位置で決めていた。
そのため、標題のすぐ後に地の文があれば、最初の必須の節が何であっても条件を満たしてしまっていた。
このことは、concept ページ120件に `howto` を適用しても1件も発火しなかったことで分かった。
型が、型としての役割を果たしていなかった。

代用できるかどうかは、節の位置ではなく、節の性質で決まる。
そこで、主題を述べる節にだけ `lead_ok` を与えるように直した。
前提や文脈は、導入の地の文では代用できない。
直した後は、concept ページ120件のうち117件で発火する。型によって文書を区別できるようになった。

節の同義語を、文書の言語の同義語だけで照合していた。
Kubernetes の日本語訳は `{{%/* heading "prerequisites" */%}}` をそのまま使っているので、
日本語の同義語だけで照合すると、111件中110件で節が無いと判定された。
両方の言語の同義語で照合するように直した。
文書の言語と見出しの言語が一致するとは限らない。

### 直した後の発火率

| コーパス | ページ | 必須の節が欠けているもの |
|---|---|---|
| 英語の task ページ | 120 | 9件（7.5%） |
| 日本語の task ページ | 111 | 6件（5.4%） |
| 英語の concept ページに `howto` を適用したもの | 120 | 117件（97.5%） |
| 日本語の concept ページに `howto` を適用したもの | 120 | 116件（96.7%） |

言語が違っても、同じ範囲に収まった。
型の異なる文書に適用するとほぼすべてで発火し、正しい型の文書に適用するとほとんど発火しない。
この差は、型が型としての役割を果たしていることを示している。
発火したページを読むと、実際に `Before you begin` が置かれていない。
`Dependency on Docker explained` のように、`task` と宣言しているのに内容が解説になっているページもある。
これは suikou の誤検出ではなく、Kubernetes の文書が自分たちのひな形から外れている箇所である。

### 検出の対象から外しても、書き方の指針からは外さない

問いと書くべき内容は、型の定義に残したままにする。
`suikou plot` と `suikou brief --doctype howto` は、
「どうやるのか」と「うまくいったことをどう確かめるのか」を引き続き問う。

検出できる項目と、書く前に問うべき項目は一致しない。
確認の手段を書くことは良い手順書の条件だが、
`確認` という見出しがあるかどうかで判定できるものではない。
この二つを分けたことが、この決定で最も効果のあった点である。

### 外部の文書で測れたのは、手順の型だけである

`design`、`decision`、`overview` の必須の節は、このリポジトリの文書でしか確かめていない。
その文書の見出しは、型に合わせて自分たちで書いたものである。
自分たちで書いた文書に自分たちの型を適用しても、確かめたことにはならない。

外部のコーパスで計測するには、型が宣言された文書が必要である。
Kubernetes の文書は `content_type` を持つが、その値は `task`、`concept`、
`reference`、`tutorial` であり、suikou の型と重なるのは `task` だけである。
`concept` と `tutorial` に対応する型は設けていない。
設けるとすれば Diátaxis の explanation と tutorial になるが、
適用して確かめる対象を用意しないまま型だけを増やすことはしない。

## D-32 設計の型は、その出典である Rust RFC に適用した時点で成り立たなかった

`design` の必須の節は、Rust RFC のテンプレートから取ったと書いた。
この記述を検証するために、`rust-lang/rfcs` の `text/` の直下にある200件に適用した。
対象は、番号の大きいものから選んだ。テンプレートが定着した後の書き方を見るためである。
型の出典そのものに適用するので、これが最も厳しい確認になる。

最初の結果では、`Design` が200件すべてで、`Non-goals` が199件で、`Scope` が198件で欠けていると判定された。
原因は、節ごとに異なっていた。

### 名前の食い違い

`Design` の200件は、必須とする節の選び方が誤っていたのではなく、節の名前を取り違えていた。

Rust RFC のテンプレートは、この節を `Guide-level explanation` と
`Reference-level explanation` と呼んでいる。実測でも、前者が157件、後者が148件あった。
同義語に `Explanation` を追加した。どちらの名前にもこの語が含まれる。
あわせて、`Implementation` と `Proposal` も追加した。どちらも設計の文書で広く使われる名前である。

### 型に存在しない節を必須にしていた

`Scope` と `Non-goals` は、Rust RFC のテンプレートには存在しない。
この二つは、Kubernetes Enhancement Proposal の様式に含まれる節である。
様式の異なるものを組み合わせて、必須にしていたことになる。

この二つを必須から外した。問いと書くべき内容は残す。
`plot` と `brief` は、「どこまでを範囲にするのか」と「何をしないのか」を引き続き問う。
D-31 と同じ分け方である。

### 解析の欠陥が二つ見つかった

見出しの字下げに、上限を設けていなかった。
4桁以上字下げした行はコードであり、CommonMark では見出しとして扱わない。
字下げしたコードの中の `#` が第1階層の見出しとして解釈され、
その文書の節が第1階層だけになり、本来の節が一つも見つからなくなっていた。
字下げを3桁までとするように直した。

コードブロックの範囲を、正規表現で除去していた。
長いコードブロックの中に短いコードブロックを入れる書き方があり、内側のブロックで閉じたと判定されていた。
そのため、その後のコードが本文として読まれ、`# [dependencies]` が見出しになっていた。
開始の行と同じ記号を使い、開始の行以上の長さを持つ行だけを閉じる行とみなす、行単位の走査に直した。
これは CommonMark の規定に従った判定である。

この二つの修正は、textlint のプリセットにも移植した。
実際の RFC 2件で、M 系の件数が両方の実装で一致することを確認した。

### 直した後の発火率

200件中21件（10.5%）で、必須の節が欠けていた。
そのうち18件は、機能の提案ではない。
ロードマップ、プロジェクトグループの憲章、チームの編成、方針についての RFC であり、
`text/` に置かれてはいるが、機能を提案する様式には従っていない。
残りの3件は、`Proposed additions` や `Solution` のように、その文書でしか使われていない節の名前を使っている。

同義語の追加は、ここでやめる。
節の名前を増やし続ければ発火はゼロに近づくが、それはコーパスに規則を合わせているだけである。
同義語を追加する根拠は、様式を定めた文書に載っている名前に限る。

## D-33 決定の型は、外部の ADR でも成り立った。節の順序も、ここで初めて測れた

`decision` の必須の節は、Michael Nygard の Architecture Decision Record から取った。
28のリポジトリから190件の ADR を集めて、この型を適用した。
`research/structure/fetch_adrs.py` は、`adr-tools` が作る最初の記録を手掛かりにして ADR を集める。
索引とひな形は決定の記録ではないので、対象から除く。

| 規則 | 190件のうち発火したもの |
|---|---|
| 必須の節が無い | 20件（10.5%） |
| 節の順序が違う | 0件 |
| 段落が長い | 6件（3.2%） |
| 末端の節に本文が無い | 2件（1.1%） |

`howto` と `design` の型ではそのままでは規則が成り立たなかったが、この型では成り立った。
違いは、一つの様式をそのまま取り入れたか、複数の様式を組み合わせたかにある。
`design` は Rust RFC と KEP を組み合わせていた。`howto` は、Diátaxis の説明を節の名前と読み違えていた。
`decision` は、ADR という一つの様式をそのまま取り入れている。

### 節の順序を初めて測れた

節の順序を判定するには、型が定める節が2つ以上見つかる必要がある。
Kubernetes の task ページでは、この条件を満たすのが120件中7件しかなく、測定にならなかった。
ADR では、190件中189件がこの条件を満たす。そのうえで、発火はゼロだった。

文脈、決定、帰結という順序は、実際の書き方と一致している。
この順序を推奨として定めてよい根拠が、この計測で得られた。

### 残った20件の内訳

11件は MADR の様式で書かれている。
MADR の様式は `Context and Problem Statement` と `Decision Outcome` を使い、
帰結を `Decision Outcome` の下の階層に置く。
節の照合は最上位の階層に限っているので、下の階層にある帰結は見つからない。

この制限は緩めない。
下の階層まで照合すると、節の中の小見出しが別の節と一致してしまい、順序の判定が誤る。
この誤りは、D-31 で実際に起きている。
MADR を扱うのであれば、下の階層まで探すのではなく、様式ごとに型を分けることになる。

残りの9件の中には、`Status` と `Context` しか持たないものがある。
決定も帰結も書かれていない決定の記録であり、これは実際の欠落である。
`Decision` の代わりに `Proposal` と書いているものもある。

ここでも、同義語の追加はやめる。D-32 と同じ基準を当てはめる。

## D-34 natural-japanese の規則を計測し、どれも採用しなかった

`coji/natural-japanese`（MIT）は、仕事で使う日本語を読みやすく書くためのスキルである。
このスキルは、28 種類の検出器、禁止語のカタログ、翻訳調のパターン集を持っている。
そこから規則を取り込めるかどうかを、このリポジトリの基準で確かめた。

規則を追加できるのは、実測値で人間と AI の範囲が重ならない場合か、
明文化されたスタイルガイドの規約を出典付きで示せる場合のどちらかである。
候補は人が挙げてよいが、採用するかどうかは計測値で決める。D-26 と同じ手順である。

### 計測の方法

`corpus/cache/k8s/` には、同じ文書の人間訳と AI 訳が組になって入っている。
同じ原文の訳どうしを比べるので、分野や題材の違いが差として混ざることはない。
参照コーパスの 798 文書もあわせて調べた。手順は `research/translationese/` にある。

### 計測の結果

| 候補 | 人間訳 | AI訳 | 参照 | 判定 |
|---|---|---|---|---|
| 「することができる」 | 2.43 | 0.85 | — | 差の向きが逆 |
| 翻訳調パターン10個 | ほぼ0 | ほぼ0 | — | 技術文書に出現しない |
| 段落頭の接続詞 | 1.6% | 1.2% | 1.6% | 人間と AI を分けられない |
| 文末の同形3連 | 11.8% | 10.5% | 6.0% | 人間と AI を分けられない |
| 二重否定 | 0.16 | 0.11 | 0.16 | 人間と AI を分けられない |
| 「の」の3連続 | 3.67 | 3.03 | 2.84 | 人間のほうが多い |
| 禁止語カタログ48語 | 最大1回 | 最大5回 | — | G² の水準に達しない |

数値は、1万文字あたりの出現数である。段落の割合だけは百分率で示している。

どの候補も採用しない。不採用の理由は、`corpus/baselines.toml` の `[rejected]` に記録した。

### 人間と AI を分けられなかった理由

禁止語のカタログは、随筆とビジネス文書を対象に作られている。
「いかがでしたか」や「見ていきましょう」は、技術文書には出てこない。
48 語のうち、このコーパスに出現したのは19語だけだった。
文書の種類が違えば、AI の書き癖も違う。これは D-28 と同じ傾向の結果である。

翻訳調のパターンについては、比較する相手の選び方に注意が必要である。
このコーパスの人間側は、英語の文書をプロが翻訳したものである。
そのため翻訳調が出るのは当然であり、文書が翻訳調かどうかを、このコーパスで判定することはできない。
計測できたのは「AI 訳が人間訳より翻訳調になっているか」であり、その答えは「なっていない」だった。

### 取り入れたもの

規則は取り込まなかったが、natural-japanese の証拠の表には取り入れる価値がある。
`corpus/reports/research/prose-rhythm-evidence-matrix.md` は、
文長の分散、バースト性、自己相関、TTR、perplexity について、
先行研究と独自の実測を照らし合わせ、「反証的」と判定している。

この表は、このリポジトリが `[rejected]` に入れた指標について、独立に同じ結論に達している。
文長の変動係数について、natural-japanese 側は、使用中の閾値で人間の文書の誤検出率が 32.4% になると計測している。
自己相関については、仮説と逆向きの結果を得て、削除の候補にしている。

別の作者が別のコーパスを使って同じ結論に達したことは、この判断を裏付ける。
`[rejected]` の根拠として、この出典を残しておく。

### 両方のツールを同じ文書に適用して比べた

規則の一覧を見るだけでは、実際に何が検出されるのかが分からない。
そこで、AI が書きそうな日本語の設計文書を用意し、両方のツールを適用した。

| | suikou | natural-japanese |
|---|---|---|
| 指摘 | 13件（5規則）と文書指標4件 | 6件（5カテゴリ） |
| 規則の重なり | ゼロ | ゼロ |

検出したものは、完全に分かれた。
suikou が指摘したのは、項目数の明記、見出しの連番、項目のそろい、時点に依存する語、
カタカナ語の優先である。どれも、後で修正するときに崩れる箇所か、内容が古くなる箇所である。
natural-japanese が指摘したのは、決まり文句、無生物主語、翻訳調、文のリズムである。
どれも、文章の自然さに関わる箇所である。

両方のツールが同じ行を指摘した箇所もあったが、理由は異なっていた。
冒頭の一文に対して、suikou は時点に依存する語を指摘し、
natural-japanese は決まり文句を指摘した。同じ行でも、判定している観点が違う。

プロの文書（Kubernetes の日本語訳の手順ページ）では、suikou が2件、
natural-japanese が1件だった。どちらのツールも、ほとんど指摘を出さなかった。

### 組になったコーパスでの指摘の量

同じ原文の人間訳12本と AI 訳12本に、両方のツールを適用した。

| | 人間訳 | AI訳 | 比 |
|---|---|---|---|
| suikou | 43件 | 62件 | 1.44 |
| natural-japanese | 87件 | 82件 | 0.94 |

natural-japanese の内訳を見ると、件数の出どころが分かる。
`translationese` は人間13件に対して AI 2件、`translationese_morph` は19件に対して2件であり、
どちらも人間訳の側に多く出ている。この傾向は、D-34 の計測の結果と一致する。
人間側は英語の文書をプロが翻訳したものなので、翻訳調が出るのは当然である。

### 差の向きが合っていた唯一の規則

`repeated_sentence_lead`（同じ文書の中で、文頭の2形態素が同じ文が6回以上ある）だけは、
期待どおり AI 訳の側に多く出た。suikou にはない規則である。
そこで、他の候補と同じ手順で計測した。

| 群 | 文書 | 発火した文書 | 100文あたり |
|---|---|---|---|
| 人間訳 | 39 | 35% | 14.2 |
| AI訳 | 78 | 50% | 16.4 |
| 参照コーパス | 60 | 26% | 10.6 |

差の向きは合っているが、人間と AI の範囲が重なる。AI と人間の比は 1.15 にとどまる。
参照コーパスでも、26%の文書で発火する。
規則を追加する条件は「範囲が重ならないこと」であり、この規則は条件を満たさない。

出力の形式も合わない。この規則は該当する文をすべて指摘するので、
71文の文書一つで17件の指摘を出した。一つの規則について示す位置を絞るという方針に反する。

この規則は採用しない。ただし、候補の中で唯一差の向きが合っていたものとして、計測値を残しておく。

## D-35 時点への依存は、時制ではなく係留の有無で判定する

文書を生成するモデルには、自分が置かれた文脈に過度に合わせてしまう性質がある。
セッションの中で文書を書くと、その時点を、文書にとってずっと続く時点だと取り違える。
たとえば `現在レイテンシが悪化しており` と書いた時点で、その文は書いた日にしか正しくなくなる。

M6 の根拠を、「文書の内容が時間とともに古くなる」という説明から、このモデルの性質へと置き直す。
こう説明すれば、この規則だけが短い指示では守られず、
禁止する語をすべて列挙する必要がある理由（`brief` の実測の結果）を説明できる。

### 時制からは、文が古くなるかどうかを予測できない

対策として、「時制を表す表現を取り除き、時点に依存しない書き方を保つ」という案があった。この案は採用しない。

| 文 | 時制 | 古くなるか |
|---|---|---|
| `2026年3月に2.5倍になった` | 過去 | 古くならない |
| `現在は640ミリ秒である` | 非過去 | 翌日には古くなる |

二つの文を分けているのは時制ではなく、絶対的な基準点があるかどうかである。

時制を判定の対象にすると、成り立っている型が崩れる。
決定の記録の文脈の節は過去形で書くものであり、
その型が公開されている ADR 190件で成り立つことは、D-33 で計測した。
手順の順序（「〜したあとに」）も時制の形で書かれるが、読む時点には依存しない。

### 「意図して時点に触れる場合は除く」を運用できる形にする

例外かどうかを書き手の判断に任せると、機械では判定できない。そこで、基準点の有無という形に置き換える。

同じ文の中に西暦、バージョン番号、番号の付いた文書のどれかがあれば、この規則は発火しない。
たとえば `lindera 6.0.0 で現在の素性の順序を確認した` は過去の事実を述べた文であり、内容が古くならない。

基準点は、文ごとに判定する。同じ段落の別の文にある年号を、この文の基準点とみなしてはならない。
小数をバージョン番号と取り違えないように、`v` の付いた形か、3つの数を並べた形だけを基準点とする。
`2.5倍` を基準点とみなすと、その文の指摘がすべて消える。実装の途中で、実際にこの問題が起きた。

### 語の一覧では検出できない形

数を伴う相対的な期間は、語を列挙しても網羅できない。
そこで、`直近3ヶ月` `過去2年` `先週` をパターンとして検出する。

この抜けは、実際の文書で確かめた。
AI が書いた設計文書に適用したところ、M6 は `現在` `現時点` `今後` `既存の` を検出したが、
`直近3ヶ月でリクエスト数が約2.5倍に増加した` は見逃していた。

追加した語は、Google の timeless documentation が挙げている `recently`、`soon`、`new` の
日本語側に当たる。同じ規約の範囲に収まっており、感覚で立てた仮説ではない。

### 計測の結果

| コーパス | 変更前 | 変更後 |
|---|---|---|
| task ページ（日本語）60本 | 119件 / 36文書 | 123件 / 36文書 |
| 参照コーパス60本 | 179件 / 39文書 | 185件 / 39文書 |
| AI 訳39本 | 85件 / 26文書 | 92件 / 27文書 |

増えた件数はわずかである。参照コーパスは、もともと時点に依存しない書き方をしているからである。
基準点による見送りが働いた例は、200文書のうち1件だった。
`既存のHyper-V分離サポートは、v1.10の試験的な機能であり` が、その例である。
この文は `v1.10` の時点での事実を述べており、内容が古くならない。

このリポジトリの文書は、すべて、変更の前でも後でも検査を通る。

### 対象にしなかった範囲

過去形そのもの、継続を表す表現（「〜している」）、順序を表す表現は、対象にしない。
手順の説明には順序が必要であり、決定の記録には経緯が必要である。
これらを取り除いても、読者が得られる情報が減るだけである。

## D-36 示す内容を増やしたうえで、レポートの字数を1割減らす

このツールの制約の一つは、出力するトークンの量を増やさないことである。
その量を実際に計測し、規則ごとに出力の量と効果を調べた。

### 規則ごとの効果

同じ原文に対する AI 訳39本と人間訳39本で、1文書あたりの発火数を比べた。

| 規則 | AI/文書 | 人間/文書 | 比 | 字/件 |
|---|---|---|---|---|
| `maint/time-dependent` | 2.36 | 2.26 | 1.05 | 59 |
| `register/prefer-katakana` | 1.36 | 0.64 | 2.12 | 84 |
| `register/rare-wago` | 1.33 | 0.41 | 3.25 | 60 |
| `maint/parallel-items` | 0.44 | 0.41 | 1.06 | 69 |
| `structure/long-paragraph` | 0.23 | 0.18 | 1.29 | 88 |
| `maint/item-count` | 0.18 | 0.10 | 1.75 | 93 |
| `maint/list-lead-in` | 0.00 | 0.46 | 0.00 | 92 |

人間と AI を最もよく分けるのは、文体の規則である。M 系は明文化された規約に基づく規則なので、
人間の文書でも発火する。この設計は D-09 で決めており、今回の測定はそれと矛盾しない。

件数で見ると、`maint/time-dependent` が最も多い。
比が 1.05 で人間と AI を分けないので、AI が書いたかどうかの判定には使えない。
それでもこの規則を残すのは、明文化された規約に基づく規則であり、指摘どおりに直せば文書が良くなるからである。

### 一致した文字列が入らない抜粋を直す

指摘の位置に付ける抜粋は、行の先頭から60字を切り出していた。
そのため、行の後ろのほうで一致した場合は、一致した文字列そのものが抜粋に入らなかった。
同じ行に複数の一致があると、まったく同じ60字が並んで表示された。
実際に、1行に3件ある指摘で、同じ抜粋が3回表示されていた。これでは、どの箇所を直せばよいか分からない。

一致した文字列を先頭に示し、その前後の狭い範囲を付ける方式に変えた。
範囲の幅は言語によって変える。日本語は14字でほぼ一つの節になるが、英語では同じ字数だと2語にしかならない。
英語は20字とした。この幅は、以前の固定の60字とレポートの総量が同じになる点を選んだものである。

### 標題の番号は、節の連番ではない

M3 は、見出しに手作業で付けた連番を検出する。その理由は、節を増減すると番号を振り直す必要があることである。

この理由は、標題には当てはまらない。ADR は `# 3. 題` という書式を使い、その番号は識別子である。
公開されている ADR 190件のうち、155件がこの書式のせいで発火していた。
先頭の第1階層の見出しを、対象から除いた。発火は155件から11件に減った。

### 自分たちの助言と、自分たちの規則が食い違っていた

`register/prefer-katakana` は、カタカナ語を勧める規則である。
一方、節の同義語には漢語しか載せていなかった。
その結果、`## コンテキスト` と書いた決定の記録に対して、
「文脈の節が無い」と指摘していた。助言に従った文書を、別の規則が受け付けていなかったことになる。
節の同義語に、カタカナ語を追加した。

### 測定の結果

| コーパス | 変更前 | 変更後 |
|---|---|---|
| 参照コーパス60本 | 71,129字 | 61,447字 |
| ADR 60本 | 38,704字 | 30,972字 |
| RFC 60本 | 58,745字 | 58,597字 |
| AI訳39本 | 46,979字 | 42,272字 |

合計では、215,557字から 193,288字になり、1割減った。
減った分は、標題の番号を対象から除いたことと、抜粋の幅を狭めたことによる。
同時に、どの位置の指摘も、一致した文字列そのものを示すようになった。
出力の量を減らしながら、伝わる内容は増えている。

## D-37 語の選択と表記を分け、用語集として外部でも使える形にする

語を選ぶときに自分の語感で決めると、無理に和語を使う方向に偏る。
D-27 では、実際にその誤りを犯している。漢語率を下げようとして、「検証」を「確かめ」に替えた。
`register/rare-wago` は文書に出てしまった和語を検出するが、語を選ぶときの規範は持っていなかった。

[yomiyasu](https://github.com/nanaism/yomiyasu)（MIT License、Copyright (c) 2026 nanaism）
が硬い文章向けに定めた規範を調べたところ、語を選ぶときに使う問いが用意されていた。
文言は引用せず、判断の枠組みだけを参考にして、独自に書き直した。

### 2つの問いを設ける

語を選ぶときは、次の問いを順に適用する。

1. その分野の書き手が、仕様書や手順書を書くときにこの語を選ぶか。
2. 英語に戻したとき、語が一語ずつ対応するか。

2つ目の問いの答えが「はい」で、1つ目の答えが「いいえ」であれば、その語は英語を一語ずつ写した言い方である。

1つ目の問いで大事なのは、繰り返し使われていることを根拠にしない点である。
AI が書いた文書の語は次の文書にそのまま受け継がれるので、同じリポジトリの中で繰り返し使われていても、定着している証拠にはならない。
このリポジトリの文書も AI が書いたものであり、この注意は自分たちにも当てはまる。

### 語の選択と表記を分ける

根拠の出どころが異なるので、語の選択と表記の2つを分けて持つ。

| 種類 | 定める内容 | 根拠 |
|---|---|---|
| `term` | 使う語の選択 | 参照コーパスの頻度と PLaMo Translate の訳語 |
| `orthography` | 語の表記 | JTCA の規約を起点とし、参照コーパスで確認 |

分ける根拠は、実測から得た。PLaMo Translate に同じ語を別々の文の中で訳させると、
`computer` を `コンピュータ` とも `コンピューター` とも出力した。
また、`サーバー`・`ユーザー`・`クラスター` には長音符号を付け、
`ブラウザ`・`パラメータ`・`フォルダ` には付けなかった。

訳語のモデルを使えば語の選択は決められるが、表記は決められない。
表記を決めるには、明文化された規約が必要である。

### 規約と実測の結果が食い違う語がある

JTCA「外来語（カタカナ）表記ガイドライン」第3版は、英語の語尾
-er、-or、-ar、-y を長音符号「ー」で表すと定めている。

参照コーパス438万字で確かめたところ、-er、-or、-ar は規約どおりだった。
一方、-y は規約と逆で、長音符号を付けない表記が多数を占めた（`プロパティ` 870 / `プロパティー` 3）。
`コンテナ` は語尾が -er に当たるが、この分野では長音符号を付けない表記が定着している（1783 / 95）。

そこで、表記は規約から一律に導かず、語ごとに実測で決めることにした。
規約と食い違う語には `measured-against-jtca` と書き、食い違いを記録に残す。

### 用語集は、外部でも使える形で置く

正本は `crates/suikou-core/data/glossary_ja.toml` に置く。
この正本から、`glossary/suikou-ja.prh.yml` と `glossary/suikou-ja.csv` を生成する。

prh の形式を選んだのは、prh が日本語の表記の揺れを直すツールとして広く使われており、
その辞書の形式がそのまま textlint で動くからである。
実際に textlint に読み込ませ、`textlint --fix` で表記を統一できることを確かめた。

### 単独の漢字一字の直訳語は、この規則では扱わない

`glossary/variant` が判定するのは、表記と、複数の文字からなる直訳語だけである。

漢字一字の語（`版`、`枝`、`題`）を部分一致で探すと、「問題」の中の「題」まで検出してしまう。
参照コーパスで「題」を部分一致で数えると613件になるが、
その大半は「問題」「課題」「話題」であり、直訳語の「題」ではない。
正しく判定するには形態素解析が必要である。`prefer-katakana` がすでに形態素の単位で判定しているので、同じ判定を重ねない。

### 自分たちの文書の表記がそろっていなかった

この規則を適用したところ、このリポジトリの4つの文書で `サーバー` と書かれていた。
用語集に従って、`サーバー` に統一した。

参照コーパスでは60文書中7文書、Kubernetes の手順ページでは60文書中10文書で発火する。
これは誤検出ではない。参照コーパス自体に表記の揺れがあり（`サーバー` 591 / `サーバー` 130）、
少ないほうの表記を指摘することが、この規則の役割だからである。

## D-38 表記は語ごとに実測で決め、決まらない語だけ長音符号を付ける

### 文脈

表記の揺れをどう統一するかについて、方針を3回変えた。

最初は、長音符号を付けない形に統一した。`サーバ`、`コンピュータ` のような形である。
次に、長音符号を付ける形に統一したほうが誤りが少ないのではないかと考えた。
JTCA「外来語（カタカナ）表記ガイドライン」第3版（2015年）が、
`-er`、`-or`、`-ar`、`-y` に長音符号を付けると定めているからである。

しかし、どちらの方針も、参照コーパスでの実際の使われ方とは合わなかった。

### 決定

語ごとに参照コーパスで出現数を数え、多いほうの表記を採用する。
数で決まらない語に限って、長音符号を付ける形を既定とする。
数で決まらないとは、多いほうの出現数が少ないほうの2倍に達しない場合か、総数が50件に達しない場合を指す。

### 根拠

参照コーパスに出現する12語、8,540件で、それぞれの方針を比べた。

| 方針 | 実際の表記と食い違う割合 | 表記を誤る語 |
|---|---|---|
| すべて長音を付ける | 45.9% | 5語 |
| すべて長音を付けない | 54.1% | 7語 |
| 語ごとに実測 | 9.5% | 0語 |

一律の方針は、どちらも半分近くを誤る。
参照コーパスでは `サーバー` が多数を占めるが、`コンピュータ` も多数を占める。
一律に統一すると、どちらかの語が必ず実際の使われ方と合わなくなる。

長音符号を付ける形を既定にしたのは、JTCA の規約がその形を定めているからである。
数で決まらない語について、規約と逆の形を選ぶ根拠はない。

### 帰結

表記は、語の選択とは分けて持つことになった。両者は、根拠の出どころが異なる。
語の選択は意味がどこまで限定されるかで決まり、表記は実際の使われ方と明文化された規約で決まる。
`glossary_ja.toml` の `[[orthography]]` と `[[term]]` が、この2つに対応する。

翻訳モデルは、語の選択には使えるが、表記には使えない。
PLaMo Translate は、同じ語に対して、文によって `コンピュータ` と `コンピューター` の
両方を出力した。語の選択では、人間の翻訳者と 90.6% 一致し（200段落）、
食い違った3件はすべて表記の違いであり、語の選び方の誤りではなかった。

実測で扱えない語は残る。参照コーパスに出現しない語は、数えられないからである。
そうした語で判断が止まらないように、既定の形を決めている。

## D-39 README の型では先頭の段落だけを必須とし、書き出しの形を規則にする

### 文脈

AI に文書を生成させると、著者が自分のために残した備忘が README に入り込む。
作業の進み具合、試して分かったこと、文書そのものの目的の宣言といった内容である。
README を読む人は、こうした情報を必要としていない。

Diátaxis は、文書の問題の多くは、一つの内容で複数の目的を同時に満たそうとすることから生じると述べている。
備忘と README は、それぞれ別の目的のために書くものである。

`overview` の型を README に適用できるかどうかは、検証していなかった。
TASKS.md は、この点を未解決の事項として挙げていた。

### 決定

`readme` の型を新しく設ける。必須とするのは、先頭の段落だけである。

`overview` の `usage` を必須から外し、同義語を追加する。

`structure/lead-opener` を設ける。この規則は、文書の書き出しとして避けるべき形を検出する。

### 根拠

広く知られた OSS の README 240件を集めて計測した。
GitHub のスター数で選び、8つのプログラミング言語に分け、1組織から3件までとした。
特定のエコシステムや組織に偏らないようにするためである。集まった README は、199の組織にわたる。

`overview` の型を適用したところ、205件（85%）で必須の節が無いと判定された。
これは、D-31 で `howto` の手順を必須から外したときや、D-32 で `design` の範囲の節を必須から外したときと同じ状態である。

| 節 | 見出しで特定できた割合 |
|---|---|
| 入れ方 | 62% |
| 寄与 | 53% |
| 許諾 | 49% |
| 文書 | 41% |
| 使い方 | 22% |

見出しで特定できる節は、最も多い `入れ方` でも 62% にとどまる。
62% の節を必須にすると、広く知られた OSS の40%を不合格にすることになる。
README は、見出しによって構造を示す型ではない。

README の構造を担っているのは、先頭の段落である。

| 計測した項目 | 値 |
|---|---|
| 先頭に段落を持つ割合 | 78%（187/240） |
| そのうち300字以内 | 83%（156/187） |
| 先頭の段落の字数の中央値 | 121 |
| 最初の見出しの位置の中央値 | 文書の13% |

必須を先頭の段落だけにしたところ、240件のうち発火したのは 11件（5%）になった。
そのうち3件は中国語の README であり、このツールの対象外である。
1件は RxJava で、主題を述べる前に、次のリリースの予定を見出しとして置いている。

同義語に、問いの形の見出しを追加した。`## What's Rails?` がこれに当たる。
`What's new` と一致してしまうおそれがあるが、240件のうち一致してしまうのは1件で、問いの形の見出しを使っているのは21件だった。

書き出しの規則には、先頭の段落 831件で0件だった形だけを採用した。

| 形 | README | Rust RFC | ADR | 参照（英語） |
|---|---|---|---|---|
| 一般論から始める | 0/199 | 0/20 | 0/10 | 0/602 |
| 著者の経緯から始める | 0/199 | 0/20 | 0/10 | 0/602 |
| 文書の目的を宣言する | 0/199 | 0/20 | 0/10 | 0/602 |
| 自己言及 | 1/199 | 0/20 | 0/10 | **37/602** |

日本語でも、参照コーパスの先頭の段落 653件で、表の上の3つの形は0件だった。

自己言及（`本文書は`、`This document describes`）は、規則に含めない。
参照コーパスの英語では6%の文書に出現し、API の説明では自然な書き方だからである。
最も AI らしい書き出しではあるが、実測の結果は、この形が普通に使われていることを示している。

この規則を実際の文書 2,080件に適用したところ、発火は0件だった。
内訳は、README 240、Rust RFC 200、ADR 190、参照コーパスの英語 652、日本語 798 である。

### 帰結

README に備忘が入り込む現象は、語ではなく、書き出しという位置で検出することになった。
`currently` や `TODO` のような語は、広く知られた OSS でも使われている。
240件のうち45件が `currently` を含んでおり、これらの語を禁止する根拠はなかった。

ただし、この計測では、性質の異なる2つのものを同じものとして数えていた。
広く知られた OSS の `currently` や `Roadmap` は、読者に向けた情報である。
予定を知らせ、採用するかどうかの判断を助け、支援を募るために書かれており、著者の備忘ではない。
語で区別できなかったのは当然だった。区別すべきなのは語ではなく、
その文が読者に何を伝えるかである。この区別は D-40 で扱う。

一方、先頭の段落に何を書くかについては、明確な規範があった。
主題を主語にして、それが何であるかを述べる。背景、目的、経緯から書き始めない。

この規則は、備忘そのものを検出するものではない。
文書の途中に書かれた備忘は、この規則では検出できない。
先頭の段落は、読者が最初に読む位置である。
そこを主題から書き始めると決めれば、備忘は文書の後ろのほうに移る。
後ろに移った備忘を取り除くのは、節が答えるべき問いに答える形で書くという規範の役割である。

## D-40 語ではなく、読者に何を伝えるかで区別する

### 文脈

D-39 では、備忘を語で検出する根拠はないと結論した。
広く知られた OSS の README 240件のうち、45件が `currently` を含み、48件が
Status や Roadmap の見出しを持っていたからである。

しかし、この計測では、性質の異なる2つのものを同じものとして数えていた。

広く知られた OSS の `currently` や `Roadmap` は、読者に向けた情報である。
予定を知らせ、採用するかどうかの判断を助け、支援を募る。つまり、読者に次の行動を示している。

AI エージェントが書く備忘は、これとは向きが逆である。
エージェント自身が後で読むための文脈であり、読者に行動を示さない。

同じ語でも、文の中で果たす役割が違う。語で区別できなかったのは当然だった。

### 決定

区別の基準は、その文が読者に何を伝えるかとする。

`structure/work-note` を設ける。この規則は、作業そのものについて述べた文を検出する。
対象は、試した案、作業で分かったこと、作業の段階、以前の状態を述べた文である。

検出するかどうかは、型によって切り替える。
設計文書と決定の記録では、何を試して何がうまくいかなかったかが、伝えるべき内容そのものだからである。
`structure.toml` の `work_notes_ok` が、この切り替えを表す。

### 根拠

広く知られた OSS の README 240件から、前向きの語を含む文 307件を取り出し、文書内の区画で分類した。

| 区画 | 件数 | 率 |
|---|---|---|
| 予告した見出しの下にある | 125 | 41% |
| 説明の地の文に混ざっている | 182 | 59% |

地の文に混ざっていた182件のうち、作業そのものについて述べた文は**0件**だった。
読者に行動を示す文が17件で、残りは機能や予定を述べた文だった。

文を区別するのは、語ではなく、何について述べているかである。

| 形 | README | 参照(英) | 参照(日) | Rust RFC | ADR |
|---|---|---|---|---|---|
| 試した案 | 0.4% | 0.2% | 0.1% | 4.5% | 3.2% |
| 判明したこと | 0% | 0.3% | 0.1% | 7.5% | 1.6% |
| 作業の段階 | 0% | 0% | 0.1% | 0% | 0.5% |
| 以前はこうだった | 0% | 0.3% | 0.3% | 5.0% | 0.5% |

読者に向けた文書では、これらの形は 0.1% から 0.4% しか出現しない。
一方、Rust RFC と ADR では 1.6% から 7.5% 出現する。
同じ形でも、設計文書と決定の記録では、伝えるべき内容になる。これが、型によって検出を切り替える根拠である。

`変更の経緯`（`we refactored`、`移動した`）は、検出する形の候補から除いた。

英語では、11件のうち8件が、読者に参照先を示していた。
`moved to their own repositories`、`renamed Redis Open Source with the v8.0 release` の
ように、どこを見ればよいか、何と呼べばよいかを伝えている。
残りの3件も、FAQ の見出しと、名前の由来についての話だった。

日本語では、`フォーカスを移動した` のような通常の動詞と区別できない。
参照コーパスでは43件が一致し、そのすべてがこの種類の誤検出だった。

実測した発火率は、次の表のとおりである。

| コーパス | 適用した型 | 発火 |
|---|---|---|
| README 240件 | `readme` | 0件 |
| Rust RFC 200件 | `design` | 0件 |
| ADR 190件 | `decision` | 0件 |
| 参照（英語）652件 | `reference` | 3件（0.5%） |
| 参照（日本語）798件 | `reference` | 5件（0.6%） |

### 帰結

同じ文が、型によって、伝えるべき内容にもなり、混ざってはいけない記述にもなる。
たとえば `別の案も試したが、うまく動かなかった` は、README では検出され、
決定の記録では検出されない。

この形を例として示す場合は、コードとして書く。地の文に書くと、検出の対象になる。

この規則は、語を対象にする規則とは性質が異なる。
`register/rare-wago` は語の頻度で判定し、文脈は考慮しない。
`structure/work-note` は、同じ語でも、置かれた文書の型によって判定が変わる。

型を宣言していない文書では、検出しない。
読者に向けた文書かどうかが分からないからである。
`.suikou/structure.toml` の `[paths]` に登録すれば、検出が有効になる。

見出しで区切られた予定や、支援の募集は検出しない。
広く知られた OSS の41%がそのように書いており、読者が読み飛ばせる形になっている。
README から予定の記述を取り除くことは求めない。見出しで予告して書くことを求める。

## D-41 規範の適用の仕方を、文書の型ごとに変える

### 文脈

入り口となる文書と参照の文書に、同じ閾値を適用していた。

広く知られた OSS の README 240件に既定の閾値を適用すると、
`en.mattr100` が 70% の文書で発火した。参照コーパス 652件では 15% である。
`en.simile_marker_per_1k` は、74% の文書で発火した。

発火率が 70% になる指標は、文書の性質ではなく、閾値が文書に合っていないことを示している。
利用者からも、入り口の README と `docs/` 以下の文書とでは求める硬さが違う、という指摘があった。

### 決定

プロファイルに、型ごとの調整を持たせる。
調整では、閾値の差し替え、指標の除外、局所の規則の除外を行えるようにする。

調整には `reason` を必須とする。組み込みの調整が理由を持っていることを、テストで確認する。
調整は利用者と相談した結果を記録する場所とし、ツールが独自に決めるものとはしない。

設定は、組み込みの全体設定、組み込みの型の設定、利用者の全体設定、利用者の型の設定の順に重ねる。

### 根拠

広く知られた OSS の README を実測した。英語は 240件（199組織、8言語）、日本語は 150件（144組織）である。

| 指標 | README | 参照 | 比 |
|---|---|---|---|
| `en.mattr100` | 70% | 15% | 4.7 |
| `en.prose_ratio` | 32% | 11% | 2.9 |
| `en.simile_marker_per_1k` | 74% | 45% | 1.6 |

地の文の割合には、文書の種類によって3倍の差がある。

| コーパス | `prose_ratio` の実測 |
|---|---|
| README 240件 | 0.170 |
| 参照（英語）652件 | 0.427 |
| Rust RFC 200件 | 0.544 |

README は地の文が 17% で、残りは箇条書きとコードである。
参照の文書では 43%、Rust RFC では 54% である。
`en.prose_ratio` の既定の閾値 0.65 を README に適用すると、すべての文書がこの値を下回る。

調整した後の発火率は、次の表のとおりである。参照コーパスの値は変わらない。

| 指標 | README 前 | README 後 | 参照 |
|---|---|---|---|
| `en.mattr100` | 70% | 6% | 15% |
| `en.prose_ratio` | 32% | 7% | 11% |
| `en.simile_marker_per_1k` | 74% | 0% | 45% |

日本語の README 150件では、調整した後の発火率が 0% から 2% の範囲に収まる。

文体の硬さの差は、どの指標でも同じ方向に出るわけではない。

| 指標 | README（日） | 参照（日） |
|---|---|---|
| `ja.kango_ratio` | 0.620 | 0.521 |
| `ja.mattr100` | 0.752 | 0.674 |
| `ja.renyo_te_ratio` | 10.16 | 6.00 |

日本語の README は、参照の文書より漢語率が高い。
名前や機能を列挙するので、漢語が増えるからである。
入り口の文書の条件を一律に緩めるのは適切ではなく、指標ごとに差の方向が異なる。

### 帰結

同じ指標が、型によって異なる閾値で判定されるようになった。
どの文書が何によって判定されたかを追跡できるように、型ごとの調整では指標を追加できないようにした。
指標の追加は、全体設定の上書きで行う。

局所の規則については、型ごとに既定で除外する設定を設けていない。
README で多く発火する `maint/list-lead-in`（340件）と `maint/parallel-items`（271件）は、
明文化されたスタイルガイドに根拠を持つ指摘であり、README に対しても妥当である。
除外の仕組みは利用者に提供するが、組み込みの設定では使わない。

型を宣言していない文書には、調整が適用されない。
調整を適用するには、`.suikou/structure.toml` の `[paths]` に登録するか、フロントマターに `doctype:` を書く。

## D-42 記録をまとめた文書に型を与える。検証では警告まで確かめる

### 文脈

`structure/work-note` を導入した後、このリポジトリの文書で11件の発火があった。
内訳は、`TASKS.md` が7件、`decisions.md` が3件、`metrics.md` が1件である。

このうち10件は、規則の側の誤りだった。
`TASKS.md` と `decisions.md` は、CLAUDE.md が記録を書く場所として指定している文書である。
規則の説明文では「経緯は決定の記録に移す」と述べているのに、
その決定の記録そのものに対して発火していた。

この二つの文書は、どちらも `reference` の型を宣言していた。
`reference` を選んだ理由は、必須の節を持たないという点だけだった。
型の定義が、文書の目的と、必須の節の有無とを、同じ軸で扱っていたことになる。

同時に、検証の方法にも欠陥が見つかった。
`suikou check --quiet` の終了コードは、error があるときだけ 1 を返す。
警告だけのときは 0 を返す。
この終了コードだけですべての文書を確認していたので、47件の警告を見落としていた。
CLAUDE.md が定める合格の条件は、error と warning が一件もないことである。

### 決定

`log` の型を設ける。これは、記録をまとめた文書、すなわち決定の記録の一覧、作業の一覧、
変更の履歴のための型である。`work_notes_ok` を与え、必須の節は定めない。

`TASKS.md` と `decisions.md` を、この型に移す。

検証は、終了コードではなく、指摘の件数で行う。

### 根拠

`log` の型は、新しい検出を追加しない。`reference` の型から条件を緩めるだけである。
外部のコーパスでは計測していないが、適用されない規則が増えるだけなので、誤検出が増える危険はない。

型を移した後、work-note の発火は、3つの文書のすべてで0件になった。
`metrics.md` の1件は残ったが、確かめると、正しい指摘だった。
`代えられるのを最初の節と決めていた時期がある` という文で、
定義を書く文書に経緯を書いていた。この部分は定義の記述として書き直し、経緯は D-31 を参照する形に変えた。

残りの47件の警告は、このリポジトリの文章そのものに対する正しい指摘だった。
新しく書いた節が、特定の語の頻度を押し上げていた。
置き換え先は、参照コーパスでの実測で決めた。

| 使っていた語 | 参照コーパス | 置き換え先 | 参照コーパス |
|---|---|---|---|
| `読み手` | 0件 | `読者` | 13件 |
| `向き` | 54件 | `方向` | 155件 |
| `測る` | 0件 | `測定` | 63件 |
| `要る` | 0件 | `必要` | 3,503件 |
| `入り口` | 1件 | `起点` | 20件 |

`読み手` が参照コーパスに1件も出現しないことは、計測するまで分からなかった。
自分の語感では、この語に問題があるとは感じていなかった。

### 帰結

すべての文書の指摘が、58件から0件になった。

検証の手順を変えた。終了コードは error しか反映しないので、検証には使わない。

```sh
for f in <全 Markdown>; do suikou check "$f" --format text; done | grep -c ':[0-9]*:[0-9]*:'
```

型の定義では、文書の目的と必須の節の有無を、別々に持つ必要がある。
`reference` と `log` は、どちらも必須の節を持たないが、目的が異なる。
`work_notes_ok` は、この違いを表すために最初に設けた項目である。
同じ必要が別の規則でも生じた場合は、項目を追加して対応する。

## D-43 密度の指標には語数の下限を設ける。較正できない指標は型ごとに除外する

### 文脈

D-41 で README の閾値を調整した後、他の型についても測定した。
ADR 190件に `decision` の型を適用すると、`en.mattr100` が 45%、
`en.prose_ratio` が 45%、`en.simile_marker_per_1k` が 75% の文書で発火した。
README の閾値を直す前と同じ状態である。

`en.simile_marker_per_1k` を調べると、原因は型ではなかった。
発火率が、文書の長さに応じて一方向に変化していた。

| 語数 | 発火率 |
|---|---|
| 0 から 400 | 86% |
| 400 から 800 | 47% |
| 800 から 1,250 | 24% |
| 1,250 から 2,000 | 16% |
| 3,000 から 5,000 | 5% |

この測定には、参照コーパス、Rust RFC、ADR の合計 1,042 文書を使った。

### 決定

`en.simile_marker_per_1k` に、語数の下限を設ける。1,250語に満たない文書では、閾値との比較をしない。

`decision` の型では、`en.prose_ratio` を除外する。
`design` と `decision` の `en.mattr100` は、較正した値に置き換える。

### 根拠

下限の値は、理論と実測の両方から導いた。

閾値は1000語あたり 0.8 である。標識1件でこの値に達する語数は、1000 ÷ 0.8 = 1,250 である。
これより短い文書では、標識が0件か、1件で閾値を超えるかのどちらかにしかならない。つまり、値の差を表せない。
実測でも、この境界より短い文書では発火率が急に上がる。

下限の判定は、指標の計算ではなく、閾値と比べる段階に置いた。
密度の値そのものは、語数に関係なく計算できるからである。
こうすることで、ゴールデンテストが参照実装との計算結果の一致を引き続き検証できる。

`ja.renyo_te_ratio` の `MIN_TE_FOR_RATIO` は、割る数が小さいと比を定義できないために設けた下限である。
今回の下限は、値は定義できるが差を表せないために設ける下限である。目的が異なるので、判定を置く場所も異なる。

下限を設けた結果、すべての型で発火率が下がった。型ごとに指標を除外する必要はなくなった。

| 型 | 変更前 | 変更後 |
|---|---|---|
| `readme` | 74% | 14% |
| `design` | 16% | 6% |
| `decision` | 75% | 4% |
| `reference` | 45% | 1% |

参照コーパスの 1% という値は、文書に記録してある人間の範囲（0.84 から 2.54）と矛盾しない。
既定の閾値 0.8 は人間と AI を分ける値として決めたものであり、Tukey の外れ値の境界とは決め方が異なる。
`suikou baseline` がこの指標をどのコーパスでも較正できないと報告するのは、
指標に欠陥があるからではなく、閾値の決め方が異なるからである。

`readme` の 14% は、正しい指摘だった。
発火した34件の地の文の語数は中央値が 2,370 で、発火しなかった57件の 1,241 より多い。
したがって、原因は地の文が少ないことではない。長くて地の文の多い README が、標識を使っていないのである。
そこで、`readme` についても、型ごとの除外を取り消した。

`en.prose_ratio` は、`decision` の型では除外した。
`suikou baseline corpus/cache/adrs` は、較正した値 -0.18 が値の範囲の外に出ると報告する。
分布が広すぎて、境界を設定できない。特定の数値を選ぶのではなく、この型には適用しないと判断した。

既定の閾値の根拠（人間 0.66 から 0.97）は、地の文が主体のコーパスで測ったものであり、
決まった形式の記録には当てはまらない。ADR は節の形式が決まっていて短く、箇条書きが主体になる。

`en.mattr100` は較正できた。`design` が 0.76、`decision` が 0.88 である。
提案の文書も決定の記録も、扱う対象ごとに語彙が変わるので、同じ語の繰り返しが少ない。

調整した後の発火率を、次の表に示す。

| 型 | `mattr100` | `prose_ratio` | `simile` |
|---|---|---|---|
| `readme` | 6% | 7% | 14% |
| `design` | 0% | 4% | 6% |
| `decision` | 0% | 0% | 4% |
| `reference` | 15% | 11% | 1% |

### 帰結

ある指標の発火率が高いとき、その原因は3つに分けられる。

| 原因 | 対処 |
|---|---|
| 文書の長さのせいで、値の差を表せない | 指標に下限を設ける。型は問わない |
| 型によって分布が異なる | 型ごとに閾値を変える |
| 分布が広すぎて、境界を設定できない | その型には適用しない |

最初は型を疑ったが、`simile` の原因は文書の長さだった。
型ごとに除外する対処を先に行うと、他の型に同じ欠陥が残ってしまう。
D-41 で `readme` から `simile` を除外したときは、`decision` で 75% 発火していることに気付いていなかった。
原因を切り分けてから、対処を選ぶ。

日本語の ADR と提案の文書のコーパスがないので、日本語側は調整していない。
`ja.mattr100` と `ja.prose_ratio` は、これらの型でも既定値のままである。

## D-44 LLM が普及した後の GitHub から集めた文書は、人間の参照コーパスにならない

### 文脈

`design` と `decision` の日本語側の閾値は、既定値のままだった。
日本語の ADR と設計文書のコーパスがなかったからである。

そこで、GitHub のコード検索で文書を集めた。95の組織から123件を、平仮名とカタカナが300字以上あることを条件に集めた。
既定の閾値を適用すると、発火率が極端に高かった。

| 指標 | 日本語 ADR 67件 | 日本語 設計文書 56件 |
|---|---|---|
| `ja.mattr100` | 86% | 82% |
| `ja.prose_ratio` | 88% | 87% |
| `ja.list_ratio` | 82% | 82% |
| `ja.renyo_per_1k` | 43% | 39% |

較正すれば、発火率は下がる。しかし、較正する前に、このコーパスが人間の書いた文章かどうかを確かめた。

### 決定

このコーパスでは較正しない。日本語側の `design` と `decision` は、既定値のままにする。

集めたコーパスは残しておく。ファイルごとの更新日で対象を絞れば、使える可能性がある。

今後、人間の参照コーパスを集める場合は、
その文書が LLM の普及より前に書かれたことを確かめる方法を、先に決めておく。

### 根拠

このツール自身の規則を使って、コーパスの汚染を測定した。
`register/rare-wago` は、プロの技術文書で使われない和語が繰り返し使われていることを検出する。
AI の特徴として導入した規則である。

| 群 | `register/rare-wago` | `maint/parallel-items` |
|---|---|---|
| 参照コーパス（概念頁、人間訳）67件 | 4% | 35% |
| k8s 手順頁（人間訳）40件 | 20% | 52% |
| GitHub から収集した手順書160件 | 35% | 61% |
| GitHub から収集した ADR 67件 | 31% | 71% |

GitHub から集めた群では、人間訳よりも AI の特徴が強く出ている。
`register/rare-wago` の発火率は 31% から 35% で、参照コーパスの 4% の8倍である。

この差には、2つの効果が混ざっている。
一つは文書の様式の違い（概念ページと手順ページで 4% と 20%）で、もう一つは書き手の違いである。
手順ページどうしで比べても 20% と 35% であり、様式をそろえても差が残る。

集めた ADR のうち、2023年より前に作られたリポジトリのものは、
サンプル25件のうち8件だった。しかし、リポジトリの作成年はファイルが書かれた年と一致しないので、
作成年だけでは対象を絞り込めない。

汚染された群で較正すると、閾値が AI の文体の側にずれてしまう。
その結果、人間と AI を分けるという閾値の目的とは逆の働きをすることになる。

### 帰結

`suikou baseline` に与えるコーパスがどのような文書かは、利用者が確かめる必要がある。
`baseline` は、与えられた文書を人間の文章として扱い、それを判定する手段を持たない。

このツールには、汚染を測定する手段がすでにある。
`register/rare-wago` と `maint/parallel-items` の発火率を、参照コーパスと比べればよい。
8倍の差が出る群は、人間の参照コーパスとして使えない。

手元にあるコーパスの出どころを、次の表に記録しておく。

| コーパス | 由来 | 人間の文章か |
|---|---|---|
| `pro_ja` 798件 | k8s、mdn、vue、react、rustbook の日本語訳 | 人間訳 |
| `pro_en` 652件 | 同じ出典の英語の原文 | 人間 |
| `rfcs` 200件 | Rust RFC | 人間（提案の時期が LLM 以前を含む） |
| `adrs` 190件 | 公開されている ADR（英語） | 未検証 |
| `readmes` 240件 | 星の数で選んだ README | 未検証 |
| `adrs_ja` 123件 | GitHub のコード検索 | **汚染** |
| `howto_ja` 200件 | GitHub のコード検索 | **部分的に汚染** |

英語側の `adrs` と `readmes` にも、同じ測定を適用した。
`register/rare-wago` は日本語専用なので、代わりに M 系の規則を使った。

| 群 | `maint/parallel-items` | `maint/trailing-etc` |
|---|---|---|
| `pro_en` 652件（参照） | 51% | 4% |
| `rfcs` 200件 | 58% | 17% |
| `adrs` 190件 | 28% | 5% |
| `readmes` 240件 | 43% | 24% |

日本語側で見られた8倍のような差は、英語側では出なかった。
`adrs` は参照より低く、28% 対 51% である。
D-41 と D-43 の較正は、この測定で問題がなかったコーパスに基づいている。

`readmes` の `maint/trailing-etc` は 24% 対 4% で、参照の6倍ある。
しかし、機能の列挙を `etc.` で終える書き方は README の慣習であり、LLM が普及する前から使われている。
スター数で選んだので、古い文書も多く含まれている。この差は、様式の違いと解釈する。

英語側で使えるのは、M 系の規則だけである。
`register/rare-wago` に相当する英語の規則は、D-28 で実装しないと決めている。
そのため、英語で汚染を測定する手段は、日本語より弱い。

## D-45 M2 は、数が後に続く内容を予告している場合にだけ適用する

### 文脈

M2 は、地の文で項目の数を述べる形を検出する。
項目を増減すると、本文と実際の項目が合わなくなるからである。

しかし実装は、地の文に一律に適用するだけで、その数が何を指しているかを判定していなかった。
TASKS.md はこの問題を「リストが続かないただの説明文で数を述べる場合も検出してしまう」と
記録し、`tests/golden/input/ja_prose.md` をその例として挙げていた。

その例は、次の形をしている。

```
無効化の方法は大きく分けて二つある。時間で切る方法と、変更を検知して切る方法である。
```

この例では、数と、その数が指す項目の列挙が、同じ文の中で完結している。
方法を増やす場合はこの文自体を書き直すことになるので、数と項目が食い違う余地がない。

### 決定

この規則は、数が後に続く内容を予告している場合にだけ適用する。予告の手掛かりを3種類定める。

一つ目は、文に `以下`、`次の`、`下記` がある場合である。これらの語は、後に続く内容を予告している。

二つ目は、箇条書き、見出し、表が続く場合である。これらは、その文とは別に編集できる構造である。

三つ目は、列挙の語（`第一に`、`1つ目`、`まず`）を含む地の文が続く場合である。

### 根拠

参照コーパス798件で発火した168件を分類した。

| | 箇条書き | 見出し | 地の文 | 無し |
|---|---|---|---|---|
| `以下`/`次の` あり | 38 | 4 | 14 | 6 |
| なし | 17 | 2 | 81 | 6 |

予告の語がなく、後に地の文が続く81件のうち、列挙の語を含むものは3件だけだった。
残りの78件は、数と項目が同じ文の中で完結している。

最初は、「後に箇条書きが続かない発火」を誤検出として数え、67%という誤検出率を出していた。
これは誤りだった。該当する箇所を読むと、後に見出しが続く場合も、項目を増減すれば本文と合わなくなる。

```
次の3つの命名規則がよく使われます。

### DNSサブドメイン名
```

この例では、規則を1つ増やすと、`次の3つ` が実際と合わなくなる。
数えている対象が箇条書きの項目なのか見出しなのかは、食い違いが起きるかどうかに関係しない。
分かれ目は、数が別の場所にある内容を指しているかどうかである。

### 帰結

参照コーパスで発火する文書が、112文書から67文書に減った。
ゴールデンテストの例も、指摘されなくなった。

規則を適用する範囲を決めるときは、規則の理由から条件を導く。
M2 の理由は「項目を増減すると本文と合わなくなる」ことである。
合わなくなるのは、数と項目を別々に編集できる場合に限られる。
後に箇条書きが続くかどうかは、その条件の一部にすぎなかった。

英語側も、同じ条件にした。`following`、`below`、`these` を予告の語とし、
`first`、`second`、`one is` を列挙の語とする。
英語の参照コーパスでは分類をしていないので、これらの語は日本語側の語に対応させて選んだものである。

## D-46 書く分量の目安は型に持たせる。ただし規則にはしない

### 文脈

型は、どの節を置くかと、各節が答える問いを持っていた。
しかし、どのくらいの分量を書くかは持っていなかった。

### 決定

`check` では、この値で発火させない。規則にはしない。

分量は、絶対的な字数ではなく、節どうしの大小の順序と、内容の構成で示す。

|---|---|---|---|---|---|
| 許諾 | 96 | 212 | 109 から 452 | 0 | 2 |
| 文書 | 91 | 349 | 171 から 854 | 0 | 1 |
| 寄与 | 157 | 386 | 202 から 766 | 0 | 2 |
| 入れ方 | 203 | 455 | 186 から 954 | 0 | 3 |

箇条書きが主体なのは `機能` だけであり、地の文が最も多いのは `設定` である。

## D-47 段階的に導入する提案の型を設ける。節の有無は、見出しの階層に関係なく判定する

### 文脈

設計に関する型は、`design` だけだった。出典は Rust RFC である。

しかし、同じ「設計」でも、求められる内容は異なる。
Kubernetes Enhancement Proposal は、運用の準備について問う。
具体的には、`Test Plan`、`Graduation Criteria`、`Upgrade / Downgrade Strategy`、
`Version Skew Strategy`、`Production Readiness Review` である。
段階的に導入する機能は、これらを決めないと導入できない。

### 決定

`enhancement` の型を設ける。出典は KEP の様式とする。

必須の節は、Summary、Motivation、Goals、Proposal の4つとする。

節があるかどうかは、見出しの階層に関係なく判定する。節の順序は、最上位の見出しだけで判定する。

### 根拠

公開されている KEP 265件を計測した。
19 の SIG から、1 SIG あたり25件までを集めた。
テンプレートを埋めずに残しているものは除いた。402件のうち212件が、これに該当した。

| 節 | 出現率 |
|---|---|
| Summary | 98% |
| Motivation | 95% |
| Goals | 94% |
| Proposal | 94% |
| Graduation Criteria | 92% |
| Implementation History | 91% |
| Non-Goals | 87% |
| Risks and Mitigations | 77% |
| Test Plan | 76% |
| Design Details | 71% |
| Alternatives | 71% |
| Production Readiness Review | 61% |
| Version Skew Strategy | 58% |
| Upgrade / Downgrade Strategy | 57% |
| Drawbacks | 53% |
| User Stories | 39% |

必須の節は、組み合わせで決めた。どれか1つが欠ければ発火するので、節ごとの出現率だけでは決められないからである。

| 必須の組み合わせ | 発火率 |
|---|---|
| Summary | 2% |
| + Motivation | 6% |
| + Goals + Proposal | 9% |
| + Non-Goals | 15% |
| + Graduation Criteria + Test Plan | 29% |

発火率が 9% の組み合わせを採用した。他の型と同じ範囲に収まる値である。

運用の準備に関する節は、必須から外した。
必須から外しても、問いと書くべき内容は残す。plot と brief は、それらの点を引き続き問う。
D-31 と D-32 と同じ扱いである。

### 節の有無を、見出しの階層で判定しない

最初にこの型を適用したところ、265件のうち262件（98%）で発火した。

原因は、見出しの階層にあった。KEP は、`Goals` を `## Motivation` の下に `###` で置いている。
節の照合が最上位の階層だけを対象にしていたので、この節が見つからなかった。

**見出しの階層は書式の選択であり、意味の違いを表すものではない。**
これは、目標が動機の一部であるという書き手の判断であり、節が欠けているわけではない。

D-33 では、この制限を緩めないと決めていた。
その理由は、「下の階層まで照合すると、節の中の小見出しが別の節と一致してしまい、順序の判定が成り立たなくなる」ことだった。

節の有無の判定と、順序の判定を分ければ、この理由は当てはまらなくなる。
節の有無は見出しの階層に関係なく判定し、順序は最上位の見出しだけで判定する。
入れ子になった見出しを最上位の見出しと並べて順序を比べても、意味がないからである。

判定を分けた結果、`enhancement` の発火率は 98% から 8% に下がった。

### 帰結

他の型も、この変更の影響を受けた。どの型でも、発火率は下がる方向に変わった。

| 型 | コーパス | 発火率 |
|---|---|---|
| `readme` | README 240件 | 4% |
| `design` | Rust RFC 200件 | 8% |
| `decision` | ADR 190件 | 7% |
| `enhancement` | KEP 265件 | 8% |
| `howto` | k8s 手順頁 41件 | 0% |

D-33 で挙げていた MADR の11件も、検査を通るようになった。
MADR は `Decision Outcome` の下に帰結を置く様式であり、帰結が欠けていたわけではなかった。

D-33 では、「様式ごとに型を分ける」という対処も挙げていた。
`enhancement` の型を設けたことは、この対処に当たる。
結果として、階層の制限を緩めることと、型を分けることの両方を行った。

型を選ぶためのツリーに、分岐を追加した。
`design` と `enhancement` は、「段階的に導入するか」という問いで分かれる。
すべての型にツリーからたどり着けることを、テストで確認している。

## D-49 文書サイトは Hugo に留める。Zensical は多言語を扱えない

### 文脈

文書サイトを Zensical に移す案が出た。
Material for MkDocs の作者による Rust と Python の生成器である。

この文書サイトは英語と日本語を1つのビルドで出している。

0.1.1 時点の文書が、任意の MkDocs プラグインを実行せず、
MkDocs のプラグイン API も公開しないと述べている。

`mkdocs-static-i18n` は、対応・非対応・予定のどの一覧にも無い。
対応一覧に無い設定は黙って無視される。
Module API は予定されているが、有償の Spark が先に提供される。

ロードマップに `Language organization` と `Language publishing` の項目はあるが、
`Now available`、`In development`、`Up next` の表に入っていない。
ロードマップ自身が、納期も順序も約束しないと書いている。
公式の更新情報は、module system を整えるあいだ 0.x に留まると述べている。

移せるかどうかを判断するため、0.1.1 を入れて試した。
文書に書かれていない点が2つ分かった。再検討する人のために残す。

| 項目 | 結果 |
|---|---|
| サブパスでの公開 | 成立する。相対リンクで出力されるため base-path の設定が不要 |

しかし、`## ライセンス` は数が指す内容ではなく、節がそこで終わったことを示しているだけである。

**数が指せるのは、その数が書かれた節の中にある内容だけである。**
そこで、後に続く見出しのうち、現在の節より深い階層の見出しだけを、予告の手掛かりとして数えることにした。

参照コーパスでの件数は、節の中の見出しが続く場合が1件、同じ階層の見出しが続く場合が1件で、差は出ない。
この変更の根拠は件数ではなく、数が指せる範囲である。
節の最後の段落に数があると必ず発火するという形は、件数が少なくても欠陥である。

この修正は、Rust、textlint、`research/mcheck.py` の3つの実装すべてに入れた。
ゴールデンテストの件数は変わらない。

### 帰結

型の仕組みを自分たちの文書に適用して初めて、見出しが慣習から外れていることが分かった。
計測する仕組みを作っただけでは、自分たちの文書は直らない。仕組みを実際に適用する作業が、別に必要である。

同じ表を、複数の場所に置かない。
`CLAUDE.md` と README のどちらを正本にするかを決め、もう一方は正本を参照する形にする。
