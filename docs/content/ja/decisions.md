この文書は、設計および実装の過程で判断が分かれた論点とその結論をまとめた意思決定記録である。後から読む人が同じ検討を繰り返さずに済むよう、判断が分かれた箇所をその都度追記する。

## D-01 文書全体で測定する指標を textlint に組み込まない

textlint はノードの位置に紐づけて指摘を返す仕組みである。文書全体を対象に算出する指標には、紐づけるべき位置が存在しない。さらに、これらの指標の多くは要素の不足を検出するものであり、形式名詞が少ない、指示詞が少ない、直喩の標識が少ないといった問題には該当箇所そのものがない。

当初は Document ノードに対して報告する textlint ルールとして実装する案を採用したが、この判断は誤りであった。textlint 内に収めると解析基盤が JavaScript に制約され、語種を返す形態素解析器が利用できなくなる。その結果として漢語率を実装できなくなり、実装上の都合で検証済みの指標を破棄することになるため、優先順位が逆転する。

そのため、前面のツールが textlint を呼び出し、独自の文書解析結果と統合する構成を採る。MCP も前面のツール自体から提供すればよい。統合したレポートを一度に返せる分、エージェントにとっても扱いやすい。

## D-02 実装言語は Rust を中心とし、Python は探索と較正に限定する

検証済みの指標はすべて純粋な Rust で実装できる。lindera-unidic が UniDic の全素性を返し、語種と活用形を取得できるためである。

Python を必要としていたのは、分詞節、名詞化、修飾の積み重ね、係り受けの距離といった指標であった。これらはいずれも実測値に基づいて除外した。深い構文解析を要する指標ほど実験設定の影響を受けやすく、先行研究で報告された効果が再現しなかったためである。

この結果を受け、役割を分離する。確定した指標は Rust で実装し、Python の用途は探索と較正に限定する。Python 側で有効性を確認できた指標だけを Rust へ移植する。

また、Claude Code の hooks から Write や Edit のたびに呼び出す運用では、起動コストを無視できない。spaCy の読み込みには2秒から5秒かかるため、本番の実行経路に Python を組み込むことはできない。

## D-03 Markdown パーサを使わず行単位で処理する

`research/` にある参照実装が行単位で処理しているため、ゴールデンテストの測定値を一致させる目的で同じ方式を採用する。外部依存を減らすことで、バージョン差に起因する不具合も抑制できる。

## D-04 形態素解析をトレイトの背後に隔離する

lindera の API や UniDic の素性順序はバージョンによって変化する。バージョン依存のコードを単一の構造体に閉じ込めることで、変更の影響を受けうる範囲を数十行に限定できる。

加えて、既定の feature に lindera を含めない構成とすることで、辞書を取得せずに規則と指標の動作を確認できる。その結果、変更後の検証を高速に行える。

## D-05 起動時に素性の順序を自己検証する

バージョンを固定するだけでは、更新時に気づかないまま動作が壊れる危険が残る。素性の順序が変わると、語種と活用形が誤った位置から読み取られる。処理自体は値を返すものの、内容が不正になる。

漢語率と連用中止は語種と活用形に依存しているため、誤った値のまま処理を続行すると指摘内容そのものが不正確になる。既知の語を入力して起動時に検証を行い、期待値と一致しない場合は異常終了するほうが安全である。

## D-06 文体ごとに閾値を分割しない

常体と敬体で指標の値が変化するかどうかを、二つのモデルの出力を用いて比較した。モデル間で変化の方向が一致せず、一定の効果は確認できなかった。文体による差はモデル間の差に比べて小さく、独立した傾向として識別できなかった。

文体の判定機能自体は残すが、用途は体言止めのような文体依存の規則を適用するかどうかの判断に限定する。閾値テーブルを文体ごとに二重管理する必要はない。

## D-07 形式名詞と漢語率の severity を info に設定する

形式名詞と漢語率は文書の種類による変動が大きい。手順書では形式名詞が閾値に抵触しやすく、概念解説では漢語率が人間ネイティブの値に近づく。さらに、漢語率は扱う話題の影響も強く受ける。

日本語の人間コーパスは解説書に偏っており、手順書のサンプルが不足している。文書の種類ごとのデータがそろうまでは severity を info に設定し、そろった時点で warning に引き上げる。

## D-08 先行研究の効果をそのまま採用しない

英語の分詞節について、人間の5.3倍という先行報告をもとに閾値を9から10と見積もった。しかし実際に測定したところ、人間の分布範囲と重なり判別指標として機能しなかった。名詞化についても同様の結果となった。

この原因は実験設定の違いにあると考えられる。先行報告は人間が書いた文章を提示して同じ文体で続きを書かせるタスクであったのに対し、本プロジェクトでは文書自体を生成させている。

先行研究は仮説を立てる際の参考にはなるが、報告された効果を異なるタスクへそのまま持ち込んではならない。

## D-09 メンテナンス性のレイヤーは人間の平均に合わせない

箇条書きの導入文を適切に記述していたのは AWS S3 ユーザーガイドだけであった。Linux kernel の文書では不完全な導入文のほうが多数を占めていた。人間の平均値に合わせて基準を決めると、このレイヤーは存在意義を失う。

このレイヤーの目的は AI らしさの除去ではない。人間が書いた大半の文書よりも品質を高めるためのレイヤーである。

## D-10 予防で除去できるレイヤーと lint でしか解消できないレイヤーを分離する

フォーマットの癖を抑える指示を与えた条件と与えない条件を比較した。その結果、フォーマット上の問題は完全に解消された一方、語彙や文構造には変化が見られなかった。

メンテナンス性に関する指示でも同様の実験を行った。構成に関する規則は簡潔な指示で完全に遵守されたが、時点依存語は詳細な指示を与えて初めてゼロになった。項目の数、見出しの連番、手動で付与した番号は、指示がなくても発生しなかった。

したがって、`brief` には指示によって遵守できる制約のみを含める。効果のない制約を盛り込むことはトークンの浪費になり、過剰な修正を招く危険もある。

副次的な効果として、メンテナンス性の指示だけで文書指標も改善した。導入文の記述を求めたことで地の文が増え、地の文比率と箇条書き比率が人間の分布範囲に近づいた。

## D-11 語の辞書を同梱せず文書から生成する

比喩のレイヤーにおいて最も難しいのは、生きた比喩と死んだ比喩の判別である。cache や handshake は技術分野で定着した用語であり、比喩ではない。

指摘されて広く知られた語は出現頻度が下がる。2024年の初頭に指摘された語群は、その直後から出現数が減少した。このため、あらかじめ同梱する辞書は陳腐化を避けられない。

対象文書そのものから辞書を生成する方式であれば陳腐化しない。プロジェクトごとに使用語彙が異なる点に加え、陳腐化への対策としてもこの方式が有効である。

## D-12 漢語率のテストは期待値の側を修正した

`kango_ratio_counts_only_content_words` のテストが失敗していた。入力「設定を変更すること」に対して実装は 0.5 を返した一方、テストは 0.5 超を期待していたためである。

`TASKS.md` ではテスト失敗時に実装側を修正する方針を定めているが、この件は例外にあたる。テストのコメントは自立語を「設定」「変更」「こと」の3語と数えていたものの、`FakeMorphology` の仕様では「する」も動詞として含まれるため、自立語は4語になる。漢語率の定義では、分母を自立語のうち語種が和・漢・外・混のいずれかに該当する語としている。したがって動詞「する」も分母に含まれ、実装が返す 2/4 が定義どおりの値であり、実装をテストに合わせると定義に反する。

このテストの目的は、助詞が分母から除外されることの確認にある。期待値を 0.5 との完全一致へ改めても目的は損なわれない。仮に助詞「を」を分母に含めると値は 0.4 になるため、除外の有無は明確に区別できる。

実装を修正すべきなのは実装が定義から逸脱している場合に限られる。期待値が定義と食い違っている場合は、期待値の側を修正する。

## D-13 M2 と M6 は出現ごとにカウントする

参照実装は1行あたりの出現回数を数えていたのに対し、Rust 実装はブロック単位で最大1件しか報告していなかった。`tests/golden/input/en_maintainability.md` に含まれる「The validator currently reports ... The latest release」は1行に2語を含んでおり、参照実装の 2 に対して Rust 実装は 1 を返していた。

検討の結果、出現ごとにカウントする方式を採用した。根拠は本プロジェクト自身の設計制約にある。1行に2件の違反があるにもかかわらず1件しか報告しない場合、指摘された箇所だけを修正しても `check --quiet` が再び異常終了する。レイヤーごとに lint と修正を往復させないという設計方針がここで崩れてしまう。

`Position` に未使用の `column` フィールドが存在していた点も、当初から出現ごとの位置情報を保持する想定であったことを示している。出現ごとに列番号を持たせることで、同一行内の複数の違反を区別できるようになった。

なお、M7 は行末のみを検査するため1行につき最大1件しか発生せず、この変更の影響を受けない。

## D-14 語数と文数は相対誤差で照合する

照合基準として、比率には絶対誤差 0.02、密度には 0.5、M 系規則には完全一致を定めていたが、語数はそのいずれにも該当しなかった。

`en_prose.md` の語数を測定すると、参照実装は 445、Rust 実装は 444 であった。差の原因は `trade-off` の扱いにある。spaCy はこれを三つのトークンに分割して記号を除外するため2語と数える一方、空白区切りでは1語と数える。この文書に含まれるハイフン付きの語はちょうど一つであり、差分と一致する。

これはトークナイザの定義差であって実装の誤りではない。完全一致を課すと、定義が異なる処理に同一の値を求めることになる。相対誤差 1% で照合することで、実質的なずれのみを検出する方針とした。

## D-15 形式名詞の測定対象範囲が参照実装と定義で食い違っている

指標の定義では、語彙指標を地の文とリスト項目の本文の両方で測定すると定めており、形式名詞もその対象に含めている。Rust 実装はこの定義に従っている。

一方で、参照実装の `research/jametrics.py` は、指示詞について地の文のみの値とリスト項目本文を含めた値の両方を算出しているものの、形式名詞については地の文のみの値しか算出していない。

`tests/golden/input/ja_maintainability.md` で実測すると、地の文のみでは 14.98、リスト項目本文を含めると 15.77 となる。差は 0.79 であり、密度の許容誤差 0.5 を超える。

この点について実装側を変更してはならない。定義には明確な根拠がある。出力の大半が箇条書きになるモデルが存在するため、地の文のみを対象にすると本文の8割以上を除外することになるからである。

食い違っているのは閾値の側である。人間の範囲である 11.095 から 11.163、および D5 の閾値 8.5 は、いずれも地の文のみの定義で算出された値である。リスト項目を含めると測定値が増加するため、D5 は較正時よりも発火しにくくなる。D5 の severity を info に設定した判断（D-07）は、この観点からも妥当であった。

再較正を実施するまで、この差異は未解消のままとなる。再較正を行うには、`research/jametrics.py` に地の文とリスト項目を対象とした算出処理を追加し、コーパス全体を再測定する必要がある。

## D-16 辞書を埋め込んだ単一バイナリとして配布する

配布形式を決定するにあたり、辞書を埋め込んだ場合のバイナリサイズを測定した。

| 構成 | サイズ |
|---|---|
| 辞書を同梱したバイナリ | 191 MB |
| 同上を xz で圧縮したアーカイブ | 26 MB |
| 辞書を含まないバイナリ | 1.1 MB |

容量の大半はシンボルではなく辞書データであるため、`strip` を適用してもサイズは削減できない。

辞書を外部ファイルとして配置し、初回実行時に取得する方式も検討した。lindera 6.0.0 には `load_dictionary_from_path` が用意されており、複製せずに読み込むことも可能である。それでも埋め込み方式を選択した。

決め手は運用形態にある。hooks から Write や Edit のたびに呼び出されるツールでは、失敗しうる経路の少なさがそのまま信頼性につながる。外部辞書方式では、ファイルの欠損、破損、バージョン不整合といった障害要因が増える。バージョン不整合は自己診断で検出できるが、検出したところで利用者は処理を続行できない。入手後にネットワーク接続を必要としない自己完結型のほうが、この用途に適している。

配布単位は OS ごとのアーカイブとする。全 OS 向けを一つにまとめると圧縮後でも 78 MB となり、利用者は使用しない OS 向けのバイナリを常に破棄することになるためである。

配布対象は x86_64 の Linux (musl)、Apple Silicon の macOS、x86_64 の Windows に限定した。Linux に musl を選んだのは glibc のバージョン依存を避けるためであり、古いディストリビューションやコンテナ環境で動作しない事態は hooks 経由の実行において支障が大きい。Intel Mac と ARM Linux は対象から除外し、必要な場合は利用者がソースからビルドする前提とした。

## D-17 辞書の feature を既定で有効にしない

`suikou-cli` に `lindera-unidic` を追加したが、既定の feature からは除外したままとした。既定に含めると `cargo test --all` の実行時に辞書が組み込まれ、辞書なしで本体を検証できるという前提（D-04）が崩れるためである。

代わりに、ビルド時と実行時のそれぞれで対策を講じた。配布用ビルドでは feature を明示指定してビルドし、起動して辞書の有無を確認してから梱包する。また、辞書を含まないバイナリで日本語の解析を求められた場合は、`morphology::load` がその場で異常終了する仕様とした。

形態素解析の結果を無言で空として返してはならない。空の結果が返ると、漢語率、連用中止、形式名詞がいずれも 0 になる。0 は閾値を下回るため指摘が出る規則と出ない規則が混在し、結果として「指摘なし」という誤った判定に至る経路が生じてしまう。

どちらのビルドかは `suikou --version` で判別できるようにした。使用しているバイナリの種別を特定できなければ、日本語が解析されない原因を追跡できないためである。

## D-18 配布物の検証は辞書の実体に対して行う

配布用ワークフローを `act` で実行した際に問題が見つかった。梱包されたバイナリのサイズが 1.2 MB しかないにもかかわらず、`--version` の出力には「UniDic 同梱」と表示されていた。辞書自体は 191 MB あるため、両者は矛盾している。

原因はリンカによる未使用コードの削除にあった。すべてのサブコマンドが `todo!()` の状態であったため `morphology::load` への到達経路が存在せず、埋め込んだ辞書データごと削除されていたのである。到達経路を設けて再ビルドしたところサイズは 191.5 MB となり、形態素解析の結果も正しく返るようになった。

スモークテストの設計にも問題があった。`--version` の表示は `#[cfg]` によるコンパイル時分岐にすぎず、feature が有効であることは示しても、辞書が実体として含まれていることは保証しない。そのため、辞書を持たないバイナリでも検証を通過してしまった。

そこで `selftest` サブコマンドを追加し、実際に辞書を読み込んで解析を実行する検証方法へ切り替えた。配布物の確認はビルド設定の有無ではなく、成果物自身の振る舞いに対して行うべきである。これは、自己診断が実際の辞書を使って素性順序を検証しているのと同じ方針に基づく。

副次的な効果として、`morphology::load` への到達経路ができたことで、`crates/suikou-cli/src/morphology.rs` に設けていた抑制を解除できた。利用者にとっても、使用しているバイナリが意図どおりのビルドかどうかを確認する手段となる。

## D-19 指摘の行番号は前処理前の行に一致させる

本プロジェクトの文書に対して `suikou check` を実行した際に問題が見つかった。指摘された行番号が実際の行より4行前を指しており、そのずれは除去したフロントマターの行数と完全に一致していた。

前処理がフロントマターとコードブロックを行ごと削除していたため、後続の行番号が繰り上がり、元のファイルと食い違っていたのである。

対処として、除去した範囲を同じ行数の改行へ置換する方式に変更した。空行は集計対象外であるため、空でない行数や箇条書き比率には影響しない。

lint の指摘は、利用者が開いているファイルの該当行を正確に示せなければ意味をなさない。算出値が正しくても位置がずれていては、指摘として機能しない。

## D-20 ドキュメントを Hugo サイト化し、既定の言語を英語にする

ドキュメントの配置を `docs/` 直下から `docs/content/{en,ja}/` へ移行し、既定の言語を英語とした。

外部テーマは導入せず、最小限の独自レイアウトを使用する。依存関係を増やさないことに加え、バージョンを固定するという本体の方針をドキュメント側でも維持するためである。

ドキュメントの正本を一つに定めたことで、サイトとリポジトリで同一の内容を二重管理する必要がなくなった。

## D-21 brief の詳細度はプロファイルではなくフラグで指定する

設計文書には、brief の詳細度をプロファイル設定に含める案が記載されている。しかし実装ではこの案を採らず、`--detail concise|balanced|detailed` フラグのみで制御する方式とした。

Profile は指標の閾値を保持するための構造体である。ここに brief 専用の設定を加えると、構造体が二つの責務を抱えることになる。較正によって書き戻す値と出力形式のみを選ぶ値が混在すると、`suikou baseline` が更新すべき範囲が曖昧になるため、閾値の保持という Profile 本来の責務を保つ方針を選んだ。

フラグの水準も当初の計画から見直した。`TASKS.md` の初期案では concise と detailed の二つだけを挙げていたが、実装を進める中で中間に balanced を設けるほうが自然だと判断した。構成規則を1文で簡潔に示しつつ時点依存語のみをすべて列挙するという brief の要件は、中間の balanced にそのまま収まる。concise はそこからさらに簡略化した形式とし、detailed には各規則の理由まで含めた。

プロファイルへ移す案は未決定事項の一覧に残している。用途ごとに既定の detail 水準を切り替えたいという要望が実際に生じた段階で、移行の是非を判断する。

## D-22 baseline の閾値は Tukey の外れ値境界で決める

`suikou baseline` の実装にあたり、閾値の算出方法を定める必要があった。`docs/content/ja/design.md` では、閾値を人間の範囲の上限と AI の範囲の下限の間に設定すると規定している。しかし baseline が参照できるのは人間コーパスのみであり、AI 側の分布は得られない。そのため、人間の分布自体を基準として外れ値とみなせる境界を求める方針を採用した。

算出手法には Tukey の外れ値境界を採用した。第1四分位と第3四分位の差を四分位範囲とし、四分位の外側へ四分位範囲の1.5倍を加えた点を境界とする。1.5 という係数は Tukey (1977) における「外れ値」の定義に用いられており、統計学で広く認知されている。独自に恣意的な余裕幅を設けるよりも、確立された定義に従うほうが根拠を説明しやすいと判断した。より緩やかな 3.0倍の「極端な外れ値」という定義もあるが、サンプル数が少ない用途では境界が外側に広がりすぎて較正の効果が薄れるため採用しなかった。

四分位の計算には hinge 法を用いる。サンプルを中央値で二分し、それぞれの半分の中央値を第1四分位と第3四分位とする。サンプル数が奇数の場合、中央値そのものはどちらの半分にも含めない。線形補間を用いるパーセンタイル法も選択肢にあるが、hinge 法は手続きが単純であり、テストの期待値を手計算で検証しやすい。

サンプル数が4件未満の指標は較正対象から除外することとした。3件以下では上半分または下半分のいずれかが1件のみとなり、四分位範囲が分布の広がりではなく個別の値によってほぼ決まってしまう。較正できない指標を 0 や仮の値で補完して出力すると、利用者が根拠のない閾値に気づけない。そのため、該当指標は出力から除外し、理由を標準エラーへ出力する仕様とした。

初期実装には欠陥があった。below 方向の指標は、比率や千字あたりの出現数のように値域が 0 以上に限られる。サンプルが狭い範囲に集中していると、Q1 - 1.5*IQR が 0 を下回る。実際に本ツールの日本語ドキュメント（`docs/content/ja/*.md`、`README.ja.md`、`CLAUDE.md`、`TASKS.md`）をサンプルとして較正したところ、`ja.demonstrative_per_1k` の境界は -4.96、`ja.keishiki_meishi_per_1k` の境界は -4.98 となった。

密度と比率は負の値をとらないため、これらの境界を下回る実測値は原理上存在せず、`check::evaluate` における below の判定条件（value < threshold）を満たす文書は現れない。にもかかわらず出力自体は有効な TOML として読み込めてしまう。そのため、この閾値を含むプロファイルで `suikou check` を実行すると指摘ゼロが返り、指摘ゼロのみを確認する検証ではこの欠陥を較正成功と誤認していた。

境界を 0 にクランプする案は採用しなかった。境界を 0 にしても密度と比率はもともと 0 以上であるため、value < 0 を満たす実測値はやはり存在せず、閾値が発火しない状況は変わらない。代わりに、below の境界が 0 以下になった場合は較正失敗とみなす方針とした。サンプル不足のときと同様に、該当指標を出力から除外し、理由を標準エラーへ出力する。

above 方向には同様の処置を行っていない。below の下限（0）はすべての指標に共通する一方、above の上限は指標ごとに異なる。比率の上限は 1 であるのに対し、千字あたりの出現数には固定の上限がない。指標ごとの上限を較正ロジックへ組み込むと指標固有の知識が混入するため、対象を below のみに限定した。

`guidance`、`direction`、`severity` は同梱の oss プロファイルからそのまま引き継ぐ仕様とした。baseline 実行のたびに文面を複製すると、oss.toml を修正した際に baseline 出力側だけ古い内容のまま残る経路が生じるためである。較正の対象は value のみに限定した。

`corpus/fetch.sh` で取得できるコーパスは実行環境になく、ライセンス上の理由からリポジトリにも含めていない。そのため、この算出方法で `corpus/baselines.toml` や同梱プロファイルと同程度の桁の値が得られるかどうかは未確認である。また、`tests/golden/input/` の文書は件数が少なく指標ごとのサンプル数が4件に満たないため、代替の検証も行えない。コーパスを配置できる環境で実行して照合するまで、TASKS.md に未検証項目として残す。

なお、較正に成功した below 方向の閾値が実際に機能することは確認済みである。先述のドキュメント群をサンプルとして較正結果に残った `ja.prose_ratio`（境界 0.69）を含むプロファイルを作成し、`suikou check --profile` を実行した。その結果、箇条書き主体の文書では発火し、地の文のみの文書では発火しないことを実測で確認した。
## D-23 textlint プリセットの実装における設計判断

`packages/textlint-rule-preset-tech-maintainability`（T7）の実装では、個別の方針決定を要する論点が複数生じた。各判断の内容と根拠を順に整理する。

**標準設定で textlint が表示するルール ID の接頭辞は `maint/` にならない。**
仕様では Rust 側の命名に揃えて `maint/list-lead-in` のような形式が求められていた。しかし `@textlint/config-loader` の `loader.js` と `@textlint/utils` の `normalizeTextlintRulePresetKey` を確認すると、プリセットの接頭辞は `.textlintrc` の設定キーから先頭の `preset-` を除去した文字列に決まる。このパッケージを標準どおり `"preset-tech-maintainability": true` として読み込むと、出力される ID は `tech-maintainability/list-lead-in` となる。設定キーは `preset-` で始まるものだけがプリセットと認識され（`isPresetRuleKey` の規定）、認識時には必ず `preset-` が除かれるため、標準の読み込み経路では `maint/` という接頭辞を実現できない。

各ルールの個別名（`list-lead-in` にあたる接頭辞以外の部分）は仕様どおり Rust 側に一致させた。接頭辞だけを変更するには npm パッケージ名を `textlint-rule-preset-maint` のように変更するしかないが、それでは配置ディレクトリである `packages/textlint-rule-preset-tech-maintainability` と名称が食い違い、構成が把握しにくくなる。そのためパッケージ名はディレクトリ名に合わせたままとし、実際に表示される ID が `tech-maintainability/` 接頭辞になる旨を README に明記した。なおゴールデンテストの照合では `@textlint/kernel` を直接呼び出して `maint/` 接頭辞で手動登録しているため、この制約を受けない（`test/support/lint.js`）。

**AST を介さず行ベースで解析する。**
textlint は Markdown を段落や見出しなどのノードへ分割し、ソフトラップで複数行にまたがる段落も単一の Paragraph ノードとして統合する。一方、`markdown.rs` の `Document::parse` は行単位でブロックを生成し、ソフトラップによる継続行も独立した行として処理する。この違いは、`en_maintainability.md` の14〜15行目のようにひとつの文が2行にまたがる段落で問題になる。ノード単位で検査すると2行分の文字列が連結され、Rust 側の実装では対象にならない語の並びが正規表現に一致してしまう。

検討した方針は、textlint の Paragraph ノードの文字列をそのまま検査する方法と、`Document::parse` と同一の行ベース解析を JavaScript へ移植し、textlint からは原文テキストのみを受け取る方法である。前者は textlint の標準的な設計に沿うものの、ノード粒度の違いによって検出件数が一致しなくなる。

採用したのは後者である。`src/lib/blocks.js` に `markdown.rs` の `preprocess`・`strip_inline`・`Document::parse`・`list_blocks`・`block_before` を正規表現も含めてそのまま移植した。各ルールは `context.getSource(node)` で原文を取得し、自前のブロック抽出を通してから検査を行う。この構成では、textlint はファイル読み込み・設定管理・診断報告の統合だけを担当し、文書構造の解析は行わない。

この方式の制約として、報告される行・列番号は前処理後の文字列を基準とする。エスケープの解除やインライン記法の除去により、前処理後の位置と原文上の位置がずれる場合がある。そこで `src/lib/position.js` は、対象行の中から一致文字列を順に検索し、原文の文字インデックスへ近似的に対応付ける。この処理は指摘の見落としを防ぐための近似であり、正確な位置までは保証しない。`tests/golden/` との照合も件数の一致のみを検証対象とし、位置精度は条件に含めていない。

**IPADIC では UniDic の体言4分類が単一の品詞に集約される。**
M1・M5の日本語ルールは、行末や項目末尾のトークンが体言止めになっているかを判定する。suikou-core は UniDic を採用しており、品詞大分類が名詞・接尾辞・代名詞・形状詞のいずれかに該当する語を体言として扱う。これに対し、textlint 環境で広く使われる kuromojin は IPADIC を用いており、この4分類を持たない。

kuromojin 3.0.1 で実測したところ、UniDic で接尾辞・代名詞・形状詞に分類される語は、IPADIC ではいずれも名詞の下位分類（品詞細分類1が代名詞・接尾・形容動詞語幹）として出力された。具体的には、「これ」は名詞/代名詞、「委員長」の「長」は名詞/接尾、「静か」は名詞/形容動詞語幹であった。したがって IPADIC 上では、pos が名詞であるかどうかという単一の条件で体言を判定できる。`src/lib/morphology-ja.js` の `isTaigen` はこの実測結果に基づいている。

連用形の扱いも実測で確認した。UniDic は「連用形-一般」のように活用形を細分化するが、IPADIC は単に「連用形」を返す（「使い」「し」で確認した）。そのため Rust 側の `cform.startsWith("連用形")` という判定条件をそのまま移植しても支障がない。

**診断メッセージの言語は対象文書の言語に合わせる。**
Rust 側の実装はメッセージを日本語に固定している。suikou-core の `finding()` は英語文書に対しても日本語のメッセージを返すことを、`en_maintainability.md` に対する `suikou check` の出力で確認した。

textlint プリセットの利用者には英語文書のみを執筆する人も含まれる。日本語だけのメッセージでは、そうした利用者にとって指摘内容を活用できない。判定ロジックと正規表現は Rust 側と完全に一致させつつ、メッセージだけは検出した文書言語に応じて日本語と英語を切り替える設計とした。両言語の文面は `src/lib/messages.js` に定義している。ゴールデンテストの照合は件数のみを比較するため、メッセージ言語の違いは完了条件に影響しない。

**テストには textlint-tester ではなく node:test を直接用いる。**
textlint-tester は Mocha の `describe` と `it` がグローバルに存在することを前提としている。それらが未定義の環境では、`method.apply(this)` を呼び出すだけの代替実装にフォールバックする。この代替実装は `testValid` や `testInvalid` が返す Promise の完了を待たないため、`node --test` 上でそのまま実行すると、lint の完了前にテストが成功扱いになるケースがあった。

Mocha を依存関係に追加して textlint-tester を使う案と、`@textlint/kernel` を直接呼び出す最小限のヘルパーを書く案を比較した。依存パッケージを増やさない方針を採り、`test/support/lint.js` に `TextlintKernel` をラップする数行のコードを実装した。プリセットの全ルールを `maint/` 接頭辞付きで登録し、`async/await` で非同期に結果を待つ構成としたことで、`node --test` の非同期テストとして正常に動作する。

**`@textlint-ja/textlint-rule-preset-ai-writing` の `no-ai-colon-continuation` と重複する指摘は抑制しない。**
同ルールはコロンの直前が述語で終わる文を kuromojin で検出しており、判定構造が M1 の日本語版と類似している。

ただし両者の目的は異なる。同ルールは AI 生成文特有の文体を対象とし、本プリセットは項目の増減に弱い箇条書きの構造を対象としている。それでも同一行が双方から指摘される場合があるが、一方を優先して他方を抑止する仕組みは設けていない。両プリセットを併用する利用者は双方の指摘を比較して取捨選択できる立場にあり、片方を抑止すると判断材料が減ってしまうためである。この重複については README に明記した。

## D-24 terms の抽出は品詞だけでなく構造上の条件で語を区切る

日本語の用語抽出では、連続する名詞をひとつの複合語としてまとめる。UniDic は「素」や「性」といった接尾辞を pos1 が接尾辞となるトークンとして分割するため、名詞のみを対象にすると「形態素解析」が「形態」と「解析」に分断され、「メンテナンス性」も「メンテナンス」だけになってしまう。この問題は、このリポジトリ自身の文書へ適用した際に判明した。

一方で、接尾辞を名詞と同等に扱うと「つ」のような助数詞まで複合語の先頭に現れる。UniDic の素性情報だけでは助数詞のみを厳密に識別できないが、専用の助数詞リストを別途用意する方針は採らなかった。代わりに、直前に名詞の連続が存在する場合に限り、接尾辞でその連続を延長する規則とした。数詞によって名詞の連続が途切れた後の接尾辞は単独で語を構成しないためである。

UniDic は空白をトークンの区切りとして消費し、トークン自体には残さない。そのため半角語が隣接するトークンをそのまま連結すると、原文に存在しない語が生成される。実際に、`design.md` の複数箇所に含まれる「Linux kernel」が「Linuxkernel」として抽出される現象を確認した。対策として、半角英数字のトークン同士が隣接する場合には間に空白を1個挿入し、半角語と日本語語が隣接する場合（「API仕様」など）は空白を入れないこととした。日本語の文章では後者の組み合わせに空白を入れない表記が一般的なためである。

一般語の除外には `metrics/ja.rs` の `KEISHIKI_MEISHI` を流用し、別の除外リストは作成しない。一般語が用語一覧に混入しても比喩判定から除外されるだけで悪影響は小さいが、専門用語を見落とす悪影響は大きい。見落としを防ぐ側を優先した判断である。

このリポジトリ自身の文書へ適用したところ、1字の候補が上位を占めた。抽出された395語のうち54語が1字であり、上位20語は文(50)、形(49)、語(48)、指示(43)、値(36)に続き、地(28)、数(27)を経て、`版`(22)、行(22)、`層`(20)まで並んだ。「地」は「地の文」が「の」で分断された断片であり、残りはどのような文章にも高頻度で現れる分野非依存の一般語である。

個別の語を列挙する除外リストは作らない。選定基準が主観に頼ることになるためである。代わりに抽出結果の文字数という構造上の条件のみで絞り込み、1字の候補を除外した。

日本語の専門用語抽出では1字候補を除外する手法が広く採られている。専門的な意味を表す語の多くは複数文字の複合語であり、1字語は最小形態素として多義化しやすく単独では分野を特定できないためである。なお、「文書」のような2字の1トークン語はこの除外対象にならない。この条件を適用した結果、このリポジトリ自身の文書における上位語は、指示、規則、指標、人間、文書、日本語、指摘、閾値、辞書、実装へと変化し、1字語はすべて除かれた。

英語側には形態素解析器も文分割処理も用意していない。そのため、すべて大文字の頭字語、文頭以外の大文字始まり語、および単一の識別子形式をとるインラインコードを手掛かりに抽出する。ただし表の行は抽出対象から除外した。このリポジトリの文書で検証したところ、表のセルは文の形式をとらないため文頭判定が機能せず、さらに同一の値が複数行で繰り返されて出現回数の下限も超えてしまうことが分かったためである。

見出しの先頭に ID が並ぶ形式でも同様の問題が生じた。`decisions.md` の見出し「D-04 The tokenizer hides behind a trait」では、先頭の語だけを文頭とみなすと後続の The を文中の大文字始まり語と誤認した。これを防ぐため、先頭から ID 形式の語が連続する間は文頭扱いとするよう修正した。

見出し先頭に複数の ID 形式語が連続するケースには別の課題が残っている。英語版の `decisions.md` にある見出し「D-13 M2 and M6 count every occurrence」では、`D-13` と `M2` の間に区切り記号がないため、隣接語が単一の複合語「D-13 M2」へ結合される。その結果 `M2` 単独の出現回数が減り、下限を下回る場合がある。ただしこれは見落としであって原文にない語を生成する誤りではないため影響は小さく、修正は採らなかった。修正するには隣接する ID 形式語をどこまで一語とみなすかの基準が必要だが、「AWS S3」のように隣接する頭字語を結合して初めて意味を成す固有名詞を壊さずに解決する規則は未確立である。

出現回数の下限は既定で2とした。1回しか現れない語では専門用語か偶然の表現かを判別する材料がなく、terms のもうひとつの目的である表記・用語の一貫性確認も反復出現があって初めて成立するためである。この値は実測ではなく、これら双方の目的から導いた下限である。

この抽出結果は比喩検出レイヤーの入力として利用する想定である。比喩検出レイヤーは未実装であるため、抽出精度の最終評価はその実装時に行う。

## D-25 MCP は依存を増やさず JSON-RPC を自前実装し、daemon は設けない

T9 では、MCP サーバーの実装方式と常駐プロセスの要否を決める必要があった。

**MCP サーバーは `serde_json` のみで実装した。**
選択肢は、`rmcp` のような専用クレートを追加する案と、`initialize`・`tools/list`・`tools/call` の3種類だけを手書きで実装する案であった。

実装が必要なリクエストはこの3種類に限られ、MCP 仕様のうち resources・prompts・サーバー発の通知は利用しない。専用クレートを導入すると未使用機能まで含めてバージョンを固定することになり、依存を `=` で厳密固定して更新ごとに `verify_schema` を実行する本リポジトリの管理コストに見合わない。`serde_json` は両クレートに導入済みであるため、追加の依存は0で済む。stdio トランスポートも、1行につき1つの JSON-RPC メッセージを送受信する単純な形式で十分である。実装は `crates/suikou-cli/src/mcp.rs` に配置し、解析処理自体は `check::analyze` と `brief::run` を呼び出す構成として CLI と MCP 間のロジック重複を避けた。

**daemon は実装しない。**
常駐化を想定した当初の根拠は辞書の再読み込みを避ける点にあったが、T2 の実測値（release ビルドで 0.68〜0.70 ミリ秒）はその根拠を支持しなかった。TASKS.md ではプロセス起動そのもののコストを別途計測したうえで判断すると定められていたため、release ビルド（`--features lindera-unidic`）を用いて短い文書に対する `suikou check` を50回実行し、壁時計の経過時間を計測した。比較対象として `suikou --version` も50回計測した。WSL2 環境での実測値を以下に示す。

| コマンド | 平均 | 最大 |
|---|---|---|
| `suikou --version` | 約1.5〜1.6ミリ秒 | 約1.9〜2.4ミリ秒 |
| `suikou check`（辞書あり、短い文書） | 約3.7〜3.9ミリ秒 | 約4.3〜4.7ミリ秒 |

`--version` は辞書を読み込まないため、その所要時間はバイナリ起動そのもののコスト（約200MBの実行ファイルの読み込み、動的リンク、引数解析）を示す。`check` との差分は2ミリ秒台であり、辞書読み込み（0.7ミリ秒）と短い文書1件の形態素解析・指標計算の合計にあたる。いずれの時間も、hooks 経由で Write や Edit のたびに起動する運用において、LLM の1ターンに要する秒単位の応答時間と比べれば無視できる水準である。

常駐プロセスを設けると、ソケットや名前付きパイプの管理、ファイル変更の検知方法、複数クライアントからの同時呼び出しの直列化といった複雑さが増える。それに見合う高速化の恩恵が得られないため、daemon は実装しない結論とした。ただし `suikou daemon` サブコマンド自体は残し、実行時に上記の実測値と判断理由を表示して終了する仕様とした。CLI から無言で削除するよりも、非実装である理由を利用者へ直接伝えられる利点を優先したためである。

## D-26 文体から外れた和語を参照コーパスとの頻度比較で検出する

生成モデルは、英語から日本語へ翻訳する際に漢語を和語へ置き換える傾向がある。「確認する」が「確かめる」に、「必要である」が「要る」になる例がそれにあたる。技術文書の文体としては軟らかすぎ、速読の妨げになる。

文体に適した語を判定する手段として、語の置換対応表は作成しない方針とした。対応表による管理では、分野ごとに異なる表現方針を網羅的に列挙しなければならなくなるためである。代わりに、プロの日本語訳コーパスにおける出現頻度との比較によって逸脱を検出する方式を採った。

対応表を作らない判断は実測結果でも確認できた。Kubernetes の文書だけを対象にすると、「使う」は Sonnet 訳に320回、プロ訳に33回出現し、「使う→使用」のような置換規則を設けたくなりやすい。ところが対象分野を Kubernetes、MDN、Vue へ拡張すると、プロ訳でも「使う」が461回現れる。同様に「次→以下」「仕組み→メカニズム」「既定→デフォルト」といった候補も棄却された。MDN が「既定」を採用しているように、表現の方針は分野ごとに異なる。

判定には Dunning (1993) の対数尤度比と Hardie (2014) の Log Ratio を併用する。対数尤度比で統計的な有意性を確認し、Log Ratio で偏りの大きさを測定する構成である。有意性のみを基準にすると、一般的な語をわずかに多く使っただけでも有意と判定されてしまうため、効果量の確認が欠かせない。

Log Ratio の閾値は実測によって定めた。参照コーパスに含めていないプロの日本語訳12頁と、このリポジトリの日本語文書とで分布を比較したところ、閾値4ではプロ訳に9語、閾値6では1語の誤検出が生じ、閾値7でゼロになった。設計方針上、人間が執筆した文書への警告は偽陽性とみなす。見落としは許容する一方で、プロの文書に対する誤検出は許容しない基準に揃えた。

参照コーパスの構築では、入門書を混ぜてはならない。Rust Book の日本語訳には「確かめる」が36回含まれており、混在させると参照データへ入り込んでしまう。これは、文書種別の違いによる差が文体の違いによる差より大きいという計測結果とも整合する。

あわせて、2分野以上に出現する語のみを参照データへ収録する条件を設けた。一つの分野だけに出現する語は分野固有の表現であり、汎用的な参照基準には適さないためである。

分野で定着している固有の語を許容するため、`.suikou/register-allow.toml` を用意した。参照コーパスは Web 関連の文書から構成されており、計算や統計に関する語彙が不足している。その偏りをプロジェクト側で補う仕組みであり、辞書を同梱せず対象文書側から補完する点は D-11 と同じ設計方針である。

## D-27 漢語率の指示文は誤りだった

D7 の指示文は当初「漢語を和語動詞に開く」としていたが、この指示は実測結果に反していた。

プロの日本語訳とこのリポジトリの文書について、自立語の語種構成を比較した結果を以下に示す。

| | 和 | 漢 | 外 | 混 |
|---|---|---|---|---|
| プロの日本語訳 | 0.384 | 0.329 | 0.280 | 0.007 |
| このリポジトリ | 0.470 | 0.463 | 0.050 | 0.017 |

プロの訳文で漢語率が低いのは、漢語を和語へ言い換えているからではない。定着したカタカナ語を用いているためであり、和語の比率自体はむしろプロ訳の方が低い。この結果を受け、指示文を「定着したカタカナ語を使い、漢語の名詞を連ねない」へ変更した。

誤った指示がもたらした悪影響は大きかった。元の指示に従って文書を書き換えた結果、「検証」が「確かめ」に、「制約」が「縛り」に、「抽出」が「取り出し」へ置き換わり、技術文書としての文体が劣化した。D-26 の規則は、この劣化を検出するために導入したものである。

指標の数値を最小化すること自体を目的にしてはならない。D7 の severity は info であり、あくまで参考値に過ぎない。その値をゼロにしようとした点に根本的な誤りがあった。文書が満たすべき条件は error と warning が発生しないことまでとし、info は参考情報として確認するにとどめる。

## D-28 文体検出の規則は英語へ適用できなかった

D-26 と同じ手法を英語にも適用できるか検証するため、異なる実験を実施したがいずれも成立しなかった。このため、英語向けの文体規則は実装しない。

最初に試したのは、対象文書と参照コーパスの語彙頻度を比較する方式である。Kubernetes、MDN、Vue の英語原文652頁・51万語から頻度表を作成し、日本語と同じ統計手法で評価した。しかし、参照に含めていないプロの英語文書14頁に対する誤検出は、閾値を9まで引き上げても20語残った。上位に現れたのは双方とも分野固有の用語であり、プロ文書側では portworx、cinder、ebs、このリポジトリ側では prose、corpus、metric であった。3分野すべてに出現する語のみへ絞り込んでも、プロ文書側には operations のような話題依存の語が残った。

原因は語彙体系の構造にある。日本語では「語種が和である」という条件によって、漢語やカタカナ語で構成される専門用語をほぼ機械的に除外できていた。英語の語彙にはそのような区別が存在しない。ある話題を扱う文書はその話題に関連する語を一般コーパスよりはるかに高頻度で使うため、出現頻度だけでは話題の語と文体上の語を分離できない。

次に試したのは、話題を完全に揃えた比較である。プロの日本語訳を LLM で英語へ逆翻訳させ、元の英語原文と対照した。対象は36頁、各3万語である。

この比較では有意な差を示す語が1語も出なかった。臨界値 15.13 に対して、最大値は your の 13.2、次点が will の 11.1 であり、いずれも原文側の方が多い。語彙選択が逆方向へ偏っているわけでもない。日本語で同一の実験設計を用いた際は「使う」が 320 対 33 となり、対数尤度比が 320 に達していたのとは対照的である。

この結果は D-08 と同じ教訓を示している。先行研究の効果量を異なるタスクへそのまま持ち込めないのと同様に、ある言語で成立した検出手法を別の言語へそのまま転用してはならない。

なお、ここで検証したのは語彙選択のみである。英語向けの指標として採用している MATTR、地の文比率、直喩の標識は別の側面を測定するものであり、これらは維持する。

実験の再現手順は `research/lexshift/` に保管している。英語の頻度表を生成する `build_reference_en.py` と、逆翻訳を行う `translate_back.sh` である。同じ検証を繰り返さないよう、成立しなかった実験のコードも残している。

## D-29 カタカナ語が優勢な漢語は対応表で置換する

D-26 では、分野によって優勢な表現が逆転する語があるため対応表を作らないと決めた。漢語とカタカナ語のペアについてはこの判断を変更し、一部の反例があっても分野横断の合計でカタカナ語が優勢であれば、そちらへ統一する方針とした。

同義ペアを機械的に抽出する手法は複数試したうえで採用を見送った。英語原文を基準に段落単位の共起からペアを結ぶ方式では、同義語ではなく連語が抽出されてしまう。実際に「永続ボリューム」や「ポート番号」のような組み合わせが得られた。リフト値と Dice 係数のいずれを用いても結果は変わらず、共起からは同義性を判定できなかった。置換関係は共起ではなく同一文脈での交替関係であり、段落単位の統計では捉えられなかった。

そこで候補の列挙と採否の判定を分離した。候補の選定は人間が行い、採否の判断は実測値に委ねる構造であり、D-26 と同じである。97組の候補を検証した結果、53組を採用した。

採用基準は、カタカナ語側の出現回数が漢語側の2倍以上であること、双方の合計が20回以上であること、さらに漢語側の出現回数が60回以下であることとした。

漢語側の上限を設けたのは多義語を除外するためである。実測すると「対象」「対応」「状態」「場合」はプロの訳文でも高頻度で使われているが、必ずしも対応するカタカナ語と同一の意味で用いられているわけではない。このリポジトリでも「対象」は扱う範囲を指しており、オブジェクトの意味ではない。プロ訳でその漢語がほとんど使われていないペアに限定することで、置換候補としての信頼性を確保できる。

直前のトークンが名詞である場合は複合語の一部とみなし、置換の対象外とする。たとえば `英語版` や `第3版` に含まれる `版` を置き換えると誤りになるためである。

特定の分野で別義として使われる語は `.suikou/register-allow.toml` で除外する。このリポジトリでは「記録」「一覧」「比率」「経路」「分岐」「実体」を除外リストに登録した。たとえば「比率」は漢語率や地の文比率を指す語であり、レートの意味では使っていない。

## D-30 文書構造を検証し、執筆前にテンプレートを提示する

文単位の規則だけでは構造に不備のある文書を修正できない。必須の節の欠落、論理展開の乱れた順序、一段落に複数の主張を詰め込んだ構成は、一文ずつ検査していても検出できないためである。

構造に関する規則は言語を問わず適用する。節の構成・順序・段落の単位は文書の論理構造に属する性質であり、特定の語彙体系には依存しないためである。実測でもこの前提を確認できた。7文以上の段落の割合はプロの英語文書で 0.27%、プロの日本語文書で 0.59% と、言語をまたいでも同じ桁に収まっている。文体規則を英語へ移植できなかった D-28 とは、この点で結果が分かれた。

文書型と必須の節は独自に考案せず、確立された標準から採用した。RFC 7322 が必須の節と推奨順序を定義している。文書型ごとの節構成は、Rust RFC テンプレート、Kubernetes Enhancement Proposal、Michael Nygard の Architecture Decision Record、Diátaxis を典拠とした。段落の上限は Google developer documentation style guide の5〜6文という指針に合わせて6文とした。主観による規則を導入しないという制約は、構造規則においても変わらない。

severity の割り当ては、必須の節の欠落のみを error とし、順序・段落長・空の節は warning とした。必須の節を欠く文書は読者の問いに答えられない。これに対し、順序や段落の長さは理解を助ける指針であって、違反を一切許さない絶対条件ではないためである。

節の照合対象は最上位階層の見出しのみとする。ただし先頭の第1階層見出しは文書タイトルであって節ではないため除外する。下位階層の見出しまで照合すると、ある節内の小見出しが別の節名に一致して順序判定が誤動作する。実際にこのリポジトリの英語設計文書で、その誤検出が発生した。

先頭の節だけは、タイトル直下の地の文で代替できる仕様とした。RFC 7322 で abstract がタイトルと目次の間に見出しなしで置かれる前例があり、README でも同じ形式が一般的である。`## これは何か` のような見出しを機械的に強制すると、かえって可読性を損なう。

### 執筆前に構成を承認する

`suikou plot` は `.suikou/plans/` にテンプレートファイルを生成する。このファイルには、各節の見出し、その節が答えるべき問い、そこで述べる主張の記入欄だけを設けてある。主張を一行で要約できない節は思考が整理できておらず、本文を書き始める前の段階でその不足を発見できる。

プロットはバージョン管理の対象外とする。成果物ではなく思考整理のための作業文書だからである。そのため CI からは参照できず、構成の照合はローカル環境とエージェントの作業ループ内でのみ機能する。これは欠点ではない。構成の誤りは執筆前に正すべきものであり、公開前の自動チェックで止める性質の問題ではないためである。

### 違反検出だけでなく執筆指針も提示する

検証規則は、違反を検出して修正を促す負の方向でしか機能しなかった。違反一覧は避けるべき書き方を示すものの、どのように書くべきかまでは示さない。

そこでテンプレート自体に、各節が答える問いと記述内容の指針を組み込んだ。`suikou plot` と `suikou brief --doctype` が執筆前にその内容を出力する。指針の文面は `structure::writing_rules` に一か所で管理し、違反指摘のメッセージと食い違いが生じないようにした。

トークン消費量は無闇に増やさない方針である。テンプレートの出力は `--doctype` が指定された場合に限定している。
## D-31 手順文書型では実測に基づき必須セクションを二項目除外した

手順文書型の必須セクションは、公開されているフレームワークを参照して設計した。Diátaxis の how-to guide に基づき、前提・手順・確認の三項目を必須として定義していたが、実務の文書に適用した段階でそのうち二項目が適合しなかった。

Kubernetes の task ページ120件に対して `howto` を適用したところ、`Steps` が120件すべてで、`Verify` が113件で欠落として検出された。警告が発生しない文書は皆無であった。

実際の見出し構成を集計すると原因が明確になる。task ページの見出しは `{{%/* heading "prerequisites" */%}}` が111件、`{{%/* heading "whatsnext" */%}}` が84件を占め、残りはページ固有の見出しで構成されている。具体的には `Create a namespace` や `Edit a Secret` のように、各ページで実施する操作名そのものが見出しになる。

手順は文書全体の本文そのものであり、単一のセクション見出しにまとめる要素ではない。Diátaxis が述べているのは「how-to guide は手順の連続で構成される」という性質であり、`Steps` という見出しの配置を求めているわけではない。見出しを `Steps` に統一させると、具体的な操作内容が見出しから失われてしまう。これは「見出しだけを追えば文書全体の論理を把握できるようにする」という基本方針に反する。

この検証結果を受け、`steps` と `verify` を必須要件から除外し、`prerequisites` のみを必須セクションとして維持することにした。

### 再計測で判明した二件の判定ロジック上の欠陥

初回の計測では `prerequisites` が120件すべてで満たされていると判定された。しかしこれは実際に要件を満たしていたわけではなく、判定規則が過度に緩かったことに起因する。

導入文による代替可否を、セクションの配置順序だけで判定していた。タイトル直下に地の文があれば、最初の必須セクションの種類を問わず充足扱いになっていた。concept ページ120件に `howto` を適用しても1件も発火しなかったことから、文書型としての区別が機能していないことが判明した。

導入文で代替できるか否かは出現位置ではなくセクションの性質による。主題を述べるセクションにのみ `lead_ok` を許可する仕様へ変更し、前提条件や文脈は導入文での代替を認めないこととした。修正後は concept ページ120件中117件で発火するようになり、文書型の判別が可能になった。

また、セクション名の同義語照合を文書の本文言語のみに限定していた。Kubernetes の日本語訳では `{{%/* heading "prerequisites" */%}}` がそのまま残されており、日本語の同義語だけで照合した結果、111件中110件がセクション欠落となった。本文の言語と見出しの言語は一致するとは限らないため、両言語の同義語を対象に照合する方式へ修正した。

| 日本語の task ページ | 111 | 6件（5.4%） |
| 英語の concept ページに `howto` を適用 | 120 | 117件（97.5%） |
| 日本語の concept ページに `howto` を適用 | 120 | 116件（96.7%） |

日英両言語でほぼ同水準の結果となった。異なる文書型へ適用した場合は大半が発火し、該当する文書型へ適用した場合はほとんど発火しない。この差異が、文書型判定が正常に機能している根拠となる。発火した task ページを個別に確認すると、実際に `Before you begin` が記述されていない。たとえば `Dependency on Docker explained` は `task` として宣言されながら内容は解説記事であり、判定側の誤検出ではなく Kubernetes 側が自社テンプレートから逸脱している事例である。

### 機械検出から除外しても執筆ガイドには残す

自動検出の対象から外した項目であっても、執筆支援の問いかけと記載指針は文書型定義に残している。`suikou plot` および `suikou brief --doctype howto` では、引き続き「どのように実施するのか」「成功をどう確認するのか」を執筆者へ問いかける。

機械的に検出できる要素と、執筆前に確認すべき要素は一致しない。動作確認の手順を示すことは優れた手順書の条件だが、`確認` という見出し名の有無だけでは判定できない。検出要件と執筆ガイドの役割を分離した点が、この判断における最大の成果である。

### 外部コーパスで検証できたのは手順文書型のみである

`design`、`decision`、`overview` の必須セクションについては、自リポジトリ内の文書でしか動作を確認していない。自リポジトリの文書見出しはあらかじめ自前の文書型に合わせて書かれているため、自己検証では妥当性の証明にならない。

外部コーパスで計測するには、文書型が明示された文書群が必要になる。Kubernetes 文書には `content_type` 属性があり、値は `task`、`concept`、`reference`、`tutorial` だが、本ツールの文書型と対応するのは `task` のみである。`concept` と `tutorial` に対応する文書型は未定義であり、追加するとすれば Diátaxis の explanation と tutorial に相当するが、検証対象のコーパスを確保しないまま文書型を増やすことはしない。

## D-32 設計文書型は由来元である Rust RFC で適合しなかった

`design` の必須セクションは Rust RFC テンプレートに基づいて定義していた。その妥当性を検証するため、`rust-lang/rfcs` の `text/` ディレクトリ直下から番号の大きい順に200件の RFC を抽出して適用した。番号の大きい側を選んだのは、テンプレート運用が定着したあとの記述傾向を評価するためである。定義の由来元そのもので検証するため、最も厳格な妥当性確認となる。

初回計測では、`Design` が200件すべて、`Non-goals` が199件、`Scope` が198件で欠落として報告された。原因はセクションごとに異なっていた。

### 見出し名の不一致

`Design` の200件は必須指定自体が誤っていたわけではなく、想定していた見出し名が実態と食い違っていた。

Rust RFC テンプレートでは該当セクションを `Guide-level explanation` および `Reference-level explanation` と命名しており、実測でも前者が157件、後者が148件に上った。両方に共通して含まれる `Explanation` を同義語へ追加するとともに、設計文書で広く用いられる `Implementation` と `Proposal` も同義語に加えた。

### テンプレートに存在しないセクションを必須にしていた

`Scope` と `Non-goals` は Rust RFC テンプレートには定義されていない。両セクションは Kubernetes Enhancement Proposal の様式に由来するものであり、異なる文書様式の要素を混在させて必須要件にしていた。

そのため両セクションを必須要件から除外し、執筆ガイドとしての問いかけと記載事項のみを残した。`plot` と `brief` では引き続き対象範囲と対象外を執筆者に問いかける。これは D-31 と同一の分離方針である。

### 解析処理で見つかった二件の不具合

見出し行のインデント幅に上限を設けていなかった。CommonMark 仕様では4桁以上の字下げはコードブロックであり、見出しとして解釈されない。インデントされたコード内の `#` を第1階層の見出しと誤認した結果、文書内の構成が第1階層のみとして解析され、本来のセクションが一切認識されなくなっていた。見出しの字下げ上限を3桁までとする仕様へ修正した。

また、コードブロックの除外処理を正規表現で実装していた。長いフェンスの内側に短いフェンスを含む記法があると、内側のフェンスでブロックが閉じたと誤認され、以降のコードが本文として解析されて `# [dependencies]` が見出し扱いになっていた。CommonMark の規定に従い、開始フェンスと同一の記号で開始以上の長さを持つ行のみを終了とみなす行走査方式へ変更した。

これら二件の修正は textlint プリセット側にも反映した。実在する RFC 2件を対象に検証し、M 系の検出件数が両実装で一致することを確認した。

### 修正後の発火率

修正後の計測では、200件中21件（10.5%）で必須セクションの欠落が検出された。このうち18件は機能提案ではなく、ロードマップ、プロジェクトグループ憲章、チーム編成、方針策定などの RFC であり、`text/` 配下に格納されてはいるものの機能提案の様式に従っていない。残る3件は `Proposed additions` や `Solution` といった一度限りの独自見出しを使っていた事例である。

同義語の追加はこの段階で終了する。見出し名の候補を増やし続ければ発火率はゼロに近づくが、それは特定コーパスへの過剰適合にすぎない。同義語追加の根拠は、様式の公式テンプレートに記載された名称に限定する。

## D-33 決定文書型は外部 ADR でも成立し、セクション順序も初めて検証できた

`decision` の必須セクションは Michael Nygard の Architecture Decision Record を基に定義した。検証のため、28のリポジトリから190件の ADR を収集して適用した。収集には `research/structure/fetch_adrs.py` を用い、`adr-tools` が最初に生成する記録ファイルを起点として探索している。インデックスファイルおよびテンプレートは決定記録ではないため対象から除外した。

| 規則 | 190件中の発火数 |
|---|---|
| 必須セクションの欠落 | 20件（10.5%） |
| セクション順序の違反 | 0件 |
| 段落が長い | 6件（3.2%） |
| 末端セクションに本文がない | 2件（1.1%） |

`howto` と `design` が外部コーパスでそのまま成立しなかったのに対し、この文書型は成立した。その差は、単一の様式をそのまま採用したか、複数様式を混在させたかにある。`design` は Rust RFC と KEP の様式を混在させており、`howto` は Diátaxis の説明文をセクション見出し名と誤解していた。一方、`decision` は ADR という単一様式をそのまま反映している。

### セクション順序を初めて検証できた

セクション順序の検査を行うには、文書型で規定されたセクションが同一文書内に2つ以上出現している必要がある。Kubernetes の task ページではこの条件を満たす文書が120件中7件にとどまり、統計的な検証にならなかった。対して ADR では190件中189件が条件を満たしたうえで、順序違反の発火件数はゼロであった。

文脈、決定、帰結という配列は実務上の記述習慣と合致している。この結果により、この並び順を推奨順序として採用する根拠が得られた。

### 欠落判定となった20件の内訳

このうち11件は MADR 様式で書かれていた。MADR では `Context and Problem Statement` と `Decision Outcome` を用い、帰結を `Decision Outcome` の下位階層に配置する。本ツールの照合処理は最上位階層の見出しのみを対象としているため、下位階層にある帰結セクションは検出されない。

この階層制限は緩和しない方針とした。下位階層まで照合対象を広げると、セクション内の小見出しが別の規定セクション名と誤って一致し、順序判定が誤るためである。この誤検出は D-31 の検証時に実際に発生している。MADR に対応する際は探索階層を下げるのではなく、様式ごとに独立した文書型を定義するアプローチをとる。

残る9件の中には、`Status` と `Context` のみで構成された文書が含まれていた。決定事項も帰結も記載されていない記録であり、正当な欠落検出である。また、`Decision` の代わりに `Proposal` を用いている文書もあった。

これらに対する同義語の追加は行わない。D-32 と同じ基準を適用する。

## D-34 natural-japanese の規則を検証し、すべて不採用とした

`coji/natural-japanese`（MIT）は、業務向けの日本語を読みやすく執筆するためのスキルであり、28種類の検出器、禁止語カタログ、翻訳調パターン集を備えている。これらの規則を本リポジトリへ取り込めるかどうかを、本リポジトリの採用基準で検証した。

規則を採用する条件は、実測値において人間と AI の分布範囲が重複しないこと、または明文化されたスタイルガイド規約を出典付きで示せることのいずれかである。候補の提案は人が行うが、採否は実測データによって判断する。これは D-26 と同一の検証手順である。

### 検証手順

計測には、同一原文に対する人間訳と AI 訳をペアで収録した `corpus/cache/k8s/` を使用した。同じ原文の訳文を比較することで、専門分野や題材の違いが差異に混入するのを防げる。あわせて参照コーパス798文書も計測対象に含めた。具体的な検証手順は `research/translationese/` に格納している。

### 計測結果

| 候補 | 人間訳 | AI訳 | 参照 | 判定 |
|---|---|---|---|---|
| 「することができる」 | 2.43 | 0.85 | — | 傾向が逆 |
| 翻訳調パターン10個 | ほぼ0 | ほぼ0 | — | 技術文書に出現しない |
| 段落頭の接続詞 | 1.6% | 1.2% | 1.6% | 分離しない |
| 文末の同形3連 | 11.8% | 10.5% | 6.0% | 分離しない |
| 二重否定 | 0.16 | 0.11 | 0.16 | 分離しない |
| 「の」の3連続 | 3.67 | 3.03 | 2.84 | 人間の方が多い |
| 禁止語カタログ48語 | 最大1回 | 最大5回 | — | G² の水準に届かない |

表の数値は1万文字あたりの出現頻度であり、段落に関する項目のみ百分率で示している。

以上の結果から、いずれの候補も不採用とした。却下理由とともに `corpus/baselines.toml` の `[rejected]` セクションへ記録している。

### 差が出なかった要因

禁止語カタログは随筆や一般的なビジネス文書を想定して作成されている。「いかがでしたか」「見ていきましょう」といった表現は技術文書には出現せず、48語のうち検証コーパスに現れたのは19語にとどまった。文書ジャンルが異なれば AI 特有の表現傾向も変わるという結果は、D-28 の知見と一致する。

翻訳調パターンについては、比較対象コーパスの性質を考慮する必要がある。人間側のデータは英語技術文書のプロによる翻訳文であるため、翻訳調の構文が含まれるのは自然である。したがって、このデータセットでは「翻訳調であるか否か」自体は判定できない。検証できたのは「AI 訳のほうが人間訳より翻訳調か」という問いであり、結果は否であった。

### 参照資料として取り込んだ知見

検出規則は不採用としたが、先方が公開している根拠資料は有用である。`corpus/reports/research/prose-rhythm-evidence-matrix.md` では、文長の分散、バースト性、自己相関、TTR、perplexity について先行研究と独自の実測結果を照合し、「反証的」と評価している。

本リポジトリが `[rejected]` に分類した指標群について、独立した検証で同一の結論に達している。文長の変動係数に関しては、先方の閾値設定で人間の文章に対する誤検出率が32.4%と計測されている。また、自己相関については仮説と逆の傾向が得られ、削除候補とされている。

別の開発者が異なるコーパスで同じ結論を得たことは、本リポジトリの判断の妥当性を高める根拠となる。`[rejected]` の根拠出典としてこの資料を記録に残す。

### 同一文書に対する比較検証

規則の一覧を眺めるだけでは実際の検出挙動を把握できない。そこで、AI が生成しそうな日本語の設計文書を用意し、双方のツールを実行して出力を比較した。

| | suikou | natural-japanese |
|---|---|---|
| 指摘数 | 13件（5規則）と文書指標4件 | 6件（5カテゴリ） |
| 規則の重複 | ゼロ | ゼロ |

検出対象は完全に分離していた。suikou が指摘したのは項目数の明記、見出しの連番、項目の並列性、時点に依存する語、カタカナ語の優先であり、いずれもメンテナンス時の修正で不整合が生じやすい箇所や、時間経過で情報が古びる箇所である。一方、natural-japanese が指摘したのは常套句、無生物主語、翻訳調、リズムであり、文章の自然さに関わる領域である。

同一行に対して双方から指摘が出た箇所もあったが、着眼点は異なっていた。冒頭の一文に対し、suikou は時点に依存する語を指摘し、natural-japanese は常套句を指摘している。同じ行を対象にしていても評価軸が異なる。

実務の文書（Kubernetes 日本語訳の手順ページ）で実行したところ、指摘件数は suikou が2件、natural-japanese が1件にとどまり、いずれも過剰な警告は発生しなかった。

### 対訳コーパスでの指摘件数

同一原文の人間訳12本と AI 訳12本に双方のツールを適用した。

| | 人間訳 | AI訳 | 比 |
|---|---|---|---|
| suikou | 43件 | 62件 | 1.44 |
| natural-japanese | 87件 | 82件 | 0.94 |

natural-japanese の内訳を確認すると、件数が偏った要因が分かる。`translationese` は人間13件に対し AI 2件、`translationese_morph` は人間19件に対し AI 2件と、いずれも人間訳側で大きく上回っている。この傾向は D-34 の計測結果と一致しており、人間側が英語文書のプロ翻訳である以上、翻訳調が多く検出されるのは自然な結果である。

### 唯一傾向が一致した規則

`repeated_sentence_lead`（文頭2形態素が同一文書内で6回以上出現するパターン）だけは、想定どおり AI 訳側で多く検出された。suikou には実装されていない規則であるため、他の候補と同一の手順で詳細を計測した。

| 群 | 文書数 | 発火した文書 | 100文あたり |
|---|---|---|---|
| 人間訳 | 39 | 35% | 14.2 |
| AI訳 | 78 | 50% | 16.4 |
| 参照コーパス | 60 | 26% | 10.6 |

傾向の方向は想定と合致しているものの、人間と AI の分布範囲が重複しており、AI と人間の比率は1.15にとどまった。参照コーパスでも26%の文書で発火している。分布範囲が重複しないことを採用条件としているため、この基準を満たさない。

出力の粒度も本ツールの方針に合致しない。該当する文をすべて列挙する仕様であるため、71文の単一文書だけで17件の指摘が出力された。単一規則あたりの指摘箇所を限定する設計方針に反する。

したがって不採用とするが、検証した候補の中で唯一想定どおりの傾向を示した規則として実測データを残しておく。

## D-35 時点依存の検出は時制ではなく係留の有無で判定する

生成モデルには、執筆時のコンテキストへ過剰に適応する性質がある。作業セッションの中で文書を作成すると、その瞬間の状態を文書全体にとって永続的な時点であるかのように記述してしまう。`現在レイテンシが悪化しており` と記した時点で、その文は執筆当日にしか成り立たなくなる。

M6 の論拠を「文書が風化する」という結果論から、この生成側の機構へと変更する。この観点から捉えることで、なぜこの規則だけが簡潔な指示では遵守されず、禁止語を網羅的に列挙する必要があるのか（`brief` の実測結果）を矛盾なく説明できる。

### 時制は判定指標にならない

対策として「時制表現を排除して無時間的な記述に統一する」という案が挙がったが、不採用とした。

| 文 | 時制 | 陳腐化するか |
|---|---|---|
| `2026年3月に2.5倍になった` | 過去 | 陳腐化しない |
| `現在は640ミリ秒である` | 非過去 | 翌日に陳腐化する |

記述が古びるかどうかを分ける要因は時制ではなく、絶対的な時点への係留があるか否かである。

時制そのものを検出対象にすると、すでに成立している文書型と矛盾が生じる。決定記録の文脈セクションは過去形で記述するのが原則であり、その形式が公開 ADR 190件で機能していることは D-33 で実証済みである。また、手順の前後関係を示す表現（「〜したあとに」）も時制の形をとるが、閲覧時点には依存しない。

### 「意図した場合は除く」を機械判定できる条件へ変換する

例外の扱いを執筆者の判断に委ねてしまうと自動化できない。そこで、係留要素の有無という機械的に判定可能な基準へ変換する。

同一文内に西暦、バージョン番号、または番号付きの文書参照が含まれる場合は、この規則の発火を抑制する。たとえば `lindera 6.0.0 で現在の素性の順序を確認した` は特定バージョン時点の事実を記録した文であり、時間が経過しても誤りにならない。

係留の判定は文単位で行い、同じ段落内の別文にある年号は適用しない。また、単なる小数をバージョン番号と誤認しないよう、`v` が付いた形式または3つ組の数値形式だけを係留として扱う。`2.5倍` をバージョン番号の係留と誤認して文全体の指摘が消えてしまう不具合が、実装過程で実際に発生した。

### 語彙一覧では網羅できない表現形式

数値を伴う相対的な期間表現は、固定の語彙リストでは網羅できない。そのため、`直近3ヶ月` `過去2年` `先週` のような表現をパターンとして検出する。

この検出漏れは実文書を用いた検証で発覚した。AI が生成した設計文書へ適用したところ、M6 は `現在` `現時点` `今後` `既存の` を正しく検出した一方で、`直近3ヶ月でリクエスト数が約2.5倍に増加した` を見逃していた。

追加した語彙群は、Google の timeless documentation ガイドラインが挙げる `recently`、`soon`、`new` の日本語対応に該当する。同一条項の適用範囲内であり、場当たり的な仮説ではない。

### 変更前後の計測結果

| コーパス | 変更前 | 変更後 |
|---|---|---|
| task ページ（日本語）60本 | 119件 / 36文書 | 123件 / 36文書 |
| 参照コーパス60本 | 179件 / 39文書 | 185件 / 39文書 |
| AI 訳39本 | 85件 / 26文書 | 92件 / 27文書 |

検出件数の増加幅は小さい。参照コーパスはもともと無時間的な表現で執筆されているためである。係留による発火抑制が働いた事例は200文書中で1件確認され、`既存のHyper-V分離サポートは、v1.10の試験的な機能であり` が該当した。この文は `v1.10` 時点の事実を記述しており、時間が経っても誤りにならない。

本リポジトリ内の文書は、変更前後のいずれのルールでもすべて検査を通過する。

### 検出対象外とした表現

過去形そのもの、状態の継続を表す表現（「〜している」）、および操作の順序表現は検出対象としない。手順文書には操作順序が不可欠であり、決定記録には意思決定の履歴が不可欠である。これらを除去しても、読者が得られる情報が失われるだけである。
## D-36 レポートの情報量を増やしつつ出力文字数を1割削減する

出力トークン数を増やさないことは、このツールの制約の一つである。実際の出力文字数を計測し、各規則のコストと効果を検証した。

### 規則ごとの検出効果

同一の原文に対する AI 訳39本と人間訳39本を比較し、1文書あたりの発火数を計測した。

| 規則 | AI 訳（件/文書） | 人間訳（件/文書） | 比 | 文字数/件 |
|---|---|---|---|---|
| `maint/time-dependent` | 2.36 | 2.26 | 1.05 | 59 |
| `register/prefer-katakana` | 1.36 | 0.64 | 2.12 | 84 |
| `register/rare-wago` | 1.33 | 0.41 | 3.25 | 60 |
| `maint/parallel-items` | 0.44 | 0.41 | 1.06 | 69 |
| `structure/long-paragraph` | 0.23 | 0.18 | 1.29 | 88 |
| `maint/item-count` | 0.18 | 0.10 | 1.75 | 93 |
| `maint/list-lead-in` | 0.00 | 0.46 | 0.00 | 92 |

AI 訳と人間訳の差が最も大きく表れるのは文体規則である。M 系の規則は明文化された規約を検査する性質上、人間が書いた文書でも発火する。この設計方針は D-09 で定めており、この計測結果とも整合している。

出力文字数が最も多い規則は `maint/time-dependent` である。比率が 1.05 で判別力がないため、AI 生成文の判定指標には使えない。それでも規則として維持するのは、明文化された規約に基づき、修正すれば文書品質が向上するためである。

### 一致箇所を含まない抜粋形式の改善

変更前の抜粋は行頭から60字を切り出す仕様であり、行の後半にある一致箇所が抜粋に含まれない問題があった。同一行に複数の一致がある場合、まったく同じ60字の抜粋が重複して出力される。実際に1行で3件の指摘が発生した際、同じ抜粋が3回出力され、どの箇所を修正すべきか判別できなかった。

そこで、一致した文字列を先頭に明示し、その前後の文脈を短い幅で添える形式へ変更した。文脈の幅は言語別に設定する。日本語では14字でほぼ一文節に相当するが、英語では2語にしかならないため、英語は20字とした。この幅は、変更前の固定60字方式とレポート総量が並ぶ値である。

### 文書タイトルの番号を節の連番と区別する

M3 は見出しへの手動連番を検出する規則である。節を増減した際に番号を振り直す手間を防ぐことが目的である。

この理由は文書全体のタイトルには当てはまらない。ADR では `# 3. 題` のように番号を識別子として用いる様式が一般的であり、公開されている ADR 190件のうち155件がこの規則に該当していた。文書先頭の第1階層見出しを検出対象から除外した結果、発火数は155件から11件へ減少した。

### 規則間の矛盾の解消

`register/prefer-katakana` はカタカナ語の使用を推奨している一方で、見出し判定用の同義語一覧には漢語しか登録されていなかった。その結果、`## コンテキスト` という見出しを持つ決定記録に対して「文脈の節が無い」と指摘され、一方の規則の助言に従った文書を別の規則が拒む矛盾が生じていた。同義語一覧にカタカナ語を追加し、この不整合を解消した。

### 計測結果

| コーパス | 変更前 | 変更後 |
|---|---|---|
| 参照コーパス60本 | 71,129字 | 61,447字 |
| ADR 60本 | 38,704字 | 30,972字 |
| RFC 60本 | 58,745字 | 58,597字 |
| AI訳39本 | 46,979字 | 42,272字 |

合計文字数は 215,557字から 193,288字となり、1割減少した。削減の要因は、文書タイトルの番号を検出対象から除外したことと、抜粋幅を短縮したことにある。あわせて、すべての指摘位置で一致した文字列そのものが明示されるようになり、出力文字数を抑えつつ伝達する情報量を増やせた。

## D-37 語の選択と表記を分離し、外部利用可能な用語集として管理する

個人的な語感に頼って語を選ぶと、不自然な和語へ偏りやすい。実際に D-27 では、漢語率を下げる目的で「検証」を「確かめ」へ言い換える誤りを犯している。`register/rare-wago` は出力済みの不自然な和語を検出できるものの、語を選ぶ段階の規範までは備えていなかった。

硬質な文章向けの規範を調査するなかで、[yomiyasu](https://github.com/nanaism/yomiyasu)（MIT License、Copyright (c) 2026 nanaism）が語を選定するための問いを定義していることを確認した。文言の引用は行わず、判断の枠組みだけを参考にして独自に書き起こした。

### 語を選定するための2つの問い

語を採用する際は、以下の問いを順に適用する。

1. その分野の書き手が、仕様書や手順書を作成する際にこの語を選ぶか。
2. 英語へ戻したとき、一語ずつ対応するか。

第2の問いに「はい」、第1の問いに「いいえ」と答える場合、その表現は英語を一語ずつ直訳した言い回しである。

第1の問いを判定するうえで重要なのは、反復を定着の根拠にしない点である。AI が生成した文書の語彙は後続の文書へそのまま引き継がれるため、同一リポジトリ内で繰り返されていても定着の証拠にはならない。このリポジトリの文書も AI が生成しており、この注意点はそのまま当てはまる。

### 語の選択と表記の分離

語の選択と表記は根拠の由来が異なるため、これら2つを分離して管理する。

| 種別 | 対象 | 根拠 |
|---|---|---|
| `term` | どの語を選ぶか | 参照コーパスの出現頻度と PLaMo Translate の訳語 |
| `orthography` | その語をどう表記するか | JTCA の規約を起点とし、参照コーパスで検証 |

分離の根拠は実測にある。PLaMo Translate に同じ英単語を異なる文脈で翻訳させたところ、`computer` に対して `コンピュータ` と `コンピューター` の双方を出力した。また、`サーバー`・`ユーザー`・`クラスター` には長音符号を付ける一方、`ブラウザ`・`パラメータ`・`フォルダ` には付けなかった。

翻訳モデルは語の選択には活用できるが、表記の統一までは決定できない。表記の統一には明文化された規約が不可欠である。

### 規約と実測が一致しない語への対応

JTCA「外来語（カタカナ）表記ガイドライン」第3版は、英語の語尾 -er、-or、-ar、-y に対して長音符号「ー」を付ける規定を設けている。

438万字の参照コーパスで実態を検証したところ、-er、-or、-ar は規約と一致した。対照的に -y では長音を付けない表記が優勢である（`プロパティ` 870 / `プロパティー` 3）。また、`コンテナ` は -er で終わる語だが、対象分野では長音を付けない表記が定着している（1783 / 95）。

このため、規約から一律に導出するのではなく、語ごとに実測結果に基づいて表記を決定する方針とした。規約と実測が食い違う語には `measured-against-jtca` を付与し、差異を記録に残す。

### 外部ツールでも利用できる用語集の配置

用語集の正本は `crates/suikou-core/data/glossary_ja.toml` で管理し、そこから `glossary/suikou-ja.prh.yml` と `glossary/suikou-ja.csv` を生成する。

prh 形式を採用したのは、日本語の表記ゆれを統一するツールとして広く普及しており、その辞書形式をそのまま textlint で読み込めるためである。実際に textlint へ辞書を読み込ませ、`textlint --fix` によって表記を統一できることを検証した。

### 単字の直訳語を検出対象外とする理由

`glossary/variant` の検査対象は、表記ゆれと複数文字からなる直訳語に限定する。

単字（`版`、`枝`、`題`）を部分一致で検索すると、「問題」に含まれる「題」のような誤検出が生じる。参照コーパスで「題」を部分一致検索すると613件が一致するが、大半は「問題」「課題」「話題」などの熟語であり、直訳語としての「題」ではない。

単字の正確な判定には形態素解析が必要である。形態素単位の判定はすでに `prefer-katakana` が担っているため、責務を重複させない。

### リポジトリ内文書での不統一と参照コーパスの揺れ

この規則を適用したところ、このリポジトリ内の4つの文書で `サーバー` と表記されている箇所が見つかり、用語集に従って `サーバー` へ統一した。

参照コーパスでは60文書のうち7文書、Kubernetes の手順ページでは60文書のうち10文書で発火する。これは誤検出ではなく、参照コーパス自体に表記ゆれが存在する（`サーバー` 591 / `サーバー` 130）ためであり、少数派の表記を指摘することこそがこの規則の役割である。

## D-38 表記は語ごとの実測で決め、判定不能な語のみ長音付きを既定とする

### 文脈

表記ゆれの統一方針は3度にわたり変更した。

最初は `サーバ` や `コンピュータ` のように長音符号を省く形へ統一した。続いて、JTCA「外来語（カタカナ）表記ガイドライン」第3版（2015年）が `-er`、`-or`、`-ar`、`-y` に長音符号を付けると規定していることから、長音符号を付ける形へ統一した方が誤りが減るのではないかと考えた。

しかし、いずれの一律方針も参照コーパスにおける実際の使われ方と合致しなかった。

### 決定

語ごとに参照コーパスでの出現回数を集計し、多数派の表記を採用する。出現回数だけでは決定できない語に限り、長音符号を付ける表記を既定とする。ここで決定できない場合とは、多数派の件数が少数派の2倍に満たない場合、または総出現数が50件に満たない場合を指す。

### 根拠

参照コーパスに含まれる12語・計8,540件を対象に、統一方針ごとの乖離を比較した。

| 方針 | 実測と相違する割合 | 不一致となる語数 |
|---|---|---|
| すべて長音を付ける | 45.9% | 5語 |
| すべて長音を付けない | 54.1% | 7語 |
| 語ごとに実測 | 9.5% | 0語 |

一律の方針では、どちらを選んでも半数近くが実態と食い違う。参照コーパスでは `サーバー` が多数派である一方、`コンピュータ` も多数派であるため、一律にそろえると必ずどちらかが不適合となる。

判定不能な語の既定を長音付きとしたのは、JTCA の規約が長音付きを採用しているためである。出現回数で決着しない語について、明文化された規約に反する側を選ぶ根拠はない。

### 帰結

表記と語の選択は根拠の由来が異なるため、別々の仕組みとして管理することになった。語の選択は意味の限定によって決まり、表記は実際の使用傾向と明文化された規約によって決まる。`glossary_ja.toml` における `[[orthography]]` と `[[term]]` が、これら2つに対応する。

翻訳モデルは語の選択には有効だが、表記の統一には使えない。PLaMo Translate は同じ語を文によって `コンピュータ` と `コンピューター` の双方で出力した。200段落の検証で、語の選択は人間の翻訳家と 90.6% 一致しており、相違した3件はすべて表記の差であって訳語の誤りではなかった。

参照コーパスに出現しない語は実測できず、集計から漏れる。そのような場合でも判断が止まらないよう、既定の表記を定めている。

## D-39 README の型は先頭段落のみ必須とし、冒頭表現を規則化する

### 文脈

AI に README を生成させると、進行状況や検証で判明した事項、文書自体の目的宣言といった著者向けの作業メモが混入しやすい。読み手にとっては不要な情報である。

Diátaxis は、ドキュメントの問題の多くが一つの内容で複数の要求に同時に応えようとすることに起因すると指摘している。著者の作業メモと README は、異なる要求に応える文書である。

`overview` 型を README に適用できるかは未検証であり、TASKS.md でも未解決の課題として挙がっていた。

### 決定

`readme` 型を新設し、必須要素は先頭段落のみとする。

あわせて、`overview` 型の必須節から `usage` を除外し、同義語を補う。

さらに、文書の冒頭として避けるべき書き出しを検出する規則 `structure/lead-opener` を追加する。

### 根拠

著名な OSS の README 240件を収集して構造を計測した。エコシステムや特定組織への偏りを防ぐため、GitHub のスター数を基準に8言語へ分散させ、1組織あたり最大3件に制限した結果、199組織からデータが集まった。

これらに `overview` 型を適用すると、205件（85%）で必須節の欠落が検出された。これは、D-31 で `howto` の手順節を必須から外し、D-32 で `design` の対象範囲節を外した際と同じ状況である。

| 節 | 見出しから特定できた割合 |
|---|---|
| インストール | 62% |
| コントリビューション | 53% |
| ライセンス | 49% |
| ドキュメント | 41% |
| 使い方 | 22% |

見出しから特定できる割合は、最も高いインストール（`入れ方`）でも 62% にとどまる。62% を必須節とすれば、著名な OSS の40%を不適合とみなすことになる。README は見出しによって構造を規定する型ではない。

構造上の特徴は先頭段落にある。

| 計測対象 | 計測値 |
|---|---|
| 先頭に段落を持つ割合 | 78%（187/240） |
| そのうち300字以内 | 83%（156/187） |
| 先頭段落の文字数の中央値 | 121 |
| 最初の見出しの位置の中央値 | 文書の13% |

必須要素を先頭段落のみに変更したところ、240件に対する発火は 11件（5%）まで減少した。このうち3件はツールの対象外である中国語の README であった。また1件は RxJava であり、主題の説明より前に次のリリースの予定を見出しとして配置していた。

同義語には `## What's Rails?` のような疑問文形式の見出しを追加した。`What's new` との衝突が懸念されたが、240件中で衝突したのは1件のみであり、疑問文形式を採用していた文書は21件であった。

冒頭表現の規則には、先頭段落 831件の調査で出現数が0件だった形式のみを採用した。

| 書き出しの形式 | README | Rust RFC | ADR | 参照（英語） |
|---|---|---|---|---|
| 一般論から始める | 0/199 | 0/20 | 0/10 | 0/602 |
| 著者の経緯から始める | 0/199 | 0/20 | 0/10 | 0/602 |
| 文書の目的を宣言する | 0/199 | 0/20 | 0/10 | 0/602 |
| 自己言及 | 1/199 | 0/20 | 0/10 | **37/602** |

日本語の参照コーパスでも先頭段落 653件を検証した結果、自己言及を除く3形式はいずれも0件であった。

`本文書は` や `This document describes` のような自己言及は規則の対象から外した。英語の参照コーパスで6%出現しており、API の説明では成立する形式だからである。AI らしさが最も強い書き出しではあるが、実測データが許容すべき形式であることを示している。

策定した規則を実在の文書 2,080件（README 240、Rust RFC 200、ADR 190、参照コーパスの英語 652、日本語 798）に適用した結果、発火は0件であった。

### 帰結

README への作業メモの混入は、特定の語彙ではなく冒頭位置での書き出しによって検出する方式となった。`currently` や `TODO` といった語は著名な OSS でも使われており、240件のうち45件が `currently` を含んでいたため、語彙そのものを禁止する根拠は得られなかった。

ただし、この集計では性質の異なる2種類の記述を同一視していた。著名な OSS における `currently` や `Roadmap` は、予定の共有、採用判断の補助、支援の募集といった読者向けの情報であり、著者の作業メモではない。語彙だけで区別できなかったのは当然であり、分けるべき基準は語そのものではなく、その文が読者に何を伝えるかである。この課題は D-40 で扱う。

一方、先頭段落に書くべき内容については明確な規範が定まった。主題を主語として対象が何であるかを述べ、背景・目的・経緯から書き始めないという原則である。

この規則は作業メモそのものを直接検出するわけではなく、文書の途中に書かれた作業メモまでは検知できない。しかし、最初に読まれる先頭段落を主題の説明から始めると規定すれば、作業メモは後半の節へ移る。後半へ移った作業メモの除去は、各節を見出しの問いに対する答えとして記述する規範が担う。

## D-40 語彙ではなく読者への伝達内容で作業メモを判定する

### 文脈

D-39 では、著名な OSS の README 240件のうち45件が `currently` を含み、48件が Status や Roadmap の見出しを持つことから、語彙によって作業メモを検出する根拠はないと結論づけた。

しかし、この計測では役割の異なる2種類の記述をひとまとめに数えていた。

著名な OSS で使われる `currently` や `Roadmap` は読者に向けた情報であり、予定を示し、採用判断を助け、支援を募ることで読者に次の行動を促す。

対照的に、AI エージェントが記す内容は向きが逆である。自身が後で読むための文脈を残しているにすぎず、読者に行動を与えない。

同じ語を使っていても役割が異なるため、語彙だけで両者を分離できないのは当然であった。

### 決定

判定基準を語彙から「その文が読者に何を伝えるか」へ移す。

作業プロセス自体に言及する文を検出する規則 `structure/work-note` を追加する。対象とするのは、試した案、判明したこと、作業の段階、以前の状態に関する記述である。

検出の有効・無効は文書型に応じて切り替える。設計文書や決定記録では、何を試して何がうまくいかなかったか自体が伝えるべき内容であるため、許可する。この設定は `structure.toml` の `work_notes_ok` で管理する。

### 根拠

著名な OSS の README 240件から、状況や予定に言及する語を含む文 307件を抽出し、配置箇所ごとに分類した。

| 配置箇所 | 件数 | 割合 |
|---|---|---|
| 内容を示す見出しの配下 | 125 | 41% |
| 説明の地の文の中 | 182 | 59% |

説明の地の文に含まれていた182件のうち、作業プロセスそのものを述べた文は**0件**であった。内訳は、読者に行動を与えるものが17件、残りは機能や予定の説明であった。

区別の基準となるのは語彙ではなく、文が何について述べているかである。

| 表現の型 | README | 参照(英) | 参照(日) | Rust RFC | ADR |
|---|---|---|---|---|---|
| 試した案 | 0.4% | 0.2% | 0.1% | 4.5% | 3.2% |
| 判明したこと | 0% | 0.3% | 0.1% | 7.5% | 1.6% |
| 作業の段階 | 0% | 0% | 0.1% | 0% | 0.5% |
| 以前はこうだった | 0% | 0.3% | 0.3% | 5.0% | 0.5% |

読者向けの文書では出現率が 0.1% から 0.4% にとどまる一方、Rust RFC と ADR では 1.6% から 7.5% に上る。同じ表現であっても、設計文書や決定記録では伝えるべき内容となることが、文書型ごとに検出を切り替える根拠である。

なお、`変更の経緯`（`we refactored`、`移動した`）は検出候補から除外した。

英語では一致した11件のうち8件が読者へ参照先を案内する記述であった。たとえば `moved to their own repositories` や `renamed Redis Open Source with the v8.0 release` のように、どこを参照すべきか、何と呼称すべきかを伝えている。除いた3件も FAQ の見出しと命名の由来に関する逸話であった。

日本語では `フォーカスを移動した` のような通常の動詞表現と区別がつかない。参照コーパスで一致した43件は、すべてこの種の誤検出であった。

実測した発火率を以下に示す。

| コーパス | 適用した型 | 発火数 |
|---|---|---|
| README 240件 | `readme` | 0件 |
| Rust RFC 200件 | `design` | 0件 |
| ADR 190件 | `decision` | 0件 |
| 参照（英語）652件 | `reference` | 3件（0.5%） |
| 参照（日本語）798件 | `reference` | 5件（0.6%） |

### 帰結

同一の文であっても、文書型によって本質的な情報とみなされるか、不要な混入とみなされるかが変わる。たとえば `別の案も試したが、うまく動かなかった` は README では検出されるが、決定記録では許容される。

例として記載する場合はコードとして記述する必要がある。地の文に直接書くと検出対象になる。

この規則は語彙ベースの規則とは性質が異なる。`register/rare-wago` が文脈を見ずに語の出現頻度で判定するのに対し、`structure/work-note` は同じ語句でも文書型によって判定結果が変わる。

文書型が宣言されていないファイルでは検出を実行しない。読者向けの文書かどうか判断できないためである。`.suikou/structure.toml` の `[paths]` に割り当てを記述すれば検出が有効になる。

見出しで明確に区切られた予定や支援の募集は検出対象としない。著名な OSS の41%がこの形式を採っており、読者が読み飛ばせる構造になっている。README から予定の記載自体を除くのではなく、見出しで明示することを求める。
## D-41 文書種別ごとに規範の適用基準を切り替える

### 文脈

導入文書とリファレンス文書に対して、一律に同一の閾値を適用していた。

著名な OSS の README 240件を既定の閾値で検査したところ、`en.mattr100` が 70% の文書で発火した。652件の参照コーパスにおける発火率は 15% である。`en.simile_marker_per_1k` の発火率も 74% に達した。

70% の文書で発火する指標は、文章の問題ではなく閾値の不適合を示している。利用者からも、README のような導入文書と `docs/` 配下の文書とでは適切な文体のフォーマルさが異なるという指摘を受けた。

### 決定

プロファイルに文書種別ごとの調整機能を持たせる。この調整では、閾値の差し替え、指標の除外、および局所規則の除外を行える仕様とする。

すべての調整項目に `reason` の記述を必須とし、組み込みの調整に理由が欠けていないことをテストで検証する。調整設定は利用者との合意事項を記録する手段とし、ツールが自動的に判断して変更する対象にはしない。

設定の適用順序は、組み込みの全体設定、組み込みの文書種別設定、利用者の全体設定、利用者の文書種別設定の順に重ねる。

### 根拠

著名な OSS の README を対象に実測を行った。内訳は英語 240件（199組織、8言語）と日本語 150件（144組織）である。

| 指標 | README | 参照 | 比 |
|---|---|---|---|
| `en.mattr100` | 70% | 15% | 4.7 |
| `en.prose_ratio` | 32% | 11% | 2.9 |
| `en.simile_marker_per_1k` | 74% | 45% | 1.6 |

地の文比率は文書種別によって3倍の差がある。

| コーパス | `prose_ratio` の実測値 |
|---|---|
| README 240件 | 0.170 |
| 参照（英語）652件 | 0.427 |
| Rust RFC 200件 | 0.544 |

README では地の文が 17% にとどまり、残りは箇条書きとコードで占められる。これに対し、リファレンス文書では 43%、Rust RFC では 54% が地の文である。`en.prose_ratio` の既定閾値である 0.65 を README に適用すると、全件が基準を下回ってしまう。

調整後の発火率を比較した結果を以下に示す。参照コーパスに対する結果は変化しない。

| 指標 | README（調整前） | README（調整後） | 参照 |
|---|---|---|---|
| `en.mattr100` | 70% | 6% | 15% |
| `en.prose_ratio` | 32% | 7% | 11% |
| `en.simile_marker_per_1k` | 74% | 0% | 45% |

日本語の README 150件についても、調整後の発火率は 0% から 2% の範囲に収まる。

文体のフォーマルさの差は一方向ではない。

| 指標 | README（日本語） | 参照（日本語） |
|---|---|---|
| `ja.kango_ratio` | 0.620 | 0.521 |
| `ja.mattr100` | 0.752 | 0.674 |
| `ja.renyo_te_ratio` | 10.16 | 6.00 |

日本語の README はリファレンス文書よりも漢語率が高い。名称や機能を列挙する記述が多く、漢語の割合が増えるためである。導入文書に対して一律の方向へ基準を緩和するのは誤りであり、指標ごとに逆方向の差異が生じうる。

### 帰結

同一の指標であっても、文書種別に応じて異なる閾値で判定されることになった。各文書にどの検査が適用されたかを追跡しやすくするため、文書種別ごとの調整では指標を追加できない制約とした。指標の追加は全体設定の上書きでのみ行う。

局所規則については、組み込み設定で文書種別ごとの除外を定義していない。README で発火件数が多い `maint/list-lead-in`（340件）および `maint/parallel-items`（271件）は、いずれも明文化されたスタイルガイドに基づく指摘であり、README に対しても妥当である。除外機能自体は利用者に提供するが、組み込み設定では使用しない。

文書種別が宣言されていない文書には調整が適用されない。適用するには、`.suikou/structure.toml` の `[paths]` に設定するか、フロントマターに `doctype:` を明記する必要がある。

## D-42 記録を集約する文書種別を設け、警告を含めて検証する

### 文脈

`structure/work-note` を導入したところ、このリポジトリ内の文書で合計11件の発火が生じた。内訳は `TASKS.md` が7件、`decisions.md` が3件、`metrics.md` が1件である。

このうち10件は規則側の誤検出であった。CLAUDE.md は記録を記述する先として `TASKS.md` と `decisions.md` を指定している。それにもかかわらず、「経緯は決定の記録へ移す」と案内する規則が決定の記録自体に発火していた。

両ファイルは `reference` 種別を宣言していた。`reference` を採用した理由は、必須セクションを持たないことだけであった。文書種別の設計において、文書の目的と必須セクションの有無が同一の軸で混同されていた。

同じタイミングで、検証手順の不備も判明した。`suikou check --quiet` の終了コードは error が存在するときだけ 1 を返し、警告のみの場合は 0 を返す。終了コードだけに頼って全文書を確認していた結果、47件の警告を見落としていた。CLAUDE.md が定める合格条件は、error と warning の双方が発生しないことである。

### 決定

記録を集約する文書向けの種別として `log` を定義する。対象は決定記録の一覧、タスク一覧、変更履歴であり、`work_notes_ok` を付与して必須セクションは定めない。

`TASKS.md` と `decisions.md` をこの文書種別へ移行する。

文書の検証は終了コードではなく、出力された指摘件数に基づいて行う。

### 根拠

`log` 種別は検査対象を増やすものではなく、`reference` よりも制約を緩和するだけである。外部コーパスでの計測は行っていないが、誤検出を増やすリスクはない。

文書種別を移行したところ、誤検出はすべて解消された。残った `metrics.md` の1件を確認したところ、`代えられるのを最初の節と決めていた時期がある` という記述が定義文書内に経緯を書いており、正当な指摘であった。定義として書き直したうえで経緯を D-31 への参照に変更した結果、3文書すべてで work-note の発火は0件となった。

見落としていた47件の警告は、リポジトリ内の文章自体に起因していた。追記したセクションが特定語句の出現頻度を増加させていたためである。置き換え語は参照コーパスにおける出現頻度の実測値に基づいて選定した。

| 元の表現 | 参照コーパス | 置き換え先 | 参照コーパス |
|---|---|---|---|
| `読み手` | 0件 | `読者` | 13件 |
| `向き` | 54件 | `方向` | 155件 |
| `測る` | 0件 | `測定` | 63件 |
| `要る` | 0件 | `必要` | 3,503件 |
| `入り口` | 1件 | `起点` | 20件 |

`読み手` が参照コーパスに1件も出現しない事実は計測によって初めて明らかになり、執筆者の語感だけでは問題に気付けなかった。

### 帰結

リポジトリ全文書に対する指摘件数は、58件から0件へ減少した。

終了コードは error しか反映しないため検証には使わず、出力行を数える手順へ変更した。

```sh
for f in <全 Markdown>; do suikou check "$f" --format text; done | grep -c ':[0-9]*:[0-9]*:'
```

文書種別の定義では、文書の目的と必須セクションの有無を分離して表現する必要がある。`reference` と `log` はどちらも必須セクションを持たないが、文書の目的が異なる。`work_notes_ok` はその差異を表す最初の属性であり、ほかの規則でも同様の区別が必要になった場合は属性を追加して対応する。

## D-43 密度指標に最小語数条件を設け、較正不能な指標は文書種別ごとに除外する

### 文脈

D-41 で README の閾値を調整した後、ほかの文書種別についても実測を行った。190件の ADR に `decision` 種別を適用すると、`en.mattr100` が 45%、`en.prose_ratio` が 45%、`en.simile_marker_per_1k` が 75% で発火した。調整前の README と同様の状態である。

`en.simile_marker_per_1k` を詳しく分析したところ、原因は文書種別ではなく文書の長さにあった。発火率は語数が増えるにつれて単調に低下していた。

| 語数 | 発火率 |
|---|---|
| 0 から 400 | 86% |
| 400 から 800 | 47% |
| 800 から 1,250 | 24% |
| 1,250 から 2,000 | 16% |
| 3,000 から 5,000 | 5% |

この計測は、参照コーパス、Rust RFC、および ADR の合計 1,042 文書を対象に実施した。

### 決定

`en.simile_marker_per_1k` に最小語数の条件を設け、1,250語未満の文書では閾値比較を行わない。

`decision` 種別では `en.prose_ratio` を検査対象から除外する。`design` と `decision` における `en.mattr100` は、較正済みの閾値へ変更する。

### 根拠

この最小語数は、理論と実測の双方から導かれる。

閾値は1000語あたり 0.8 であるため、直喩の標識が1件出現しただけで閾値に達する語数は 1000 ÷ 0.8 = 1,250 となる。これより短い文書では、標識が0件か、1件で即座に閾値を超えるかの二値しか取りえず、指標としての分解能が失われる。実測値でも、この境界を下回ると発火率が急上昇する。

この最小語数条件は、指標値の算出段階ではなく閾値との比較段階に配置した。密度の値自体は語数にかかわらず算出可能であり、ゴールデンテストにおいて参照実装との計算結果の一致を引き続き検証できるようにするためである。

`ja.renyo_te_ratio` の `MIN_TE_FOR_RATIO` は分母が小さい場合に比が定義不能になることを防ぐ条件であるのに対し、こちらは値は定義できるものの分解能が不足するための条件である。目的が異なるため、適用する処理段階も分けている。

最小語数条件の導入により、すべての文書種別で発火率が改善し、文書種別ごとの除外は不要になった。

| 文書種別 | 導入前 | 導入後 |
|---|---|---|
| `readme` | 74% | 14% |
| `design` | 16% | 6% |
| `decision` | 75% | 4% |
| `reference` | 45% | 1% |

参照コーパスでの発火率 1% は、文書に記録されている人間の範囲（0.84 から 2.54）と整合する。既定の閾値 0.8 は人間と AI の文章を分離する目的で算出されており、Tukey の柵を用いる手法とは異なる。`suikou baseline` がどのコーパスでもこの指標を較正できないと報告するのは、指標の欠陥ではなく算出方法の違いによるものである。

`readme` に残った 14% の発火は正当な指摘であった。発火した34件における地の文語数の中央値は 2,370 であり、発火しなかった57件の中央値 1,241 を上回っている。地の文の不足ではなく、長大で地の文が多い README に直喩の標識が使われていないことが原因である。このため、`readme` に設定していた個別の除外は撤回した。

一方、`en.prose_ratio` は `decision` 種別から除外した。`suikou baseline corpus/cache/adrs` を実行すると、較正値 -0.18 が値域外であると報告される。分布の幅が広すぎて有効な境界を設定できないため、無理に数値を選ばず適用対象から除外する判断をした。

既定の根拠（人間の範囲 0.66 から 0.97）は地の文中心のコーパスから得られたものであり、定型的な記録文書には当てはまらない。ADR は各セクションが定型かつ短文で、箇条書きが中心になりやすいためである。

`en.mattr100` は較正に成功し、`design` が 0.76、`decision` が 0.88 となった。設計提案書も意思決定記録も扱う主題ごとに語彙が変化するため、語の反復が少なくなりやすい。

すべての調整を反映した後の発火率を表にまとめる。

| 文書種別 | `mattr100` | `prose_ratio` | `simile` |
|---|---|---|---|
| `readme` | 6% | 7% | 14% |
| `design` | 0% | 4% | 6% |
| `decision` | 0% | 0% | 4% |
| `reference` | 15% | 11% | 1% |

### 帰結

指標の発火率が高すぎる場合の原因と適切な対処は、次のように分類できる。

| 原因 | 対処 |
|---|---|
| 文書が短く分解能が不足している | 文書種別を問わず指標に最小語数条件を設ける |
| 文書種別によって分布が異なる | 文書種別ごとに閾値を変更する |
| 分布が広すぎて境界を定められない | 該当の文書種別では指標を除外する |

これら3通りの原因のうち、当初は文書種別の違いを疑っていたが、`simile` の実態は文書長の問題であった。原因を特定しないまま種別ごとの除外を先行させると、ほかの文書種別に同じ欠陥が残存する。実際に D-41 で `readme` から `simile` を除外した時点では、`decision` で 75% が発火している問題を見逃していた。対処を選ぶ前に原因を切り分ける手順が不可欠である。

日本語の ADR および設計提案書のコーパスが不足しているため、日本語側の調整は行っていない。`ja.mattr100` と `ja.prose_ratio` は、これらの文書種別でも既定値のままである。

## D-44 LLM 普及前の執筆を確認できない GitHub 収集文書は参照コーパスに採用しない

### 文脈

日本語の ADR と設計文書のコーパスが存在しなかったため、`design` と `decision` の日本語側閾値は既定値のまま残っていた。

そこで GitHub のコード検索を用い、平仮名とカタカナが300字以上含まれることを条件として95組織から123件の文書を収集した。既定の閾値を適用すると、発火率は極端に高くなった。

| 指標 | 日本語 ADR 67件 | 日本語 設計文書 56件 |
|---|---|---|
| `ja.mattr100` | 86% | 82% |
| `ja.prose_ratio` | 88% | 87% |
| `ja.list_ratio` | 82% | 82% |
| `ja.renyo_per_1k` | 43% | 39% |

較正を行えば発火率は低下する。しかし較正に踏み切る前に、収集したコーパスが人間の文章として妥当かどうかを検証した。

### 決定

このコーパスは較正に使用しない。日本語側の `design` と `decision` については既定の閾値を維持する。

収集済みのコーパス自体は破棄せず保管する。ファイル単位の更新日時で絞り込めば活用できる余地があるためである。

人間の参照コーパスを収集する際は、LLM が普及する以前に書かれた文書であることを確認する手段を事前に定めてから作業する。

### 根拠

AI 生成文の混入度合いを、ツール自身の規則を用いて測定した。`register/rare-wago` は、専門的な技術文書では使われない和語の反復を検出する規則であり、AI 文章の特徴を捉える目的で導入されている。

| コーパス群 | `register/rare-wago` | `maint/parallel-items` |
|---|---|---|
| 参照コーパス（概念ページ、人間訳）67件 | 4% | 35% |
| k8s 手順ページ（人間訳）40件 | 20% | 52% |
| GitHub から収集した手順書 160件 | 35% | 61% |
| GitHub から収集した ADR 67件 | 31% | 71% |

GitHub から収集した文書群では、人間訳の文書群よりも AI 的な特徴が顕著に表れた。`register/rare-wago` の発火率は 31% から 35% であり、参照コーパスの 4% と比べて8倍に達する。

この数値には、文書様式の違い（概念ページ 4% 対 手順ページ 20%）と書き手の違いという2つの要因が混在している。手順ページ同士を比較しても 20% 対 35% の差があり、様式を揃えても明確な差が残る。

収集した ADR から25件を抽出して調べたところ、2023年より前に作成されたリポジトリに由来する文書は8件のみであった。リポジトリの作成年は個別ファイルの執筆年と一致しないため、リポジトリ作成日だけでは十分な絞り込みができない。

AI 生成文が混入したコーパスで較正を行うと、閾値が AI の文体側へ移動してしまう。その結果、人間と AI の文章を分離するという閾値本来の目的が損なわれる。

### 帰結

`suikou baseline` へ入力するコーパスの品質は、利用者自身が検証する必要がある。`baseline` コマンドは渡された文書をすべて人間の文章とみなして処理するため、書き手を判定する機能を持たない。

ただし混入度合いを測定する手段自体はツールに備わっている。`register/rare-wago` と `maint/parallel-items` の発火率を参照コーパスと比較すればよく、8倍もの差が生じる文書群は人間の参照コーパスとして不適格と判断できる。

保持している各コーパスの由来と検証状況を表に整理する。

| コーパス | 由来 | 人間の文章か |
|---|---|---|
| `pro_ja` 798件 | k8s、mdn、vue、react、rustbook の日本語訳 | 人間訳 |
| `pro_en` 652件 | 同一出典の英語原文 | 人間 |
| `rfcs` 200件 | Rust RFC | 人間（LLM 普及前の提案を含む） |
| `adrs` 190件 | 公開されている英語 ADR | 未検証 |
| `readmes` 240件 | スター数で選定した README | 未検証 |
| `adrs_ja` 123件 | GitHub のコード検索 | **汚染** |
| `howto_ja` 200件 | GitHub のコード検索 | **部分的に汚染** |

英語側の `adrs` と `readmes` に対しても同様の測定を実施した。`register/rare-wago` は日本語専用であるため、代わりに M 系の規則を用いた。

| コーパス群 | `maint/parallel-items` | `maint/trailing-etc` |
|---|---|---|
| `pro_en` 652件（参照） | 51% | 4% |
| `rfcs` 200件 | 58% | 17% |
| `adrs` 190件 | 28% | 5% |
| `readmes` 240件 | 43% | 24% |

日本語側で見られた8倍のような大きな差は確認されなかった。`adrs` の発火率は 28% 対 51% と参照コーパスを下回っている。D-41 と D-43 の較正は、この検証を通過したコーパスに基づいている。

`readmes` では `maint/trailing-etc` が 24% 対 4% と6倍になっている。機能の列挙を `etc.` で結ぶ表現は LLM の普及以前から定着している README の慣習であり、スター数基準で選定したため作成時期の古い文書を多く含むことから、様式の差異として解釈している。

英語側では M 系の規則しか利用できない。`register/rare-wago` に相当する英語規則は D-28 で実装しないと決定済みであり、AI 生成文の混入を検知する能力は日本語側よりも限定的である。

## D-45 M2 は数値が前方参照している場合にのみ適用する

### 文脈

M2 は、地の文の中で項目数を明示する表現を検出する規則である。後から項目を増減させた際に、本文の記述と実態が一致しなくなるのを防ぐ目的で設けられている。

当初の実装では地の文全体に一律適用しており、その数値が何を指しているかを確認していなかった。TASKS.md にも「リストが続かないただの説明文で数を述べる場合も検出してしまう」と課題が記され、`tests/golden/input/ja_prose.md` が事例として挙げられていた。

該当する記述は次のとおりである。

```
無効化の方法は大きく分けて二つある。時間で切る方法と、変更を検知して切る方法である。
```

この例では、項目数と列挙内容がその場で完結している。方法を追加する際はこの記述自体を書き換えることになり、数値と項目数が一致しなくなる余地がない。

### 決定

数値が前方参照を行っている場合にのみ適用する。判定条件としては、文中の語句、直後の文書構造、後続の地の文の表現という3種類の観点を用いる。

文中に `以下`、`次の`、`下記` が含まれている場合は、後続の要素を予告しているため対象とする。

直後に箇条書き、見出し、または表が続く場合は、その文とは独立に編集できる構造であるため対象とする。

直後に列挙を示す表現（`第一に`、`1つ目`、`まず`）を含む地の文が続く場合も対象とする。

### 根拠

798件の参照コーパスで発生した168件の発火を、語句と後続構造の組み合わせで分類した。

| | 箇条書き | 見出し | 地の文 | 後続なし |
|---|---|---|---|---|
| `以下`/`次の` あり | 38 | 4 | 14 | 6 |
| なし | 17 | 2 | 81 | 6 |

前方参照を示す語句がなく地の文が続く81件のうち、列挙の表現を含んでいたのは3件のみであった。残る78件は、数値と列挙がその場で完結していた。

当初は「箇条書きが続かない発火」を一律に誤検出とみなし、誤検出率 67% と算出していた。しかし実際の箇所を確認したところ、この前提は誤りであり、見出しが続く構成でも本文との不整合が起こることが分かった。

```
次の3つの命名規則がよく使われます。

### DNSサブドメイン名
```

規則を1つ追加すると、`次の3つ` という記述は事実と合わなくなる。数え上げの対象が箇条書きの項目か見出しかは、不整合の起き方に関係しない。判定の基準とすべきは、数値が別の箇所を参照しているかどうかである。

### 帰結

参照コーパスにおける発火数は、112文書から67文書へ減少した。ゴールデンテストに挙げられていた事例も抑止された。

規則の適用範囲を定める際は、規則を設けた理由から条件を導出する必要がある。M2 の理由は「項目を増減すると本文が合わなくなる」点にあり、その問題が生じるのは数値と項目を別々に編集できる場合に限られる。箇条書きが後続するかどうかは、条件の一部にすぎなかった。

英語側にも同一の条件を導入した。前方参照を示す語として `following`、`below`、`these` を、列挙を示す語として `first`、`second`、`one is` を設定している。英語の参照コーパスに対する個別分類は行っていないため、この語彙一覧は日本語側からの対応付けによって定めた。
## D-46 節の記述量は型で定義するが、規則にはしない

### 文脈

ドキュメントの型には、配置する節の種類と各節が答えるべき問いが定義されていたが、記述量の目安は定義されていなかった。その結果、執筆者が各節の分量を個別に判断することになり、節ごとの粒度が揃わなかった。

### 決定

各節に `scale` を持たせ、`plot` と `brief` から出力する。一方で、`check` では発火させず、規則としては扱わない。

記述量の目安は絶対的な文字数ではなく、節同士の相対的な大小関係と内容の構成によって示す。

### 根拠

著名な OSS の README 221件を対象に計測した。収集した240件のうち、中国語で書かれた19件は対象外としている。本ツールの対象言語が日本語と英語であるためである。

| 節 | 件数 | 文字数の中央値 | 下位1/4〜上位1/4 | 箇条書きの行数 | 地の文の行数 |
|---|---|---|---|---|---|
| ライセンス | 96 | 212 | 109〜452 | 0 | 2 |
| ドキュメント | 91 | 349 | 171〜854 | 0 | 1 |
| コントリビューション | 157 | 386 | 202〜766 | 0 | 2 |
| インストール | 203 | 455 | 186〜954 | 0 | 3 |
| 使い方 | 72 | 480 | 211〜920 | 0 | 2 |
| 説明 | 32 | 668 | 403〜969 | 0 | 3 |
| 設定 | 54 | 739 | 327〜1568 | 0 | 7 |
| 機能 | 78 | 1032 | 495〜1815 | 6 | 2 |

ライセンスから機能まで5倍の幅があり、節ごとの順序と構成は安定している。`機能` だけが箇条書きを中心としており、`設定` は地の文の行数が最も多い。

**規則にしない理由は、四分位範囲が中央値の 2.5 倍から 3 倍まで広がる点にある。** 人間が書いた文書の分布が分離しないため、閾値を設定できない。同じ理由で除外した候補は D-43 および `corpus/baselines.toml` の `[rejected]` に記録されている。

コードブロックの有無も必須条件にはできない。インストールに相当する `入れ方` 節203件のうち、コードブロックを含むのは100件（49%）にとどまる。残りの半数は、Wiki への誘導、ビルド手順の文章による解説、配布物一覧などで構成されている。

### 計測手法を3回修正した

最初の計測では、対象範囲と分類条件に誤りがあった。

| 誤り | 影響 |
|---|---|
| 本文がほぼ空の節を集計対象にした | 実質的な内容が小見出し配下にある節が標本に混入した |
| 見出しの部分一致で節を分類した | `What's New` が `説明` に誤分類された |
| 中国語の README を集計対象に含めた | 対象外の言語が標本に混入した |

これらの誤りを修正した結果、`説明` の件数は 49 から 32 へ、`機能` の文字数の中央値は 731 から 1032 へと変動した。計測手順は `research/structure/measure_granularity.py` に実装されている。

### 帰結

`scale` を定義している型は `readme` のみである。他の型についてはコーパスによる計測を実施していない。対象となる型が `readme` に限定されることはテストで確認している。

また、日本語と英語の双方の定義が揃っていることもテストで検証している。片方の言語が欠けると、その言語の出力から指標が消えてしまうためである。

README の変種は作成しなかった。ライブラリ向けとアプリケーション向けで構造が分かれるか計測したところ、API に関する節を持つものが 10%、パッケージマネージャーによるインストール方法を示すものが 14% にとどまり、56% はいずれの群にも属さなかった。節の構成は連続的に分布しており、明確な群には分かれなかった。

## D-47 段階的リリース向けの提案型を追加し、節の存在判定は階層を問わない

### 文脈

設計文書向けの型は Rust RFC を出典とする `design` のみであった。

同じ設計文書であっても、求められる内容は異なる。Kubernetes Enhancement Proposal（KEP）では、`Test Plan`、`Graduation Criteria`、`Upgrade / Downgrade Strategy`、`Version Skew Strategy`、`Production Readiness Review` といった運用準備の事項が問われる。段階的にリリースする機能では、これらを定めずに進めることはできない。

### 決定

KEP の様式を出典とする `enhancement` 型を追加する。

必須とする節は Summary、Motivation、Goals、Proposal の4項目とする。

節が存在するかどうかは見出しの階層を問わず判定し、順序の検証のみ最上位の見出しを対象とする。

### 根拠

公開されている KEP 265件を計測した。19 SIG から1 SIG あたり最大25件を対象とし、テンプレートのまま未記入の文書は除外した。402件のうち212件がこの除外対象に該当した。

| 節 | 出現率 |
|---|---|
| Summary | 98% |
| Motivation | 95% |
| Goals | 94% |
| Proposal | 94% |
| Graduation Criteria | 92% |
| Implementation History | 91% |
| Non-Goals | 87% |
| Risks and Mitigations | 77% |
| Test Plan | 76% |
| Design Details | 71% |
| Alternatives | 71% |
| Production Readiness Review | 61% |
| Version Skew Strategy | 58% |
| Upgrade / Downgrade Strategy | 57% |
| Drawbacks | 53% |
| User Stories | 39% |

必須項目は個別の出現率ではなく、組み合わせ全体で決定した。いずれか1つでも欠ければ規則が発火するためである。

| 必須項目の組み合わせ | 発火率 |
|---|---|
| Summary | 2% |
| + Motivation | 6% |
| + Goals + Proposal | 9% |
| + Non-Goals | 15% |
| + Graduation Criteria + Test Plan | 29% |

発火率が 9% となる組み合わせを採用した。他の型と同程度の水準に収まるためである。

運用準備に関する節は必須項目から除外した。ただし問いと記述すべき内容は定義に残しており、plot と brief は引き続き執筆者へ確認を促す。D-31 および D-32 と同じ方針である。

### 見出し階層に依存しない節の存在判定

当初この型を適用したところ、265件中262件（98%）で発火した。原因は見出しの階層にあった。KEP では `Goals` を `## Motivation` の配下に `###` で配置する様式をとるが、節の照合が最上位の見出しのみを見ていたため検出できなかった。

**見出しの階層はフォーマット上の選択であって、意味的な欠落ではない。** 目標を動機に属する項目として構成しただけであり、節そのものが存在しないわけではない。

D-33 では、下位の階層まで参照すると節内の小見出しが別の節として誤認され、順序判定が破綻するという理由から、この制限を緩和しないと判断していた。

存在判定と順序判定を分離することで、その懸念は当たらなくなる。節の有無は階層を問わず確認し、順序は最上位の見出しのみで検証する。入れ子の見出しを最上位の見出しと並べて順序を論じても意味がないためである。

この分離により、`enhancement` の発火率は 98% から 8% まで低下した。

### 帰結

この変更は他の型にも影響し、発火率はいずれも低下する方向に動いた。

| 型 | コーパス | 発火率 |
|---|---|---|
| `readme` | README 240件 | 4% |
| `design` | Rust RFC 200件 | 8% |
| `decision` | ADR 190件 | 7% |
| `enhancement` | KEP 265件 | 8% |
| `howto` | k8s 手順ページ 41件 | 0% |

D-33 で課題として挙げられていた MADR の11件も検証を通過するようになった。`Decision Outcome` の配下に帰結を配置する様式であり、帰結自体が欠けていたわけではなかったためである。

D-33 では「様式ごとに型を分ける」という対策も挙げられていた。`enhancement` 型の追加がその方針に該当する。結果として、階層制限の緩和と型の分割の双方を実施したことになる。

型を選択する決定木にも分岐を追加した。`design` と `enhancement` は「段階的にリリースするか」という基準で分岐する。決定木からすべての型へ到達できることはテストで確認している。

## D-49 文書サイトは Hugo に留める。Zensical は多言語を扱えない

### 文脈

文書サイトを Zensical に移す案が出た。
Material for MkDocs の作者による Rust と Python の生成器である。

この文書サイトは英語と日本語を1つのビルドで出している。
`defaultContentLanguage` を英語とし、`[languages]` で `content/en` と `content/ja` を指している。

### 決定

Hugo に留める。Zensical には移さない。

### 根拠

Zensical は1つのビルドで2言語を扱えない。文書に明記されている。

> Zensical only supports setting a canonical language for the entire project.

`docs_dir` は単一のパスを取り、言語はプロジェクト全体の設定である。
言語切り替えは、別のサイトへのリンクを手で書く形になる。

プラグインで補う道も無い。
0.1.1 時点の文書が、任意の MkDocs プラグインを実行せず、
MkDocs のプラグイン API も公開しないと述べている。

`mkdocs-static-i18n` は、対応・非対応・予定のどの一覧にも無い。
対応一覧に無い設定は黙って無視される。
Module API は予定されているが、有償の Spark が先に提供される。

ロードマップに `Language organization` と `Language publishing` の項目はあるが、
`Now available`、`In development`、`Up next` の表に入っていない。
ロードマップ自身が、納期も順序も約束しないと書いている。
公式の更新情報は、module system を整えるあいだ 0.x に留まると述べている。

### 実機で確かめたこと

移せるかどうかを判断するため、0.1.1 を入れて試した。
文書に書かれていない点が2つ分かった。再検討する人のために残す。

| 項目 | 結果 |
|---|---|
| サブパスでの公開 | 成立する。相対リンクで出力されるため base-path の設定が不要 |
| 言語切り替えの設定 | `[[project.extra.alternate]]` で出る。文書に鍵の名前が無い |
| `site_dir` | プロジェクトの直下に限られる。外へ出すと拒否される |
| 独自のフロントマター | 保持される。`doctype` は影響を受けない |
| ビルド | 0.26 秒。出力 592K。Hugo は 796K |

2プロジェクト構成（`docs/en` と `docs/ja` に設定を各1つ）なら成立する。

### 採らなかった理由

2プロジェクト構成は `nav` を2つの設定ファイルで二重に維持することになる。
D-48 で「同じ表を複数の場所に置かない」と決めた直後であり、そこと衝突する。

査読前の草稿にある備忘は、この方法では見えない。

後続に見出しが現れたことで、前方参照と誤判定されていた。`## ライセンス` は数値が指し示す対象ではなく、単に直前の節が終わったことを示すにすぎない。

**数値が指し示せる対象は、その節の内部にある要素に限られる。** そこで、カウント対象とする見出しを、その節より深い階層のものだけに限定した。

参照コーパスにおける該当件数は、節の内部が1件、兄弟見出しが1件であり、件数面での差はない。修正の根拠は件数ではなく、数値が指し示せる論理的な範囲にある。節の末尾の段落に数値が含まれるだけで必ず発火する挙動は、発生件数が少なくても欠陥である。

同一の表を複数箇所で重複管理しない。`CLAUDE.md` と README のどちらを正本とするかを定め、もう一方は参照にとどめる。

## D-51 neon の文体をこのリポジトリの基準として採用する

### 文脈

2026-11-24 のコミット 7d07fc5 で、Gemini（neon）がこのリポジトリの26ファイルを書き直した。書き直しは文体の全面的な変換であり、冒頭を定義文に、見出しを体言止めの名詞句に、段落をハードラップせず1行にまとめ、和語をカタカナ語と漢語へ置き換えた。一文の長さは中央 31字から 42字へ、本文行の長さは中央 33字から 91字へ伸びた。

書き直し前の文体は変更前の閾値を満たしていたが、書き直し後は日本語側で複数の指標が閾値を超えた。英語側では逆に局所指摘が25件から1件へ減った。

人間コーパスと AI コーパスの実測範囲に対する書き直し後の位置を以下に示す。

| 指標 | 人間ネイティブ | AI 4モデル | 書き直し前 | neon |
|---|---|---|---|---|
| renyo_te_ratio | 1.79–2.00 | 3.62–15.94 | 1.42 | 9.00 |
| renyo_per_1k | 2.29–2.71 | 4.81–6.75 | 2.48 | 4.60 |
| kango_ratio | 0.326–0.397 | 0.455–0.519 | 0.456 | 0.550 |
| mattr100 | 0.569–0.581 | 0.629–0.665 | 0.585 | 0.611 |
| demonstrative_per_1k | 5.69–6.47 | 1.38–3.39 | 8.14 | 5.72 |
| keishiki_meishi_per_1k | 11.10–11.16 | 4.99–6.95 | 10.71 | 8.84 |

`renyo_te_ratio` は AI 範囲の中央に入り、`kango_ratio` は AI 範囲を超えている。一方 `demonstrative_per_1k` は人間ネイティブの範囲に改善した。

### 決定

neon の文体をこのリポジトリの文書の基準として採用する。閾値の緩和は `.suikou/profile.toml` のプロジェクト単位の上書きに限定し、組み込みの `oss` プロファイルは変更しない。緩めた閾値は利用者の文書に届かない。

ただし、規則の精度の修正2件は利用者にも届く。`register/rare-wago` は表層がすべてカタカナの語を和語の判定から除外するようになり、`structure/missing-section` は `事前準備` を前提の節として認めるようになった。どちらも偽陽性を減らす方向にのみ働く。

閾値は `suikou baseline` の出力をそのまま採らず、このリポジトリの日本語文書9件の実測の最大値に 3% 程度の余裕を足して決めた。`baseline` が使う Tukey の上側フェンス（Q3 + 1.5×IQR）はコーパス内の外れ値を見つけるツールであり、文体の基準を決めるツールではない。サンプル9件では最大値を大きく超える位置に落ちる。`ja.renyo_te_ratio` では較正値 23.21 が実測の最大 12.75 の 1.8 倍、かつ AI 4モデルの実測範囲の上端 15.94 をも超えた。較正値を採ると、この指標は AI 文を一切検出しなくなる。

`ja.list_ratio` と `ja.prose_ratio` は上書きしない。実測は 0.167（既定 0.25）と 0.870（既定 0.75）で、どちらも一度も発火していない。発火していない指標を緩めるのは根拠の無い緩和である。

`ja.demonstrative_per_1k` は緩和しない。`baseline` が「較正した境界が値域の外に出て、この閾値は永久に発火しない」として較正を断るためである。既定の 4.5 を保ち、下回っていた3件の文書に指示詞を補った。

### 根拠

既定の閾値を neon の実測値から引き直す案は採らない。その場合 `renyo_te_ratio` の閾値は 23.21 となり、AI 4モデルの実測範囲 3.62–15.94 が丸ごと閾値の下に収まる。`kango_ratio` も同様である。この2つの指標が AI 文を検出しなくなり、ツールの主張そのものが変わる。

採用した閾値と、それによって失う検出力を以下に示す。

| 指標 | 既定 | 実測の最大 | 採用値 | AI 4モデル | 検出力 |
|---|---|---|---|---|---|
| ja.renyo_te_ratio | 3.0 | 12.75 | 13.2 | 3.62–15.94 | 範囲の上側のみ残る |
| ja.renyo_per_1k | 4.0 | 7.16 | 7.4 | 4.81–6.75 | 失う |
| ja.mattr100 | 0.60 | 0.6235 | 0.64 | 0.629–0.665 | ほぼ失う |
| ja.kango_ratio | 0.52 | 0.5871 | 0.59 | 0.455–0.519 | 失う |

`ja.renyo_per_1k` と `ja.mattr100` と `ja.kango_ratio` では、この文体を通す閾値が AI の実測範囲の中か上に来ることを避けられない。実測の最大がすでに AI 範囲に達しているためである。`CLAUDE.md` の連用中止の密度 7.16 は、測定した4モデルのいずれよりも高い。この3つで検出力が落ちることは承知の上で採る。`ja.renyo_te_ratio` だけは実測の最大が AI 範囲の中にあり、13.2 を採ることで範囲の上側に対する検出が残る。

型ごとの `[doctype.*]` に手で値を置く案も採らない。型ごとのサンプルは log、design、howto、overview、readme がいずれも1件であり、過適合になる。D-41 が型ごとの調整を導入した根拠は README 240件と参照コーパス652件の実測であって、1件ではない。ツール自身が4件未満の較正を断る水準を、手で置くことで迂回してはならない。

採用に伴って3つの偽陽性も是正した。`register/prefer-katakana` の `検査→テスト` は27件発火していたが、このリポジトリで `検査` は lint の検査を指し、`テスト` は `cargo test` を指すため、置換すると誤りになる。

`register/rare-wago` は `トレイト` を `トレ` と `イト` に割った辞書の出力を受け、`イト` の語彙素 `糸` を和語として検出していた。変更前のガードは1文字のカタカナだけを除いており、2文字が通っていた。

このガードを広げると和語をカタカナで書いた語も外れる。実測では形式名詞と代表的な和語13語の単独の出現がプロの日本語訳798件で1件、AI 執筆の日本語150件で0件であった。その1件は生理学の文脈の `ヒト` であり、種の名前という分野の慣習である。

硬い文体の語（`否`、`留まる`、`内訳`）と執筆を論じる領域の語（`表記ゆれ`、`書き出し`）も誤検出であった。参照コーパスが Kubernetes、MDN、Vue の日本語訳という Web の文書であり、これらの register が手薄なためである。

ただし、指摘された和語のすべてを許可語にはしない。参照コーパス798件での出現数を語ごとに測定し、0件の語は置換した。`改める`（0件）を `変更する`（266件）へ、`上がる` を `増加する`（45件）へ、`取りこぼし`（0件）を `見落とし`（6件）へ替えた。この2語は CLAUDE.md の段階6 が挙げる身体動作の和語に当たる。

表記の少数派も統一した。`保守`（2件）を `メンテナンス`（17件）へ、`書式`（4件）を `フォーマット`（11件）へ統一し、許可語から外した。`食い違う` は0件だが12箇所に及ぶため置換は採らず、`TASKS.md` に案件として記録した。

`structure/missing-section` は体言止めの見出しと衝突した。neon は前提の節を `事前準備` と改名しており、同義語の一覧に無かったためである。`事前準備` を同義語に足した。`structure.toml` の冒頭は `register/prefer-katakana` について同じ原則を記録している。ツール自身が勧める書き方に従った文書を、別の規則が拒んではならない。

段落単位の計測は別の案件とした。実測では `ja.kango_ratio` が閾値 0.64 で書き直し前 3.6% に対し neon 15.5% となり、4.3 倍に分かれる。`ja.renyo_te_ratio` は `MIN_TE_FOR_RATIO` の門により562段落のうち38段落しか値が出ず、段落単位では成立しない。`ja.renyo_per_1k` は測れるが、超過が段落の半数に散るため位置を指せない。経緯は `TASKS.md` にある。
