suikou の調整とは、自分の文書を計測し、その文書の性質に合う値へ閾値を変更する作業である。
好みに合わせて閾値を書き換える作業とは異なる。

## 調整を始める前に確認すること

調整を始める前に、`suikou check` を一度実行する。
どのレイヤーの指摘が出ているかによって、設定を書くファイルが変わる。

```sh
suikou check docs/*.md --format text
```

合否は指摘の件数で判断する。
終了コードは error があるときだけ 1 を返すので、終了コードだけを見ると warning を見落とす。

```sh
suikou check docs/*.md --format text | grep -c ':[0-9]*:[0-9]*:'
```

## suikou が検査する対象

suikou にはレイヤーが3つあり、レイヤーごとに調整する場所が異なる。

| レイヤー | 検査の対象 | 出力 | 例 |
|---|---|---|---|
| 局所の規則 | 行の中の表現の形 | 位置と修正方法 | `maint/list-lead-in`、`register/rare-wago` |
| 文書指標 | 文書全体の数値 | 書き直しを指示する文 | `ja.kango_ratio`、`en.mattr100` |
| 構造の規則 | 節の有無と順序 | 足りない節 | `structure/missing-section` |

局所の規則は位置を示すので、どこを直せばよいかがすぐに分かる。
文書指標は数値をそのまま出力せず、指示の文に変換してから出力する。
構造の規則は、文書が宣言した型に対してだけ適用する。

日本語では、形態素解析で語種と活用形を判定する。英語では、語を単位にして判定する。
この言語ごとの違いは、`tokenizer.rs` の内部だけで扱っている。

各指標と各規則の厳密な定義は [指標の定義]({{< relref "metrics.md" >}}) に書いてある。
レイヤーの分け方と、各レイヤーの役割は [設計]({{< relref "design.md" >}}) で説明している。

## 閾値の決め方

閾値は、プロの書き手が書いた文書を計測して導いた。
閾値の値は、人間の文体と AI の文体の分布が分かれる位置に設定している。

文末の連用中止の比を例に取る。
この比は、人間のネイティブの文書で 2.00、人間による翻訳で 1.79、AI の文書で 3.62 から 15.94 だった。
この結果から、閾値を 3.0 に定めた。

語感に頼って閾値を変更すると、人間と AI を分けている境界の位置がずれる。
閾値を変更するときは、自分のコーパスを計測してから値を決める。

各指標がどのコーパスでどのような値を示したかは、[指標の定義]({{< relref "metrics.md" >}}) に書いてある。
不採用にした指標の一覧は、`corpus/baselines.toml` の `[rejected]` にある。

## 調整できる項目と設定の場所

次の表は、変更したい内容から設定の場所を探すためのものである。

| 変更したい内容 | 設定の場所 |
|---|---|
| すべての文書の閾値を変える | `.suikou/profile.toml` の `[thresholds]` |
| 文書の型ごとに閾値を変える | `.suikou/profile.toml` の `[doctype.<型>]` |
| 特定の指標を出力しない | `.suikou/profile.toml` の `disable` |
| 特定の型で局所の規則を出力しない | `[doctype.<型>]` の `rules` |
| プロジェクトで定めた名前を固定する | `.suikou/defined.toml` |
| 表記の揺れを追加する、または打ち消す | `.suikou/glossary.toml` |
| 分野に固有の語を許可する | `.suikou/terms.toml` |
| 文書に型を割り当てる | `.suikou/structure.toml` の `[paths]` |

設定ファイルに書いた項目だけが、組み込みの値を置き換える。プロファイル全体を写して書く必要はない。

型ごとの調整は、次の形式で書く。

```toml
[doctype.readme]
reason = "入り口の文書であり、箇条書きが主になる"
rules = ["structure/long-paragraph"]

[doctype.readme.thresholds."ja.kango_ratio"]
value = 0.65
```

`reason` には、その調整をした経緯を書く。
組み込みの調整には理由が書かれていることを、テストで確認している。
経緯を残すのは、後から読む人が同じ検討を繰り返さなくて済むようにするためである。

設定ファイルの形式と、設定を重ねる順序は、[指標の定義]({{< relref "metrics.md" >}}) の「閾値の調整」に書いてある。
用語集を蓄える3つの場所の違いは、[書き方]({{< relref "writing.md" >}}) で説明している。

## うまく調整するための進め方

### 自分のコーパスで閾値を較正する

`suikou baseline` を実行すると、与えたコーパスから閾値を計算する。

```sh
suikou baseline docs/ --lang ja > .suikou/profile.toml
```

較正できない指標は、理由を標準エラー出力に書き、出力する設定からは除く。
較正できないのは、サンプルが足りない指標と、境界が値の範囲の外に出てしまい二度と発火しなくなる指標である。
こうした指標を 0 や仮の値で埋めないので、根拠のない閾値が設定されていれば気付ける。

### 発火率で閾値の妥当性を判断する

ある指標が 70% の文書で発火する場合、原因は文書の性質ではなく、閾値が文書に合っていないことにある。

広く知られた OSS の README 240件に、既定の閾値を適用した結果を次の表に示す。

| 指標 | README | 参照コーパス |
|---|---|---|
| `en.mattr100` | 70% | 15% |
| `en.prose_ratio` | 32% | 11% |

この発火率の差を根拠に、文書の型ごとに閾値を分けることにした。
自分のコーパスでも、同じ方法で発火率を測れる。

```sh
for f in docs/*.md; do suikou check "$f" --format text; done | grep -oE 'ja\.[a-z_]+' | sort | uniq -c
```

### 発火率が高い原因を切り分ける

発火率が高い原因には次の3種類があり、種類ごとに対処が異なる。

| 原因 | 確認の方法 | 対処 |
|---|---|---|
| 文書が短く、指標に分解能がない | 語数の帯ごとに発火率を見る | 指標に下限を設ける。型は問わない |
| 型によって分布が異なる | 型ごとに発火率を比べる | 型ごとに閾値を変える |
| 分布が広すぎて境界を引けない | `suikou baseline` の報告を読む | その型では指標を適用しない |

最初に型を疑うと、他の型に同じ欠陥が残る。
比喩の標識の密度は、型の問題のように見えたが、実際は文書の長さの問題だった。
経緯は [決めたことの記録]({{< relref "decisions.md" >}}) の D-43 に書いてある。

### 一回の変更では一つの項目だけを変える

設定を変更するたびに、発火率を計測する。
複数の項目を同時に変えると、どの変更が効果を生んだのかが分からなくなる。

### info は参考として読む

合格の条件は、error と warning が一件もないことである。
漢語率のような参考値は info に分類されており、ゼロにすることを目指す値ではない。

## 避けるべき調整

### 指標の値を最小にすることを目標にしない

漢語率をゼロにしようとして漢語を和語の動詞に置き換えた結果、文体が悪くなったことがある。
漢語率を下げたい場合は、定着したカタカナ語を使い、漢語の名詞を連ねないようにする。
この失敗は [決めたことの記録]({{< relref "decisions.md" >}}) の D-27 に記録している。

### 指摘を出さなくするためだけの調整をしない

`disable` にすべての指標を並べれば、指摘は出なくなる。
しかし、出なくなった指摘の分だけ、文書の問題が見えなくなる。

発火率が高い指標については、最初に原因を切り分ける。
原因を確かめないまま指標を除くと、同じ欠陥が他の文書に残る。

### 語感で語を置き換えない

指摘された語を何に置き換えるかは、参照コーパスで出現数を数えてから決める。
`読み手` はプロが書いた日本語 400 万字の中に1件も出現せず、`読者` は13件出現する。
この差は、計測するまで分からない。

語を選ぶ手順は、[書き方]({{< relref "writing.md" >}}) の「選定の手順」で説明している。

## 調整の結果を確認する方法

調整を終えたら、同じコーパスに対して suikou をもう一度実行する。

```sh
for f in docs/*.md; do suikou check "$f" --format text; done | grep -c ':[0-9]*:[0-9]*:'
```

発火率が 10% 前後に収まっていれば、閾値は自分の文書に合っている。
発火率が 70% のまま残っている指標は、閾値の問題ではなく、原因の切り分けが終わっていない状態にある。

指摘が 0件になった場合は、指標や規則を除きすぎていないかを確かめる。
確かめるには、`.suikou/profile.toml` の `disable` と `rules` に並んだ項目の数を見る。

この文書が扱うのは調整の手順だけである。
指標の定義は [指標の定義]({{< relref "metrics.md" >}}) に、設計の根拠は [設計]({{< relref "design.md" >}}) に、
個々の判断の経緯は [決めたことの記録]({{< relref "decisions.md" >}}) に書いてある。
