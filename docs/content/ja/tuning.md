suikou の調整は、閾値を好みで書き換える作業ではない。
自分の文書を計測して、その性質に合う位置へ閾値を変更する作業である。

## 前提

調整の前に `suikou check` を一度適用する。
どのレイヤーの指摘が出ているかによって、書くファイルが変わる。

```sh
suikou check docs/*.md --format text
```

判断は指摘の件数で行う。
終了コードは error でのみ 1 を返すため、これだけを見ると warning を見落とす。

```sh
suikou check docs/*.md --format text | grep -c ':[0-9]*:[0-9]*:'
```

## suikou が何を見ているか

レイヤーが3つあり、レイヤーごとに調整の場所が違う。

| レイヤー | 見るもの | 出力 | 例 |
|---|---|---|---|
| 局所の規則 | 行の中の形 | 位置と直し方 | `maint/list-lead-in`、`register/rare-wago` |
| 文書指標 | 文書全体の数値 | 書き直しの指示文 | `ja.kango_ratio`、`en.mattr100` |
| 構造の規則 | 節の有無と順序 | 不足している節 | `structure/missing-section` |

局所の規則は位置を示すため、どこを直すかがそのまま分かる。
文書指標は数値をそのまま出力せず、指示の文に変換して出力する。
構造の規則は、文書が宣言した型に対してだけ適用される。

日本語は形態素解析で語種と活用形を判定する。英語は語の単位で判定する。
この境は `tokenizer.rs` の内側に閉じてある。

各指標と各規則の厳密な定義は [指標の定義]({{< relref "metrics.md" >}}) にある。
レイヤーの分け方と、レイヤーごとに何を担うかは [設計]({{< relref "design.md" >}}) にある。

## 閾値がどこから来たか

閾値はプロの人間が書いた文書を計測して導いてある。
人間の文体と AI の文体が分かれる位置に置いてある。

文末の連用中止の比を例として示す。
人間のネイティブは 2.00、人間の翻訳は 1.79、AI は 3.62 から 15.94 である。
閾値は 3.0 とする。

語感で閾値を変更すると、この分離が崩れる。
変更するときは自分のコーパスを計測してから決定する。

どの指標がどのコーパスで何を示したかは [指標の定義]({{< relref "metrics.md" >}}) にある。
採用しなかった指標の一覧は `corpus/baselines.toml` の `[rejected]` にある。

## どこを調整できるか

変えたいものから引く。

| 変えたいこと | 書く場所 |
|---|---|
| 閾値を全体で変える | `.suikou/profile.toml` の `[thresholds]` |
| 文書の型ごとに閾値を変える | `.suikou/profile.toml` の `[doctype.<型>]` |
| 指標を出力しない | `.suikou/profile.toml` の `disable` |
| 局所の規則を型ごとに出力しない | `[doctype.<型>]` の `rules` |
| プロジェクトで決めた名前を固定する | `.suikou/defined.toml` |
| 表記の揺れを追加する、または打ち消す | `.suikou/glossary.toml` |
| 分野の語を許可する | `.suikou/terms.toml` |
| 文書に型を割り当てる | `.suikou/structure.toml` の `[paths]` |

書いた欄だけが組み込みの値を置き換える。プロファイル全体を複製する必要はない。

型ごとの調整は次の形で書く。

```toml
[doctype.readme]
reason = "入り口の文書であり、箇条書きが主になる"
rules = ["structure/long-paragraph"]

[doctype.readme.thresholds."ja.kango_ratio"]
value = 0.65
```

`reason` には調整の経緯を書く。
組み込みの調整が理由を持つことをテストが確認している。
後から読む人が同じ検討を繰り返さずに済む形で残す。

フォーマットと重ねる順序は [指標の定義]({{< relref "metrics.md" >}}) の「閾値の調整」にある。
用語集の3つの蓄積場所の違いは [書き方]({{< relref "writing.md" >}}) にある。

## 調整のコツ

### 自分のコーパスで較正する

`suikou baseline` が、与えたコーパスから閾値を算出する。

```sh
suikou baseline docs/ --lang ja > .suikou/profile.toml
```

較正できない指標は、理由を標準エラーに出力して出力から除外する。
サンプルが不足している指標と、境界が値域の外へ出て永久に発火しなくなる指標である。
0 や仮の値で埋めないため、根拠のない閾値に気付ける。

### 発火率で妥当性を判断する

指標が 70% の文書で発火する場合、それは文書の性質ではなく閾値の不一致である。

著名な OSS の README 240件に既定の閾値を適用した結果を示す。

| 指標 | README | 参照コーパス |
|---|---|---|
| `en.mattr100` | 70% | 15% |
| `en.prose_ratio` | 32% | 11% |

この差が、文書の型ごとに閾値を分割する根拠になった。
自分のコーパスでも同じ測り方ができる。

```sh
for f in docs/*.md; do suikou check "$f" --format text; done | grep -oE 'ja\.[a-z_]+' | sort | uniq -c
```

### 発火率が高い原因を分ける

原因は次の3種類であり、対処もそれぞれ違う。

| 原因 | 確かめ方 | 対処 |
|---|---|---|
| その文書の長さで分解能が無い | 発火率を語数の帯ごとに見る | 指標に下限を設定する。型を問わない |
| 型によって分布が違う | 型ごとに発火率を比べる | 型ごとに閾値を変える |
| 分布が広すぎて境界が引けない | `suikou baseline` の報告を読む | その型では適用しない |

型を先に疑うと、ほかの型に同じ欠陥が残る。
比喩の標識の密度は型の問題に見えたが、文書の長さの問題であった。
経緯は [決めたことの記録]({{< relref "decisions.md" >}}) の D-43 にある。

### 一度に一つだけ変える

変更ごとに発火率を計測する。
複数を同時に変更すると、どちらが有効だったかが分からなくなる。

### info は参考として読む

条件は error と warning が無いことまでとする。
漢語率のような参考値は info であり、ゼロにする対象ではない。

## やらない調整

### 指標の最小化を目標にしない

漢語率をゼロにしようとして和語の動詞へ置き換えた結果、文体が劣化した経緯がある。
漢語率を下げるなら、定着したカタカナ語を使い、漢語の名詞を連ねないようにする。
この失敗の記録は [決めたことの記録]({{< relref "decisions.md" >}}) の D-27 にある。

### 黙らせるだけの調整をしない

`disable` に全部を並べれば指摘は消える。
消えた指摘の分だけ、文書の問題が見えなくなる。

発火率が高い指標は、まず原因を区分する。
原因を確かめずに除外すると、同じ欠陥がほかの文書に残る。

### 語を語感で置き換えない

指摘された語の置き換え先は、参照コーパスで数えてから決定する。
`読み手` はプロの日本語 400 万字に1件も現れず、`読者` が13件現れる。
計測するまでこの差は分からない。

語を選ぶ手順は [書き方]({{< relref "writing.md" >}}) の「選定の手順」にある。

## 確認

調整の後に、同じコーパスへ再度適用する。

```sh
for f in docs/*.md; do suikou check "$f" --format text; done | grep -c ':[0-9]*:[0-9]*:'
```

発火率が 10% 前後に収まっていれば、閾値が自分の文書に合っている。
70% のまま残っている指標は、閾値ではなく原因の区分が済んでいない。

0件になった場合は、除外を入れすぎた可能性を確かめる。
`.suikou/profile.toml` の `disable` と `rules` の行数を見る。

この文書は調整の手順だけを扱う。
指標の定義は [指標の定義]({{< relref "metrics.md" >}})、設計の根拠は [設計]({{< relref "design.md" >}})、
個々の判断の経緯は [決めたことの記録]({{< relref "decisions.md" >}}) にある。
