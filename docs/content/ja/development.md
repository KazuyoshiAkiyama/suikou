本書は、このリポジトリで開発作業を行う際に遵守すべき事項をまとめたリファレンスである。ビルド手順、依存バージョンの固定方針、形態素解析の扱い、およびゴールデンテストの運用を定める。

## ディレクトリ構成

| パス | 役割 |
|---|---|
| `crates/suikou-core` | 解析エンジンのコア実装 |
| `crates/suikou-cli` | CLI と MCP サーバーの実装 |
| `packages/` | textlint 用の局所ルール |
| `skills/suikou` | エージェント向けスキル定義 |
| `research/` | キャリブレーションおよび探索用の Python スクリプト |
| `corpus/` | 基準値データおよびコーパス取得スクリプト |

## ビルドとテスト

Rust クレートのテストおよび静的解析には、以下のコマンドを使用する。

```sh
cargo test --all                           # 形態素解析なし。速い。まずこれ
cargo test --all --features lindera-unidic # 辞書を含む。遅い
cargo fmt --all
cargo clippy --all-targets -- -D warnings
```

デフォルトの feature には lindera を含めていない。辞書をダウンロードせずにテストを実行できるため、修正内容の検証を高速に行える。

配布用バイナリをビルドする際は、形態素解析用の feature を明示的に指定する。

```sh
cargo build --release -p suikou-cli --features lindera-unidic
```

辞書を含まないビルドは英語のみに対応する。このビルドに対して日本語の解析を要求した場合、空の結果を返すのではなく即座に異常終了する。実行環境に導入されているビルドがどちらの構成であるかは、`suikou selftest` で判別できる。

## 依存バージョンの固定

すべての依存クレートは `=` でバージョンを厳密に固定し、`Cargo.lock` もリポジトリにコミットする。指定するバージョン番号は、crates.io 上に実在することを確認したうえで記載する。

依存クレートのなかでも、lindera のバージョン管理は特に厳密に行う必要がある。lindera はバージョンによって API の仕様と UniDic の素性順序が変化するためである。素性順序に不整合が生じると、語種と活用形が検知されないまま誤った値になる。漢語率と連用中止は語種と活用形に依存しているため、誤った値のまま処理が進むと指摘内容そのものが不正確になる。

lindera を更新した際は、`LinderaMorphology::verify_schema` による検証を必ず実行する。この処理では既知の例文を解析し、品詞・語種・活用形が所定の位置から取得できることを確認する。不整合を検出した場合は、修正対象の定数を明示して異常終了する。検知されないまま誤った値を返すよりも、異常終了させる方が安全であるためである。

## 形態素解析の扱い

形態素解析器はバージョンによって挙動が変化するため、依存範囲を局所化している。バージョンに依存する実装は `crates/suikou-core/src/tokenizer.rs` 内の `LinderaMorphology` に限定し、その他のモジュールはすべて `Morphology` トレイト経由で形態素解析を利用する。テスト実行時は `FakeMorphology` を使用するため、辞書を組み込まない環境でも動作確認が可能である。

指標を追加する際も、このトレイト経由の設計を維持する必要がある。トレイトを介さず直接依存すると、辞書なし環境でのテストが実行できなくなる。

実測値として、release ビルドにおける埋め込み辞書の読み込み時間は 0.7 ミリ秒、読み込み後の1文あたりの解析時間は 9.6 マイクロ秒である。計測には以下のコマンドを使用する。

```sh
cargo run --release --features lindera-unidic --example dict_load
```

## 指標ごとの解析対象の分離

語彙に関する指標（MATTR、漢字率、漢語率、指示詞、形式名詞）は `Document::body()` を対象に算出する。一方、文構造に関する指標（文長、読点、連用中止、テ形接続）は `Document::prose()` を対象とする。

語彙指標の計測対象を地の文だけに限定してはならない。出力の大半を箇条書きで構成するモデルが存在するため、地の文のみを抽出すると本文の8割以上が解析対象から除外される結果となる。

## 前処理の順序と行番号の保持

`markdown.rs` の `preprocess` における処理順序は厳密な意味を持つ。バックスラッシュによるエスケープの解除を後段へ移動させると、文分割が正しく機能しなくなる。AWS の doc_source がこのエスケープ形式を採用しており、エスケープを解除しない場合、平均文長は3倍以上に増加する。

この挙動は `tests/golden/input/en_escaped.md` によって固定している。

前処理で除去した範囲は、元の行数と同数の改行に置換する。これにより、レポートの指摘位置とユーザーが参照している行番号が一致する。解析値自体が正確であっても、行番号が一致していなければ指摘として実用にならないためである。

## 発火率の計測

規則の追加や閾値の変更を行った際は、参照コーパスに対する発火率を計測する。

```sh
cargo run --release --example structure_rate -- corpus/cache/pro_en en
cargo run --release --example structure_rate -- corpus/cache/pro_ja ja
```

`suikou check` は規則ごとに出力する検出位置の件数に上限を設けているため、CLI の出力結果からは総件数を集計できない。上記のサンプルプログラムは規則を直接呼び出して集計するものであり、計測値は `TASKS.md` に記録する。

参照コーパスはライセンス上の理由からリポジトリに含めていない。計測前に `corpus/fetch.sh` を実行して取得する。

必須セクションの規則を計測するには、文書型が宣言されたコーパスが必要になる。

```sh
python research/structure/fetch_typed.py corpus/cache/typed 120
```

このスクリプトは Kubernetes の `content_type:` ごとにページを収集する。収集した文書に対し、`.suikou/structure.toml` の `[front_matter]` 設定で本ツールの文書型へマッピングしたうえで `check` を実行する。使用する設定ファイルは `research/structure/structure.toml` である。

規則を変更した際は、変更前後でレポートの総文字数を比較する。`git worktree` を用いて変更前のバージョンをビルドし、同一のコーパスに対して実行した出力文字数の合計を照合する。

`design` 型の検証には Rust RFC を用いる。

```sh
python research/structure/fetch_rfcs.py corpus/cache/rfcs 200
```

文書型の由来元そのものを対象とするため、最も厳格な検証となる。

`decision` 型の検証には公開されている ADR を用いる。

```sh
python research/structure/fetch_adrs.py corpus/cache/adrs 200 12
```

この計測用の設定ファイルは `research/structure/structure-adr.toml` に配置されている。

## ゴールデンテスト

ゴールデンテストは、参照実装との間で解析結果の値を統一するために設けている。

`crates/suikou-core/tests/golden_rules.rs` が規則の検出件数を、`golden_metrics.rs` が文書指標をそれぞれ `tests/golden/expected/` 配下の期待値と照合する。英語のテストケースは辞書なしで動作し、日本語のテストケースは `--features lindera-unidic` を指定して実行される。

lindera と fugashi は異なるトークナイザであるため、照合には許容誤差を設けている。比率指標は絶対誤差 0.02、1000文字あたりの密度は 0.5 までを許容し、M 系の規則は完全一致を要求する。語数および文数はトークナイザの定義に依存するため、相対誤差 1% までを許容する。

許容誤差を超える差異が生じた場合は、いずれの実装が妥当であるかを都度判断し、その根拠を決定記録に残す。Python 側の実装が常に正しいとは限らない。

## 直感による規則追加の禁止

**直感に基づいて規則を追加しないことは、このリポジトリで最も重要な制約である。**

文体の特徴に関して直感で立てた仮説は、検証すると大半が成立しない。本プロジェクトの設計過程でも、仮説の多くが実測値によって棄却されている。翻訳調の研究においても同じ現象が起きている。

規則を追加する場合は、いずれかの客観的な根拠を示す必要がある。

- 人間によるコーパスと AI 出力の実測値があり、両者の分布範囲が重複しないこと。
- 明文化されたスタイルガイドの規約があり、その出典を示せること。

除外された指標とその理由は `corpus/baselines.toml` の `[rejected]` に記録されている。**ここに記載された指標を導入してはならない。**具体的には、文長の変動係数、外来語率、および英語の分詞節と名詞化が該当する。これらはいずれも「AI らしさの指標」として広く言及される要素だが、実測すると人間の文章の分布範囲と重複する。

## 出力トークン量の抑制

レポートの出力トークン量を抑えるため、出力形式には制約を設けている。

- ルールの説明はルールごとに一度だけ出力し、行ごとに繰り返さない。
- 各ルールで提示する検出位置の上限は `Report::MAX_POSITIONS_PER_RULE` 件までとする。
- 閾値の範囲内に収まっている指標は出力しない。
- 文書指標は数値のままではなく、指示文に変換して出力する。

これらの制約は、レイヤーごとに lint と修正を往復させないための設計に基づいている。レポートの出力形式を変更する際は、この設計目的に反していないかを確認する必要がある。
