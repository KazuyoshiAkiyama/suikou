作り方、バージョンの固定方、形態素解析の扱い、そしてゴールデンテストについて書く。
これらはいずれも、このリポジトリで作業するときに遵守する事項である。

## 作りとテスト

本体を確認するときは、次のコマンドを使う。

```sh
cargo test --all                           # 形態素解析なし。速い。まずこれ
cargo test --all --features lindera-unidic # 辞書を含む。遅い
cargo fmt --all
cargo clippy --all-targets -- -D warnings
```

既定の feature に lindera を入れていない。
そのため辞書を取得せずに本体を確認できて、修正したところを確認するのが速い。

配布用のビルドでは、その feature を書くことになる。

```sh
cargo build --release -p suikou-cli --features lindera-unidic
```

辞書を含まないバージョンは英語だけを扱うものである。
そのバージョンに日本語を求めた場合は、空の解析結果を返さずにその場で異常終了する。
どちらのバージョンがこの環境にあるかは `suikou selftest` で確認できる。

## バージョンを固定する

バージョンを固定することには理由がある。その理由をここに書く。

依存はすべて `=` で固定して、`Cargo.lock` も置くことにする。
そのバージョンは crates.io で実在を確認してから書く。

lindera はいちばん厳密に扱うことにする。
API の形と UniDic の素性の順序が、バージョンで変わるためである。
その順序が一致しなくなると、語種と活用形が気付かれずに壊れる。
漢語率と連用中止がこの二つに依存しているため、
壊れた値のまま動くと、指摘の内容そのものが誤りになる。

lindera を更新した場合は、`LinderaMorphology::verify_schema` を必ず通す。
知っている文を流して、品詞と語種と活用形が思った位置から取れることを確認する。
一致せずいた場合は、どの定数を直せばよいかを示して異常終了する。
気付かれずに誤った値を返すよりも、異常終了する方がよいためである。

## 形態素解析の扱い

形態素解析は、バージョンによって振る舞いが変わるものである。

バージョンに依存するコードは、`crates/suikou-core/src/tokenizer.rs` の
`LinderaMorphology` だけに置いてある。
ほかのモジュールは `Morphology` トレイト越しにしか形態素解析を使わない。
テストでは `FakeMorphology` を使うため、辞書がない場合でも確認できる。

指標を追加するときも、この境を越えない。
越えると、辞書なしでテストが回らなくなる。

測定した値では、埋め込んだ辞書の読み込みが release で 0.7 ミリ秒だった。
1文の解析はそのうえで 9.6 マイクロ秒だった。

```sh
cargo run --release --features lindera-unidic --example dict_load
```

## 指標の対象範囲を混ぜない

語彙の指標（MATTR、漢字率、漢語率、指示詞、形式名詞）は `Document::body()` を使う。
文の構成の指標（文長、読点、連用中止、テ形接続）は `Document::prose()` を使う。

語彙の指標を地の文だけで測定してはならない。
出力の大半が箇条書きになるモデルがあるためである。
その場合、本文の8割以上を破棄することになる。

## 前処理の順序を変えない

`markdown.rs` の `preprocess` は順序に意味がある。
バックスラッシュのエスケープを戻す処理を後ろへ動かすと、文分割が成り立たない。
AWS の doc_source がこの形式であり、戻さない場合の平均文長は3倍以上にふくらむ。

`tests/golden/input/en_escaped.md` がこの振る舞いを固定している。

取り除いた範囲は、同じ数の改行に置き換えることにする。
そうすることで、指摘が使う人の開いている行を指すようになる。
値が正しくても、位置が一致せずいればその指摘は役に立たない。

## 発火率を測る

規則を追加したり閾値を変更したりした場合は、参照コーパスに対する発火率を計測する。

```sh
cargo run --release --example structure_rate -- corpus/cache/pro_en en
cargo run --release --example structure_rate -- corpus/cache/pro_ja ja
```

`suikou check` は規則ごとに示す位置を打ち切るため、CLI の出力からは件数を数えられない。
この例は規則を直に呼ぶ。計測した値は `TASKS.md` に記録する。

コーパスは `corpus/fetch.sh` で取得する。ライセンスの都合でリポジトリには入れない。

必須の節を計測する場合は、型の宣言を持つコーパスが要る。

```sh
python research/structure/fetch_typed.py corpus/cache/typed 120
```

Kubernetes の `content_type:` ごとに頁を集める。
`.suikou/structure.toml` の `[front_matter]` でこちらの型に読み替えてから `check` を当てる。
その設定は `research/structure/structure.toml` にある。

レポートの字数は、規則を変更したときに前後で比べる。
`git worktree` で変更前のバージョンをビルドし、同じコーパスに当てて字数を合計する。

`design` の型は Rust RFC で計測する。

```sh
python research/structure/fetch_rfcs.py corpus/cache/rfcs 200
```

型の出どころそのものに当てるため、最も厳しい確認になる。

`decision` の型は公開されている ADR で計測する。

```sh
python research/structure/fetch_adrs.py corpus/cache/adrs 200 12
```

設定は `research/structure/structure-adr.toml` にある。

## 語を選ぶときの規範

語を選ぶときは、自分の語感で決めない。一般的な言い方を調べてから決める。

### 選定の手順

規則を思い出した順に当てると、結論が揺れる。順番を決めておく。

先に**制約**を当てる。成立するかしないかが決まり、候補が減る。
次に**選好**を当てる。残った候補に順序を付ける。
最後に**表記**を決め、**記録**する。

| 段 | 当てるもの | 種類 | 手法 |
|---|---|---|---|
| 1 | 定義した名前か | 制約 | `.suikou/defined.toml` を見る。あればそれで確定し、以降は行わない |
| 2 | 候補を挙げる | — | 思いつく語を並べる。ここは語感でよい |
| 3 | その分野で書かれるか | 制約 | 参照コーパスの頻度。0件なら落とす |
| 4 | 名詞と動詞の組が成立するか | 制約 | 組だけを取り出して読む |
| 5 | 意味が狭いか | 選好 | 対訳の散り方。収束する語を採る |
| 6 | 身体の動作の像に寄っていないか | 選好 | 同程度に狭いなら、像の薄い語を採る |
| 7 | 表記を決める | — | 参照コーパスで語ごとに数える。決まらなければ長音に倒す |
| 8 | 記録する | — | `glossary_ja.toml` に根拠つきで書く |

制約を先に当てる理由は、選好で順序を付けたあとに除外すると無駄になるためである。
段4で成立しない場合は段2に戻る。動詞を入れ替えると、段5の分析もやり直しになる。

### 段3の手法: 参照コーパスの頻度

```sh
grep -c "根因" corpus/cache/pro_ja/*.md
```

参照コーパスはプロの日本語訳であり、書くときに選ばれた語がそのまま出る。
0件なら、その分野では書かれない語である。

分野が合わない場合は効かない。
参照は API の説明であり、規範や上限を定める文が現れない。
`を置く` の置き換え先が決まらなかったのはこのためである。経緯は T19 にある。

### 段4の手法: 組だけを取り出して読む

```sh
cargo run --release --features lindera-unidic --example collocation -- <人間の側> <AIの側>
```

形態素解析で名詞と動詞の組を数え、人間の側に無く AI の側にある組を挙げる。
自動では適切な組を決められない。挙がった組を人が見る。

### 段5の手法: 対訳の散り方

```sh
plamo-translate server &
python research/glossary/narrow.py --ja2en 置く 配置する 設定する
python research/glossary/narrow.py --en2ja place configure deploy
```

方向によって対象が違う。

| 方向 | 測るもの | 使う場面 |
|---|---|---|
| `--ja2en` | その日本語がいくつの英語に分かれるか | 日本語の語の広さを知る |
| `--en2ja` | その英語がいくつの日本語に分かれるか | 揃える先を決める |

最小限の文型に語を入れて訳させる。コーパスの文では話題の語が混ざり、計測にならない。

実測の例を挙げる。

| 語 | 収束 | 訳 |
|---|---|---|
| 配置する | 100% | place×6 |
| 作成する | 100% | create×6 |
| 作る | 83% | create×5 make×1 |
| 置く | 67% | place×4 set×1 establish×1 |
| 設定する | 67% | set×4 configure×2 |

`置く` と `設定する` は同程度に広い。
`置く` を `設定する` にしても曖昧さは減らない。採るなら `配置する` である。
このツールを作る前は、広い語を広い語に入れ替える不適切な提案をしていた。

対象の語の訳が文型の名詞と重なる場合は計測にならない。
`configure` の訳は `設定` であり、文型の `設定を` と重なる。
その場合は数値を出さず、計測できないと返す。

### 段6の手法: 像の濃さで選ぶ

同程度に狭い語が残った場合は、身体の動作の像が薄い方を採る。
**この種類の語は AI らしさを強く印象づける。**
技術文書は、物を動かす話ではなく仕組みを説明する話である。

| 避ける | 選ぶ |
|---|---|
| 外す | 除外する |
| 落とす | 除去する |
| 拾う | 検出する |
| 寄せる | 統一する |
| 突き合わせる | 照合する |

実測では、ここに挙げた語をこのリポジトリは参照コーパスの8倍から32倍使っていた。
`外す` は参照コーパスで1万字あたり 0.06 だが、このリポジトリでは 1.90 であった。

`register/rare-wago` はこの種類を検出できない。
参照コーパスにも少数は現れるため、同規則の下限（参照の128倍）に届かない。
頻度では届かないが、選好としては決められる。`glossary/variant` がその役目を持つ。

一覧に無い語も同じ理由で避ける。
迷ったときは、その語が手や体の動きを思わせるかを問う。

### 逆向きの誤りに注意する

漢字の割合を下げるためだけに語を替えない。
`確認`、`使用`、`停止`、`動作`のように技術文書でふつうに使う漢語は、和語にしない。
その誤りを実際に犯した経緯が D-27 にある。

硬いだけで中身のない漢語（`多角的`、`包括的`）は別の問題として見直す。
助詞を省いて漢語を連ねた箇所は、語を残したまま助詞と動詞を補って分解する。

### 段8の手法: 用語集に記録する

調べて決めた語は `crates/suikou-core/data/glossary_ja.toml` に書く。
根拠として実測した値を併記する。
`glossary/` の汎用のフォーマットは `research/glossary/build_glossary.py` で作り直す。

表記は語の選択と分けて持つ。根拠の由来が違うためである。

### 反復を根拠にしない

段3で問うのは、その分野の書き手が仕様や手順書に書くときにこの語を選ぶかである。
話して通じるかではない。

同じ文書や同じリポジトリで繰り返し使っていることは、根拠にしない。
AI が書いた文書の語は次の文書にそのまま移るため、反復は定着の証拠にならない。
このリポジトリの文書は AI が書いたものであり、この点は自分に当てはまる。

段4で挙がった組に、正しい動詞を自動で当てることはできない。
動詞 32,822 語から統計で候補を出す方法は、上位600語ほどで正解率80%にとどまる
（中野・冨浦 2011）。決めるのは人である。経緯は T19 にある。

## README の書き方

### 先頭の段落に主題を置く

著名な OSS の README 240件を計測した結果、構造は見出しではなく先頭の段落にあった。

| 計測対象 | 値 |
|---|---|
| 先頭に段落を持つ割合 | 78% |
| そのうち300字以内 | 83% |
| 先頭の段落の字数の中央値 | 121 |

名前を主語にして、何であるかを述べる。300字以内に収める。

```markdown
# suikou

suikou は技術文書の lint である。日本語と英語を扱う。
```

背景、目的、経緯から始めない。
この3つの冒頭は、先頭の段落 831件（README、Rust RFC、ADR、参照コーパス）で0件であった。
`structure/lead-opener` が検出する。

### 見出しを必須にしない

見出しで同定できる節は、最大の `入れ方` でも 62% にとどまる。
`readme` の型が必須とするのは先頭の段落だけである。

ただし問いは残る。`suikou plot README.md --doctype readme` が節ごとの問いを並べる。

| 節 | 問い |
|---|---|
| 何であるか | これは何か。一文で言えるか |
| 入れ方 | どう入れるのか |
| 使い方 | 最短でどう使うのか |
| 文書 | 詳しくはどこを読むのか |
| 寄与 | どう手を入れるのか |
| 許諾 | どの条件で使えるのか |

### 型ごとに硬さを変える

同じ閾値を README と参照の文書に当てることはできない。
README は地の文が 17%、参照の文書は 43%、Rust RFC は 54% である。

調整は `.suikou/profile.toml` に書く。

```toml
[doctype.readme]
reason = "利用者と調整した結果。入り口は箇条書きが主になる"
rules = ["structure/long-paragraph"]

[doctype.readme.thresholds."ja.kango_ratio"]
value = 0.65
```

`reason` は必須に近い扱いとする。組み込みの調整は試験で理由の有無を確かめている。
緩めた判断は、利用者と相談した結果として残す。こちらの判断で緩めない。

硬さの差は一方向ではない。
日本語の README は参照より漢語率が高い（0.62 対 0.52）。
一律に緩めるのは誤りで、指標ごとに向きを見る。詳細は D-41 にある。

### 著者の備忘を置かない

進行の状態、試して判明したこと、まだ直していない箇所は README に置かない。
読む側はそれを必要としない。

Diátaxis は、文書の問題の多くは一つの内容が複数の必要に同時に応えようとすることに
由来すると述べている。備忘と README は別の必要に応える。

置き場所は決まっている。

| 内容 | 置き場所 |
|---|---|
| 判断が分かれた箇所 | `docs/content/*/decisions.md` |
| 確信のない値、見送った案 | `TASKS.md` |
| 詳しい説明 | `docs/content/` |

語で検出することはできない。
`currently` や `TODO` は著名な OSS でも使用されており、240件のうち45件が `currently` を
含む。禁止する根拠が無い。検出できるのは冒頭の位置だけである。経緯は D-39 にある。

## PLaMo Translate の使い方

PLaMo Translate は翻訳の専用モデルであり、手元で動く。
必須ではない。使うのは、文書を一から作るときと、語の選択を確認するときとする。

### この環境で選ぶ大きさ

| 条件 | 選ぶモデル | 根拠 |
|---|---|---|
| VRAM 8GB 以下、または GPU なし | `plamo-3-translate-2b` Q4_K_M（1.81GB） | Linux の既定。読み込みが速く、文の単位では足りる |
| VRAM 12GB 以上 | `plamo-2-translate` 10B Q4（約6.2GB） | 段落の単位まで当てられる |

この環境は VRAM 8GB であるため 2B を使う。

### 大きさごとの適用範囲

2B は語と文の単位に限る。段落や文書の全体を書き換える用途には当てない。
10B は段落の単位まで当てられるが、読み込みに時間がかかるため常駐で使う。

どちらの大きさでも、出力をそのまま文書に貼らない。
`lint` を `糸くず`と訳した例があり、分野の語を取り違える。
読むのは「どの語を当てたか」までとする。

### 動かし方

```sh
export PLAMO_TRANSLATE_CLI_LLAMA_SERVER=<llama-server のパス>
plamo-translate server &          # 常駐。モデルの読み込みを一度で済ませる
plamo-translate --from English --to Japanese --input "..."
```

常駐なしでは1件 5.1 秒、常駐ありでは 1.3 秒であった。
語をまとめて調べるときは常駐を起動する。

`llama-server` は b11960 以降が要る。
ビルド済みの配布は glibc 2.38 を要求するため、この環境ではソースから作った。

## ゴールデンテスト

ゴールデンテストは、参照の実装と値を統一するためのものである。

`crates/suikou-core/tests/golden_rules.rs` が規則の件数を、
`golden_metrics.rs` が文書指標を、`tests/golden/expected/` の値と照合する。
英語は辞書なしで走り、日本語は `--features lindera-unidic` で実行される。

lindera と fugashi は別のトークナイザであるため、照合には許容範囲を置く。
比率は絶対の誤差 0.02、1000文字あたりの密度は 0.5、M 系の規則は完全一致を求める。
語数と文数はトークナイザの定義に依存するため、相対の誤差 1% とする。

幅を超えた指標が出た場合は、どちらの実装が正しいかをそのつど決める。
そしてその根拠を決定の記録に残すことにする。Python の側が常に正しいとは限らない。

## 直感で規則を足さない

**これがこのリポジトリでいちばん重い制約である。**

文体の特徴について直感で立てた仮説は、確認すると大半は成立しない。
このプロジェクトでも、設計の途中で立てた仮説の多くが測定した値で落ちている。
翻訳調の研究でも同じことが起きている。

規則を追加するときは、次のいずれかの根拠を示す。

- 人間のコーパスと AI の出力の測定した値。その幅が重ならないこと。
- 明文のスタイルガイドの規約。その出典を示すこと。

`corpus/baselines.toml` の `[rejected]` に、除外した指標とその理由が書いてある。
**ここに載っている指標を導入してはならない。**
文長の変動係数、外来語率、英語の分詞節と名詞化がこれにあたる。
いずれも「AI らしさの指標」として広く言われているものだが、測定すると人間の範囲と重なる。

## トークンの出る量を増やさない

トークンの出る量を抑えることには、次のような制約がある。

レポートの形には制約がある。

- ルールの説明はルールにつき一度だけ出力する。行ごとに繰り返さない。
- ひとつのルールにつき示す位置は `Report::MAX_POSITIONS_PER_RULE` 件までとする。
- 閾値の内に収まっている指標は出力しない。
- 文書指標は数ではなく指示の文に変換して出力する。

この制約は、レイヤーごとに lint と修正を往復させないための設計である。
その形を変更するときは、この目的を壊していないかどうかを確認する。

## 文書を書くときの約束

このリポジトリの文書は、このツールが課す規則に自分で従って書く。

### 書く前に構成を決める

文書を一から作るときは、本文より先に構成を決める。

```sh
suikou plot docs/content/ja/example.md --doctype design
```

`.suikou/plans/` に節の見出しと、その節が答える問いを書いた文書ができる。
節ごとに主張を一行で書き、その内容の承認を得てから本文に進む。
主張を書けない節は、まだ考えが足りていない。

プロットはバージョン管理しない。思考の側の文書であり、成果物ではないためである。
本文を書いたあとに構成を変えた場合は、プロットも直す。
`structure/plot-mismatch` が食い違いを示す。

生成に渡す指示は、型を指定して作る。

```sh
suikou brief --doctype design --lang ja
```

節ごとの問いと書き方の指針が、禁じる形より先に出る。

### 文書の型を宣言する

`docs/content/` 以下はフロントマターに `doctype:` を書く。
フロントマターを持てない文書は `.suikou/structure.toml` の `[paths]` に書く。
型を宣言した文書には、必須の節と推奨する順序の判定が加わる。

### 守る形


- 箇条書きは完全な文で導いて、導入文が項目と文法で結びつく形にしない。
- 地の文に項目の数を書かない。
- 見出しに連番を付けない。
- 時点に依存する語を使わない。触れる場合は西暦かバージョン番号で係留する。
- 暗喩を使わない。必要なら直喩か例え話にする。
- プロの技術文書で使われない和語を繰り返さない。`register/rare-wago` が検出する。
- 一段落に一つの主張だけを置く。6文を超えたら分割する。
- 節は、その見出しが示す問いに答える形で書く。
- Hugo のショートコードを引用する場合は、逃がした形で書く。
  Hugo は Markdown より先にショートコードを処理するため、コードの囲みの中でも実行される。

置く前に `suikou check` を適用することにする。
条件は error と warning が出ないことまでとする。info は参考として読む。

指標を最小化することを目標にしてはならない。
漢語率は info であって参考値である。それをゼロにしようとして和語の動詞に置き換えた結果、
「検証」が「確かめ」になるなど文体が劣化した。経緯は決定の記録の D-27 にある。
漢語率を下げるなら、定着したカタカナ語を使い、漢語の名詞を重ねないようにする。
