この文書は、ビルドの方法、バージョンの固定方法、形態素解析の扱い、ゴールデンテストを説明する参照資料である。
ここに書いた事項は、どれもこのリポジトリで作業するときに守るべき決まりである。

## ディレクトリの配置

| 場所 | 内容 |
|---|---|
| `crates/suikou-core` | 解析処理の中核 |
| `crates/suikou-cli` | CLI と MCP サーバー |
| `packages/` | textlint 向けの局所ルール |
| `skills/suikou` | エージェント向けのスキル |
| `research/` | 較正と探索に使う Python のコード |
| `corpus/` | 基準にした値と、コーパスを取得するスクリプト |

## ビルドとテストの方法

本体の動作を確認するときは、次のコマンドを使う。

```sh
cargo test --all                           # 形態素解析なし。速い。まずこれ
cargo test --all --features lindera-unidic # 辞書を含む。遅い
cargo fmt --all
cargo clippy --all-targets -- -D warnings
```

lindera は既定の feature に含めていない。
そのため、辞書を取得しなくても本体を確認でき、修正箇所の確認にかかる時間が短い。

配布用にビルドするときは、その feature を指定する。

```sh
cargo build --release -p suikou-cli --features lindera-unidic
```

辞書を含まないバージョンは、英語の文書だけを扱う。
このバージョンで日本語の解析を求めると、空の解析結果を返さずに、その時点で異常終了する。
手元にどちらのバージョンがあるかは、`suikou selftest` で確認できる。

## バージョンを固定する理由と方法

依存のバージョンを固定しているのには理由がある。この節では、その理由を説明する。

依存はすべて `=` でバージョンを固定し、`Cargo.lock` もリポジトリに含める。
バージョンを書く前に、そのバージョンが crates.io に実在することを確認する。

依存の中で最も厳しく扱うのは lindera である。
lindera はバージョンによって、API の形と UniDic の素性の並び順が変わるからである。
素性の並び順が合わなくなると、語種と活用形の判定が、誰にも気付かれないまま誤った値を返すようになる。
漢語率と連用中止はこの二つの判定に依存しているので、
誤った値のまま動き続けると、指摘の内容そのものが間違ったものになる。

lindera を更新したときは、必ず `LinderaMorphology::verify_schema` を通す。
このテストは、内容の分かっている文を解析させ、品詞と語種と活用形が想定した位置から取り出せることを確認する。
位置が合わなかった場合は、どの定数を修正すればよいかを示して異常終了する。
誤った値を黙って返すより、異常終了するほうが望ましいからである。

## 形態素解析をどこで扱うか

形態素解析は、バージョンが変わると動作も変わる処理である。

バージョンに依存するコードは、`crates/suikou-core/src/tokenizer.rs` の
`LinderaMorphology` だけに置いている。
他のモジュールは、`Morphology` トレイトを通してのみ形態素解析を使う。
テストでは `FakeMorphology` を使うので、辞書がない環境でも動作を確認できる。

指標を追加する場合も、この境界を越えない。
境界を越えると、辞書がない環境でテストを実行できなくなる。

計測では、埋め込んだ辞書の読み込みにかかる時間は release ビルドで 0.7 ミリ秒だった。
読み込んだ後、1文の解析にかかる時間は 9.6 マイクロ秒だった。

```sh
cargo run --release --features lindera-unidic --example dict_load
```

## 指標ごとの測定範囲を混同しない

語彙の指標（MATTR、漢字率、漢語率、指示詞、形式名詞）には `Document::body()` を使う。
文の構成の指標（文長、読点、連用中止、テ形接続）には `Document::prose()` を使う。

語彙の指標を、地の文に限定して測定してはならない。
モデルによっては、出力の大半が箇条書きになるからである。
その場合に地の文だけで測ると、本文の8割以上を捨てることになる。

## 前処理の実行順序を変更しない

`markdown.rs` の `preprocess` では、処理の順序に意味がある。
バックスラッシュのエスケープを戻す処理を後ろに移すと、文分割が正しく動かなくなる。
AWS の doc_source はこのエスケープを含む形式であり、戻さずに測ると平均文長が3倍以上に増える。

この動作は、`tests/golden/input/en_escaped.md` を使ったテストで固定している。

前処理で除去した範囲は、同じ数の改行で置き換える。
こうすることで、指摘が示す行番号が、利用者が開いているファイルの行と一致する。
値が正しくても、位置がずれていれば、その指摘は役に立たない。

## 発火率の測り方

規則を追加したときや閾値を変更したときは、参照コーパスに対する発火率を計測する。

```sh
cargo run --release --example structure_rate -- corpus/cache/pro_en en
cargo run --release --example structure_rate -- corpus/cache/pro_ja ja
```

`suikou check` は規則ごとに示す位置の数を打ち切るので、CLI の出力からは件数を数えられない。
この example は規則を直接呼び出す。計測した値は `TASKS.md` に記録する。

コーパスは `corpus/fetch.sh` で取得する。ライセンス上の理由で、コーパスはリポジトリに含めない。

必須の節に関する規則を計測するには、文書の型が宣言されたコーパスが必要になる。

```sh
python research/structure/fetch_typed.py corpus/cache/typed 120
```

このスクリプトは、Kubernetes の文書を `content_type:` ごとに集める。
集めた文書は、`.suikou/structure.toml` の `[front_matter]` で suikou の型に対応付けてから `check` を適用する。
この対応付けの設定は `research/structure/structure.toml` にある。

規則を変更したときは、レポートの字数を変更の前後で比べる。
`git worktree` で変更前のバージョンをビルドし、同じコーパスに適用して字数を合計する。

`design` の型は、Rust RFC を使って計測する。

```sh
python research/structure/fetch_rfcs.py corpus/cache/rfcs 200
```

この計測は型の出典そのものに規則を適用するので、最も厳しい確認になる。

`decision` の型は、公開されている ADR を使って計測する。

```sh
python research/structure/fetch_adrs.py corpus/cache/adrs 200 12
```

この計測の設定は `research/structure/structure-adr.toml` にある。

## ゴールデンテストの役割

ゴールデンテストは、参照実装と値をそろえるためのテストである。

規則の件数は `crates/suikou-core/tests/golden_rules.rs` が、
文書指標は `golden_metrics.rs` が、それぞれ `tests/golden/expected/` の値と照合する。
英語のテストは辞書なしで実行でき、日本語のテストは `--features lindera-unidic` を付けて実行する。

lindera と fugashi はトークナイザが異なるので、照合には許容範囲を設ける。
比率は絶対誤差 0.02、1000文字あたりの密度は 0.5 までを許容し、M 系の規則には完全な一致を求める。
語数と文数はトークナイザの定義に左右されるため、相対誤差 1% までを許容する。

許容範囲を超える指標が出たときは、どちらの実装が正しいかを個別に判断する。
判断の根拠は決定の記録に残す。Python 側の値が正しいとは限らない。

## 感覚に頼って規則を追加しない

**このリポジトリの制約の中で、この制約が最も重い。**

文体の特徴について感覚で立てた仮説は、検証するとほとんどが成り立たない。
このプロジェクトでも、設計の途中で立てた仮説の多くが、測定値によって否定されている。
翻訳調の研究でも、同じことが起きている。

規則を追加するときは、次のどちらかを根拠として示す。

- 人間のコーパスと AI の出力を測定した値。両者の範囲が重ならないことを示す。
- 明文化されたスタイルガイドの規約。規約の出典を示す。

`corpus/baselines.toml` の `[rejected]` には、不採用にした指標と、不採用の理由が書いてある。
**この一覧に載っている指標は、導入してはならない。**
文長の変動係数、外来語率、英語の分詞節と名詞化が、これに該当する。
どれも「AI らしさの指標」として広く知られているが、測定すると人間の範囲と重なる。

## 出力するトークンの量を増やさない

出力するトークンの量を抑えるために、レポートの形に制約を設けている。

制約の内容は次のとおりである。

- 規則の説明は、一つの規則につき一回だけ出力する。行ごとに繰り返さない。
- 一つの規則について示す位置は、`Report::MAX_POSITIONS_PER_RULE` 件までとする。
- 閾値の範囲内に収まっている指標は出力しない。
- 文書指標は、数値ではなく指示の文に変換して出力する。

これらの制約は、レイヤーごとに lint と修正を往復させないための設計である。
レポートの形を変更するときは、この目的が損なわれていないかを確認する。
