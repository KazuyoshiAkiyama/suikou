作り方、版の固め方、形態素解析の扱い、そしてゴールデンテストについて書く。
これらはいずれも、このリポジトリで作業するときに守ることである。

## 作りとテスト

本体を確かめるときは、次のコマンドを使う。

```sh
cargo test --all                           # 形態素解析なし。速い。まずこれ
cargo test --all --features lindera-unidic # 辞書を含む。遅い
cargo fmt --all
cargo clippy --all-targets -- -D warnings
```

既定の feature に lindera を入れていない。
そのため辞書を落とさずに本体を確かめられて、直したところを確かめるのが速い。

配る用のビルドでは、その feature を書くことになる。

```sh
cargo build --release -p suikou-cli --features lindera-unidic
```

辞書を含まない版は英語だけを扱うものである。
その版に日本語を求めた場合は、空の解析結果を返さずにその場で落ちる。
どちらの版が手元にあるかは `suikou selftest` で確かめられる。

## 版を固める

版を固めることには理由がある。その理由をここに書く。

依存はすべて `=` で固めて、`Cargo.lock` も置くことにする。
その版は crates.io で実在を確かめてから書く。

lindera はいちばん厳しく扱うことにする。
API の形と UniDic の素性の並びが、版で変わるためである。
その並びがずれると、語種と活用形が黙って壊れる。
漢語率と連用中止がこの二つに寄りかかっているため、
壊れた値のまま動くと、指摘の中身そのものが誤りになる。

lindera を更新した場合は、`LinderaMorphology::verify_schema` を必ず通す。
知っている文を流して、品詞と語種と活用形が思った位置から取れることを確かめる。
ずれていた場合は、どの定数を直せばよいかを示して落ちる。
黙って誤った値を返すよりも、落ちる方がよいためである。

## 形態素解析の扱い

形態素解析は、版によって振る舞いが変わるものである。

版に寄りかかるコードは、`crates/suikou-core/src/tokenizer.rs` の
`LinderaMorphology` だけに置いてある。
ほかのモジュールは `Morphology` トレイト越しにしか形態素解析を使わない。
テストでは `FakeMorphology` を使うため、辞書がない場合でも確かめられる。

指標を足すときも、この境を越えない。
越えると、辞書なしでテストが回らなくなる。

測った値では、埋め込んだ辞書の読み込みが release で 0.7 ミリ秒だった。
1文の解析はそのうえで 9.6 マイクロ秒だった。

```sh
cargo run --release --features lindera-unidic --example dict_load
```

## 指標の対象範囲を混ぜない

語彙の指標（MATTR、漢字率、漢語率、指示詞、形式名詞）は `Document::body()` を使う。
文の組み立ての指標（文長、読点、連用中止、テ形接続）は `Document::prose()` を使う。

語彙の指標を地の文だけで測ってはならない。
出力の大半が箇条書きになるモデルがあるためである。
その場合、本文の8割以上を捨てることになる。

## 前処理の順序を変えない

`markdown.rs` の `preprocess` は順序に意味がある。
バックスラッシュのエスケープを戻す処理を後ろへ動かすと、文の切り分けが成り立たない。
AWS の doc_source がこの形であり、戻さない場合の平均文長は3倍以上にふくらむ。

`tests/golden/input/en_escaped.md` がこの振る舞いを固めている。

取り除いた範囲は、同じ数の改行に置き換えることにする。
そうすることで、指摘が使う人の開いている行を指すようになる。
値が正しくても、位置がずれていればその指摘は役に立たない。

## ゴールデンテスト

ゴールデンテストは、参照の実装と値をそろえるためのものである。

`crates/suikou-core/tests/golden_rules.rs` が規則の件数を、
`golden_metrics.rs` が文書指標を、`tests/golden/expected/` の値と突き合わせる。
英語は辞書なしで走り、日本語は `--features lindera-unidic` で走る。

lindera と fugashi は別のトークナイザであるため、突き合わせには幅を置く。
比率は絶対の誤差 0.02、1000文字あたりの密度は 0.5、M 系の規則はぴたり一致を求める。
語数と文数はトークナイザの定めに寄りかかるため、相対の誤差 1% とする。

幅を超えた指標が出た場合は、どちらの実装が正しいかをそのつど決める。
そしてその根拠を決定の記録に残すことにする。Python の側が常に正しいとは限らない。

## 思いつきで規則を足さない

**これがこのリポジトリでいちばん重い縛りである。**

文体の癖について思いつきで立てた見立ては、確かめると大半が外れる。
このプロジェクトでも、設計の途中で立てた見立ての多くが測った値で落ちている。
翻訳調の研究でも同じことが起きている。

規則を足すときは、次のいずれかの根拠を示す。

- 人間のコーパスと AI の出力の測った値。その幅が重ならないこと。
- 明文のスタイルガイドの決まり。その出どころを示すこと。

`corpus/baselines.toml` の `[rejected]` に、落とした指標とその理由が書いてある。
**ここに載っている指標を持ち込んではならない。**
文長の変動係数、外来語率、英語の分詞節と名詞化がこれにあたる。
いずれも「AI らしさの指標」として広く言われているものだが、測ると人間の幅と重なる。

## トークンの出る量を増やさない

トークンの出る量を抑えることには、次のような縛りがある。

レポートの形には縛りがある。

- ルールの説明はルールにつき一度だけ出す。行ごとに繰り返さない。
- ひとつのルールにつき示す位置は `Report::MAX_POSITIONS_PER_RULE` 件までとする。
- 閾値の内に収まっている指標は出さない。
- 文書指標は数ではなく指示の文に直して出す。

この縛りは、層ごとに lint と直しを往復させないための設計である。
その形を変えるときは、この目的を壊していないかどうかを確かめる。

## 文書を書くときの約束

このリポジトリの文書は、この道具が課す規則に自分で従って書く。

- 箇条書きは完全な文で導いて、導入文が項目と文法で結びつく形にしない。
- 地の文に項目の数を書かない。
- 見出しに連番を付けない。
- 時点に寄りかかる語を使わない。
- 隠れたたとえを使わない。要るなら直喩か例え話にする。

置く前に `suikou check` をかけることにする。
自分の道具の規則に従えない文書を置くと、その道具の説得力がなくなるためである。
