本書は、suikou を用いて技術文書を執筆する際の規範と手順をまとめたリファレンスである。用語の選定基準、README の構成方針、および文書生成に渡す指示の作成方法を扱う。

ツールの実装方針と維持すべき不変条件は[開発]({{< relref "development.md" >}})に、対象文書に合わせて閾値をカスタマイズする手順は[調整]({{< relref "tuning.md" >}})に記載している。

## 用語選定の規範

技術文書の用語は、書き手個人の語感ではなく、対象分野における一般的な用法を調査したうえで決定する。

### 選定のワークフロー

判断基準を思いついた順に適用すると選定結果が不安定になるため、評価の手順を固定する。

最初に**制約**を適用して不適格な候補を除外し、次に**選好**によって残った候補に優先順位を付ける。最後に**表記**を確定させ、根拠とともに**記録**する。

| ステップ | 確認事項 | 区分 | 実施手法 |
|---|---|---|---|
| 1 | 定義済みの用語に該当するか | 制約 | `.suikou/defined.toml` を参照する。記載があればその用語で確定し、後続のステップを終了する |
| 2 | 候補を列挙する | — | 想起される候補語を列挙する。この段階に限り語感を用いてよい |
| 3 | 対象分野で実際に使われているか | 制約 | 参照コーパスでの出現頻度を調べる。0件であれば候補から除外する |
| 4 | 名詞と動詞の共起が自然か | 制約 | 名詞と動詞のペアのみを抽出して妥当性を確認する |
| 5 | 語義が十分に狭いか | 選好 | 対訳の分散度合いを計測し、訳語が収束する語を優先する |
| 6 | 身体的な動作のイメージに偏っていないか | 選好 | 語義の狭さが同程度であれば、身体動作を連想させにくい語を優先する |
| 7 | 表記を確定する | — | 参照コーパスで語ごとに表記の出現数を数える。優劣が付かない場合は長音ありの表記を採用する |
| 8 | 結果を記録する | — | `glossary_ja.toml` に根拠データを添えて記載する |

制約を選好より先に適用するのは、優先順位を付けた後に制約違反で除外される手戻りを防ぐためである。ステップ4で共起が不成立と判断した場合はステップ2へ戻る。動詞を変更すると、ステップ5の対訳分析も再実行が必要になる。

### 参照コーパスでの出現頻度を確認する（ステップ3）

参照コーパス内の出現数を次のコマンドで集計する。

```sh
grep -c "根因" corpus/cache/pro_ja/*.md
```

参照コーパスはプロによる日本語訳で構成されており、実務の執筆で採用された語彙がそのまま反映されている。検索結果が0件の語は、その分野の文書では用いられない表現と判断できる。

ただし、参照コーパスと執筆対象の分野が一致しない場合、この検証は機能しない。参照コーパスは API リファレンスの説明文が中心であり、規範や上限を規定する表現が出現しないためである。`を置く` の代替語をこの手法で特定できなかった原因もそこにあり、詳細な経緯は T19 に記録されている。

### 名詞と動詞の共起を確認する（ステップ4）

共起ペアの抽出には次のコマンドを用いる。

```sh
cargo run --release --features lindera-unidic --example collocation -- <人間の側> <AIの側>
```

形態素解析によって名詞と動詞のペアを集計し、人間が執筆した文書には見られず AI が生成した文書にのみ現れるペアを列挙する。共起の適切さは自動判定できないため、抽出されたペアは必ず人が確認する。

### 対訳の分散度合いを計測する（ステップ5）

翻訳モデルを用いて、訳語のばらつきを次のコマンドで計測する。

```sh
plamo-translate server &
python research/glossary/narrow.py --ja2en 置く 配置する 設定する
python research/glossary/narrow.py --en2ja place configure deploy
```

指定する翻訳方向によって、計測対象と用途が異なる。

| 翻訳方向 | 計測対象 | 主な用途 |
|---|---|---|
| `--ja2en` | 単一の日本語が何種類の英語へ分散するか | 日本語の語義の広さを把握する |
| `--en2ja` | 単一の英語が何種類の日本語へ分散するか | 日本語の統一訳を決定する |

翻訳時には最小限の文型テンプレートに対象語を当てはめる。コーパスから取り出した実文には話題固有の語彙が混入するため、正確な計測にならない。

実際の計測結果を次に示す。

| 対象語 | 収束率 | 出力された訳語 |
|---|---|---|
| 配置する | 100% | place×6 |
| 作成する | 100% | create×6 |
| 作る | 83% | create×5 make×1 |
| 置く | 67% | place×4 set×1 establish×1 |
| 設定する | 67% | set×4 configure×2 |

この結果から、`置く` と `設定する` の語義の広さは同程度であることが分かる。したがって、`置く` を `設定する` に言い換えても曖昧さは解消されない。語義を限定するなら `配置する` を選ぶ必要がある。計測を経ずに語を選ぶと、広い語を別の広い語へ置換する修正案になる。

なお、対象語の訳語がテンプレート内の名詞と重複する場合は計測が成立しない。たとえば `configure` の訳語である `設定` は、テンプレート中の `設定を` と重複する。このようなケースでは数値を算出せず、計測不能として返す仕様となっている。

### 身体動作のイメージが薄い語を選ぶ（ステップ6）

語義の狭さが同程度の候補が残った場合は、身体的な動作を連想させにくい語を選択する。**身体動作を想起させる語彙の多用は、文章に強い AI らしさを与える。**技術文書が説明すべき対象は、物理的な物の操作ではなくシステムの仕組みである。

| 避ける語 | 採用する語 |
|---|---|
| 外す | 除外する |
| 落とす | 除去する |
| 拾う | 検出する |
| 寄せる | 統一する |
| 突き合わせる | 照合する |

実測では、避ける語として挙げた表現がこのリポジトリ内で参照コーパスの8倍から32倍の頻度で使われていた。具体例として、`外す` の出現率は参照コーパスで1万字あたり 0.06 であったのに対し、このリポジトリでは 1.90 に達していた。

この種の語彙は `register/rare-wago` では検出できない。参照コーパスにも少数ながら出現するため、同規則の検出下限である参照の128倍に達しないためである。頻度ベースの自動検出は効かないものの、用語選好として指定することは可能であり、その役割を `glossary/variant` が担う。

表に記載のない語についても判断基準は同じである。選択に迷った際は、その語が手や体の動きを直接連想させるかどうかを基準に検討する。

### 過度な和語化による誤りを防ぐ

漢字の比率を下げることだけを目的に用語を変更してはならない。`確認`、`使用`、`停止`、`動作` のように技術文書で定着している一般的な漢語は、和語に言い換えずにそのまま用いる。この誤りを実際に犯した経緯は D-27 に記録されている。

一方で、`多角的` や `包括的` のように形式張っているだけで情報量の乏しい漢語は、別の課題として見直す必要がある。また、助詞を省略して漢語名詞を連続させた箇所は、漢語自体は変えずに助詞と動詞を補って分解する。

### 用語集に根拠とともに記録する（ステップ8）

調査を経て確定した用語は、`crates/suikou-core/data/glossary_ja.toml` に登録し、判断根拠となった実測値を併記する。`glossary/` 配下の汎用フォーマットは、`research/glossary/build_glossary.py` を実行して再生成する。

なお、表記ルールと用語選定ルールは根拠の由来が異なるため、分離して管理する。

### 文書内の反復を定着の根拠にしない

ステップ3で確認すべき点は、口頭で意味が通じるかどうかではなく、その分野の書き手が仕様書や手順書を執筆する際に実際にその語を選ぶかどうかである。

同一の文書やリポジトリ内で繰り返し使われている事実は、妥当性の根拠にならない。AI が生成した文書の語彙は後続の文書へそのまま引き継がれるため、反復は一般的な定着の証拠とはみなせない。このリポジトリの文書も AI によって執筆されており、この注意点は自身にもそのまま該当する。

ステップ4で抽出された共起ペアに対して、適切な動詞を自動で割り当てることはできない。動詞 32,822 語を対象に統計的手法で候補を推定しても、上位600語ほどの範囲で正解率80%にとどまる（中野・冨浦 2011）。最終的な採否は人が判断する必要があり、その経緯は T19 に記されている。

## README の書き方

### 先頭段落で主題を定義する

著名な OSS の README 240件を調査したところ、共通する構造上の特徴は見出しの構成ではなく先頭段落に表れていた。

| 計測項目 | 実測値 |
|---|---|
| 先頭段落を備える割合 | 78% |
| そのうち300字以内に収まる割合 | 83% |
| 先頭段落の文字数の中央値 | 121 |

先頭段落では対象の名前を主語にし、それが何であるかを300字以内で簡潔に述べる。

```markdown
# suikou

suikou は技術文書の lint である。日本語と英語を扱う。
```

背景、目的、経緯から書き始めてはならない。これら3種類の書き出しは、README、Rust RFC、ADR、および参照コーパスを合わせた先頭段落 831件の調査において0件であった。冒頭形式の違反は `structure/lead-opener` によって検出される。

### 特定の見出しを必須にしない

見出しから役割を特定できるセクションは、最も出現率の高い `入れ方`（インストール手順）であっても 62% にとどまる。このため、`readme` 種別で必須とする要素は先頭段落のみである。

見出し自体は必須としないものの、読者が抱く主要な問いは共通している。`suikou plot README.md --doctype readme` を実行すると、各セクションが答えるべき問いの一覧が出力される。

| セクション | 答えるべき問い |
|---|---|
| 概要 | これは何か。一文で説明できるか |
| インストール | どのようにインストールするか |
| 使い方 | 最短手順でどのように使うか |
| ドキュメント | 詳細な情報はどこを参照すればよいか |
| 貢献 | どのように変更や貢献を行えるか |
| ライセンス | どの利用条件で使用できるか |

### 文書種別ごとに基準の厳格さを調整する

README とリファレンス文書に対して同一の閾値を適用することは適切でない。地の文の割合は README で 17%、リファレンス文書で 43%、Rust RFC で 54% と大きく異なるためである。

文書種別ごとの調整内容は `.suikou/profile.toml` に記述する。

```toml
[doctype.readme]
reason = "利用者と調整した結果。入り口は箇条書きが主になる"
rules = ["structure/long-paragraph"]

[doctype.readme.thresholds."ja.kango_ratio"]
value = 0.65
```

設定項目 `reason` は必須に準ずる扱いとし、組み込みの調整値についてはテストで理由の記載有無を検証している。基準を緩和する場合は利用者と合意した経緯を記録として残し、独断で緩和してはならない。

また、文書種別ごとの指標の差は一方向ではない。日本語の README はリファレンス文書よりも漢語率が高い（0.62 対 0.52）。一律に条件を緩めるのではなく、指標ごとに傾向の向きを確認して調整する。詳細は D-41 にまとめている。

### 開発者向けの作業メモを記載しない

作業の進行状況、試行で判明した事項、未修正の課題は README に記載しない。読者にとって不要な情報であるためである。

Diátaxis のフレームワークでも、技術文書における問題の多くは、一つの文書で複数の異なる要求を同時に満たそうとすることから生じると指摘されている。開発者向けの作業メモと README は、満たすべき読者の要求が異なる。

情報の性質に応じて、記載先を明確に分ける。

| 情報の性質 | 記載先 |
|---|---|
| 設計判断が分かれた経緯 | `docs/content/*/decisions.md` |
| 根拠が未確定の値や見送った案 | `TASKS.md` |
| 詳細な解説 | `docs/content/` |

作業メモの混入を特定のキーワードだけで検出することはできない。たとえば `currently` や `TODO` は著名な OSS の README でも使われており、240件中45件に `currently` が含まれている。単語自体を禁止する根拠はなく、自動検出の対象にできるのは冒頭の位置に限られる。この判断の経緯は D-39 にある。

## PLaMo Translate の使い方

PLaMo Translate はローカル環境で動作する翻訳専用モデルである。利用は必須ではないが、文書を新規に作成する際や、用語選択の妥当性を確認する場面で活用する。

### 環境に応じたモデルサイズの選択

ハードウェア構成に応じて、使用するモデルサイズを選択する。

| 実行環境 | 選択するモデル | 選定理由 |
|---|---|---|
| VRAM 8GB 以下、または GPU なし | `plamo-3-translate-2b` Q4_K_M（1.81GB） | Linux 環境の標準構成。読み込みが速く、文単位の処理には十分である |
| VRAM 12GB 以上 | `plamo-2-translate` 10B Q4（約6.2GB） | 段落単位の処理まで対応できる |

この作業環境は VRAM 8GB であるため、2B モデルを使用する。

### モデルサイズごとの適用範囲

2B モデルの利用は単語単位および文単位に限定し、段落や文書全体の書き換えには使用しない。10B モデルは段落単位まで対応可能だが、モデルの読み込みに時間を要するため、サーバーとして常駐させて運用する。

いずれのサイズを用いる場合でも、翻訳の出力結果をそのまま文書へ貼り付けてはならない。`lint` を `糸くず` と訳した事例があり、専門分野の用語を誤訳するおそれがあるためである。確認する対象は「どの語が選択されたか」という語彙の傾向にとどめる。

### 起動と実行方法

常駐サーバーを起動したうえで翻訳コマンドを実行する手順は次の通りである。

```sh
export PLAMO_TRANSLATE_CLI_LLAMA_SERVER=<llama-server のパス>
plamo-translate server &          # 常駐。モデルの読み込みを一度で済ませる
plamo-translate --from English --to Japanese --input "..."
```

処理時間の実測値は、常駐なしの場合が1件あたり 5.1 秒、常駐ありの場合が 1.3 秒であった。複数の語をまとめて調査する際は常駐サーバーを起動しておく。

実行には b11960 以降の `llama-server` が必要となる。ビルド済みバイナリは glibc 2.38 を要求するため、この環境ではソースコードからビルドして用意した。

## 文書執筆時のルール

このリポジトリに含まれるすべての文書は、suikou 自身が課す検査ルールに従って執筆する。

### 文書種別を選択する

利用可能な文書種別は、次のコマンドで確認する。

```sh
suikou doctype          # 問いと型の一覧
suikou doctype --list   # 型の一覧だけ
```

文書種別は読者が達成したい行動に基づいて分類されており、最大2問の質問に答えることで決定する。

### 執筆前に構成を固める

文書を新規に作成する場合は、本文を書き始める前に全体の構成を確定させる。

```sh
suikou plot docs/content/ja/example.md --doctype design
```

このコマンドを実行すると、各節の見出しと対応する問いを記した構成ファイルが `.suikou/plans/` に生成される。各節の主張を一行で記述し、その構成について承認を得てから本文の執筆へ移る。一行の主張を書けない節は、検討がまだ不十分であることを示す。

プロットファイルは最終成果物ではなく思考整理用の文書であるため、バージョン管理の対象に含めない。本文執筆後に構成を変更した場合は、プロットファイル側も同期して更新する。両者に食い違いがあると `structure/plot-mismatch` が検出する。

文書生成に渡す指示文は、対象となる文書種別を指定して出力する。

```sh
suikou brief --doctype design --lang ja
```

出力される指示文では、禁止事項よりも先に各節の問いと執筆指針が提示される。

### 文書種別を宣言する

`docs/content/` 配下の文書では、フロントマターに `doctype:` を記載して種別を宣言する。フロントマターを持てない文書については、`.suikou/structure.toml` の `[paths]` セクションに種別を登録する。文書種別を宣言すると、必須セクションの有無と推奨される節順序の検査が有効になる。

### 遵守すべき記述ルール

文書の執筆時には、次に挙げる記述上の制約を守る。

- 箇条書きの直前には句点で終わる完全な文を記載し、導入文が箇条書きの項目と文法的に連結する形を避ける。
- 地の文に項目の個数を記載しない。
- 見出しに連番を付けない。
- 時点に依存する表現を使わない。時期に言及する必要がある場合は、西暦またはバージョン番号で明示する。
- 暗喩を使わない。比喩を用いる必要がある場合は、直喩または例え話として表現する。
- プロの技術文書で使われない和語を反復しない。該当箇所は `register/rare-wago` が検出する。
- 一段落に含める主張は一つに限定し、6文を超える場合は段落を分割する。
- 各節は、その見出しが示す問いへの回答になるように構成する。
- Hugo のショートコードを引用する場合は、エスケープした形式で記述する。
  Hugo は Markdown の解釈より先にショートコードを処理するため、コードブロック内であっても実行されてしまう。

文書を配置する前に `suikou check` を実行する。合格基準は error および warning が発生しないこととし、info は参考情報として確認する。

指標の最小化自体を目標にしてはならない。漢語率は info レベルの参考値にすぎず、これをゼロにしようとして和語動詞へ置換した結果、「検証」が「確かめ」に変わるなど文体が劣化した経緯が決定記録の D-27 に残されている。漢語率を抑えたい場合は、定着したカタカナ語を取り入れ、漢語名詞の連続を避ける方法で調整する。
