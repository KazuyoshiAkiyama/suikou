この文書は、suikou を使って文書を書くときに従う規範と手順をまとめた参照資料である。
扱う範囲は、語の選び方、README の構成、生成に渡す指示である。

ツールの構築方法と、変えてはならない不変条件は[開発]({{< relref "development.md" >}})で説明している。
閾値を自分の文書に合わせる手順は[調整]({{< relref "tuning.md" >}})に書いてある。

## 語を選ぶときの規範

語は、自分の語感に頼って選ばない。一般にどう書かれているかを調べてから選ぶ。

### 選定の手順

規則を思い付いた順に適用すると、結論がそのたびに変わる。そのため、適用する順番を固定している。

最初に**制約**を適用する。制約は、その語が使えるかどうかを決めるもので、適用すると候補が減る。
次に**選好**を適用し、残った候補に順位を付ける。
最後に**表記**を決めて、**記録**を残す。

| 段 | 確かめる内容 | 種類 | 手法 |
|---|---|---|---|
| 1 | プロジェクトで定義した名前があるか | 制約 | `.suikou/defined.toml` を調べる。定義があればその名前に決め、以降の段は行わない |
| 2 | 候補を挙げる | — | 思い付く語を並べる。この段では語感に頼ってよい |
| 3 | その分野の文書で使われる語か | 制約 | 参照コーパスでの頻度を調べる。0件の語は候補から除く |
| 4 | 名詞と動詞の組み合わせが成り立つか | 制約 | 組み合わせだけを取り出して読む |
| 5 | 語の意味が狭いか | 選好 | 対訳がどれだけ分かれるかを見る。訳が一つに収束する語を採る |
| 6 | 身体の動作を思い起こさせない語か | 選好 | 意味の狭さが同程度なら、身体の動作を思わせにくい語を採る |
| 7 | 表記を決める | — | 参照コーパスで語ごとに出現数を数える。決まらない場合は長音符号を付ける表記にする |
| 8 | 記録する | — | 根拠を添えて `glossary_ja.toml` に書く |

制約を先に適用するのは、選好で順位を付けた後に候補を除くと、順位付けの作業が無駄になるからである。
段4で組み合わせが成り立たなかった場合は、段2に戻る。動詞を入れ替えたときは、段5の分析もやり直す。

### 段3では参照コーパスでの頻度を調べる

```sh
grep -c "根因" corpus/cache/pro_ja/*.md
```

参照コーパスはプロが訳した日本語の文書であり、翻訳者が書くときに選んだ語がそのまま現れる。
参照コーパスでの出現が0件であれば、その語はその分野の文書では使われない。

分野が合わない場合、この手法は使えない。
参照コーパスは API の説明文であり、規範や上限を定める文は含まれていない。
`を置く` の置き換え先が決まらなかったのは、この制約のためである。経緯は T19 に書いてある。

### 段4では組み合わせだけを取り出して読む

```sh
cargo run --release --features lindera-unidic --example collocation -- <人間の側> <AIの側>
```

このコマンドは、形態素解析で名詞と動詞の組み合わせを数え、人間の側には無く AI の側にだけある組み合わせを一覧にする。
組み合わせが適切かどうかは、自動では判定できない。一覧に挙がった組み合わせは、人が読んで判断する。

### 段5では対訳がどれだけ分かれるかを見る

```sh
plamo-translate server &
python research/glossary/narrow.py --ja2en 置く 配置する 設定する
python research/glossary/narrow.py --en2ja place configure deploy
```

翻訳の方向によって、測る対象が異なる。

| 方向 | 測る対象 | 使う場面 |
|---|---|---|
| `--ja2en` | 一つの日本語が、何通りの英語に訳されるか | 日本語の語の意味の広さを調べる |
| `--en2ja` | 一つの英語が、何通りの日本語に訳されるか | 表記をそろえる先の語を決める |

語は、最小限の文型に入れて訳させる。コーパスの文を使うと、話題の語が訳に混ざるので計測にならない。

次の表は実測の例である。

| 語 | 収束 | 訳 |
|---|---|---|
| 配置する | 100% | place×6 |
| 作成する | 100% | create×6 |
| 作る | 83% | create×5 make×1 |
| 置く | 67% | place×4 set×1 establish×1 |
| 設定する | 67% | set×4 configure×2 |

`置く` と `設定する` は、意味の広さが同程度である。
`置く` を `設定する` に替えても、曖昧さは減らない。替えるなら `配置する` を選ぶ。
このツールを作る前は、意味の広い語を別の広い語に替えるという不適切な提案をしていた。

調べる語の訳が、文型に含まれる名詞と重なる場合は、計測が成り立たない。
たとえば `configure` の訳は `設定` であり、文型の `設定を` と重なる。
この場合は数値を出さず、計測できないという結果を返す。

### 段6では身体の動作を思わせにくい語を選ぶ

意味の狭さが同程度の語が残った場合は、身体の動作を思い起こさせにくい語を採る。
**この種の語は、文書に AI らしい印象を強く与える。**
技術文書が説明するのは仕組みであり、物を手で動かす話を書くわけではない。

| 避ける | 選ぶ |
|---|---|
| 外す | 除外する |
| 落とす | 除去する |
| 拾う | 検出する |
| 寄せる | 統一する |
| 突き合わせる | 照合する |

実測すると、このリポジトリは表に挙げた語を、参照コーパスの8倍から32倍の頻度で使っていた。
`外す` の頻度は、参照コーパスでは1万字あたり 0.06 だったが、このリポジトリでは 1.90 だった。

`register/rare-wago` では、この種の語を検出できない。
この種の語は参照コーパスにも少しは現れるので、同じ規則の下限（参照コーパスの128倍）に達しないからである。
頻度による検出では届かないが、選好として指定することはできる。この指定は `glossary/variant` が担う。

表に無い語も、同じ理由で避ける。
判断に迷ったときは、その語が手や体の動きを思わせるかどうかを考える。

### 逆方向の誤りを避ける

漢字の割合を下げることだけを目的に、語を替えてはならない。
`確認`、`使用`、`停止`、`動作`のように技術文書で普通に使う漢語は、和語に替えない。
この誤りを実際に犯した経緯は、D-27 に記録している。

堅いだけで内容のない漢語（`多角的`、`包括的`）は、別の問題として見直す。
助詞を省いて漢語を連ねている箇所は、語はそのまま残し、助詞と動詞を補って文を分ける。

### 段8では用語集に記録する

調べて決めた語は、`crates/suikou-core/data/glossary_ja.toml` に書く。
その際、根拠となる実測値も一緒に書く。
`glossary/` にある汎用フォーマットのファイルは、`research/glossary/build_glossary.py` で生成し直す。

表記は、語の選択とは別に記録する。根拠の出どころが異なるからである。

### 使用の反復を根拠にしない

段3で確かめるのは、その分野の書き手が仕様書や手順書を書くときに、この語を選ぶかどうかである。
話し言葉で意味が通じるかどうかは問わない。

同じ文書や同じリポジトリの中で繰り返し使っていることは、根拠にしない。
AI が書いた文書の語は次の文書にそのまま受け継がれるので、繰り返し使われていても、定着している証拠にはならない。
このリポジトリの文書も AI が書いたものであり、この注意は自分たちにも当てはまる。

段4で一覧に挙がった組み合わせに、正しい動詞を自動で割り当てることはできない。
動詞 32,822 語から統計的に候補を出す方法では、上位600語ほどまで見ても正解率は80%にとどまる
（中野・冨浦 2011）。動詞を決めるのは人である。経緯は T19 に書いてある。

## README の書き方

### 先頭の段落に主題を書く

広く知られた OSS の README 240件を計測した結果、文書の構造を担っているのは見出しではなく先頭の段落だった。

| 計測した項目 | 値 |
|---|---|
| 先頭に段落がある README の割合 | 78% |
| そのうち先頭の段落が300字以内のもの | 83% |
| 先頭の段落の字数の中央値 | 121 |

先頭の段落では、名前を主語にして、それが何であるかを書く。長さは300字以内に収める。

```markdown
# suikou

suikou は技術文書の lint である。日本語と英語を扱う。
```

背景、目的、経緯から書き始めない。
これら3つの書き出しは、先頭の段落 831件（README、Rust RFC、ADR、参照コーパス）の中に0件だった。
この書き出しは `structure/lead-opener` が検出する。

### 見出しを必須にしない

見出しで特定できる節は、最も多い `入れ方` でも 62% にとどまる。
そのため、`readme` の型で必須とするのは先頭の段落だけである。

ただし、各節が答えるべき問いは残る。`suikou plot README.md --doctype readme` を実行すると、節ごとの問いが一覧になる。

| 節 | 問い |
|---|---|
| 何であるか | これは何か。一文で説明できるか |
| 入れ方 | どうやって導入するのか |
| 使い方 | 最も短い手順でどう使うのか |
| 文書 | 詳しい説明はどこにあるのか |
| 寄与 | どうやって開発に参加するのか |
| 許諾 | どの条件で利用できるのか |

### 型ごとに求める硬さを変える

README と参照の文書に、同じ閾値を適用することはできない。
地の文の割合は、README が 17%、参照の文書が 43%、Rust RFC が 54% である。

調整は `.suikou/profile.toml` に書く。

```toml
[doctype.readme]
reason = "利用者と調整した結果。入り口は箇条書きが主になる"
rules = ["structure/long-paragraph"]

[doctype.readme.thresholds."ja.kango_ratio"]
value = 0.65
```

`reason` は、ほぼ必須の項目として扱う。組み込みの調整については、理由が書かれているかをテストで確認している。
条件を緩めた判断は、利用者と相談した結果として記録に残す。作業する側の判断だけで条件を緩めてはならない。

硬さの差は、どの指標でも同じ方向に出るわけではない。
日本語の README は、参照の文書より漢語率が高い（0.62 対 0.52）。
したがって、すべての条件を一律に緩めるのは適切でなく、指標ごとに差の方向を確かめる。詳細は D-41 にある。

### 著者の備忘を README に書かない

作業の進み具合、試して分かったこと、未修正の箇所は、README に書かない。
README を読む人は、こうした情報を必要としていない。

Diátaxis は、文書の問題の多くは、一つの内容で複数の目的を同時に満たそうとすることから生じると述べている。
備忘と README は、それぞれ別の目的のために書くものである。

備忘の書き先は、内容ごとに決まっている。

| 内容 | 書き先 |
|---|---|
| 判断が分かれた箇所 | `docs/content/*/decisions.md` |
| 確信のない値、見送った案 | `TASKS.md` |
| 詳しい説明 | `docs/content/` |

備忘は、語を手掛かりにしては検出できない。
`currently` や `TODO` は広く知られた OSS でも使われており、240件のうち45件が `currently` を
含んでいる。これらの語を禁止する根拠はない。検出できるのは、文書の冒頭という位置だけである。経緯は D-39 にある。

## PLaMo Translate の使い方

PLaMo Translate は、翻訳に特化したモデルであり、手元の環境で動かせる。
使うことは必須ではない。使う場面は、文書を新しく作るときと、語の選択を確かめるときに限る。

### この環境で使うモデルの大きさ

| 条件 | 選ぶモデル | 根拠 |
|---|---|---|
| VRAM 8GB 以下、または GPU なし | `plamo-3-translate-2b` Q4_K_M（1.81GB） | Linux での既定。読み込みが速く、文単位の用途なら十分に使える |
| VRAM 12GB 以上 | `plamo-2-translate` 10B Q4（約6.2GB） | 段落単位の用途まで使える |

この環境の VRAM は 8GB なので、2B を使う。

### モデルの大きさごとに使える範囲

2B は、語と文の単位の用途に限って使う。段落や文書全体を書き換える用途には使わない。
10B は段落の単位まで使えるが、読み込みに時間がかかるので、常駐させて使う。

どちらの大きさのモデルでも、出力をそのまま文書に貼り付けない。
`lint` を `糸くず`と訳した例があるように、分野の語を取り違えることがある。
出力から読み取るのは、「どの語を当てたか」までにとどめる。

### 起動と実行の方法

```sh
export PLAMO_TRANSLATE_CLI_LLAMA_SERVER=<llama-server のパス>
plamo-translate server &          # 常駐。モデルの読み込みを一度で済ませる
plamo-translate --from English --to Japanese --input "..."
```

1件の翻訳にかかる時間は、常駐させない場合が 5.1 秒、常駐させた場合が 1.3 秒だった。
語をまとめて調べるときは、先にサーバーを常駐させる。

`llama-server` は b11960 以降のバージョンが必要である。
配布されているビルド済みのバイナリは glibc 2.38 を必要とするので、この環境ではソースからビルドした。

## 文書を書くときの決まり

このリポジトリの文書は、このツールが課す規則に自ら従って書く。

### 文書の型を選ぶ

```sh
suikou doctype          # 問いと型の一覧
suikou doctype --list   # 型の一覧だけ
```

型は、読者がその文書で何をしようとしているかによって決まる。最大2問の問いに答えると型が決まる。

### 書く前に構成を決める

文書を新しく作るときは、本文を書く前に構成を決める。

```sh
suikou plot docs/content/ja/example.md --doctype design
```

このコマンドを実行すると、`.suikou/plans/` に、節の見出しと各節が扱う問いを書いた文書が作られる。
節ごとに主張を一行で書き、その内容について承認を受けてから本文に取りかかる。
主張を書けない節は、検討が足りていない。

プロットはバージョン管理の対象にしない。プロットは考えた過程を書いた文書であり、成果物ではないからである。
本文を書いた後で構成を変えたときは、プロットも修正する。
プロットと本文の食い違いは、`structure/plot-mismatch` が指摘する。

生成に渡す指示は、型を指定して作る。

```sh
suikou brief --doctype design --lang ja
```

この指示では、節ごとの問いと書き方の指針が、禁止する形より前に表示される。

### 文書の型を宣言する

`docs/content/` 以下の文書は、フロントマターに `doctype:` を書く。
フロントマターを持てない文書は、`.suikou/structure.toml` の `[paths]` に登録する。
型を宣言した文書には、必須の節と推奨する節の順序についての判定が追加される。

### 守るべき文書の形

このリポジトリの文書は、次の形を守る。

- 箇条書きの前には完全な文を置き、導入の文が項目と文法的につながる形にしない。
- 地の文に項目の数を書かない。
- 見出しに連番を付けない。
- 時点に依存する語を使わない。時点に触れる場合は、西暦かバージョン番号で示す。
- 暗喩を使わない。必要なときは直喩か例え話にする。
- 専門家が書く技術文書に出てこない和語を、何度も使わない。この形は `register/rare-wago` が検出する。
- 一つの段落には一つの主張だけを置く。6文を超えたら段落を分ける。
- 各節は、見出しが示す問いに答える形で書く。
- Hugo のショートコードを例として引用するときは、エスケープした形で書く。
  Hugo は Markdown より前にショートコードを処理するので、コードブロックの中に書いても実行されてしまう。

文書をリポジトリに加える前に、`suikou check` を実行する。
合格の条件は、error と warning が一件も出ないことである。info は参考として読む。

指標を最小にすることを目標にしてはならない。
漢語率は info に分類される参考値である。漢語率をゼロにしようとして漢語を和語の動詞に置き換えた結果、
「検証」が「確かめ」になるなど、文体が悪くなった。経緯は決定の記録の D-27 に書いてある。
漢語率を下げたい場合は、定着したカタカナ語を使い、漢語の名詞を連ねないようにする。
