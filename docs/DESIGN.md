# suikou 設計書

技術文書のAI臭さを除去し、メンテナンス性を高めるための多層 lint とハーネス。
対応言語は日本語と英語に限定する。

この文書自体、ここで定める規則に従って書いてある。
箇条書きは完全な文で導入し、地の文に項目数を書かず、隠喩を使わない。

---

## 1. 目的と適用範囲

### 解こうとしている問題

生成AIが書いた技術文書には、単語レベルにとどまらない特徴がある。
比喩と婉曲表現の多用、文末表現の偏り、接続詞のこなれなさ、
そして必要以上に具体的でメンテナンスしにくい構造がこれにあたる。
既存のツールは単語辞書か表記規則のいずれかしか扱っておらず、これらに届かない。

### 適用範囲

技術文書とテクニカルライティングに限定する。
小説、広告、SNS投稿は対象外とする。好ましい文章はコンテクストによって異なるため、
用途を絞らなければ規則を決められない。

### 設計上の最重要制約

層ごとに lint の結果を出力して都度AIが修正する構造を採らない。
トークン消費を抑えるため、一度の実行で全層の指摘を出し、一度の修正で直せる形にする。

## 2. 設計の根拠となった実測

規則はすべて実測か明文の規範に基づく。直感で決めた規則は一つもない。
この方針を採った理由は、直感ベースの文体特徴が実証すると大半が外れるためである。
翻訳調研究（Meldrum 2009）とAI臭さ研究（逆瀬川 2026）という独立した二領域で、
同じことが確認されている。

### 人間コーパス

日本語はネイティブ執筆と翻訳の両方を集めた。
ネイティブ執筆は kaityo256 の技術書2点と future-architect のコーディング規約、
翻訳は Kubernetes 公式日本語訳、Vue 公式日本語訳、Linux kernel の ja_JP 翻訳を使った。

英語は Linux kernel Documentation、gcc、Rust Book、Django、
Google eng-practices、AWS S3 ユーザーガイド、AWS CloudFormation ユーザーガイドを使った。

### AI コーパス

Claude、Gemini、ChatGPT、Grok の4モデルから232本を収集した。
条件は言語2種、プロンプト3種（概念解説・手順書・設計判断）、
日本語の文体3種、書式抑制の有無で構成した。
収集は条件ごとに新規チャットで行い、メモリとカスタム指示を無効化した。

### 有効と判定した指標

| MATTR100 | 0.559〜0.581 | 0.629〜0.665 | 日 |
| MATTR100 | 0.58〜0.69 | 0.72〜0.82 | 英 |
| 地の文比率 | 0.816〜0.847 | 0.480〜0.711 | 日 |
| 地の文比率 | 0.66〜0.97 | 0.31〜0.56 | 英 |
| 漢語率 | 0.326〜0.397 | 0.455〜0.519 | 日 |
| 漢字率 | 0.220〜0.307 | 0.343〜0.394 | 日 |
| 指示詞（千字） | 5.685〜6.469 | 1.380〜3.388 | 日 |
| 形式名詞（千字） | 11.095〜11.163 | 4.990〜6.953 | 日 |

| 直喩・例示標識（千語） | 0.84〜2.54 | 0.00〜0.60 | 英 |

連用中止とテ形接続の比が最も強く分離する。
テ形は話し言葉寄りで節を一体化するのに対し、連用中止は書き言葉寄りで節を並べる。
AIは後者に偏る。これは Reinhart らが英語で見つけた現在分詞節の過剰と同じ現象にあたり、
南不二男のA類従属節という枠組みで両言語をつなげられる。

指示詞と形式名詞は、AIが人間より**少なく**使う点に注意する。
欠落の検出であり、位置を特定できない。

### 棄却した指標

文長変動係数は翻訳日本語と区別がつかなかった。
外来語率、サ変名詞＋を＋する/行う、読点密度は人間と重なった。

英語の現在分詞節と名詞化は人間帯と重なった。
Reinhart らが報告した5.3倍という効果量は、今回のタスクに転移しなかった。
原因は実験設計の違いと見ている。
Reinhart らは人間の文章を与えて続きを書かせたが、今回は文書の作成を指示した。
**先行研究の効果量をタスクをまたいで流用してはならない。**

### 書式抑制の実験

「箇条書き、太字、見出しを使わず地の文だけで書け」と指示した条件では、
書式が完全に消えた。太字、箇条書き、見出し、em dash のいずれもゼロになった。

一方で語彙と文構造は変わらなかった。
Claude の日本語で敬体と敬体抑制版を比べると、MATTR は 0.642 から 0.650、
連用中止は 5.31 から 4.83 で、いずれも誤差の範囲である。

この結果が層の分担を決めている。
プロンプトで消せるのは書式層だけであり、語彙層と文構造層は lint でしか押さえられない。

### モデル差

書式はモデル固有の癖が支配的である。
em dash は Claude が 10.32／千語 に対し Gemini がゼロ、
太字は Gemini が 95.4／千語 に対し日本語の Grok がゼロだった。

MATTR、連用中止比、形式名詞、指示詞は4モデルすべてで同方向に振れた。
**閾値を持つ規則は、モデル非依存のこれらの指標にだけ設定する。**

### 文体の影響

常体と敬体で指標が変わるかを、Claude と Grok の概念解説で対比した。

| 指標 | Claude 常/敬 | Grok 常/敬 |
|---|---|---|
| MATTR | 0.652 / 0.657 | 0.624 / 0.620 |
| 連用中止 | 5.12 / 5.31 | 5.33 / 3.27 |
| 地の文比率 | 0.618 / 0.371 | 0.915 / 0.922 |
| 形式名詞 | 7.68 / 3.03 | 4.37 / 7.24 |

モデル間で方向が一致しない。文体そのものによる体系的な影響は見られず、差はモデル差に吸収される。
**閾値を常体と敬体で分ける必要はない。** 文体の判定は、体言止めのような文体依存の規則を
適用するかどうかにだけ使う。

### ジャンルの影響

プロンプトの種類による差は大きい。文体の影響よりはるかに大きく、AIと人間の差に匹敵する。

| 指標 | 概念解説 | 手順書 | 設計判断 | 人間native |
|---|---|---|---|---|
| 連用中止／千字 | 3.83 | 7.69 | 4.90 | 2.71 |
| 漢語率 | 0.435 | 0.498 | 0.523 | 0.397 |
| 形式名詞／千字 | 4.63 | 8.11 | 4.00 | 11.16 |
| 指示詞／千字 | 3.25 | 0.22 | 1.27 | 6.47 |
| 地の文比率 | 0.526 | 0.345 | 0.507 | 0.847 |

最悪条件で閾値の余裕を評価すると、連用中止、指示詞、MATTR、地の文比率は
どのジャンルでも人間帯と重ならない。

一方で形式名詞は手順書で8.11に達し、閾値8.5との余裕がほとんどない。
漢語率は概念解説で0.435であり、人間ネイティブの0.397との差が薄い。
この二つはジャンル別の閾値を用意するか、severity を下げる必要がある。

### 生成順の影響

一括プロンプトで8本をまとめて生成した影響を、条件内で中心化して順位との相関で確認した。
構造系の指標はいずれもゼロ近傍であり、文体のドリフトは起きていない。
漢語率だけ相関が +0.405 と大きいが、本設計では順位とトピックが一致しているため、
順序効果ではなくトピック効果と解釈する。
漢語率がトピックに敏感であるという点は、上のジャンル分析と整合する。

### メンテナンス性の指示は守られるか

規則をプロンプトに入れた条件を追加し、遵守率を測った。
簡潔な指示（2文）と詳細な指示（規則7項目）の2水準を置いた。

| | 条件 | M1違反率 | M5混在率 | M6／千 | M7／千 |
|---|---|---|---|---|---|
| EN Grok | 指示なし | 0.63 | 0.05 | 0.59 | 0.20 |
| EN Grok | 簡潔 | 0.00 | 0.00 | 0.44 | 0.00 |
| JA Grok | 指示なし | 0.06 | 0.14 | 0.44 | 0.15 |
| JA Grok | 簡潔 | 0.00 | 0.00 | 0.37 | 0.00 |
| JA Grok | 詳細 | 0.00 | 0.00 | 0.00 | 0.00 |
| EN Claude | 指示なし | — | 0.04 | 0.72 | 0.00 |
| EN Claude | 簡潔 | 0.00 | 0.00 | 0.32 | 0.00 |
| EN Claude | 詳細 | 0.00 | 0.00 | 0.00 | 0.00 |

構造の規則（箇条書きの導入文、項目の平行性、「など」終わり）は簡潔な指示で完全に守られた。
語彙の規則（時点依存語）は簡潔な指示では半減にとどまり、詳細な指示で初めてゼロになった。

項目数の明示、見出しの連番、手動番号は、指示がない条件でもほとんど発生しない。
これらは予防層に入れる必要がない。

Claude は指示がない条件で箇条書きの導入文を一度も書かなかった。
リストは24ブロックあるが、その直前は常に見出しかリストである。
不正な導入文ではなく導入文の不在という別の失敗形であり、地の文比率0.150と整合する。

指示には副次効果がある。メンテナンス性の指示だけで文書指標が改善した。

| 指標 | Claude 指示なし | 簡潔 | 人間native |
|---|---|---|---|
| 地の文比率 | 0.150 | 0.702 | 0.847 |
| 箇条書き割合 | 0.633 | 0.273 | 0.172 |
| 形式名詞／千字 | 2.75 | 8.11 | 11.16 |

導入文を書かせた結果として地の文が生じ、地の文比率と箇条書き割合が人間帯に近づいた。
一方で連用中止と指示詞は改善しない。

簡潔な指示には出力を縮める作用もある。
日本語の Grok は13629字から8010字に、英語の Grok は5053語から2260語に減った。
詳細な指示ではこの縮小が起きない。

## 3. 検出対象

検出対象は二つの集団に分かれる。
文や行の単位で真偽が決まり指摘位置を持つものと、
文書全体でしか計算できず指摘位置を持たないものである。
後者の多くは欠落の指摘であり、原理的に位置がない。

### D 系: 文書スコープ指標

| ID | 対象 | 言語 | 閾値 | 予防可能 |
|---|---|---|---|---|
| ID | 対象 | 言語 | 閾値 | 予防可能 | severity | 頑健性 |
|---|---|---|---|---|---|---|
| D1 | MATTR が高い | 日英 | 日 >0.60 / 英 >0.71 | 部分的 | warning | 高 |
| D2 | 地の文比率が低い | 日英 | 日 <0.75 / 英 <0.65 | 可 | warning | 高 |
| D3 | 連用中止 ÷ テ形接続の比 | 日 | >3.0 | 不可 | warning | 高 |
| D4 | 連用中止の密度 | 日 | >4.0／千字 | 不可 | warning | 高 |
| D5 | 形式名詞の不足 | 日 | <8.5／千字 | 可 | info | 低 |
| D6 | 指示詞の不足 | 日 | <4.5／千字 | 不可 | warning | 高 |
| D7 | 漢語率が高い | 日 | >0.42 | 不可 | info | 低 |
| D8 | 箇条書き割合が高い | 日 | >0.25 | 可 | warning | 中 |
| D9 | 直喩・例示標識の不足 | 英 | <0.8／千語 | 不可 | warning | 中 |

閾値は人間帯の上限とAI帯の下限の間に置いた。

頑健性はジャンルによる変動への耐性を示す。
D5 と D7 はジャンルとトピックへの感度が高く、最悪条件で人間帯とほぼ接する。
ジャンル別の人間ベースラインが揃うまでは severity を info に置き、
揃った時点で warning に昇格させる。

### M 系: メンテナンス性

| ID | 対象 | 形式 | 根拠 |
|---|---|---|---|
| M1 | 箇条書きの導入文が項目と文法的に結合している | 二値 | Google developer documentation style guide |
| M2 | 地の文で項目数を明示している | 二値 | 同上 |
| M3 | 見出しに節の連番がある | 二値 | 同上 |
| M4 | 箇条書きに手動で番号を振っている | 二値 | 同上 |
| M5 | リスト項目の構文が平行でない | 二値 | 同上 |
| M6 | 時点依存語を使っている | 二値 | Google timeless documentation |
| M7 | 列挙が「など」「etc.」で終わっている | 二値 | 同上 |

M 系はAI臭さではなくメンテナンス性を根拠に持つ。
AI以前から存在する問題であり、AIの世代交代でも陳腐化しない。

M 系だけはコーパスの平均に合わせてはならない。
箇条書きの導入文を正しく書いているのは AWS S3 ユーザーガイドだけで、
Linux kernel は不完全な導入が105件に対し完全な導入が16件だった。
人間の平均に合わせると、この層は意味を失う。

### N 系: 規範的だが実測ではAIに出なかったもの

体言止め、サ変名詞＋を＋する/行う、文末の3連続重複、隠喩辞書がここに入る。
いずれも人間が書いた文章の校正には有効なので残すが、severity を下げる。

隠喩辞書は指摘されると陳腐化する。
2024年初頭に指摘された delve、intricate、realm は、指摘の直後から頻度が下がった。
辞書層を単独の防御線にしてはならない。

### A 系: LLM判定が必要なもの

生きた比喩と死んだ比喩の弁別、比喩に説明が伴っているかの判断、
過剰な具体性がメンテナンス性を損なうかの判断、用語の一貫性がここに入る。

lint では疑わしい箇所の列挙までとし、判断はハーネス側に委ねる。

## 4. アーキテクチャ

### 分割の基準

出力を誰が消費するかで分ける。

エディタと人間が読むものは textlint を直接呼ぶ。局所ルールだけを扱う。
位置が意味を持ち、増分実行が速い。

エージェントとCIが読むものはフロントツール `suikou` が扱う。
文書指標、合成レポート、トークン制御を担当する。

```
suikou
├─ textlint --format json      局所ルール（M1〜M7、既存3プリセット）
├─ 文書解析器                   D1〜D9
├─ 統合と修正方針の合成
└─ 出力: Markdown / JSON / MCP
```

局所ルールは textlint ルールとして公開するため、単体で NeoVim から使える。
`suikou` はその textlint を呼び出すので、実装は重複しない。

### 実装言語

検証を通った指標はすべて純 Rust で実装できる。
lindera-unidic が UniDic 2.1.2 の全素性を返し、語種と活用形が取得できるためである。
D3 の連用中止は活用形、D7 の漢語率は語種で判定できる。

Python が必要だったのは現在分詞節、名詞化、modifier stack、依存距離であり、
これらはすべて棄却した指標である。

そこで二層に分ける。

**Tier 1（確定済み・本番）** は純 Rust で実装する。
D 系、M 系、N 系のすべてを含む。単一バイナリで、hooks からの高頻度起動に耐える。

**Tier 2（探索・較正）** は Python で実装する。
コーパス較正、新指標の探索、閾値の再計算を担当する。本番の実行経路には入らない。

Tier 2 で有効性が確認された指標だけを Tier 1 に移す。

名詞化と modifier stack はモデル依存の指標として価値があるため、
将来これらを本番で使う場合に限り、常駐サイドカー方式を採る。
行区切り JSON の標準入出力で Python を常駐させ、モデルのロードを一度に抑える。
オプトインとし、既定では無効にする。

### 性能要件

Claude Code の hooks から Write と Edit のたびに実行される運用を想定する。
この用途では起動コストが支配的になるため、
UniDic 辞書は mmap で読み込むか、daemon モードを用意する。

## 5. CLI 仕様

| コマンド | 役割 |
|---|---|
| `suikou brief [--profile P] [--lang L]` | 生成前にプロンプトへ入れる制約ブロックを出力する |
| `suikou check <path>` | 局所指摘と文書指標の統合レポートを出力する |
| `suikou baseline <glob>` | コーパスから閾値を較正しプロファイルを生成する |
| `suikou terms <glob>` | 文書群から用語集と allowlist を抽出する |
| `suikou mcp` | MCP サーバとして起動する |
| `suikou daemon` | 常駐モードで起動する |

`check` の主なオプションを示す。

- `--format md|json|text` は出力形式を選ぶ。既定は md とする
- `--lang auto|ja|en` は言語を指定する。既定は auto とする
- `--profile oss|service|reference|tutorial|<path>` は閾値の組を選ぶ
- `--budget <tokens>` はレポートの上限を指定する
- `--quiet` は exit code だけを返す

### brief が出す制約

書式層とメンテナンス性層だけを出力する。
MATTR や連用中止比などの語彙・文構造指標は出力しない。

書式抑制の実験で、書式はプロンプトで完全に消えるが語彙と構造は変化しないと分かっている。
効かない制約をプロンプトに入れることは、トークンの無駄であり、過剰修正の危険もある。

メンテナンス性の指示は、規則の種類によって必要な分量が違う。
構造の規則は簡潔に書き、時点依存語だけは禁止語を列挙する。
指示がなくても発生しない規則は brief に入れない。

| 規則 | brief での扱い |
|---|---|
| M1 箇条書きの導入文 | 1文で書く |
| M5 項目の平行性 | 1文で書く |
| M7 「など」終わり | 1文で書く |
| M6 時点依存語 | 禁止語を列挙する |
| M2 項目数の明示 | 入れない |
| M3 見出しの連番 | 入れない |
| M4 手動番号 | 入れない |

簡潔な指示は出力を縮める作用を持つ。
プロファイルに brief の詳細度を設定として持たせ、用途に応じて選べるようにする。

## 6. 出力スキーマ

### JSON

```json
{
  "document": [
    {
      "metric": "ja.renyo_te_ratio",
      "value": 15.94,
      "threshold": 3.0,
      "direction": "above",
      "guidance": "..."
    }
  ],
  "local": [
    {
      "ruleId": "maint/list-lead-in",
      "severity": "error",
      "message": "...",
      "positions": [{ "line": 12, "column": 1, "text": "..." }],
      "truncated": 0
    }
  ]
}
```

### Markdown

```
## 書き直しの方針

（違反した文書指標から合成する。3〜5行。個別の数値は並べない）

## 直す箇所

### 箇条書きの導入文が項目と結合している — maint/list-lead-in（6件）

- L12 「以下の目的で使います:」
- L45 ...
```

### トークン削減

トークン消費の抑制が最重要制約であるため、出力は次の規則に従う。

- ルールの説明文はルールにつき一度だけ出力する。行ごとに繰り返さない
- 一つのルールにつき提示する位置は20件までとし、超過分は件数だけを示す
- 閾値の範囲内にある指標は出力しない
- `--budget` の指定時は severity の順に切り詰める

### 文書指標から修正方針への変換

数値を並べてもモデルは何をすべきか判断できない。指標を指示文に変換する。

| 違反指標 | 生成する指示 |
|---|---|
| D1 MATTR が高い | 同じ対象は同じ語で呼ぶ。言い換えを止める |
| D2 地の文比率が低い | 箇条書きに分解した内容を地の文に戻す |
| D3、D4 連用中止が多い | 「〜し、」で繋いだ節を分割するか「〜して、」に変える |
| D5 形式名詞が少ない | 漢語の名詞化を「〜すること」等の和語表現に戻す |
| D6 指示詞が少ない | 段落間の接続に指示詞を使い、名詞の再掲を減らす |
| D7 漢語率が高い | 漢語を和語動詞に開く |
| D8 箇条書きが多い | 箇条書きを地の文に戻す |
| D9 直喩標識が少ない | 比喩を使うなら直喩または例示として明示する |

### severity

| severity | 対象 | 根拠 |
|---|---|---|
| error | メンテナンス性層 M1〜M7 | 客観的で議論の余地がない |
| warning | 文書指標 D1〜D9 の閾値超過 | 閾値に幅があり文脈に依存する |
| info | モデル依存指標、辞書層、Tier 2 指標 | 参考値であり陳腐化するものを含む |

AI臭さよりメンテナンス性を重く扱う。前者は閾値の問題だが、後者は規定違反だからである。

hooks で差し戻す条件は設定で変更できるようにする。

## 7. 規則の仕様

### 文体の判定

常体と敬体で文末の癖が異なるため、規則を切り替える必要がある。

入り口を分けず、ブロック単位で判定する。
一つの文書が本文は敬体、箇条書きは常体という構成を取ることが正当であり、
入り口レベルの切り替えでは粒度が粗すぎる。

文書指標の閾値は文体で分けない。
常体と敬体を対比した結果、モデル間で方向が一致せず、体系的な影響が見られなかったためである。
文体の判定は、文体依存の規則を適用するかどうかの判断にだけ使う。

判定は文末の形態素で行う。設定で `style: auto | desumasu | dearu` を上書きできるようにする。

文体に依存する規則を示す。

- 体言止めは地の文では禁止し、箇条書きでは許容する
- 冗長な文末の辞書を敬体と常体で分ける

### 箇条書きの導入文（M1）

日本語で正しい形は、句点で終わる完全文に箇条書きが続く形か、
体言にコロンが付いて箇条書きが続く形である。
連用形、助詞、接続助詞で終わる導入は、項目と文法的に結合するため項目の増減で壊れる。

英語は導入文に the following、as follows、these、below、steps のいずれかを含むかで判定する。
厳密には定形動詞の有無を見るべきだが、この辞書判定だけで
AWS S3 ユーザーガイド（30対145）と Linux kernel（105対16）を分離できている。

### 比喩層

分野で確立した用語は比喩ではない。
cache、tree、handshake、キャッシュ、ハンドシェイクは用語であり規制対象外とする。

問題は、説明を伴わずに使われる新規の隠喩である。
逆瀬川の385語のうち「入口」「土台」「核心」「線引き」の類型と
「切り分ける」「潰す」「踏み込む」「溶かす」の類型、
Kobak の291語、Reinhart の tapestry や amidst がこれにあたる。

直喩と例え話は条件付きで許容する。
条件は TYPO3 の規定にある通り、前後で平易な言葉による実際の説明を伴うことである。

allowlist は同梱せず `suikou terms` で文書から生成する。
プロジェクトごとに用語が違うためであり、
同時に辞書の陳腐化問題に対する構造的な回答にもなる。

## 8. ハーネス

### 思考ファイルと成果物ファイルの分離

過剰な具体性への対策を、ワークスペースの規約として実装する。

```
docs/guide.md              成果物。lint の対象とする
.suikou/notes/guide.md     思考。lint の対象としない
```

スキルは次のように指示する。
検討した選択肢、却下した案、確信のない具体値、根拠、測定の出典は notes に書く。
確定した内容だけを成果物に書く。

効果は二つある。
モデルが考えを見せようとする傾向に正当な行き先を与えることで、成果物から過剰な具体性が減る。
加えて根拠が文書の隣に残るため、後の保守で「なぜこう書いたか」を辿れる。

書く問題を、置き場所の問題に変換することがこの設計の要点である。

### ワークフロー

1. `suikou brief` の出力をプロンプトに入れる
2. 生成し、成果物と notes を作る
3. `suikou check` を一度実行し、統合レポートを得る
4. 修正を一パスで実施する
5. `suikou check --quiet` で検証する

層ごとの lint と修正のループを回さない。
局所指摘がどこを直すかを伝え、文書指標から合成した方針がどう直すかを伝える。

### 用語集

`suikou terms` で既存文書から分野用語を抽出し `.suikou/terms.toml` に置く。

terms に載る語は確立した用語として比喩判定から除外する。
terms に載らない隠喩的語彙だけを指摘する。
同じ仕組みで用語の一貫性も検査できる。

## 9. リポジトリ構成

```
suikou/
├─ crates/suikou-core      解析器（lindera-unidic, pulldown-cmark）
├─ crates/suikou-cli       CLI と MCP サーバ
├─ packages/               npm。textlint の局所ルール
```

単一リポジトリにする理由は、CLI の出力スキーマとスキルの期待がずれることを防ぐためである。
同一コミットで管理し、ゴールデンファイルテストで固定する。

スキルの正本はこのリポジトリに置き、dotfiles 側から取り込む。
実体を dotfiles に置くと、CLI のバージョンと独立に動いてしまう。

### パッケージの分割

npm 側は用途ごとに分ける。

- `textlint-rule-preset-tech-maintainability` は M1〜M7 を収める。日英に対応する。
  AI臭さと独立した価値を持つため、単体で使える
- `textlint-rule-preset-ja-ai-structure` は日本語の文レベル規則を収める

## 10. 既存 OSS との関係

| パッケージ | 扱い | 理由 |
|---|---|---|
| textlint-rule-preset-ja-technical-writing | 併用する | 表記と局所的な読みやすさを完全にカバーしており重複しない |
| @textlint-ja/textlint-rule-preset-ai-writing | 部分併用する | 誇張表現、機械的な太字、リスト書式を再利用する |
| p1ass/textlint-rule-preset-ai-words-ja | 併用する | 辞書層として使う。陳腐化を前提とし単独の防御線にしない |
| D1〜D9、M1〜M7 | 新規に実装する | 既存にない |

`@textlint-ja/textlint-rule-preset-ai-writing` の `no-ai-colon-continuation` と M1 は近い。
前者はコロンの前が述語で終わる形を禁じ、後者は導入文が項目と文法的に結合しているかを見る。
目的が異なるため両立するが、同じ箇所を二重に指摘する場合がある。
フォーマッタ側で同一行の重複をまとめる。

既存プリセットが本プロジェクトの層と重複しない点は確認済みである。
`textlint-rule-preset-ja-technical-writing` は文長の上限を100文字に置くが、
AI文の平均文長は39.2文字で引っかからない。読点の上限も3個だが、AI文は1文あたり0.95個である。

## 11. P7 計画

### 実装の順序

メンテナンス性層から着手する。
規則が二値で閾値を持たず、規範の出典が明確で、AI臭さとは独立した価値を持つためである。
この層だけでも単体で有用なものが出来上がる。
追加実験で、この層の指示が生成時にほぼ完全に守られること、
そして守らせるだけで文書指標まで改善することが分かっており、投資効率が最も高い。

次に日本語の文書指標のうち頑健なものを実装する。
D1、D2、D3、D4、D6 がこれにあたる。
連用中止とテ形接続の比が最も強く分離し、lindera-unidic の活用形だけで実装できる。

D5 と D7 は severity を info に置いて実装する。
ジャンル別の人間ベースラインが揃った時点で閾値を見直す。

英語側と、MCP および daemon は後回しにする。

Python 版の `jametrics.py`、`enmetrics.py`、`mcheck.py` が
すべての指標の参照実装になっている。
Rust 実装はこれらと同じ値を返すことをゴールデンテストで確認する。

### 評価

偽陽性率を人間コーパスで測る。
Linux kernel、gcc、Rust Book、Django、AWS、Kubernetes 日本語訳、Vue 日本語訳を対象とし、
error として報告される件数を数える。

M 系は人間コーパスでも大量に検出されるはずである。
Linux kernel の箇条書き導入は不完全な形が優勢だった。
これは偽陽性ではなく、実際に改善の余地がある箇所として扱う。
ただし件数が多すぎると使えないため、既定の severity を調整する必要が出るかもしれない。

D 系は人間コーパスで警告が出ないことを確認する。こちらは偽陽性として扱う。

### 人間コーパスの補強

日本語のネイティブ執筆コーパスは解説書に偏っている。
ジャンルによる変動が大きいと分かった以上、手順書型のネイティブ日本語を集める必要がある。
D5 と D7 の severity を warning に上げられるかは、この補強にかかっている。

## 12. 未決事項

P7 の実装と評価を経てから決める。

- `suikou brief` の出力をスキルが毎回呼ぶか、SKILL.md に静的に埋めるか
- brief の詳細度をプロファイルの設定としてどう表現するか。
  簡潔な指示は出力を縮める副作用を持つため、既定値の選択に判断が要る
- daemon モードのプロトコル。WSL2 環境での動作確認が必要になる
- 閾値のジャンル別分割の粒度。ジャンルをどう判定するかも含めて決める
- AWS と Google の日本語ドキュメントをコーパスに加える方法。GitHub には置かれていない
- 日本語のネイティブ執筆コーパスの拡充。現状は2ソースで、いずれも解説書である

### 解決済みの論点

次の項目は実測で決着したため、実装前に検討する必要はない。

- 文体ごとに閾値を分けるか。分けない
- 一括プロンプトで収集したデータが使えるか。使える
- メンテナンス性の指示が守られるか。構造の規則は簡潔な指示で守られ、語彙の規則は詳細な指示が要る
- 文書スコープの指標を textlint の中に収めるか。収めず、フロントツールが担当する
- 実装言語。Rust を中心とし、Python は較正と探索に限定する
