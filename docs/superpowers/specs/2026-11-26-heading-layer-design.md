# 見出しの検査レイヤーの設計

見出しの検査レイヤーとは、見出しの文字列だけを対象とする規則をひとつのモジュールへ集約し、本文を対象とする規則から分離する構成である。規則ごとに対象ブロックを個別に絞っているため、どの規則が見出しに当たるかがコードを読むまで分からない。この設計はその境界を明示し、あわせて章タイトルの形式を検査する規則を追加する。

## 動機

見出しに適用される規則の一覧が、どの文書にも書かれていない。`docs/content/ja/metrics.md` の「指標ごとの対象範囲」は計測対象を「地の文およびリスト項目の本文」と述べるだけで、見出しに触れていない。

実装を読むと、対象ブロックの指定が規則ごとにばらばらである。

| 層 | 見出しへの適用 | 実装箇所 |
|---|---|---|
| 文書指標（`ja.*`、`en.*`） | 対象外 | `markdown.rs:333` の `body()` が地の文とリスト項目だけを連結する |
| `register/rare-wago`、`register/prefer-katakana` | 対象外 | `register.rs:249` |
| `glossary/variant`、`glossary/defined-name` | 対象外 | `glossary.rs:160` |
| `maint/time-dependent` | 適用される | `rules/mod.rs:552` が `match b.kind` の外にある |
| `maint/numbered-heading` | 見出し専用 | `rules/mod.rs:519` |
| `ja.list_ratio` | 分母に入る | `markdown.rs:262` が見出し行を `non_empty_lines` に数える |

`maint/time-dependent` が見出しに当たるのは、`m6.extend` の位置が偶然そうなっているためである。意図した設計ではない。

`glossary/defined-name` には別の欠陥がある。`glossary.rs:380` の `check_defined` はどこからも呼ばれていない。`crates/` 全体を検索して呼び出しが1件もないことを確認した。単体テストはあり、`glossary.rs:81` の表は重大度を error と記載し、`docs/content/ja/tuning.md` と `writing.md` は `.suikou/defined.toml` を利用者向けの設定として案内している。それでも規則は発火しない。見出しを見ないどころか、本文も見ていない。

同時に、章タイトルの形を定める規約が実装にも文書にもない。`skills/ja-style/SKILL.md` に「手順を示す文書とスキルでは動詞で終える」と書いたが、この条文は見出しの階層を区別していない。その結果、同ファイルの第2階層の見出し8件のうち7件が用言で終わる形になった。参照コーパスの実測では、この形は5%未満の少数派である。

## 扱う範囲

見出しのレイヤーの新設と、そこに置く規則の定義を扱う。対象は次のとおりである。

- 見出しに当てる規則を集めたモジュールの新設。
- 章タイトルの形式を検査する規則 `structure/heading-form` の新設。
- `maint/numbered-heading` と `maint/time-dependent` の見出しへの適用を、偶然ではなく明示に変える作業。
- `glossary/defined-name` の配線。本文と見出しの双方に当てる。
- 検出された見出しの書き直し。`skills/suikou/SKILL.md` と `skills/ja-style/SKILL.md` の2件である。
- 日本語と英語の `metrics.md` への対象範囲の追記。
- 発火率の計測。`docs/content/ja/development.md:75` が規則の追加時に求める手順であり、`crates/suikou-core/examples/structure_rate.rs` を拡張して計測し、値を `TASKS.md` に記録する。

## 扱わない範囲

本文側の整備は後の作業に回す。`.suikou/defined.toml` の新設、語彙選定手順への固有名の例外、`ja.list_ratio` の分母の明記、`CLAUDE.md` と `writing.md` の見出し規約の修正が該当する。利用者が「先に見出し」と指定したためである。

`glossary/defined-name` は本文と見出しの双方に配線するが、`.suikou/defined.toml` は作らない。設定ファイルが無い状態では `defined()` が空の一覧を返し、規則は何も報告しない。配線の正しさは、固定の一覧を渡す単体テストで検証する。固有名を登録すると本文側に指摘が出るため、その作業は後に回す。

この配線は、`.suikou/defined.toml` を置いている下流の利用者にとって挙動の変更になる。重大度 error の規則が初めて発火するようになる。`tuning.md` と `writing.md` がこの設定ファイルを案内しているため、何も報告しない現状を欠陥とみなし、配線を修正として扱う。ただし `skills/ja-style/SKILL.md` の見出し規約だけは、同ファイルの見出しを直す作業と同じ箇所にあるため、この範囲に含める。

英語に対する見出しの形式の規則は作らない。実測の根拠は後述する。

`suikou brief` には章タイトルの規約を加えない。`brief.rs` は M2、M3、M4 を意図して省いており、テスト `m2_m3_m4_are_left_out` がそれを固定している。加えるべきかどうかは別に判断する。`TASKS.md` に見送りとして記録する。

`corpus/baselines.toml` の `[rejected]` には追記しない。`[rejected]` は指標の一覧であり、規則を書く場所ではない。章タイトルの用言率を指標にしてはならないという判断は、決定の記録に書く。

実装済みの規則の判定内容は変更しない。`maint/time-dependent` が見出しに当たる挙動も、表に対して当たる挙動も、そのまま保つ。移動するのは判定の置き場所だけである。

レポートの節の構成も変更しない。見出しの指摘は位置を持つため、実装済みの「修正する箇所」に入る。独立した節を設けると出力が増え、`CLAUDE.md` の出力トークン量の制約に反する。規則の識別子で見分けられる。

## 実測データ

計測は `structure::sections` と同じ定義で行った。先頭の第1階層の見出しを標題として除外し、残りのうち最も浅い階層だけを章タイトルとして数えた。末尾の括弧と句読点を落としたうえで、最後の形態素の品詞で形を判定した。日本語の文字を含まない見出しは数えていない。

| コーパス | 件数 | 章タイトルの用言率 | 発火する文書の割合 |
|---|---|---|---|
| `pro_ja`（人間のネイティブ執筆 798件） | 1930 | 4.8% | 10.0% |
| `adrs_ja`（公開 ADR 123件） | 881 | 1.8% | 5.0% |
| `howto_ja`（手順書 200件） | 1004 | 13.0% | 25.1% |
| `ai_docs_ja`（AI の出力 150件） | 851 | 6.6% | 15.8% |
| `k8s`（人間による翻訳） | 277 | 19.5% | 17.8% |

章タイトルはどのコーパスでも体言止めが大半を占める。このリポジトリの日本語文書では、`decisions.md` と2件の SKILL.md を除いた63件がすべて体言止めである。

人間と AI では分離しない。`pro_ja` の 4.8% に対し `ai_docs_ja` は 6.6% であり、差は文体判定に使える幅ではない。したがってこの値を文書指標として導入してはならない。`corpus/baselines.toml` の `[rejected]` に並ぶ指標と同じ性質である。採用の根拠は、人間と AI の判別ではなく、参照コーパスで優勢な慣行からの逸脱である。`register/rare-wago` が参照コーパスとの頻度比較で和語を検出する方式（D-26）と同じ立て方になる。

`howto_ja` の発火率 25.1% は、`docs/content/ja/tuning.md` が示す適合の目安 10% を大きく超える。中身を読むと、`テーブルを作成する`、`データをダウンロードする`、`StarRocks Helm チャートリポジトリを追加する` のような手順の一歩が並んでいた。手順書では章そのものが一つの操作であり、用言で終える形が正しい。閾値の不適合ではなく型による分布の差であるため、型で除外する。

英語は全階層が名詞句である。`pro_en` の章タイトル 2842件のうち動名詞で始まるものは 9.1%、`ai_docs` は 5.8% で、命令形はそれ未満である。命令形が現れるのは `docs/content/en/tuning.md` の手順の節だけ（`Generate a baseline from your corpus` ほか9件）であり、体言止めと述語止めのような二分がそもそも存在しない。英語に規則を作らない判断は、文体の規則が英語へ移らなかった D-28 と D-50 の結論と一致する。

ADR の標題の形式は日英で異なる。日本語の `decisions.md` は述語で終わる決定文（`形態素解析をトレイトの背後に隔離する`）、英語は動名詞句（`Isolating the tokenizer behind a trait`）である。双方ともこのリポジトリで定着した慣行であり、変更する根拠は見つからなかった。

## 採った案と採らなかった案

三つの案を検討した。

第一の案は、追加する規則を `structure.rs` の関数として置くものである。変更は最小で済む。ただし見出しに当たる規則が `rules/mod.rs`、`glossary.rs`、`structure.rs` の三箇所に散ったままになり、動機に挙げた問題が残る。

第二の案は、兄弟の見出しの形が混ざったときに検出する規則にするものである。`maint/parallel-items` と同じ立て方になり、型による除外が不要になる。ただし章タイトルがすべて用言で揃っている文書を通してしまう。利用者が解こうとしている問題がまさにそれであるため、目的に合わない。

第三の案を採る。見出しのレイヤーをモジュールとして独立させ、見出しに当てる規則をそこへ集約する。章タイトルの形は、参照コーパスの実測に基づいて体言止めを既定とし、分布が異なる型を除外する。利用者はこの案を選んだ。

## 見出しのレイヤーの構成

`crates/suikou-core/src/headings.rs` を新設する。このモジュールは `BlockKind::Heading` のブロックだけを読み、ほかのブロックを見ない。モジュールの先頭に、どの層が見出しを見てどの層が見ないかの表を置く。これが利用者の求めた分離の実体である。

規則の識別子ごとに `LocalFinding` を1件だけ作るという制約を守る。`report.rs:136` の `to_markdown` は `local` の要素ごとに `### 文面 — 識別子（n件）` の節を1つ出力するため、同じ識別子で2件返すと説明文が二重に出る。`CLAUDE.md` の「各ルールの説明文は、ルールごとに一度のみ出力する」に反し、`MAX_POSITIONS_PER_RULE` の20件が producer ごとの上限になって合計40件まで出る。

そのため、見出しだけに当たる規則は `LocalFinding` を返し、本文と見出しの双方に当たる規則は `Position` を返して本文側の producer が1件に束ねる。

| 規則 | 見出しのレイヤーが返すもの | 束ねる場所 |
|---|---|---|
| `structure/heading-form` | `LocalFinding` | 見出しだけに当たる |
| `maint/numbered-heading` | `LocalFinding` | 見出しだけに当たる |
| `maint/time-dependent` | `Vec<Position>` | `rules::check_all` の M6 |
| `glossary/defined-name` | `Vec<Position>` | `glossary::check_defined` |

呼び出しは `crates/suikou-core/src/check.rs` の `evaluate_with_glossary` に置く。`register` と `glossary` を呼んでいる箇所の隣である。CLI に置いてはならない。`check::evaluate` は `lib.rs:26` で再公開された library の入口であり、そこから `maint/numbered-heading` が消えると library の利用者に対する後退になる。

節の存在と順序を見る `structure/missing-section` と `structure/section-order` は移さない。これらは見出しを文字列として検査するのではなく、文書の骨格として読む。`structure.rs` に残す。

`structure/heading-form` は `lang == Lang::Ja` のときだけ呼ぶ。英語の経路では `crates/suikou-cli/src/morphology.rs:20` の `UnusedMorphology::tokenize` が `unreachable!` で落ちるため、言語で絞らない実装は英語と判定された文書でパニックを起こす。英語の文書に混ざった日本語の章タイトルは検査しない。検査するには形態素解析器の読み込みを変える必要があり、この設計の範囲を超える。

## structure/heading-form の定義

章タイトルの最後の形態素が用言であるときに検出する。重大度は warning とする。参照コーパスに5%弱の正当な例が残るため、error にはしない。

判定の手順を定める。

まず `structure::sections` で章タイトルを取る。この関数は先頭の第1階層の見出しを標題として除外し、残りのうち最も浅い階層だけを返す。階層を2に固定しないのは、`##` から始まる文書と `###` から始まる文書の両方を同じ定義で扱うためである。

次に末尾を整える。`。`、`：`、`、`、`！`、`？`、`.` と空白を除去し、末尾が閉じ括弧であれば対応する開き括弧までを除去する。`設定を変更する（任意）` を取り逃がさないためである。

続いて対象を絞る。日本語の文字を1字も含まない見出しは対象外とする。`ja.renyo_per_1k` のような識別子の見出しが英語側の文書にも日本語側の文書にもあり、これを形態素解析の結果で判定すると意味を持たない。

最後に形を見る。整えた文字列を形態素解析し、最後の形態素の品詞大分類が `動詞`、`助動詞`、`形容詞` のいずれかであれば検出する。体言止めの判定には `Token::is_taigen` がすでにあり、`maint/parallel-items` が使っている。用言の判定はその裏側になる。品詞がそれ以外（補助記号など）のときは検出しない。

指摘の文面は「章タイトルが用言で終わっている。体言止めの名詞句にする」とする。位置は見出しの行の第1列である。

## 型による除外

分布が異なる2つの型を除外する。除外は組み込みプロファイル `crates/suikou-core/profiles/oss.toml` と `service.toml` の双方の `[doctype.<型>]` の `rules` に書く。この経路は `profile.rs:188` の `silenced` として実装済みであり、型ごとに局所の規則を除去する仕組みが動いている。規則の側に型の分岐は持たせない。片方のプロファイルにだけ書くと、走る規則そのものが2つの組み込みプロファイルで食い違う。

| 型 | 除外の根拠 |
|---|---|
| `howto` | 章タイトルが手順の一歩である。`howto_ja` の発火率 25.1% が根拠である |
| `log` | 作業の項目が動作である。`TASKS.md` の章タイトル32件のうち27件が該当する |

`decision` は除外しない。当初は除外する設計にしたが、根拠が成立しなかった。第一に、このリポジトリの `docs/content/ja/decisions.md` はフロントマターで `doctype: "log"` を宣言しており、48件という件数は `log` の根拠であって `decision` の根拠ではない。第二に、公開 ADR は1決定を1ファイルに書く形を取り、決定文は第1階層の標題に置かれる。`structure::sections` は標題を外すため、判定対象になるのは `背景`、`決定`、`採用理由` のような体言止めの節名である。`adrs_ja` の発火率 5.0% は決定文に由来せず、`docs/content/ja/tuning.md:156` が示す適合の目安 10% の内側にある。根拠のない `reason` を組み込みプロファイルに書くことは `CLAUDE.md` が禁じている。

`log` の根拠はこのリポジトリの `TASKS.md` だけであり、外部コーパスで確認していない。`log` 型そのものが記録を集約する文書のために D-42 で設けた型であるため、このリポジトリの慣行を根拠とする。これはこの設計での判断として記録する。

型を宣言していない文書にも当てる。`silenced` は型が解決できたときにだけ働くため、宣言の無い文書では除外が効かない。`structure/long-paragraph` と `structure/lead-opener` も型を問わず当てており、その前例に合わせる。帰結として、型を宣言していない手順書は 25.1% の割合で指摘を受ける。その文書は型を宣言するか、`.suikou/profile.toml` で規則を落とすことになる。

除外しない型では、このリポジトリで12件が検出される。`skills/suikou/SKILL.md` の5件と `skills/ja-style/SKILL.md` の7件である。双方とも `.suikou/structure.toml` で `reference` 型として宣言している。

## skills の見出しの修正

検出された12件を体言止めの名詞句に書き直す。

`skills/suikou/SKILL.md` は neon が書いた文書であり、見出しがエージェントへの指示そのものになっている。この文書を `howto` 型として宣言し直せば除外されるが、`howto` 型は前提の節を必須とするため `structure/missing-section` が発火する。利用者は型を変更するのではなく見出しを修正する案を選んだ。

書き直しは意味を保つ。`本文の前に構成を設計する` は、節の中身が「本文を書く前に構成を確定させる手順」であるため、その中身を名詞句で言い直す。指示の強さが落ちる箇所では、見出しではなく本文の側に動詞の文を置く。

`skills/ja-style/SKILL.md` では、見出しを修正するとともに見出し規約の条文も修正する。v0.2.0 の条文は文書の種類で形式を決めているが、実測は階層で決まることを示した。章タイトルは体言止め、第3階層以下は体言止めを既定として手順の一歩と禁止事項のときだけ用言、という形式に書き換える。第3階層の用言率は `pro_ja` で 20.9%、`howto_ja` で 15.0% であり、少数ではあるが正当な形式である。

## 文書への追記

日本語と英語の `metrics.md` に、見出しのレイヤーの節を加える。内容は、どの規則が見出しに当たるかの一覧と、`structure/heading-form` の判定手順と、型による除外とその根拠である。「指標ごとの対象範囲」の表には、文書指標と文体の規則が見出しを対象外とすることを明記する。

`docs/content/*/decisions.md` に決定を1件追記する。記録すべき論点は、人間と AI で分離しない値を規則の根拠にした理由、英語に規則を作らなかった理由、型を3つ除外した根拠、そして見出しのレイヤーを分けた理由である。

モジュールの名前と関数の分割、`headings.rs` の中での規則の並び、テストの置き場所は作る側が決める。`structure.rs` と `register.rs` が取っている形に合わせる。

英語版の指摘の文面は、実装済みの規則の英語の文面と語調を揃える。

## ゴールデンテストへの影響

`crates/suikou-core/tests/golden_rules.rs:31` は `rules::check_all` を直接呼び、その結果から M3 と M6 の件数を数えて参照実装の出力と照合している。M3 を移すと、この件数が 1 から 0 に落ちて照合が失敗する。

対処は、ゴールデンテストの `count` が `rules::check_all` と `headings::check` の双方を呼んで結果を連結する形に変える。参照実装の期待値 `tests/golden/expected/rules.json` は書き換えない。判定内容を変えていないため、期待値が変わるなら移動を誤っている。M6 は `rules::check_all` が1件に束ねたまま返すため、連結の対象は `maint/numbered-heading` だけである。

`tests/golden/input/ja_maintainability.md` の M6 は2件とも地の文にあるため、見出しを本文側のループから外しても件数は動かない。

`structure/heading-form` はゴールデンテストに列を足さない。参照実装 `research/` に対応する実装がなく、照合する相手がないためである。同じ入力に対する期待値は、`headings.rs` の単体テストで固定する。

`packages/textlint-rule-preset-tech-maintainability/test/golden.test.js` は textlint の出力を固定値と比べており、Rust の関数を呼ばない。指摘の件数が変わらないため、このテストは影響を受けない。

## 作る側に委ねること
