# suikou

suikou は、日本語と英語の技術文書を対象とする lint ツール兼執筆ハーネスである。

生成 AI が執筆した技術文書には、語彙の偏りにとどまらない特有の傾向が現れる。具体的には、比喩の多用、文末表現の偏り、文と文の接続の不自然さ、そして細分化しすぎたことでメンテナンス性を損なう構成などが挙げられる。suikou はこれらの傾向を検出し、メンテナンスしやすい文書へ改善するためのツールである。

## 仕組み

### 実測値と明文規約に基づく規則設計

suikou には、直感だけで定めた規則を一切含めていない。文体の特徴に関する直感的な仮説は、実際に検証すると大半が成立しないためである。この傾向は、翻訳調の研究と AI 文の研究という異なる領域で共通して確認されている。

各規則の閾値の根拠となる実測値は `corpus/baselines.toml` に記録してある。不採用とした指標と、その判断理由も同じファイルに残している。不採用の記録を残すのは、同じ仮説を何度も再検証したり修正したりする無駄を避けるためである。

### 位置を持つ指摘と文書全体の指摘の分離

suikou が検出する対象は、行や文の単位で正誤が決まり位置情報を持つ指摘と、文書全体を通してしか計測できず位置情報を持たない指摘に分かれる。位置情報を持たない指摘の大半は、記述の不足に関するものである。存在しない要素には文書内の位置が存在しないため、位置情報を付与できない。

この分類は、一度の実行と一度の修正で対応を完了させるという要件に応える設計である。位置情報を持つ指摘が修正箇所を示し、文書全体から導いた方針が修正の方向性を示す。両者が同時にそろうことで、レイヤーごとに修正を繰り返す手間を省ける。

### AI らしさから独立したメンテナンス性のレイヤー

M1 から M7 の規則は、Google developer documentation style guide の明文規約に基づいている。これらが扱う課題は AI の普及以前から存在するものであり、モデルの世代が進んでも陳腐化しない。そのため、メンテナンス性のレイヤーだけを独立して利用することもできる。

## インストール

GitHub Releases で OS ごとのアーカイブを配布している。アーカイブには辞書が同梱されているため、ダウンロード後はネットワーク接続を必要としない。Linux 版は musl で静的リンクされており、glibc のバージョンに依存しない。

```sh
tar xf suikou-v<version>-<target>.tar.xz
cd suikou-v<version>-<target>
install -m 755 suikou ~/.local/bin/
suikou selftest
```

Windows では zip アーカイブを展開し、`suikou.exe` を PATH に含まれるディレクトリへ配置する。

`suikou selftest` は、辞書を実際に読み込んで解析を実行し、動作を検証するコマンドである。辞書を含まないバイナリを導入している場合、この段階で異常終了する。辞書の有無を表示情報だけで判定すると誤るおそれがあるため、実際の解析処理によって確認する方式を採っている。

ソースからインストールする場合は feature を指定する。

```sh
cargo install --git https://github.com/KazuyoshiAkiyama/suikou suikou-cli --features lindera-unidic
```

この feature を省略すると辞書を含まない構成でインストールされ、英語のみが対象となる。その状態で日本語を指定すると、suikou はその場で異常終了する。辞書がないまま空の解析結果を返してしまうと、漢語率も連用中止も 0 として算出され、閾値を下回った結果「指摘なし」という誤判定につながるためである。

## 使い方

執筆を始める際は、最初に文書の型を選ぶ。選定のための質問は最大2問である。

```sh
suikou doctype
```

型が決まったら、本文を書く前に全体の構成を作成する。

```sh
suikou plot docs/guide.md --doctype howto
```

このコマンドを実行すると、`.suikou/plans/` に各節の見出しと、それぞれの節が答えるべき問いが書き出される。各節の主張を一行で記述し、承認を得てから本文の執筆へ移る。プロットは執筆前の思考を整理するための文書であるため、バージョン管理の対象には含めない。

文書生成に渡す指示は、型を指定して出力する。出力内容では、禁止事項の一覧よりも先に、節ごとの問いと記述指針が配置される。

```sh
suikou brief --doctype howto --lang ja
```

書き終えた文書は `check` で検証する。

```sh
suikou check docs/guide.md
```

`suikou mcp` は、標準入出力を通じて JSON-RPC 2.0 で通信する MCP サーバーとして動作する。`initialize`、`tools/list`、`tools/call` の各メソッドに対応し、`check` と `brief` をツールとして提供する。MCP 対応エージェントは端末向けの出力文字列を解析する必要がなく、CLI と同一の判定処理を直接呼び出せる。

```sh
suikou mcp
```

MCP クライアント側では、サーバーの起動コマンドに `suikou`、引数に `mcp` を設定する。

詳しいインストール手順と使い方は[ドキュメント](docs/)に記載している。

## ドキュメント

プロジェクトのドキュメントは `docs/` 配下に格納している。Hugo でビルドできる構成になっており、英語版と日本語版の両方を用意している。デフォルトの言語は英語である。

```sh
cd docs && hugo server
```

| ドキュメント | 内容 |
|---|---|
| design | 設計の全体像。実測値とその根拠を含む |
| metrics | 各指標の厳密な定義。移植や移行の際に参照する |
| decisions | 意思決定の経緯 |
| writing | 語彙の選択基準と README の構成規約 |
| development | 配置、構成方法、バージョンの固定方法、形態素解析の扱い |

遵守すべき事項は `CLAUDE.md` に、作業の順序は `TASKS.md` に記載している。

## 実装状況

サブコマンドはすべて実装済みである。ただし、起動が数ミリ秒で完了するため `daemon` は設けない方針とした。test、fmt、clippy は、デフォルトの feature と `--features lindera-unidic` のいずれの構成でも通過する。また、ゴールデンテストによって、Rust 側の規則、textlint 側の規則、参照実装の件数が一致する状態を保っている。

各部分の状況は `CLAUDE.md` で管理している。このファイルに転記すると内容が古くなりやすいためである。実際に、転記していた記述を削除する前は、5つの部分で記載内容が実態より古くなっていた。
