# suikou

技術文書の lint とハーネス。日本語と英語を扱う。

生成AIが書いた技術文書には、語の選び方だけにとどまらない特徴がある。
比喩の多用、文末の形式の偏り、文と文のつなぎのぎこちなさ、
そして細かく書きすぎて後からメンテナンスしにくくなる構造がそれにあたる。
suikou はこうした特徴を見つける。
そのうえで、文書を後から保ちやすい形に近づけるためのものである。

[English](README.md) · [文書](docs/)

## 考え方

### 規則はすべて実際に測定した値か、明文の規約による

直感で決めた規則はひとつも入れていない。
文体の特徴について直感で立てた仮説は、確認してみると大半は成立しないためである。
このことは翻訳調の研究とAI文の研究という、別々の領域で同じように確認できている。

規則の閾値のもとになった値は `corpus/baselines.toml` にある。
採らなかった指標と、その理由もそこに書いてある。
採らなかったものを残してあるのは、同じ仮説を何度も確かめ修正せずに完了させるためである。

### 見つける対象は二つに分かれる

行や文の単位で真偽が決まって位置を持つものと、
文書の全体でしか測れなくて位置を持たないものがある。
後者の多くは不足している点の指摘である。
不足しているものには位置がないため、その指摘は位置を持てない。

この分け方は「一度の実行で、一度の直しで完了させる」という求めに応えるためのものである。
位置を持つ指摘がどこを修正するかを伝えて、
文書の全体から作った方針がどう修正するかを伝える。
この二つがそろうため、レイヤーごとに修正を往復させずに済む。

### 保ちやすさのレイヤーはAIらしさから独立している

M1 から M7 は Google developer documentation style guide の明文の規約による。
これは AI が広まる前からある問題であり、モデルが世代を重ねても古びない。
そのため、このレイヤーだけを抽出て使うこともできる。

## 入れ方

GitHub Releases に OS ごとの書庫を置いてある。
辞書を同梱してあるため、取ってきたあとはネットワークが必要ない。
Linux は musl で静的に結合してあるため、glibc のバージョンによらずに動く。

```sh
tar xf suikou-v<version>-<target>.tar.xz
cd suikou-v<version>-<target>
install -m 755 suikou ~/.local/bin/
suikou selftest
```

Windows では zip を開いて、`suikou.exe` を PATH の成功した場所に置く。

`suikou selftest` は辞書を実際に読んで解析させるためのものである。
辞書の欠けたバージョンを掴んでいる場合は、そこで異常終了する。
この確認の方法にしてあるのは、辞書があるかどうかを表示だけで判じると誤るためである。

ソースから入れる場合は feature を指定する。

```sh
cargo install --git https://github.com/KazuyoshiAkiyama/suikou suikou-cli --features lindera-unidic
```

feature を省くと辞書を含まないバージョンが入る。
そのバージョンは英語だけを扱う。そのため日本語を指定した場合は、その場で異常終了する。
気付かれずに空の解析結果を返すと、漢語率も連用中止も 0 になる。
その値は閾値の下にあるため、「指摘なし」という誤った結びに至ることになる。

## 使い方

文書を一から作るときは、本文より先に構成を決める。

```sh
suikou plot docs/guide.md --doctype howto
```

`.suikou/plans/` に、節の見出しと、その節が答える問いが並ぶ。
節ごとの主張を一行で書いて、承認を得てから本文に進む。
プロットはバージョン管理しない。思考の側の文書だからである。

生成に渡す指示は、型を指定して作る。
節ごとの問いと書き方の指針が、禁止の一覧より先に並ぶ。

```sh
suikou brief --doctype howto --lang ja
```

書いたものは `check` で確認する。

```sh
suikou check docs/guide.md
```

`suikou mcp` は、標準入出力で JSON-RPC 2.0 を話す MCP サーバとして起動する。
`initialize`・`tools/list`・`tools/call` に応じ、`check` と `brief` をツールとして出す。
MCP に対応したエージェントは、端末向けの文字列を解釈せずに、CLI と同じ判定を
そのまま呼び出せる。

```sh
suikou mcp
```

MCP クライアントの設定では、サーバの起動コマンドとして `suikou`、引数として `mcp`
を指定する。

詳しい入れ方と使い方は[文書](docs/)にある。

## 文書

文書は `docs/` にある。Hugo で作れる形にしてあり、英語と日本語の両方を置いてある。
既定の言語は英語とする。

```sh
cd docs && hugo server
```

| 文書 | 内容 |
|---|---|
| design | 設計の全体。測定した値と根拠を含む |
| metrics | 指標の厳密な定義。移すときに使う |
| decisions | 決めたことの経緯 |
| development | 構成方、バージョンの固定方、形態素解析の扱い |

`CLAUDE.md` に遵守する事項を、`TASKS.md` に作業の順序を書いてある。

## 状態

サブコマンドはすべて書いてある。ただし `daemon` は置かないと決めた。起動が数ミリ秒で完了するためである。
test と fmt と clippy は、既定の feature でも `--features lindera-unidic` でも通る。

| 部分 | 状態 |
|---|---|
| ブロック抽出と前処理 | 書いてある。単体テストあり |
| M1 から M7 の規則 | 書いてある。単体テストあり |
| 日本語と英語の文書指標 | 書いてある |
| `check` サブコマンド | 書いてある |
| lindera の接続 | 書いてある。lindera 6.0.0 で確認した |
| ゴールデンテスト | M 系と文書指標をつないである |
| `brief`、`baseline`、`terms`、`mcp` | 書いてある |
| textlint の局所ルール | 書いてある |
