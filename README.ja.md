# suikou

suikou は技術文書向けの lint とハーネスであり、日本語と英語の文書を扱う。

生成AIに書かせた技術文書には、語彙の選択以外にも目立つ傾向が出る。
具体的には、比喩が多いこと、文末の形が偏ること、前後の文の接続が不自然になること、
細部まで書き込みすぎて保守しづらい構成になることである。
suikou はこれらの傾向を文書の中から検出する。
そのうえで、文書を保守しやすい形へ直していく。

## suikou の仕組み

### どの規則も実測値か明文の規約に基づく

感覚だけで決めた規則は一つも入れていない。
文体の特徴について感覚で立てた仮説は、検証するとほとんどが当てはまらないからである。
この結果は、翻訳調の研究と AI が書いた文の研究という、互いに独立した分野で共通して得られている。

各規則の閾値の元になった値は、`corpus/baselines.toml` に記録している。
不採用にした指標と、不採用の理由も同じファイルに書いてある。
不採用の指標を記録に残すのは、同じ仮説を何度も検証し直す手間を省くためである。

### 検出する問題は二種類に分かれる

一つは、行や文の単位で正誤が決まり、文書内の位置を持つ問題である。
もう一つは、文書全体を通してでないと測れず、位置を持たない問題である。
後者の多くは、文書に足りないものを指摘する。
足りないものは文書のどこにも存在しないので、その指摘も位置を持てない。

この区別は、「一度の実行と一度の修正で作業を終える」という要件を満たすために設けている。
位置を持つ指摘は、どこを直すかを伝える。
文書全体から作る方針は、どう直すかを伝える。
この二つが同時に届くので、レイヤーごとに検査と修正を往復する必要がない。

### 保ちやすさのレイヤーは AI らしさの判定から独立している

M1 から M7 は、Google developer documentation style guide に明文化された規約に基づく。
これらの規約が扱う問題は AI が普及する以前からあるので、モデルの世代が進んでも規約は古くならない。
そのため、このレイヤーだけを取り出して使うこともできる。

## 導入方法

GitHub Releases に、OS ごとの書庫を置いている。
書庫には辞書が同梱されているので、ダウンロードした後はネットワークに接続しなくても使える。
Linux 版は musl で静的リンクしているので、glibc のバージョンに関係なく動作する。

```sh
tar xf suikou-v<version>-<target>.tar.xz
cd suikou-v<version>-<target>
install -m 755 suikou ~/.local/bin/
suikou selftest
```

Windows では zip を展開し、`suikou.exe` を PATH の通ったディレクトリに置く。

`suikou selftest` は、辞書を実際に読み込んで文を解析させるコマンドである。
辞書が欠けたバージョンを入手していた場合は、このコマンドが異常終了する。
このような確認方法にしているのは、辞書の有無を表示だけで判断すると誤ることがあるからである。

ソースからインストールする場合は、feature を指定する。

```sh
cargo install --git https://github.com/KazuyoshiAkiyama/suikou suikou-cli --features lindera-unidic
```

feature を指定しないと、辞書を含まないバージョンがインストールされる。
このバージョンは英語しか扱えないので、日本語を指定するとすぐに異常終了する。
もし異常終了せずに空の解析結果を返すと、漢語率も連用中止も 0 になる。
この値は閾値を下回るので、「指摘なし」という誤った結論が出てしまう。

## 基本的な使い方

文書を書くときは、最初に文書の型を選ぶ。型は最大2問の問いに答えると決まる。

```sh
suikou doctype
```

型を決めたら、本文より先に構成を決める。

```sh
suikou plot docs/guide.md --doctype howto
```

このコマンドを実行すると、`.suikou/plans/` に各節の見出しと、各節が答える問いが一覧になる。
節ごとの主張を一行で書き、承認を受けてから本文に取りかかる。
プロットは考えた過程を書いた文書なので、バージョン管理の対象にしない。

生成に渡す指示は、型を指定して作る。
指示の中では、節ごとの問いと書き方の指針が、禁止事項の一覧より前に並ぶ。

```sh
suikou brief --doctype howto --lang ja
```

書いた文書は `check` で確認する。

```sh
suikou check docs/guide.md
```

`suikou mcp` を実行すると、suikou は標準入出力で JSON-RPC 2.0 をやり取りする MCP サーバーとして起動する。
このサーバーは `initialize`・`tools/list`・`tools/call` に応答し、`check` と `brief` をツールとして提供する。
MCP に対応したエージェントは、端末向けの出力文字列を解析しなくても、
CLI と同じ判定を直接呼び出せる。

```sh
suikou mcp
```

MCP クライアントの設定では、サーバーの起動コマンドに `suikou` を、引数に `mcp` を指定する。

導入方法と使い方の詳細は[文書](docs/)で説明している。

## 文書の構成

文書は `docs/` に置いている。Hugo でサイトを生成できる形式で、英語版と日本語版の両方がある。
既定の言語は英語である。

```sh
cd docs && hugo server
```

| 文書 | 内容 |
|---|---|
| design | 設計の全体像。測定値と根拠を含む |
| metrics | 各指標の厳密な定義。他の実装へ移植するときに使う |
| decisions | 各決定に至った経緯 |
| writing | 語の選び方と README の構成についての規範 |
| development | ファイルの配置、ビルド方法、バージョンの固定方法、形態素解析の扱い |

`CLAUDE.md` には守るべき事項を、`TASKS.md` には作業の順序を書いている。

## 実装の状況

サブコマンドはすべて実装済みである。ただし `daemon` は設けないことにした。
起動が数ミリ秒で終わるためである。
test と fmt と clippy は、既定の feature でも `--features lindera-unidic` を付けても通る。
ゴールデンテストにより、Rust の規則と textlint の規則と参照実装が、同じ件数を返す状態を保っている。

部分ごとの実装状況は `CLAUDE.md` に書いている。
ここに写しを置くと、写しの内容が古くなるからである。
実際、この節から写しを取り除く前には、5つの部分の記載が実態より遅れていた。
