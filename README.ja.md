# suikou

技術文書の lint とハーネス。日本語と英語を扱う。

生成AIが書いた技術文書には、語の選び方だけにとどまらない癖がある。
たとえを使いすぎる癖、文末の形が偏る癖、文と文のつなぎがこなれない癖、
そして細かく書きすぎて後から直しにくくなる癖がそれにあたる。
suikou はこうした癖を見つける。
そのうえで、文書を後から保ちやすい形に近づけるためのものである。

[English](README.md) · [文書](docs/)

## 考え方

### 規則はすべて実際に測った値か、明文の決まりによる

思いつきで決めた規則はひとつも入れていない。
文体の癖について思いつきで立てた見立ては、確かめてみると大半が外れるためである。
このことは翻訳調の研究とAI文の研究という、別々の領域で同じように確かめられている。

規則の閾値のもとになった値は `corpus/baselines.toml` にある。
採らなかった指標と、その理由もそこに書いてある。
採らなかったものを残してあるのは、同じ見立てを何度も確かめ直さずに済ませるためである。

### 見つける対象は二つに分かれる

行や文の単位で真偽が決まって位置を持つものと、
文書の全体でしか測れなくて位置を持たないものがある。
後者の多くは足りない点の指摘である。
足りないものには位置がないため、その指摘は位置を持てない。

この分け方は「一度の実行で、一度の直しで済ませる」という求めに応えるためのものである。
位置を持つ指摘がどこを直すかを伝えて、
文書の全体から作った方針がどう直すかを伝える。
この二つがそろうため、層ごとに直しを往復させずに済む。

### 保ちやすさの層はAIらしさから独立している

M1 から M7 は Google developer documentation style guide の明文の決まりによる。
これは AI が広まる前からある問題であり、模型が世代を重ねても古びない。
そのため、この層だけを取り出して使うこともできる。

## 入れ方

GitHub Releases に OS ごとの書庫を置いてある。
辞書を同梱してあるため、取ってきたあとはネットワークが要らない。
Linux は musl で静的に結合してあるため、glibc の版によらずに動く。

```sh
tar xf suikou-v<version>-<target>.tar.xz
cd suikou-v<version>-<target>
install -m 755 suikou ~/.local/bin/
suikou selftest
```

Windows では zip を開いて、`suikou.exe` を PATH の通った場所に置く。

`suikou selftest` は辞書を実際に読んで解析させるためのものである。
辞書の欠けた版を掴んでいる場合は、そこで落ちる。
この確かめ方にしてあるのは、辞書があるかどうかを表示だけで判じると誤るためである。

ソースから入れる場合は feature を指定する。

```sh
cargo install --git https://github.com/KazuyoshiAkiyama/suikou suikou-cli --features lindera-unidic
```

feature を省くと辞書を含まない版が入る。
その版は英語だけを扱う。そのため日本語を指定した場合は、その場で落ちる。
黙って空の解析結果を返すと、漢語率も連用中止も 0 になる。
その値は閾値の下にあるため、「指摘なし」という誤った結びに至ることになる。

## 使い方

```sh
suikou check docs/guide.md
```

詳しい入れ方と使い方は[文書](docs/)にある。

## 文書

文書は `docs/` にある。Hugo で作れる形にしてあり、英語と日本語の両方を置いてある。
既定の言語は英語とする。

```sh
cd docs && hugo server
```

| 文書 | 中身 |
|---|---|
| design | 設計の全体。測った値と根拠を含む |
| metrics | 指標の厳密な定め。移すときに使う |
| decisions | 決めたことの経緯 |
| development | 組み立て方、版の固め方、形態素解析の扱い |

`CLAUDE.md` に守ることを、`TASKS.md` に作業の順序を書いてある。
