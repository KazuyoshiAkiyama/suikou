# suikou

suikou は、技術文書の草稿から AI が書いたと分かる癖を除き、後から保守しやすい構成に整えるためのスキルである。

## 本文の前に構成を決める

文書を新しく作る場合は、本文を書く前に構成を決める。

```sh
suikou plot docs/guide.md --doctype howto
```

このコマンドを実行すると、`.suikou/plans/docs/guide.md` に各節の見出しと、各節が答える問いが一覧になる。
節ごとに主張を一行で書き、人に見せて承認を受けてから本文に取りかかる。
主張を一行にまとめられない節は、検討が足りていない。

文書の型は `design`、`decision`、`howto`、`reference`、`overview` のいずれかを選ぶ。
プロットは考えた過程を書いた文書なので、バージョン管理の対象にしない。

## 執筆を始める前の準備

`suikou brief` を実行し、表示された指針と制約に従って書く。

```sh
suikou brief --doctype howto --lang ja
```

`--doctype` を指定すると、各節の問いと書き方の指針が、禁止事項の一覧より前に表示される。
採るべき書き方を先に示し、避ける書き方をその後に示す順序である。

brief に載る制約は、指示によって守らせられる項目に限られる。
語彙や文の組み立てに関する指標は、指示を与えても変わらないと分かっているので、brief には含まれない。
これらの指標は、書き終えた後に `suikou check` で直す。

## 検討内容と成果物を分ける

成果物のファイルには、決定した内容だけを書く。

次の項目は `.suikou/notes/<成果と同じ名前>.md` に書く。

- 検討した選択肢と、採らなかった案。
- 確信の持てない細かな値。
- 根拠と、測定の出典。
- 後で確認したい事項。

この分け方には二つの効果がある。
考えた過程を示したがる癖に別の書き先を用意するので、成果物に細かすぎる記述が入りにくくなる。
また、根拠が文書のそばに残るので、後で修正するときに「なぜこう書いたか」を追える。

notes は lint の対象外とする。

## 書き終えた後の検査

`suikou check` を一回だけ実行する。

```sh
suikou check docs/guide.md
```

レポートは二つの部分からなる。

- 「書き直しの方針」は、文書全体の傾向を示す。特定の位置は持たない。
- 「修正する箇所」は、行を特定した指摘である。

両方を読んでから、修正を一回でまとめて行う。
方針だけを見て全体を書き直すことも、箇条書きで並んだ指摘だけを直すこともしない。

`structure/` で始まる指摘は、構成についての指摘である。
節が足りない状態、節の順序が想定と違う状態、一つの段落に複数の主張が入っている状態を指摘する。
これらは文を直しても解消しないので、節を増減するか段落を分けて対処する。
プロットのある文書で構成を変えたときは、プロットも合わせて更新する。

修正を終えたら、`suikou check --quiet` で確認する。

## check と修正の往復を避ける

check と修正を何度も繰り返さない。
一回の check ですべてのレイヤーの指摘が出揃うので、修正も一回で終えられるからである。
確認のために check を実行するのは二回目までとする。
