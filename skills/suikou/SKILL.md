# suikou

技術文書の草稿から、AI が書いたと分かる癖を取り除く。
そのうえで、後からメンテナンスしやすい構成に近づけるためのものである。

## 構成を決めてから書く

文書を一から作るときは、本文より先に構成を決める。

```sh
suikou plot docs/guide.md --doctype howto
```

`.suikou/plans/docs/guide.md` に、節の見出しと、その節が答える問いが並ぶ。
節ごとに主張を一行で書いて、それを人に見せて承認を得てから本文に進む。
主張を一行で書けない節は、まだ検討が不足している。

型は `design`、`decision`、`howto`、`reference`、`overview` から選ぶ。
プロットはバージョン管理しない。思考の側の文書だからである。

## 書き始める前に

`suikou brief` を動かして、示された指針と制約を守って書く。

```sh
suikou brief --doctype howto --lang ja
```

`--doctype` を付けると、節ごとの問いと書き方の指針が、禁止の一覧より先に並ぶ。
書くべき書き方が先にあって、避ける書き方が後に続く順序である。

brief が示す制約は、指示で守れることだけである。
語彙や文の組み立ての指標は指示では変わらないと分かっているため、そこには入らない。
それらは書いたあとに `suikou check` で修正することになる。

## 考えと成果を分ける

成果のファイルには、決まった中身だけを書く。

次のものは `.suikou/notes/<成果と同じ名前>.md` に書く。

- 考えた選び方と、落とした案。
- 確信のない細かい値。
- 根拠と、測った出どころ。
- 後で確認したいこと。

この分け方には二つの効き目がある。
考えを示したいという癖に行き先を与えることで、成果から細かすぎる書き方が減る。
それに加えて根拠が文書の隣に残るため、後の修正で「なぜこう書いたか」をたどれる。

notes は lint の対象にしない。

## 書いたあとに

`suikou check` を一度だけ動かす。

```sh
suikou check docs/guide.md
```

そのレポートは二つに分かれている。

- 「書き直しの方針」は文書の全体の傾きを示す。位置を持たない。
- 「修正する箇所」は行を特定できる指摘である。

その両方を読んだうえで、修正を一度で行う。
方針だけを見て全体を書き直したり、箇条書きの指摘だけを修正したりはしない。

`structure/` で始まる指摘は構成に関わる。
節の不足、順序の相違、一段落に複数の主張を詰め込んだ状態を指摘する。
これらは文の修正では解消しない。節の増減か段落の分割で対応する。
プロットを書いてある文書で構成を変更した場合は、プロットの側も更新する。

修正が終わったら `suikou check --quiet` で確認する。

## 繰り返さない

check と修正を何度も往復させない。
一度の check ですべてのレイヤーの指摘が揃うため、一度の修正で完了するからである。
確認のための二度目までとする。
